# 家庭营养师第一版怎么推进

当前目标是拿一个可以亲手点通的 Uni-app 小程序原型，与老大和两组研发同事确认产品流程。2026-09-22 已由用户确认：先做 Uni-app 微信小程序，Flutter 后续再做。现有代码完成交互演示，不代表一期约 45 天的生产系统已经交付。

## 先拿原型确认这四件事

1. 建档能否控制在四步以内；姓名/称呼、年龄、身高体重、健康情况、目标、口味和过敏原哪些必填，哪些可稍后补充。
2. AI 首页是否就是唯一主入口；配餐、菜单、采购、拍照都从对话卡片进入，记录后返回同一个营养师。
3. 菜单是否采用“共同菜品 + 按成员分餐”；优先减少重复做饭，在无法兼容的情况下转专业复核。
4. 买菜是跳已有商城、小程序内商品页还是新的订单页；正式开发前由商城负责人确定落点和跳转参数。

视觉使用奶油色、深绿色和家庭餐桌元素，参考附件中的对话首页、渐进建档和商品卡片关系。没有复用参考产品的角色形象、标识和界面素材。

## 你负责的范围

| 模块 | 小程序侧负责 | 同事或外部服务负责 |
| --- | --- | --- |
| 登录和建档 | 授权交互、分步表单、字段校验、成员切换、错误恢复 | 微信凭证验证、业务会话、成员授权、档案存储 |
| AI 对话 | 文字与语音入口、流式输出、加载/失败/重试、菜单卡片 | 语音识别、上下文选择、知识检索、营养计算、规则校验 |
| 菜单与做饭 | 菜品、份量、做法、替换入口、采购跳转 | 配餐结果、成员差异、食材克数、配方版本 |
| 食材商城 | 展示清单、家中已有食材勾选、携带清单跳转 | SKU 匹配、价格库存、配送、支付、订单、售后 |
| 拍照和记录 | 相机/相册、压缩上传、候选菜品确认、食量确认、记录展示 | 图片识别、营养数据匹配、计算区间、保存记录、反馈分析 |

原会议分工：林恬伊负责 Uni-app；刘北萍负责商城、订单与供应链；刘潇、宋红阳负责 AI Agent。接口清单应由三方共同确认，不需要小程序开发者独自承担全部 AI 和电商逻辑。

## 原型完成后建议顺序

| 顺序 | 可交付结果 | 完成条件 |
| --- | --- | --- |
| 第一步 | 用当前原型评审页面和路径 | 三方确认建档字段、菜单结构、商城落点、拍照确认项 |
| 第二步 | 固定接口样例及异常状态 | 给前端可读的 JSON；确定任务状态、错误码、版本与负责人 |
| 第三步 | 微信开发者工具中运行 | 填 AppID，检查胶囊避让、基础库、样式和导航；手机真机验证 |
| 第四步 | 接登录和家庭档案 | 正常登录、退出、会话过期、成员访问控制全部跑通 |
| 第五步 | 接对话与拍照任务 | 包含超时、拒绝授权、识别不出、结果修正与取消上传 |
| 第六步 | 接商城与记录反馈 | 用同一家庭及同一计划贯通完整链路，再评估试点 |

以上是推进顺序，不是未经团队确认的工期承诺。参考方案的 45 天还包含专业资料、供应链、联调和试点，依赖不齐时不能只靠前端排期保证。

## Supabase 在架构中的位置

建议保留 Uni-app → 业务 API/Edge Functions → Supabase 与 AI 服务的边界。Supabase 可承担 Postgres、对象存储和鉴权相关能力，但不是配餐引擎。

微信登录需要后端使用 wx.login 的 code 与微信服务核验身份，再建立业务会话及 Supabase 身份映射；不能将前端传来的 openid 当成已验证身份。具体 JWT、Supabase Auth 接入路径由后端定案。数据库按家庭和成员授权设计 RLS；家庭管理员不自动获得所有成员健康信息访问权限。

多模态模型密钥、微信 AppSecret、Supabase service-role 凭证只存服务端。小程序使用经过校验的接口，不把模型 SDK 和管理密钥打包进去。图片上传要约束大小和格式，私有存储通过受控签名链接读取。微信请求域名、部署区域及网络可用性须在真机联调前验证。

## 建议先冻结的返回结构

配餐响应至少含 planId、version、memberIds、meal、dishes、ingredients（g 和生熟状态）、portions、cookingSteps、reviewStatus、shoppingListId。对话卡片引用 planId，不从自由文本里解析商品或热量。

拍照响应至少含 analysisId、status、candidates、missingFields、confidence、estimateRange、sourceVersion。用户确认后再创建 mealRecord，并保存 memberId、mealTime、consumedPortion 与修正项。

购物清单至少含 planId、ingredientId、requiredAmount、unit、skuId、packSize、quantity、price、stockStatus。价格和库存必须由商城在确认订单前再核验。

## 开源项目初筛

2026-09-22 查阅了所列 GitHub 仓库的元数据、README 和部分文件树。以下是初筛，没有运行这些项目，也没有验证识别准确率或生产可用性；本原型没有复制其源码。

| 仓库 | 已核验定位 | 对本项目的用途 |
| --- | --- | --- |
| [Calorie-Calculator](https://github.com/mggger/Calorie-Calculator) | JavaScript/Next.js 图片热量示例；README 使用 Gemini | 看最短上传链路。其 README 的 NEXT_PUBLIC 模型密钥配置不应照搬到客户端；真实调用放服务端 |
| [photo-calorie-tracker](https://github.com/bobo23456/photo-calorie-tracker) | OpenClaw 技能，按日期写 Markdown 饮食记录与汇总 | 借鉴记录完整度、日期范围汇总；不是移动端 SDK 或现成识别服务 |
| [smooth-app](https://github.com/openfoodfacts/smooth-app) | Open Food Facts 官方 Flutter 应用，有独立扫码模块 | 借鉴扫码、图像上传与食品信息交互；Flutter 界面不能直接放进 Uni-app |
| [openfoodfacts-ai](https://github.com/openfoodfacts/openfoodfacts-ai) | README 明确为实验、训练和 AI 项目追踪仓库 | 研究包装、营养表、类别识别；生产集成入口应继续查 Robotoff，不能把该仓库当餐盘热量 API |
| [AI_Calories_Tracker](https://github.com/VrajVyas11/AI_Calories_Tracker) | README 描述 Flutter + Clarifai 识别 + USDA 营养数据 + Supabase | 后续 Flutter App 的分层参考；需要先评估中式混合菜、份量确认与本地数据覆盖 |

许可证也需单独核验：前两个仓库 API 分别识别为 Apache-2.0 和 MIT，smooth-app 为 Apache-2.0；openfoodfacts-ai 和 AI_Calories_Tracker 的 API 许可证字段为空。后者 README 显示 MIT 徽章，但读取的文件树未见 LICENSE，不能据徽章直接认定可复制商用。模型权重、食品数据库、图片和代码授权应分别确认。

技术研究优先级：先用多模态 API 验证“餐食候选识别 → 用户纠错/确认份量 → 查询营养数据 → 展示估算区间”；之后才评估扫码和包装食品数据库。对中式家常菜，隐形用油、调味、成品重量和剩余食物无法从单张照片可靠确定。

## 已知原型边界

当前只有早餐/晚餐固定样例。目标与口味保存并显示，但不会据此训练模型或产生经审核的个性化营养计算。个人分餐选择仅在当前页面生效，尚未影响共享采购量。商品价格为样例，没有订单和支付。照片仅能本机预览，演示估算来自固定虚拟餐盘，不对应上传照片。语音使用明确标注的示例句；反馈卡是应用内演示，不是微信订阅消息。建档和饮食记录使用本地存储，无真实账号隔离，不适合录入真实健康数据。

后续还需要完整服务端状态管理、隐私授权、活动量/医嘱等字段、断网恢复、订阅消息以及专业规则与模型评估。
