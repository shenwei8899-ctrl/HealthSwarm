# 全人群配餐接口契约

更新日期：2026-10-13。适用方案为《家庭 AI 营养师全人群配餐修改方案》。建档没有新增孕产阶段字段，正式服务通过现有 `registerApiAdapters()` 注册；请求路径、鉴权和服务端持久化由后台契约确定。

## 服务入口

| 方法 | 请求内容 | 返回内容 |
| --- | --- | --- |
| `generateMealPlan(input)` | 请求 ID、规则版本、日期、餐次、所选成员、目标、口味、相关对话、换菜请求及允许引用的已支付做法快照 | 结构化本餐建议，按下述规则校验 |
| `generateExclusivePlan(input)` | 请求 ID、规则版本、计划档位、开始日期、21 天数量、成员及已有上下文 | `generationId` 和 21 个连续日期的 `days`；每一天包含三份符合本餐契约的 `plans` |
| `generateNutritionFeedback(input)` | 日期、餐次、对应成员已确认的实际记录、成员资料和相关上下文 | `text` 与实际引用的 `recordIds`；不能引用请求范围之外的记录 |
| `chatText(input)` | 消息 ID、用户文字、当前日期及允许使用的成员资料 | 非空 `text`；自由问答的模型和业务处理在服务端完成 |

成员包含现有档案资料，以及根据建议日期计算的年龄。只有生日可靠时才计算月龄；未知年龄为 `null`。无生日且无法区分历史默认值来源的 30 岁不被当成已确认年龄。报告仅包含已经核对、且本人拥有或允许共享的内容。服务端仍须独立验证账号、家庭、成员及报告访问权限，不能将前端传入视为授权。

对话上下文保留消息 ID、成员 ID、来源日期与时间，只引用相关用户陈述，不将 AI 回复当成健康事实。明日计划通过消息引用复用今天的相关陈述；原陈述更正、撤回后，相应建议需要重新分析。没有相关陈述时，不猜测孕产情况，不对全部女性成员例行追问。

## 本餐返回对象

| 字段 | 约束 |
| --- | --- |
| `status` | `passed`、`needs_info` 或 `conflict`；人群身份不是拒绝使用条件 |
| `generationId`、`date`、`meal` | 生成版本非空，日期和餐次必须与请求一致 |
| `issues` | 数组；每项含 `type`、`message`，类型为 `needs_info`、`conflict`、`ingredient_conflict`；非通过状态必须有具体原因 |
| `reply` | 可选的用户说明，不用于解析份量或替代结构化检查结果 |
| `dishes` | 通过状态的菜品数组，每项包含 `name`、`recipeId`、`recipeVersion`、全部已知 `ingredients` 和非空 `steps`；可带详情、注意事项及营养 |
| `steps` | 本餐有固体菜品时为非空做法数组；仅提供喂养建议且没有菜品时可为空数组 |
| `products` | 商品数组，每项含 ID、名称、全部已知配料、包装数值 `pack`、单位 `unit`、以分计的非负整数 `priceCents` |
| `memberDemands` | 每位请求成员恰有一项，包含 `memberId`、依据 `sourceReference` 和 `ingredients` 数组；需求项为 `productId`、非负数 `amount`、与商品相同的 `unit` |
| `memberNotes` | 每位请求成员恰有一项，包含 `id`、`portion`、`notes` 和个人 `dishes`；个人菜品份量含 `recipeId`、`recipeVersion`、非负数 `amount`、`unit: g`、`foodState: cooked_edible`、依据 `sourceReference` |

个人吃法可以只返回说明、不返回无法确定的克数，但不得把未知值伪造成零。没有固体菜品的喂养建议可使用空菜品与商品数组，仍须返回每位成员的适当说明与所依据的建议。需要补充信息或存在冲突的结果不携带可结算的个体化商品清单。

需求单位不匹配、成员归属不完整、个人菜品配方版本不匹配、重复个人菜品、配料缺失或做法缺失时，前端拒绝结果并提供重试。前端不会从自由文本解析食材用量或使用儿童、孕产身份乘成人份量的固定系数。

商品需求先跨成员汇总，再跨所选餐次合并同一 SKU、包装和单位，最后向上取整采购包装数。前端忽略服务返回的旧包装数量，使用校验后的结构化需求重算；正式商品、库存与最终报价仍由商城服务确认。

## 营养口径

菜品 `nutrition` 遵守《菜品营养字段与后端存储契约》。只有每 100 克熟制后可食部分、明确来源和配方依据的数据可以用于本餐汇总。示例数据或来源缺失时按暂无数据处理。

个人熟重与对应配方匹配时，按每 100 克数值计算实际建议份量的营养，再汇总本餐。六项为能量、蛋白质、脂肪、碳水化合物、膳食纤维和钠。任何一份所需数据未知时，该项汇总保持未知；真实零值仍为零。缺少个人份量时，不把每 100 克菜品营养直接展示成个人摄入或全餐合计。

## 保存与复核

本餐结果按日期和餐次保存，依据包括所选成员资料、相关用户消息、换菜请求及规则版本。页面打开读取同一份结果，依据发生相关变化后重新分析。同一请求同时发生时复用进行中的任务，账号切换、依据变化或新请求已替代旧请求时，旧结果不得写入当前缓存。

21 天结果逐日校验日期、三餐及成员数据，不使用两天样例循环冒充正式计划。订单保存购买时的菜谱及营养快照；当前吃法复核不能更改已支付商品、金额、配方或配送。对已购菜谱的个人份量必须匹配快照中的配方版本，不将另一道新菜的份量挪到旧菜上。

当前默认演示模式只验证流程；正式方法未注册时返回服务错误。模型、专业营养规则、真实配方、报价与服务端持久化的可用性需要后台联调和实际验收，不能由本地测试推定。
