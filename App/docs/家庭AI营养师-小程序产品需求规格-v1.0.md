# 家庭 AI 营养师：微信小程序产品需求规格 v1.3

2026-10-21 主线确认：正式客户端只允许微信登录，云端本人资料完整并确认当前版本后进入 AI 对话首页；受邀人接受邀请后也遵守这一落点，不重新设置全家使用方式和默认就餐者。普通家庭邀请可多人建立各自档案，绑定成员邀请仅由一个账号认领已有档案。商城不提供独立登录或逛商城入口。采购支持本餐、今日安排下方“一键选购”汇总，以及 AI 判断明确购买意图后展示真实指定菜品食材包；对话购包无需先加入今日餐单。详见[实施说明](统一微信主线实施说明-20261021.md)。此前历史流程与本条冲突时以本条为准。

更新日期：2026-10-13
用途：内部团队、外包团队共同设计和实现可实际使用的微信小程序；作为页面设计、业务规则、数据契约和验收的共同基线。
依据：用户在本轮讨论中的明确选择与修订；现有《家庭营养师-详细实现方案-讨论稿》仅保留早期探索、源码现状和技术参考。

> **让每个家庭，拥有自己的 AI 营养师。**
>
> 围绕家人的健康状况，提供个性化膳食建议、全家可执行的每日食谱与拍照饮食分析，并连接蔬菜包、肉类包等食材购买服务，构建从健康管理到家庭餐桌的日常服务闭环。

## 1. 产品范围与文档效力

1. **目标是可实际使用的微信小程序。** 首期覆盖真实账号与家庭资料、AI 膳食建议与饮食记录、普通食材订单及一次支付的 21 天计划，并在小程序内完成支付、配送、计划管理和售后。页面、状态、数据和接口须围绕真实业务设计，联调时可以使用测试环境和虚拟数据。
2. 当前优先只做微信小程序。团队已确定使用 Supabase；现有 Uni-app 页面是可复用的开发起点，Flutter App 暂不列入当前产品范围。
3. 服务对象为全体家庭成员，儿童、孕期、产后、哺乳期及有基础病的成员均可使用。AI 根据具体成员、已有资料和成员归属明确的对话信息分析菜单、个人份量与做法，并执行饮食安全检查，不设置人工审核流程。建档不增加孕期、产后、哺乳期等阶段字段或必填项；确有需要时在对话中追问。年龄或特殊人群身份本身不得作为整餐拒绝或禁止使用的条件。修改范围与验收详见[全人群配餐修改方案](家庭AI营养师-全人群配餐修改方案.md)。
4. 本文的“**已确认**”指用户已拍板的体验和业务方向；“**待团队定稿**”指需相关负责人制定的生产规则。后端尚不可用的交互评审和联调阶段，可用**明确标为测试数据**的菜谱、商品、价格、审核和支付状态点通流程；测试数据不得冒充真实推荐、实时报价或履约承诺。正式产品的菜谱、净菜商品、库存和价格须由实际业务数据提供。
5. 本文件是**目标产品规格，不是现有功能清单或原型交付范围**。已经确认的需求应据此实施；尚未定稿的生产细则在第 11 节标明决策人和依赖。

## 2. 全局信息架构与主线

首页以当天 AI 对话和“今日饮食计划”为中心。左上角“历史记录”进入**按天归档的 AI 对话**；右上角进入“我的”。输入框上方保留并按顺序展示四个业务入口：**AI专属计划 → 家庭健康档案 → 拍照看热量 → 今日饮食计划**，并增加“**加入社群**”入口；点击“加入社群”直接弹出二维码，不进入独立说明页，二维码由运营配置，不写死在客户端。第四个“今日饮食计划”小入口的作用见第 4.2 节。家庭健康档案可在首次建档、AI 首页入口或“我的 → 我的家”查看和补充；推荐页不重复提供档案按钮。AI 对话页的“AI专属计划”与“我的 → AI专属计划”进入同一个计划推荐页；首页不重复放订单入口。“历史记录”不显示最近饮食记录来冒充聊天历史。

“我的”页面顺序确定为：顶部“**我的家 · 成员数**”卡片，点击查看家庭健康档案；其下是“**使用方式：个人使用／家庭使用 · 更改**”；“**饮食与反馈**”分组含“饮食记录、反馈”；“**计划与订单**”含“AI专属计划、我的订单”；“**资料管理**”含“AI 记住的事、健康设备”；“**设置**”先后含“隐私与账号”和“合作商合作”，合作入口紧接在“隐私与账号”下方。家庭健康档案采用“家庭总览页 → 成员详情页”两级结构，具体内容见第 3.1 节。对话中“查看记忆”进入“AI 记住的事”，对话里的撤回入口保留。家庭健康档案由顶部卡片进入，不在下方再放一个重复入口。“健康设备”辅助文案为“连接血压计等健康设备”，点击进入标题为“健康设备”的页面，仅展示图标和“**敬请期待**”；本版不提供设备绑定、授权、手动录入或模拟测量数据。实际设备类型、接入和数据展示后续另行设计，见第 11 节。

完整用户主线为：

`微信登录并建立业务会话 → 选择个人使用／家庭使用并完成必填建档信息 → 家庭使用者分享小程序邀请卡片、对方登录并主动接受后填写或核对成员资料 → 当天 AI 对话与自动生成的今日饮食计划 → 按需调整早餐／午餐／晚餐的具体就餐成员 → AI 分析、生成或更新菜单、套餐和关联食材包并自动完成饮食安全检查 → 菜单页或计划详情页显示简洁安全状态 → 查看生成后的本餐基本信息、营养与注意事项及购买前完整图文烹饪内容 → 本餐采购或今日汇总采购并核对地址/日期/商品价格 → 支付 → 普通配送或 21 批配送 → 收货后从订单详情／配送批次按餐点击“开始做饭” → 整餐烹饪页切换菜品 → 拍照、食谱选菜或手动记餐 → 保存同一条记录（仅保存／保存并聊聊这一餐）→ 饮食记录与反馈 → 下一餐/次日计划`。

| --- | --- |

## 3. 家庭建档、资料与饮食检查

### 3.1 建档与成员

- 首个登录账号建立“我”的档案；选择家庭使用时，该账号成为家庭创建人。家人可由创建人先建未认领档案，也可通过小程序分享邀请卡片独立登录并加入，具体区分普通家庭邀请和绑定成员邀请，见第 3.2 节。
- 新用户直接进入三页建档流程；每页保存进度，返回上一页可修改，完成后进入 AI 对话首页并读取建档信息自动生成今日三餐，用户查看后再调整。受邀成员按第 3.2 节进入受邀建档，不重复选择使用方式或默认就餐成员。家庭成员的基本信息、偏好、限制和报告分别保存，切换当前成员时不覆盖其他成员。

| 页码 | 页面与填写内容 |
| --- | --- |
| 1/3 先认识每位成员 | 提示“添加需要照顾的人，资料可以逐步补充。”，选择“**只为自己**”或“**自己和家人**”。首次仅建立“我”，家人由用户主动添加。通过成员标签切换，按当前成员填写姓名／称呼、性别、出生日期、与“我”的关系、身高（cm）、体重（kg）；身高、体重等资料可后补，头像可上传或用默认头像，不另设上传头像步骤。选择“自己和家人”时，勾选“通常一起吃饭的是哪些人？”，至少选择一位，默认人数由所选成员计算，允许超过四位；新增成员不自动选为就餐者。“只为自己”按本人一位安排并隐藏家人标签与就餐勾选，切换方式保留已有家人档案和家庭就餐选择。默认选择不代替每餐的就餐者调整。保存并继续保存本页所有成员与选择，切换成员不丢填写内容。 |
| 2/3 饮食目标与基础健康 | 按“当前成员 → 基础病情况 → 系统饮食管理摘要 → 饮食目标 → 口味偏好 → 菜系偏好”的顺序填写和展示；基础病对应的饮食管理摘要由后端规则生成，只读展示，不让用户关闭疾病规则。 |
| 3/3 健康限制与报告 | 切换成员，按“食物过敏 → 食物不耐受 → 饮食忌口 → 医生饮食要求 → 体检报告”的顺序展示各行及当前摘要或状态。点击过敏、不耐受、忌口或医生饮食要求时，从底部弹出约半屏高的编辑面板；保存后关闭面板并刷新当前摘要。点击体检报告进入当前成员的报告管理界面。 |

已完成首次建档后，从 AI 首页“家庭健康档案”或“我的 → 我的家”进入**家庭总览页 → 成员详情页**，维护成员资料时不再跳回三步建档流程。“健康限制与报告”标题右侧不展示“续填”；用户直接点击下方各行。过敏、不耐受、忌口和医生饮食要求使用半屏编辑面板，不新开完整详情页。

- **家庭总览页。**顶部标题“家庭健康档案”和一句简短说明；下方纵向排列成员卡，每人一张：左侧头像，中间姓名、年龄、性别，右侧进入详情的箭头。成员列表底部是整行“添加家庭成员”按钮，页面底部保留小程序导航；不在成员卡增加档案完整度或健康摘要看板。
- **成员详情页。**顶部返回、标题（如“妈妈的健康档案”）及编辑入口；成员信息区展示头像、姓名、年龄、性别、与“我”的关系。正文按“**基础资料 → 基础病情况 → 每日饮食**”排列，恰好三个独立一级卡片，不承担趋势分析或摄入统计看板功能。
- **基础资料。**收纳身高、体重、出生日期、关系、饮食目标、口味及菜系偏好、食物过敏、食物不耐受、饮食忌口、医生饮食要求和体检报告。内部可用“成员信息、偏好与目标、饮食限制、医生要求、体检报告”等小标题分区，不增设一级卡片；报告仍进入当前成员原有的报告管理界面。
- **基础病情况。**用少量标签展示当前成员已填写的基础病，并注明“用户自述”；保留未填写与无已知基础病的区别。
- **每日饮食。**展示当前成员今日实际保存的饮食记录，不展示计划吃什么；没有记录时标为“未记录”，不推断为没有进食。

第 3 页按当前成员分别保存，家庭模式下可切换成员，顶部始终显示“正在填写：成员称呼”。页面字段和规则如下：

1. **基础病情况。**提问“是否有已知基础病？”，必须主动选择“确认没有”或“有／选择内容”，不提供“暂不填写”，也不默认替用户确认没有。选择“有／选择内容”后至少选择一项“糖尿病、高血压、高血脂、高尿酸／痛风、肾脏疾病、其他”；选择“其他”时必须手动填写具体情况。基础病信息标记为“用户自述”，不能直接显示成平台确诊结果。
2. **系统生成的饮食管理摘要。**后端根据已选基础病调用受控规则自动生成并只读展示主要饮食管理原则。例如高血压可提示重点控制钠含量、减少高盐调味品、腌制食品和高钠加工食品，并优先采用清蒸、炖煮等方式。选择多种基础病时，后端合并规则并处理冲突；用户不能通过取消勾选关闭疾病规则。该摘要属于饮食管理参考，不代替诊断或医生医嘱；已填写的医生饮食要求优先于通用规则。
3. **饮食目标。**至少明确选择一项，可多选“控糖、控压、控脂、低嘌呤、减脂、增肌、补充蛋白质、饮食均衡、改善蔬菜摄入”，也可补充具体文字目标。没有特别目标时可以主动选择“饮食均衡”。目标表达用户希望改善的方向，不代表用户患有对应疾病；例如选择“控糖”不能自动认定为糖尿病。
4. **口味偏好。**合并原先重复的“口味”和“口味偏好”，至少明确选择一项，可多选“清淡、少油、少盐、偏甜、酸甜、咸鲜、微辣、香辣、麻辣、不吃辣”，支持填写自定义口味。没有特别偏好时可主动选择“不限口味”。
5. **菜系偏好。**独立于口味展示，至少明确选择一项，可多选“家常菜、粤菜、川菜、湘菜、鲁菜、苏菜、徽菜、快手菜”，支持填写自定义菜系。没有特别偏好时可主动选择“不限菜系”。

基础病、饮食目标、口味和菜系由用户填写；基础病对应的饮食管理要求全部由后端规则生成。自定义内容与预设选择一并保存到当前成员，不跨成员共用。

第 4 页按当前成员分别填写以下内容：

- **过敏食材：**与饮食忌口分开。必须主动选择“确认没有”或“有／选择内容”；选择有时至少选择一项“麸质谷物、含坚果、含乳、含大豆、含花生、含蛋、鱼类、含甲壳类”，也可自定义添加具体食物或成分。已知过敏食材用于菜品及商品**全部配料**的冲突检查。
- **食物不耐受：**与食物过敏分开。必须主动选择“确认没有”或“有／选择内容”；选择有时必须选择或补充具体食物或成分，例如乳糖不耐受、麸质不耐受。已知不耐受用于推荐前的配料检查；冲突未解决时与过敏冲突一样阻止购买，但页面必须明确其为“不耐受”，不得冒充食物过敏或医疗诊断。
- **饮食忌口：**必须主动选择“确认没有”或“有／选择内容”；选择有时至少选择一项“坚果、面筋、豆制品、鸡蛋、葱蒜、香菜、乳制品、牛羊肉、海鲜、辛辣”，支持自定义添加具体内容。
- **医生饮食要求：**点击这一行弹出当前成员的半屏编辑面板，**不在此面板设置体检报告上传入口**。必须主动选择“确认没有”或“有／选择内容”；选有后必须以文字填写具体要求，例如需限制的食物或摄入量，不能用控糖等目标标签代替医嘱。医生饮食要求优先于系统按基础病生成的通用饮食管理摘要；存在无法自动合并的冲突时提示用户复核，由 AI 重新分析与检查；仍无法处理时按第 3.3 节停止可购买的个体化推荐。
- **体检报告：**“体检报告”行是报告模块的唯一入口；从首次建档或家庭健康档案点击时，均进入当前成员的同一个报告管理界面。在该界面可拍照、从微信聊天选择或选择设备文件，文件须明确关联当前成员，显示上传及处理状态并允许查看。识别出的内容先让用户核对，不自动作为确诊结果写入档案。设备文件入口的小程序可用范围需在真机核对，无法使用时提供可用的替代选择方式。

保存后，对应行显示当前成员的简短摘要，例如“高血压 · 有医生饮食要求”；基础病明确选择“确认没有”才显示“无已知基础病”。草稿和历史资料的“未填写”不同于明确的“没有”，不会自动改成“确认没有”；完成建档提交前须补齐必填状态。成员之间互不共用这些状态。体检报告未上传时显示“尚未上传”。

- **一般数据异常提醒。**身高体重输入无效、基础病与饮食目标矛盾、过敏与不耐受信息互相矛盾、体检指标异常或字段间明显不一致时，弹出提醒框说明需复核的字段，允许返回修改或继续保存。该提醒只用于信息复核，不输出医疗诊断，也不替代已知过敏／不耐受冲突的购买阻断和基础病个体化方案的 AI 分析与饮食安全检查。

- “我的”显示当前使用方式并提供“更改”。确认切换前说明“家人档案与历史记录会保留；已支付计划仍按购买时的内容执行”；用户取消则保持原方式，确认后更新以后生成建议时的默认适用成员。切换不改写已支付计划、订单、商品、价格或配送安排。
- 完成建档前，每位建档成员必须填写有效出生日期，明确已知基础病、食物过敏、食物不耐受、饮食忌口和医生饮食要求状态，并至少选择或填写一项饮食目标、口味偏好、菜系偏好。选择有时必须提供具体内容。必填缺失时停留在对应成员与步骤，前后端均拒绝不完整建档；身高、体重、性别和体检报告保持可后补。
- 建档阶段**不要求收货地址和联系电话**；下单时再选择或新增。

### 3.2 登录、家庭邀请与共享权限

1. **登录与手机号验证。**小程序先通过微信登录与服务端校验建立账号会话。通过邀请加入家庭本身不强制获取或验证手机号；涉及下单、配送、找回账号或其他敏感账号操作时，再由本人通过微信手机号能力或验证码提供并验证手机号。仅在表单中输入手机号不能证明身份，也不直接授予家庭访问权。
2. **邀请流程与分享入口。**通过小程序右上角“**··· → 转发**”发送邀请卡片，不再以输入对方手机号作为邀请入口。在家庭总览页分享时生成普通家庭邀请，只绑定家庭，不绑定某位成员；同一卡片可由多人接受，暂不设置有效期、家庭成员人数上限，本期暂不考虑邀请撤销与重新生成。在未认领的成员详情页（如“妈妈的健康档案”）分享时生成绑定该成员的邀请；页面内保留“**邀请本人加入**”按钮，两种入口使用同一流程，仅向有邀请权限的人开放。卡片可写“邀请你加入我的家庭，核对你的健康资料”，不展示基础病、过敏等健康信息；链接携带后台可识别的签名邀请凭证，用户不需要查看或手动输入邀请码。对方打开卡片后先微信登录，再查看邀请人、家庭名称和共享范围，明确点击“确认接受邀请加入家庭”等按钮后才加入，也可以拒绝。
3. **档案认领与受邀建档。**普通家庭邀请接受后进入受邀成员建档，填写本人的成员资料并创建档案；绑定成员邀请接受后先核对已有预填资料，再修改或补充，不重复创建档案。一份成员档案只能由一个账号认领，已认领后不能通过转发让另一账号认领。受邀流程填写姓名／头像、性别、出生日期、关系等基本资料，以及基础病、饮食目标与偏好、过敏、不耐受、忌口、医生饮食要求和体检报告；不重复询问“个人使用／家庭使用”或“平时几个人一起吃饭”，完成后进入家庭页面。账号、家庭、人员档案和账号与家庭的成员关系必须作为不同数据对象保存。
4. **共享查看。**已接受邀请的家庭成员可查看家庭成员、共同菜单、饮食计划、家庭共享记录和配送进度。过敏、不耐受、忌口、医生饮食要求和配餐必需的健康限制按接受页明示的范围在家庭内共享；体检报告需本人明确同意后才向家庭成员开放。
5. **编辑与敏感操作。**已认领档案的成年成员默认编辑自己的健康资料；家庭创建人可维护尚未认领的档案和邀请状态。支付、退款和收货地址变更由下单人或获授权的家庭管理员执行；其他成员可查看已共享的订单与配送状态。个人 AI 对话默认不向全家公开，由对话形成的家庭菜单和共同计划可共享。
6. **邀请状态和异常。**记录受邀人的待接受、已接受或已拒绝状态；普通家庭邀请在他人接受后仍可用于其他人加入。无效凭证、无邀请权限或绑定档案已被其他账号认领时不得加入或重复认领，也不得泄露家庭健康信息。本期不要求过期、撤销和重发交互。移除成员、退出家庭、转移家庭创建人、更换手机号和解散家庭均需保留可审计的状态变化，并立即撤销后续访问权。

### 3.3 健康信息对建议和购买的影响

- 健康资料不足时，仍可浏览通用内容，也**可以推荐通用食材包**；页面提示哪些成员资料未填写，并展示已知配料与过敏原。不得声称通用包已符合某位成员未知的基础病、过敏或不耐受限制。
- 首期采用三级饮食安全机制：第一层在建档及家庭健康档案中记录成员的食物过敏、食物不耐受、饮食忌口和医生饮食要求；第二层在生成菜单、套餐和关联食材包前，由系统根据本次适用成员以及菜品、商品的全部已知配料自动检查并排除已知冲突；第三层在菜单页或计划详情页以简洁状态展示检查结果。正常情况下仅显示“已避开已知冲突”，不要求用户再次确认，也不在购买流程增加独立安全确认页。
- 推荐前检查和档案、菜单、配料或商品数据变化后的自动复核，应使“发现冲突”只作为异常兜底状态。若仍发现冲突，系统先自动重新生成安全建议，并按第 5.1 节重算受影响的建议、食材需求和 SKU／包装，采购商品或数量变化时更新未支付报价；若仍无法消除过敏、不耐受、明确忌口或医生饮食要求冲突，必须指出适用成员、冲突原料和受影响菜品或商品并阻止购买。不能仅靠用户点击“我已知晓”放行冲突内容。AI 无法完成个体化适配或饮食安全判断时，不得标成可购买的个体化专属方案。
- **基础病成员的 AI 处理。**糖尿病、高血压、高血脂、高尿酸／痛风、肾脏疾病、多基础病和“其他”统一由 AI 分析与饮食安全检查处理，具体模型、规则和冲突处理方案由后端设计。不设置人工审核流程，不向用户展示“待提交、待审核、退回补资料、审核通过”等状态。无已知基础病且资料完整时简洁展示适用成员与限制；有基础病且信息可用时，生成后的本餐基本信息区域展示基础病饮食摘要、医生要求和注意事项，并按需提供成员不同份量或替代餐。成员选择列表不增加“特殊人群／需重点关注”标签，也不增加推荐前确认页。
- **信息不足与分析失败兜底。**信息缺失但没有已知冲突时，只提供明确标记的通用建议或通用食材包，不声称完成个体化适配。存在已知冲突或无法判断安全时，不提供可购买的个体化菜单，提示补充资料或稍后重试；不转入人工审核流程。
- AI 从对话中提取疾病等信息时保留“**用户自述**”来源，用于后续 AI 分析与饮食安全检查；自动提取本身不等于确诊或专业结论。

## 4. 每天一个 AI 对话、今日饮食计划与记忆

### 4.1 每日对话、次日提议与记忆

1. **每日对话**以北京时间 00:00 切分。当天继续同一对话；历史记录按日期列出过去的 AI 对话和摘要，点开可读对应消息。饮食记录在“我的 → 饮食记录”。
2. AI 对话需接入团队确定的模型与受控业务服务。无法可靠回答的问题说明限制并引导补充信息或稍后重试，饮食安全无法判断时按第 3.3 节处理；早期开发可以用固定脚本做联调，但不能作为正式服务能力。
3. 用户在对话中谈到“明天吃什么”，AI 当场给出明日餐次提议；保存后的提议在次日**没有正常执行中的 AI专属计划时**优先成为“今日饮食计划”，标明“AI 提议，可修改”。后端在北京时间零点后总结当天聊了什么、明日安排与未完成事项；历史中可看到摘要。定时任务失败或迟到时须有补跑和避免重复写入的机制。
4. AI 发现明确、成员归属清楚且值得长期保留的家庭信息，例如某位成员持续不吃辣椒或新提到的健康情况，可以直接写入长期家庭档案/记忆，**不再要求用户重复确认**；同时在当天对话中以轻量提示或“本次处理结果”说明记住了什么，并提供“查看记忆”和“撤回”。一次性的“今天有点咸”只关联该餐记录并用于当餐反馈，提供“查看反馈”；明确持续的“以后不吃香菜”才写入对应成员的长期记忆。“查看记忆”进入“我的 → 资料管理 → AI 记住的事”；用户也可从该入口查看、修改和删除记忆。成员不明、语义不确定或无法判断是一次体验还是长期规则时必须先追问，不得无感写错成员或把一次体验升级为长期限制。疾病类信息可免去重复确认但必须保留“用户自述”来源，不得自动变成确诊或专业审核结论。
5. 记餐后进入当天对话须携带刚保存的记录 ID；文字或语音回答、AI 回应和处理结果都关联该记录。若用户话语意在更正实际食量、菜品或就餐成员，AI 先展示拟更正内容并请用户确认，再更新记录版本、当餐/当日/近期趋势和下一餐建议的依据；未确认前不改写原始记录。
6. 日终摘要、次日提议和长期记忆属于不同对象；档案变化后，旧的未支付个体化建议自动失效并重新分析、生成，优先级仍按第 4.2 节执行；已支付计划、订单和履约快照不被改写。

### 4.2 今日饮食计划的展示、来源与去向

- 进入 AI 对话页时，页面上方自动展示“**今日饮食计划**”早餐、午餐、晚餐卡片。它是普通页面内容，向下滑动时逐渐离开屏幕，**不吸顶**。每餐右上角用明显的胶囊按钮汇总人数，如“**👥 2人用餐**”，点击在当前 AI 页打开约半屏高的成员勾选面板，确认后关闭并更新该餐；早餐、午餐、晚餐可选择不同具体成员，列表不加特殊人群标签。人数按钮应有足够点击面积，设计参考约 70～90px 宽、至少 40～44px 高。每餐下方“**查看本餐安排 >**”是明确的页面入口，不设置整卡任意位置点击跳转。输入框上方四个业务入口中的第四个“今日饮食计划”是小入口：点击后在当前 AI 对话内容下方**临时展开同一份**今日三餐卡片，不重新生成另一份计划，不作为 AI 消息保存，也不写入当天对话历史；同一区域另设“加入社群”入口，直接弹出运营配置的二维码，不进入独立说明页。
- 三餐来源按优先级自动选择：**已购买、已到生效日且正常执行的 AI专属计划**提供该计划当天的三餐；没有这种计划时，**前一天已保存的明日 AI 提议**优先；若也没有该提议，再由 AI 参考当前使用方式和适用成员的家庭档案规划三餐。计划尚未生效、暂停或结束时，不使用其菜谱作为今日三餐，继续按后两项来源选择。首次完成建档后读取建档信息自动生成今日三餐，后续仍按上述优先级自动选择或生成，用户查看后再调整，不先增加本餐核对页。页面说明当前三餐来源，顶部卡片与临时展开卡片保持一致。
- 点击档案／明日提议来源餐次卡的“**查看本餐安排 >**”，直接进入该餐的“**本餐安排与食材购买清单合并页**”，不再先进入独立菜品页后通过“一键备齐食材”跳到第二个购买页。正常执行中的 AI专属计划餐次的入口仍进入该计划当天对应餐次和履约路径，不把计划餐次误导至普通食材包购买路径。
- 用户可在 AI 对话中调整**怎么吃**的建议，包括个人份量、吃法和每餐具体就餐成员。成员变化后按第 5.1 节自动执行条件重算，更新安全检查、尚未固定的建议及必要的未支付报价；卡片右上角同步汇总人数。上述调整与已支付计划的履约快照分开：不修改已支付订单、商品、价格或配送安排。需要实际变更已支付计划时，应进入对应计划或订单允许的正式变更流程。

### 4.3 今日饮食计划“一键采购”

- 在“今日饮食计划”区域右下角增加“**一键采购**”，汇总当天早餐、午餐、晚餐的食材需求，进入**今日采购清单**，不直接下单或支付。正常执行中的已购买 AI专属计划隐藏该按钮，避免重复采购。
- 按实际食材与 SKU 跨餐合并需求，再映射包装数量，不把各餐已经向上取整的包装数量直接相加；保留用户已标记为家里已有、不购买的食材选择，允许取消某一餐的采购。
- 今日采购清单展示合并后的商品、规格、数量和实际金额，用户核对后进入正常结算，再核对商品、数量、地址和价格。成员或菜单变化时按第 5.1 节更新需求与必要的未支付报价；不修改已支付订单。

## 5. 三餐、本餐购买合并页、菜品做法与“换一换”

### 5.1 三餐与家庭分餐

- “今日饮食计划”和 21 天计划每天都展示**早餐、午餐、晚餐**。正式计划需要保存 21 天各餐的实际菜谱与版本；开发测试可复用样例菜谱，不能把测试数据展示成已完成的个体化建议。
- 家庭优先是一桌共享菜，再按成员展示粗略分餐和不同健康约束。份量允许用“少量／一般／较多／不确定”等易懂表达；不要求准确称重。
- 个人使用时，新生成的普通三餐建议默认面向“我”；家庭使用时默认考虑已建档家庭成员。每餐通过右上角人数胶囊的半屏面板选择具体就餐成员，三餐可不同；即使人数相同而仅替换成员，也必须重新检查基础病、过敏、不耐受、忌口和医生要求。
- **成员变化的条件重算。**业务顺序为“修改本餐成员 → 重新检查健康约束 → 判断菜单是否调整 → 重算每道菜目标份量 → 汇总食材需求量 → 映射实际 SKU／包装规格 → 判断采购商品或数量是否变化 → 有变化时更新未支付报价”。建议层始终重算，采购层按需更新，不按人数线性加价；菜品改变时重新计算相关食材和采购映射。例如番茄需求 300g／450g 均可对应 1 盒 500g，价格可不变；鸡胸肉需求 350g／600g 则可对应 1／2 盒 500g。示例仅解释包装计算，不作为固定用量或售价。
- **采购选择保留。**重算时尽量保留仍存在食材的用户勾选状态，已取消的盐、油、葱姜蒜等只更新需求量，不自动重新勾选；新出现食材默认勾选，已不再需要的食材同步移除。系统自动计算，不让用户选择“是否重新计算食材”；用结果说明变化，例如“已按 3 位就餐成员更新本餐建议，采购数量无需调整”“已按 3 位就餐成员重新计算食材，预计金额 ¥68 → ¥82”或“因爸爸的饮食限制，已调整 1 道菜，并同步更新食材清单和预计金额”。金额及成员均为文案示例，正式结果读取实际数据。
- **支付后的边界。**不修改已支付计划的菜谱快照、订单、商品、价格或配送；来自执行中计划的餐次仍展示已购买内容，成员变化只更新分餐、吃法、安全提示或替代餐建议。本期不增加补充购买提示、入口或增购流程，实际订单变更仍使用原有正式变更流程。
- 菜品卡至少展示菜名、主要食材、风味信息和相关营养/健康标签。“蒜香”“咸鲜”等应对应实际配方；“抗氧化”“增强免疫”“三高友好”等只是讨论中的**标签示例**，未经专业团队核定依据、适用条件和文案前，不作为正式菜品功效结论发布。

### 5.2 单菜“换一换”

三餐中**有可替换候选的菜**，就在这道菜卡片右侧展示图标与“换一换”；没有合格候选时直接隐藏入口。点击后**直接**展示最多 3 道同类型、营养结构相近且热量差不多的合格候选；只有 1～2 道时展示实际候选。用户选 1 道，**只替换当前菜**。候选卡展示菜品信息、标签及对食材、价格和做法的差异。选择后同步当前菜单、营养与注意事项、相关食材包/清单、未支付报价和烹饪步骤，并重新执行饮食安全检查；已支付订单保留支付时快照。

该流程**不询问不喜欢原菜的原因，不记录哪位成员不喜欢，不因换菜自动写入口味记忆**。候选仍须遵守已知过敏、医嘱等约束；正式候选覆盖需与后端、营养团队确认，不能用不合格菜品凑数。

### 5.3 AI 回复后的本餐入口

用户问“今晚全家吃什么？”等问题后，AI 必须遵循“**先分析，再推荐**”：先用一段自然语言结合本餐具体成员的基础病、系统饮食管理摘要、医生饮食要求、过敏、不耐受、忌口、饮食目标和口味等资料，说明当前分析、推荐思路及需要注意的地方，再提供“查看晚餐菜单”等餐次菜单入口。商品或计划卡与分析内容在信息层级和视觉上分开，不能把 AI 回复画成开场即逐项列菜、列套餐或推销食材包。此处的问法和入口文案是场景示例，不限定用户只能问晚餐。

完成分析并生成安全建议后，才可在 AI 回复**下方**展示本餐摘要、关联食材包或“查看本餐安排与购买清单”入口；最终均进入第 5.4 节的合并页。菜品更换后同步合并页中的菜品、营养估算、注意事项、食材清单和未支付报价，并重新执行自动饮食安全检查。示意图里的具体菜名、分类、价格和商品卡数量均为展示样例，不写成固定业务数据。

### 5.4 本餐安排与食材购买清单合并页

普通早餐、午餐或晚餐使用一个合并页完成“看本餐安排”和“选择购买食材”。**先生成推荐菜单，再进入本页展示本餐基本信息，不增加推荐前核对页。**页面上方的基本信息区域集中展示本餐餐次、具体就餐成员与人数、营养和注意事项，不展示“预计用时”或“菜品数量”；其下展示本餐全部菜品、所需食材、包装规格、数量、单项价格、已选食材数量和订单合计金额。结构顺序为“本餐基本信息（含本餐就餐者、营养与注意事项）→ 本餐菜品 → 本餐所需食材和购买清单 → 合计金额与直接购买”。页面不再设置用于跳到第二个购买页的“**一键备齐食材**”按钮；底部直接保留“去结算／直接购买”。

“本餐营养与注意事项”在上方基本信息区域按两层展示：**本餐总体**包含预计热量及范围、蛋白质、脂肪、碳水／糖类估算、简洁饮食安全状态（正常时“已避开已知冲突”）和主要烹饪注意事项；**成员差异**仅对有不同要求的成员展示与基础病、医生要求、过敏、不耐受和忌口有关的份量、吃法或替代餐，例如少盐、控制主食份量或无乳糖替代，不把所有成员重复列一遍。有基础病且信息可用时在此展开相应饮食管理摘要与注意事项。数值须基于实际菜单、配方、份量和可用营养数据，明确标注估算性质、单位和依据；无可靠数据时显示“暂无法估算”，不能用固定演示值冒充本餐结果。这里展示的是菜单生成后的本餐估算，不把生成前的目标范围写成本餐实际含量。

食材选择、当前金额、本餐就餐者和浏览位置属于该合并页的临时交互状态。用户从菜品做法详情返回时不得重新初始化已选食材或金额；在页面栈和平台能力允许时恢复原浏览位置。换菜或成员变化后按第 5.1 节同步菜品、食材、包装数量和必要的未支付报价，并保留仍适用的食材勾选状态；已支付订单仍保留支付时快照。

### 5.5 单道菜完整烹饪详情页（购买前可查看）

合并页中的每一道菜均可点击，并在购买前进入独立的“单道菜完整烹饪详情页”，不得用半屏弹层代替。详情页至少展示菜品名称、菜品图片、预计制作时间、所需食材及用量、完整文字制作步骤、每一步对应图片、注意事项，以及“返回本餐安排与购买清单”入口。返回后按第 5.4 节保留合并页状态。

2026-10-13 确认补充：每道菜在菜品图片／名称大卡片之后、预计制作时间卡片之前新增“营养信息”卡片，按两行三列展示**能量、蛋白质、脂肪、碳水化合物、膳食纤维、钠**。统一注明“每 100 克熟制后可食部分”和估算／检测性质，能量单位 kcal、钠单位 mg、其余单位 g；缺失值显示“暂无数据”，不能用 0 替代。数据由后端按菜谱版本持久化并随菜谱返回，已购订单保留营养快照；收货后整餐烹饪页随菜品切换展示同一对象。测试值明确标注，字段及存储要求见[菜品营养字段与后端存储契约](菜品营养字段与后端存储契约.md)。

文字加分步骤图片是所有菜品默认且完整的烹饪讲解形式，首期可不提供视频，视频不作为必需交付内容。仅当某道菜具备与当前配方、用量和步骤一致并通过内容审核的正式视频素材时，才额外展示视频；没有视频的菜不显示“视频待补充”或空播放器，也不得用无关视频占位。后续视频更新不改变已购买计划保存的菜谱版本；具体覆盖及素材标准列入第 11 节待决事项。

### 5.6 收货后的烹饪入口

用户在购买前即可查看第 5.5 节的完整图文烹饪内容；收货后在**订单详情／配送批次**按早餐、午餐、晚餐列出菜品，每餐提供“**开始做饭**”。点击进入对应**整餐烹饪页**，标题如“午餐制作”，顶部保留菜品标签，默认展示第一道菜，切换时同步菜名、图片、预计制作时间、所需食材及本餐用量、完整文字步骤、每步图片和制作／饮食注意事项。不显示“这餐要做”标题或“当前选中，可点击切换菜品”说明。购买前与收货后内容同源，已购买计划使用支付时保存的菜谱版本，不维护相互矛盾的两套菜谱。

菜品切换不承担任务进度：**不设置单道菜“已完成”按钮，不显示完成勾选，不记录单菜完成状态，不要求逐道确认，也不展示“1/3 道已完成”等进度。**整餐页底部统一入口为“**去拍照记录这一餐**”，进入拍照记餐页面。

### 5.7 商品与购买安全边界

单包详情可展示商品图片、名称、类别、对应菜品、价格、规格／数量、“这个包里有什么”和对应做法入口。饮食安全检查按第 3.3 节在推荐前自动完成，并在菜单页或计划详情页显示简洁结果；单包详情和购买流程不再设置独立的“忌口／过敏／不耐受确认”步骤。进入购买流程后直接核对地址、商品、数量、配送和价格。

家庭档案不足时照常显示**通用食材包**，并提示未知健康资料、已知配料和过敏原；“未填写”不等于“确认没有”。推荐前排除已知冲突；档案、菜单、配料或商品数据变化后自动复核并在异常时重新生成安全建议。仍无法消除冲突时阻断相应商品，不得进入购买。普通包进入普通订单；“AI专属计划”入口进入与“我的”入口共用的计划推荐页，标明“一次支付、分 21 批配送”，不把计划总价伪装成普通单包价。

## 6. AI专属计划、价格与配送

### 6.1 双入口、推荐页与计划详情

AI 对话页输入框上方的第一个入口与“我的 → AI专属计划”进入**同一个计划推荐页**。保留“**为您推荐的专属计划**”标题，标题下用现有“基于……家庭档案，展示……”一类简短说明交代推荐依据；不增加大段 AI 分析，也不增加 AI 解释或建议哪一档更适合用户。资料缺失时显示“未填写”，不暗示已完成个体适配，并提示可从“我的 → 我的家”补充。推荐页不重复设置家庭档案入口；日常 AI 对话的“先分析，再推荐”仍按第 5.3 节执行。

计划首期按 21 天预计总价及食材、规格和菜品丰富度差异分为“**经济型／标准型／品质型**”三个档次。每张计划卡展示图片、名称、档次、适用成员、主要差异、**首批三餐食材预估价**和**21 天预计总价**，点击“查看计划”进入详情。三档具体金额区间由商城、供应链和产品负责人定稿，未定稿前只能使用显著标记的测试数据。切换日常使用方式不改变已购买计划原有的适用成员、菜谱与履约快照。涉及慢病成员的个体化方案仍遵守第 3.3 节的 AI 分析与饮食安全检查要求。

计划详情展示计划名称、档次、适用成员、**21 天每天早餐／午餐／晚餐的实际菜谱与版本**；首屏可预览第 1、2 天，并能查看全部 21 天。配套净菜区域列出商品图、名称、规格、数量和价格，支持进入“全部净菜”查看完整清单，不以少量预览商品代替全部报价。页面按第 6.2 节显示自动饮食安全检查状态；正常时仅显示“已避开已知冲突”，不要求用户再次确认。底部区分“21 天计划预计总价”与首批食材价；安全检查通过后，“下一步”直接进入确认配送。推荐、菜谱、商品与报价来自实际业务数据；后端尚不可用时，可用**显著标明的测试数据**走通交互，不把固定样例称为真实推荐或实时报价。

### 6.2 三级饮食安全检查与异常兜底

AI专属计划遵守第 3.3 节的三级机制，不设置独立的忌口、过敏或不耐受确认页。第一层读取本次适用成员的食物过敏、食物不耐受、饮食忌口和医生饮食要求；第二层在生成 21 天菜单、套餐和配套净菜前检查菜品及商品全部已知配料并排除冲突；第三层在计划详情页显示简洁状态。正常情况下只显示“已避开已知冲突”，不要求用户再次确认。

档案、适用成员、菜单、配料或商品数据变化后自动复核。若异常发现冲突，系统自动重新生成安全建议，可替换全家菜品，或把原菜仅安排给无冲突成员并为受影响成员自动生成无冲突替代餐；仅标记“此成员不吃”但没有替代餐不算解决。每次调整后重新检查**每位成员的菜单、全部配料、采购商品与数量、首批及 21 天价格**。若仍无法找到安全替代、配料信息不足或复核失败，明确显示成员、冲突类型、冲突原料及受影响菜品或商品并阻止进入配送和结算；已知冲突不能靠“我已知晓”绕过。

### 6.3 一次支付和统一报价口径

AI专属计划覆盖从分析、分档推荐和计划选择、推荐前自动饮食安全检查、21 天三餐、净菜核对、地址与生效日期、**一次支付**，到 21 个批次跟踪、暂停/恢复、取消剩余批次、退款试算和逐批售后的完整业务流程。购买流程不增加独立的过敏／不耐受确认步骤。推荐、详情、配送、结算和订单页区分预估价、支付前有效报价与已支付快照；报价变化时提示用户重新核对。

| 金额名称 | 正式产品定义 |
| --- | --- |
| 首批三餐食材价 | 第 1 批早餐、午餐、晚餐**全部**食材合并后按实际 SKU、包装规格和实时价格计价；不是一顿菜价。 |
| 21 批商品价 | 根据 21 批实际菜谱、食材需求、SKU、包装、库存和报价**逐批计算再求和**。 |
| 计划服务费、配送费 | 分项显示各项适用金额及计费依据；收费规则和金额由商城、供应链负责人定稿。 |
| 一次支付总价 | `21 批商品价 + 计划服务费 + 配送费 - 可用优惠`；以结算预览和支付前复核结果为准。 |

**统一原则：首批价和 21 天总价始终分别展示。** 推荐页和详情页可展示有来源、有有效期的预估价；结算及支付前必须获取有效报价并再次展示地址、全部商品、数量、费用与优惠，支付后保存报价和计划快照。旧页面把同一金额同时标为首批和总价、而局部商品合计又不同的做法不能沿用。测试金额只能出现在明确标为测试数据的评审／联调环境，不能写死进正式商品、推荐卡或结算页。

### 6.4 地址、生效日期与 21 批配送

- 确认配送页按**地址 → 第 1 批预计送达日 → 21 批配送安排**排列。顶部地址卡进入独立的“选择配送地址”页；有多个地址时先选再确认，空地址簿显示“还没有收货地址”和“新增收货地址”。新增、编辑使用同一表单，填写收件人、电话、省／市／区、详细地址，可选标签和默认地址；“保存并使用”校验必填内容后将所选地址带回确认配送页。建档阶段不索取地址及电话。
- **计划生效日期 = 第 1 批食材的预计送达日**，不是支付日。先选地址再显示后端根据供货、截单时间、地址、节假日和运力返回的可预约日期；选定后列出 21 批预计日期及各批早餐、午餐、晚餐，支持展开全部批次。原页面“至少两天后”只能作为开发测试约束，能否成为正式规则须由履约团队决定。地址变化导致日期或报价失效时要求用户重新选择和核对，不静默改期。
- 点击“核对商品与价格，去结算”后再次展示地址供用户确认，并复核 21 批商品和价格；有效地址、可预约日期、无已知冲突的菜单和有效报价缺少任一项时，不能进入支付。
- 下单时选择的**一个地址用于全部 21 批**，订单和各批次保存地址快照。后续改地址簿不自动改已支付订单。支付后可针对**某一个未发货批次**自助改址，其他批次不变；已发货批次提示联系配送或客服。

### 6.5 暂停、恢复、取消与退款

已支付计划的详情页允许选择从某个**尚可变更的未发货批次**开始暂停、查看新排程、恢复并确认；已发货、配送中、已收货批次维持原状态。用户可以“取消剩余计划”，先看可取消批次清单和**实时退款预览**，再次确认后展示申请中、处理中、成功或失败待处理。已发货/已收货批次的问题进入逐批售后，不混入“取消剩余”的退款。

**正式退款金额、服务费与优惠分摊、截单时间、暂停上限、备货后能否取消**须由商城和供应链负责人定稿并由服务端计算。前端显示实际申请状态与支付渠道回执，不提前承诺到账。

## 7. 普通订单、计划订单与售后

### 7.1 列表和详情

订单列表采用用户已认可的“**全部／进行中／已完成**”三栏。全部按下单时间倒序；进行中包括待支付、待备货、待配送、配送中、部分批次已收、计划暂停、售后或退款未结；已完成收纳已履约且无未结事项的订单，或取消与退款流程已经有最终结果的订单。取消订单在卡片状态显示“已取消”，避免误写“配送完成”。

卡片显示订单类型、编号、下单时间、商品摘要、一次支付金额和当前状态。21 天卡额外显示“**已收 X／21 批**”、下一批日期、暂停/售后提示。一批收货不代表整单完成。点卡片进入详情；查看物流、申请售后、再买一单可作快捷入口。再购需重新核对商品、库存和价格；重购计划还要重新选生效日期与地址。

### 7.2 售后发起和处理

普通订单先选受影响商品与数量；21 天订单**先选已发货或已收货的批次，再选本批商品与数量**。用户先选期望结果“**希望补发／希望退款／请工作人员联系我**”，再选问题原因和填写说明；期望不等于处理承诺。

| 原因 | 用户填写或选择 | 可能的处理方向，以核实结果为准 |
| --- | --- | --- |
| 商品问题 | 商品、数量、不新鲜/破损/规格不符等描述，可附照片。 | 补发、退款或人工处理。 |
| 少件／漏件 | 缺少的商品和数量。 | 核对后补发或退款。 |
| 配送问题 | 批次、延误/送错地址/损坏等说明，可附照片。 | 联系配送、重新配送或人工处理。 |

提交前展示订单、批次、商品、问题与期望结果摘要。服务端实际接收申请后生成可再次查看的售后记录，按“已提交 → 处理中 → 待补资料／处理完成”等真实状态更新；结果显示补发商品、实际退款金额或不通过原因。已有同批同商品的处理中申请时先引导查看，避免重复提交。提交失败时保留用户填写内容并可重试，不显示虚假的受理或退款成功。

**批次隔离验收**：第 7 批申请售后时第 1–6 和第 8–21 批不受影响；同一批可只选某一商品；取消剩余未发货批次的退款试算与某已收货批次商品售后分开展示。

## 8. 饮食记录、餐后对话与反馈

### 8.1 统一记餐与两个保存去向

饮食记录是统一对象，可由**拍照分析、从当天食谱选菜或手动填写**建立；不另设容易混淆的“餐后记录”。可在餐前粗估，不强制拍餐后剩菜照，也不要求称重。

1. **拍照前选择范围、就餐者和餐次。** 拍单人餐盘时选对应的一位成员；拍家庭共享桌菜时选本餐参与成员。这是拍摄范围选择，独立于“个人使用／家庭使用”的日常使用方式。进入拍照页直接取景，中央拍照，右下角相册上传。拒绝相机权限仍可从相册、当天食谱或手填进入记录。
2. **底部上拉分析页。** 拍照后原画面变暗留在背景，分析页展示照片缩略图、识别出的菜品、**大致**热量和估算范围，以及蛋白质、脂肪、碳水／糖类估算。实际结果须关联用户上传的照片与识别任务，显示分析中、失败和重试状态；不把照片估算说成精确摄入。
3. **过敏与不耐受风险匹配。**页面结合菜品识别结果、已知菜谱或商品配料、用户补充信息和本餐成员档案，提示可能涉及的过敏原及食物不耐受风险。不得声称仅凭照片就能准确识别过敏原或不耐受成分；配料来源不完整或无法判断时显示“暂无法确认”，不能输出“安全食用”等虚假结论。 针对成员的拍照分析及后续反馈使用其基础病、医生要求和饮食限制生成适用注意事项，不输出医疗诊断。
4. **只粗略评估每位成员。** 家庭桌菜先确认桌上有哪些菜，再让每位成员粗选吃过哪些菜和“少量／一般／较多／不确定”；分别展示宽范围估算或“不确定”。不得把整桌热量自动分给个人，更不得给每位成员记一份完整桌菜。个人餐盘只确认个人菜品与大致份量。
5. **原照片纠错。** 底部提供“**拍照认错？重新识别**”。用户可语音或文字说明“这其实是番茄炒蛋”，用**原照片 + 纠错信息**重新识别；“重新拍照／更换相册图片”是另一入口。失败时保留原结果和已经填写的份量；识别结果需经真实照片集验证，不能只根据模型自述准确率放行。
6. **两个保存去向，同一条记录。** 三种入口均先确认成员、餐次、菜品与粗略份量，保存为同一类型、带唯一 ID 的饮食记录；“**仅保存**”与“**保存并聊聊这一餐**”是保存后的两个去向，防止连点生成两条。前者提示保存成功并可返回；后者携带这条记录的 ID 进入**当天 AI 对话**，AI 主动问：“这餐吃下来怎么样？有什么想告诉我的吗？”用户可用文字或语音反馈。跳转失败也不重复保存。两种去向保存的记录都可进入“我的 → 饮食记录”和“我的 → 反馈”。
7. **反馈与长期记忆。** 一次性的“今天有点咸”关联该餐并用于当餐反馈；明确、成员归属清楚且持续的忌口、口味偏好等可直接写入长期家庭记忆，以轻量提示说明并提供查看与撤回，不重复弹窗确认。疾病类表述标“用户自述”并用于后续 AI 分析与饮食安全检查；成员或语义不明确时仍须追问。若 AI 将一句话理解为记录更正，先让用户确认更正内容，再修改记录并刷新反馈；不把一次性口味体验直接改成实际摄入数据。

### 8.2 “我的 → 饮食记录”：原始记录与更正

“饮食记录”是查看事实的独立页面：可按家庭成员（含全家视图）和日期查找，以早餐、午餐、晚餐列出当天记录；缺失的餐次标“**未记录**”，不推断为没有进食。每张已记录卡展示餐次、时间、照片标识、就餐成员和菜品摘要，点入记录详情。家庭共享桌菜可有一张照片和共享菜品清单；详情切换成员时只展示该成员**已确认**的菜品、粗略份量和摄入估算，不把整桌估算复制给每个人。

记录详情展示原照片（若有）、记录来源、菜品与逐项营养明细，以及本餐概览中的估算值、范围、单位和计算依据。照片无法确定准确重量、隐形用油或每位成员实际食量；无可靠依据的指标显示“暂无法估算”，不编造数值。用户可更正菜品、成员归属和实际份量；保存更正时保留记录 ID 与版本，随后更新对应的当餐、当日、近期趋势及下一餐建议依据。饮食记录页提供原始记录和更正，不承担 AI 分析结果页的职责。

### 8.3 “我的 → 反馈”：当餐、当日、近期趋势

“反馈”与“饮食记录”在“我的”中是两个独立入口。反馈页的“查看范围”可切换**全家／单个成员**，并提供“**当餐／当日／近期趋势**”切换；当餐可选日期和餐次，当日可选日期，近期趋势可选近 7 天或近 30 天。全家视角展示有记录依据的共享菜品和相关反馈，并可跳转“查看饮食记录”；切到成员后，只使用该成员已确认吃过的菜和粗略份量生成有数据依据的反馈，不把共享桌菜的整桌摄入当成个人摄入。所有反馈基于已保存且已确认的记录及关联的用户补充反馈，标明依据、时间范围和缺失数据；区分用户输入、AI 推断与规则计算，不把演示数值写成健康结论。

- **当餐**：展示该成员的餐次、已记录菜品和实际份量，给出“亮点、可改进处、优化方案”，并注明依据；提供“更正记录”进入对应记录详情，以及“告诉 AI 这餐吃下来的感受”进入携带记录 ID 的当天对话。无记录时显示未记录状态，不生成针对该餐的评价。
- **当日**：列出早餐、午餐、晚餐中已记录的餐次及“未记录”的餐次，已记录项可查看；“今日亮点、今日可改进处、明天的优化方案”仅依据当天已有记录生成。缺失餐次不能当成没吃，也不能据此评价全天饮食或全天摄入量；明确写明依据了几餐、缺失了哪些餐。
- **近期趋势**：主图优先展示**已记录餐次中的蔬菜搭配情况**，例如每天“有蔬菜搭配的已记录餐次／当天已记录餐次”；仅有数据依据时才能切换其他饮食指标。图表标明统计日期、已记录餐次数、缺失餐次和无记录日；无记录日不作为 0 餐蔬菜搭配参与趋势判断。每日记餐次数只用于提示数据完整度，不作为主趋势图；固定演示热量不绘成准确的健康趋势。样本不足时只描述已有记录，不判断饮食变化方向。

用户新增关联该餐的主观反馈，或确认了记录更正后，按同一记录 ID 和最新版本重新生成受影响的当餐、当日及近期趋势；下一餐建议读取已确认的记录版本，说明采用了哪些记录。删除或撤回记录时也要同步撤销其分析依据，避免旧结论继续显示。

## 9. 合作商合作通道

合作商合作入口放在**“我的 → 设置”中，紧接在“隐私与账号”下方**，菜品推荐、食材包列表和购买页不再展示该入口。菜单项名称为“合作商合作”，辅助文案为“供应、渠道及经销合作申请”。点击进入独立“合作商合作”页，页面按以下顺序展示：

1. **合作类型：**先选择“供应商／渠道商／经销商”之一，其他合作类型后续再补充。
2. **合作要求：**根据所选类型展示对应要求。供应商关注食材来源、品质、新鲜度、资质、溯源、储运、供货稳定性和售后配合；渠道商和经销商的准入条件由相关业务负责人定稿。页面明确“具体准入标准由对应负责人审核”。
3. **简短留言表单：**公司名称、合作类型、联系人姓名、联系电话、合作地区和补充说明构成通用字段；供应食材类别等只适用于供应商的字段不得强制渠道商或经销商填写。三种类型的最终差异化字段在第 11 节定稿。字段校验后可提交。
4. **反馈：**后台实际接收并保存申请后显示“**已收到，工作人员将联系您**”；失败或超时时保留表单、提示重试，不显示成功态。

合作申请独立于消费者订单和家庭健康数据。具体接收、通知、类型化资质审核与资料保留规则由相应业务负责人确定。

## 10. 技术边界与评审验收

### 10.1 已知平台方向与接口责任

当前客户端是**微信小程序**；可在现有 Uni-app/Vue 代码上继续开发。团队已确定使用 **Supabase**，拟承载用户鉴权及家庭健康、对话/记录等数据；团队提供的商城方案基于 FastAdmin/ThinkPHP/MySQL，涉及商品、库存、供应商、支付、配送和售后。两套后端的微信身份映射、令牌、数据边界和实际可调用接口仍待团队联调确认。多模态 AI 与拍照识别服务需通过受控后端接入；五个外部开源项目仅作参考，不视为已经集成的能力。

### 10.2 产品验收场景

| 场景 | 必须看到的关键结果 |
| --- | --- |
| 首次使用与切换方式 | 三页建档；首步合并使用方式、成员资料和默认就餐选择。“只为自己”按本人一位；“自己和家人”按勾选成员计数，至少一位，人数可超过四位。首次仅有“我”，家人主动添加且不自动纳入就餐选择；逐页保存、返回可改、切换成员不串资料。切换方式保留家人资料及家庭就餐选择，旧四步草稿映射到新三步。从“我的”确认切换后档案及历史保留，已支付计划和订单不变。跳过健康资料仍可进首页。 |
| 登录与家庭邀请 | 微信身份经服务端校验后建立会话；家庭总览页右上角“··· → 转发”生成普通家庭邀请，可多人接受、暂不设置有效期和成员上限，本期不要求撤销／重发。未认领成员详情页转发或“邀请本人加入”生成同一绑定邀请，仅有权限的人可操作，一份档案只能一个账号认领。卡片不含健康信息；打开后登录、查看邀请与共享范围、主动接受后进入受邀建档；普通邀请创建本人档案，绑定邀请核对并补充预填资料，不重复选择使用方式和共同人数。无效凭证或重复认领不泄露家庭资料。加入本身不强制验证手机号，下单、配送或敏感操作需要时再验证。 |
| 第 3 页饮食目标与基础健康 | 顶部显示当前成员；基础病按三态填写并支持糖尿病、高血压、高血脂、高尿酸／痛风、肾脏疾病和其他，“其他”显示手动文字输入框；基础病标记“用户自述”。后端生成只读饮食管理摘要并能合并多病规则，用户不能关闭疾病规则；医生饮食要求优先。饮食目标、合并后的口味偏好和菜系偏好按第 3.1 节保存且不跨成员。 |
