# 菜品营养字段与后端存储契约

确认日期：2026-10-13。每道菜的详情页均展示营养卡片，位于菜品主图／名称大卡片之后、预计制作时间卡片之前；收货后的整餐烹饪页复用此卡片，随当前菜品切换。

## 展示与计量口径

六项固定按两行三列显示：能量、蛋白质、脂肪；碳水化合物、膳食纤维、钠。当前统一为**每 100 克熟制后可食部分**，不以采购包装重量、生料重量或全餐数值替代。计量口径不明或不支持时显示暂无数据，不自行改单位或换算。

数值使用结构化数字或 `null`。`null` 表示未知，真实的 `0` 仍展示为 0；负值、非有限数字、字符串视为无可用数据。标签、单位和精度由前端统一维护，后端不得把单位拼入数值。小于展示精度的正值用 `<0.1 g` 或 `<1 mg/kcal`，避免四舍五入成零。

## 菜谱数据与接口对象

菜品／做法对象携带 `nutrition`，而非从菜名或 AI 文案中提取。示例数字为界面测试数据，不可作为真实配方营养来源：

```json
{
  "recipeId": "example-fish",
  "recipeVersion": "example-v1",
  "name": "清蒸鲈鱼",
  "nutrition": {
    "basis": "per_100g",
    "foodState": "cooked_edible",
    "energyKcal": 120,
    "proteinG": 20,
    "fatG": 4,
    "carbohydrateG": 1,
    "fiberG": null,
    "sodiumMg": 280,
    "source": "demo",
    "sourceReference": "ui-fixture-v1"
  }
}
```

| API 字段 | 后端建议列名 | 单位／约束 |
| --- | --- | --- |
| `energyKcal` | `energy_kcal` | kcal，可空、非负数 |
| `proteinG` | `protein_g` | g，可空、非负数 |
| `fatG` | `fat_g` | g，可空、非负数 |
| `carbohydrateG` | `carbohydrate_g` | g，可空、非负数 |
| `fiberG` | `fiber_g` | g，可空、非负数 |
| `sodiumMg` | `sodium_mg` | mg，可空、非负数，不是食盐重量 |
| `basis` | `basis` | 本版固定 `per_100g` |
| `foodState` | `food_state` | 本版固定 `cooked_edible` |
| `source` | `source` | `calculated`／`measured`／`unavailable`；测试环境可用 `demo` |
| `sourceReference` | `source_reference` | 计算记录或检测报告标识；未知用 `null` |

`source=unavailable` 时六项均为 `null`。部分指标未知时，其余已有可靠依据的指标可以展示。生产值由后端按配方、食材用量、调料用量、熟制成品可食重量和专业规则计算，或使用对应菜谱版本的检测值；AI 不凭菜名编数字。前端分别显示“营养估算”或“营养检测”，测试值明确显示“测试数据 · 示例估算”。

## 后端持久化要求

- 数据归属为**菜谱版本**：`recipe_id + recipe_version`。可放入既有菜谱版本表，或建立同键的营养子表；适配已有后端模型后决定实际表名。六项列建议用可空的 `NUMERIC`，不能以 `DEFAULT 0` 表示未知，并对非空值实施有限、非负校验。
- 同版本关联配方、食材／调料和成品重量。变更做法、调料、用量或成品口径后重新计算，并生成新的菜谱版本。每 100 克数值不随就餐人数简单倍增，也不能直接作为个人实际摄入。
- 菜单、换菜候选、菜品详情、计划中的菜品、订单中的单菜做法返回同一套对象。接口路径按既有菜谱业务接口定稿，不新增独立且重复的营养真值来源。
- 支付／下单时随菜谱一并保存 `nutrition` 快照，包括口径、数值和来源。普通订单及 21 批计划的每批每餐都保留各自版本，查询已购菜谱读快照；菜谱库更新不得回填或覆盖已购订单。
- 旧订单或旧菜谱没有营养数据时，卡片仍显示六项“暂无数据”。只有获得原配方版本和可靠依据后，才可按明确的数据修复流程补齐，不能借用现行同名菜的数值。
- 后端校验生产数据来源、写入权限和菜谱版本关系，客户端仅展示，不能由客户端上传的数值覆盖生产营养记录。

## 本次实现与联调边界

`DishNutritionCard.vue` 共用卡片；`dish-nutrition.js` 定义字段、单位、校验及缺失值格式；`createDishGuide()` 接收菜品自带的 `nutrition` 并优先使用。显式返回 `null` 不会用示例值补齐。演示模式下无此字段的已知样例使用集中测试数据，未知菜品显示暂无数据；真实服务模式不会以样例补数。

新模拟订单将营养对象随 `cookingGuide.dishGuides`／`cookingGuides[].guides[].dishGuides` 保存到现有本机订单快照。已购买计划回到菜品详情时保留原有营养对象，收货后的菜品切换也读取同一份快照。

当前工程的真实菜谱／营养服务尚未接入。本次实现前端结构、本机演示持久化和此存储契约，**没有执行服务器数据库迁移，也没有把样例写入生产后端**。后端联调时需落实版本表／营养列、真实数据计算或审核、接口映射和服务端订单快照，并验证服务端保存及跨设备读取。

## 验收要点

1. 每道菜详情均有六项卡片，位置和两行三列布局一致；切换菜品显示该菜的数据。
2. 非空数值附正确单位，`0` 与 `null` 不混淆；口径缺失或错误不展示成每 100 克数值。
3. 后端提供的对象优先于演示数据，部分缺失、全部缺失及旧快照不会被样例补齐。
4. 普通订单和 21 批订单保存及刷新后保持原快照，后续修改原菜谱不改变已购数值。
5. 后端完成真实持久化与跨设备读取后，才能宣称营养数据已在后端保存；本地测试与构建不能替代此验收。
