# 家庭 AI 营养师全人群配餐修改方案

日期：2026-10-13
状态：本地原型已按方案实施；正式服务联调与微信真机验收待完成。

小程序面向全体家庭成员，儿童、孕期、产后、哺乳期等人群均可使用。配餐应结合具体成员和已知信息进行适配，不能仅凭年龄或特殊人群身份拒绝服务。建档保留现有字段与流程，不增加孕期、产后、哺乳期等阶段选项、必填项或单独页面。

本次调整覆盖成员数据、AI 对话、饮食适配、逐人份量、采购汇总、换菜、21 天计划及其测试。正式配餐仍由 AI 与受控业务服务分析、计算和检查；本地演示数据只用于验证交互与数据流。

## 已确认的产品规则

1. 所有家庭成员均可建档、参与配餐、记录饮食、查看反馈及使用购买流程。年龄小于 18 岁不再触发整餐阻断。
2. 不设置特殊阶段建档字段，不要求用户选择是否怀孕、孕周、产后阶段或哺乳状态，也不在成员选择列表增加特殊人群标签。
3. AI 使用现有档案、成员归属明确的对话信息、已核对且有访问权限的报告内容，以及医生饮食要求分析当前建议。未提供的信息保持未知，不推断为没有特殊情况。
4. 需要补充信息时，AI 围绕当前建议在对话中提出具体问题；不要求用户返回建档新增阶段资料，也不对每位女性成员例行询问孕产状态。
5. 健康情况、年龄与阶段影响菜单、份量、做法和注意事项。已知过敏、不耐受、忌口、医嘱冲突仍须处理，不能通过删除身份拦截一并移除这些检查。
6. 原有成员权限、报告共享规则、逐餐成员选择、计划来源优先级和已支付订单快照规则继续适用。不存在新增人工健康审核步骤。

## 成员资料与年龄处理

建档仍使用姓名、性别、出生日期、关系、身高、体重、基础病、目标、偏好、过敏、不耐受、忌口、医生要求和报告等现有资料。此次不增加生理阶段字段，也不将孕产情况强制归入基础病。

年龄由出生日期结合建议对应日期计算，不能仅减出生年份。已有可靠生日优先于旧的缓存年龄；历史档案只有年龄时可作为已有自述信息使用，不能把默认生成的 30 岁当作用户填写。无法区分来源的旧记录应保留不确定性，必要时询问真实年龄。生日未填写或无效时，年龄使用未知值；空字符串、未来生日和无效日期不得转成有效年龄。

婴幼儿需要精细年龄时，可由出生日期推导月龄，无须新增建档输入项。儿童不能直接套用成人 BMI 常见范围；身高、体重的输入合法性与健康评价分开。没有适用依据时，不展示“BMI 异常”等健康判断。对话中已明确的相关情况也应参与数据解释，不能因未设阶段字段继续默认使用普通成人规则。

“没有已知基础病”只表示该项自述状态，不表示成年人、健康已确认或不存在其他饮食需求。`MemberFields.vue` 与 `memory.js` 中由无基础病状态生成的“一般成人”描述应一并改为中性文案。

## 对话中的信息使用

用户可以直接说“我怀孕了，今晚吃什么”“孩子两岁，今天吃饭不太方便”或“家人正在哺乳，想安排三餐”。AI 将信息关联到明确的成员，用于本次菜单与吃法分析；成员不明确时先询问对象，不写入错误成员。

AI 仅在生成当前建议确有需要时追问，例如需要了解已有医生饮食要求或当前进食方式。问题在对话中完成，用户可以暂不提供；此时保持未知，只给信息足以支持的建议，不声称完成了所有个体化适配。

这类信息保存在已有对话及其来源记录中，按现有记忆规则决定是否需要继续引用。不能把孕期、哺乳或“今天食欲差”等信息自动变成永久忌口或永久身份。跨天引用应带来源和时间，需要复核时在对话中确认；用户更正或撤回后，相关未支付建议不再继续沿用旧信息。后端可整理计算所需的临时上下文，但不能借此新增必填建档字段。

没有相关信息时，不根据性别、关系或外观猜测孕产状态。报告内容未核对前不能当成确诊或已确认事实，访问报告仍遵守现有共享权限。

## 菜单份量与营养计算

生成服务先针对每位本餐成员分析吃法与需求，再组合家庭菜单。可以共享的菜品优先共享；有差异时提供个人份量、烹饪或食物形态调整，必要时安排适合该成员的替代菜。低月龄成员应依据喂养方式给出相应建议，不能因为参与家庭餐就直接套用成人固体菜谱。

个人份量由受控计算与有效配方依据提供，不能在前端直接规定“儿童等于半个成人”“孕妇等于若干成人”之类固定系数，也不能把 AI 自由文本中的任意克数当成已经校验的计算结果。

建议返回数据至少包含以下内容，具体接口名称由开发时与后台契约统一：

| 数据 | 要求 |
| --- | --- |
| 成员与餐次 | 明确成员 ID、目标日期、餐次及本次成员集合 |
| 个人建议 | 按成员返回菜品、份量或可支持的份量范围、单位、食物形态及相关注意事项 |
| 计量口径 | 区分熟制后可食重量、生料需求与采购包装重量；换算有配方依据 |
| 食材需求 | 来自具体菜谱及成员份量，包含配料与必要换算，能够追溯到配方版本 |
| 营养数据 | 来源、计量基准与配方版本明确；未知值为 `null`，真实零值仍为 0 |
| 分析依据 | 引用已有档案版本和允许使用的对话、报告、医嘱来源，不新增阶段表单字段 |
| 检查结果 | 返回具体问题、对应成员或菜品、可采取的动作，不返回只有“特殊人群不支持”的泛化结果 |

菜品营养卡仍遵守现有《菜品营养字段与后端存储契约》：每 100 克熟制后可食部分，展示能量、蛋白质、脂肪、碳水化合物、膳食纤维和钠。个人餐次摄入与全餐汇总属于另外的计算对象，不能把每 100 克数值直接当成个人摄入或全餐总量。

`MealNotes.vue` 读取实际个人建议，不再输出 `XXg`。没有可靠份量时显示“份量待确认”或服务提供的可支持描述；没有可靠营养数据时显示暂无数据。演示模式可提供明确标注的示例数据，不能据此宣称儿童或孕产营养计算已完成。

## 饮食检查与异常恢复

检查按当前推荐内容判断。年龄与特殊情况用于适配，不能成为“此成员不允许使用小程序”的理由。对具体建议仍无法处理的问题，保留可解释的限制和恢复路径。

| 情况 | 页面行为 | 继续方式 |
| --- | --- | --- |
| 已知信息足以生成并通过检查 | 展示菜单、个人建议、食材及可用报价 | 正常查看做法与购买 |
| 信息不足以支持具体份量或某条个体化建议 | 明确缺少什么，保留已有内容与成员入口，不声称完成精确适配 | 在对话中回答必要问题，或查看可支持的通用建议；未验证的个体化清单不进入结算 |
| 已知过敏、不耐受或医嘱与候选菜品冲突 | 指出受影响成员与菜品，尝试替换或调整 | 重新分析并通过检查后进入购买，取消购买某项商品不能绕过菜谱冲突 |
| 医嘱或信息互相矛盾 | 展示具体矛盾，不生成无法确认的个体化清单 | 用户补充或更正后重新分析；其他无关功能仍可使用 |
| AI 服务失败或暂不可用 | 展示失败与重试，不用“补充档案”掩盖接口错误 | 重试原请求，避免重复保存或重复生成 |

保留既有急症提示路径，急症提示与日常配餐适配分开处理。不会新增“我已知晓，仍然购买”的绕过入口。

聊天、今日三餐、专属计划和购买页使用同一份检查结果。`blocked` 等旧字段如需兼容，由适配层映射结构化问题，不能由各页面分别拼出不同的安全结论。涉及购买的未验证建议不得通过局部取消勾选变成已通过检查。

## 采购换菜与计划同步

采购计算顺序统一为：逐人成员需求 → 菜谱食材需求 → 同餐汇总 → 所选餐次跨餐汇总 → SKU 映射 → 包装数量与报价。包装数量由合并后的需求向上取整，不能先按成员或餐次取整再相加。

成员、个人份量或菜品变化后，同步更新未支付菜单、食材、包装数与必要报价。换菜使用同一套需求计算，不能在 `meal-customization.js` 中继续直接乘人数。经济型、标准型、品质型与 21 天计划也统一调用适配服务，计划档位不覆盖成员限制。

保留用户已标记为不购买或家中已有的商品选择。对应食材仍参与菜谱检查，取消购买不代表成员不会吃到该成分。报价变化后，结算前重新核对商品、数量、地址和金额。

修改某一餐的成员只影响对应日期与餐次，不删除孩子的家庭档案，不自动修改其他餐次。适配结果形成后保存并跨页面复用；打开页面读取同一份结果。仅在明确修改、依据变化或结果失效时重新分析，不能因打开页面反复生成不同菜单。

未支付建议保存生成版本、目标日期、成员集合、档案版本及实际引用的上下文版本。相关信息更正或规则升级后，旧建议需要复核；新的无关聊天不能导致所有已保存计划反复失效。年龄与对话信息的时效按计划对应日期判断。

已支付订单的商品、金额、配方、配送和交易营养快照保持购买时内容。当前成员信息变化时，重新给出分餐建议、做法调整和具体冲突提醒，不改写订单，也不重新生成采购替换已购商品。需要改动真实订单时进入现有正式变更流程。

## 实施顺序

1. 同步人群范围文档，修正年龄数据、中性健康描述和年龄直接拦截；确认建档未增加任何阶段项。
2. 固定适配输入、逐人建议、食材需求、检查结果及上下文来源的接口契约，分别提供演示和正式服务适配。
3. 贯通逐人份量、家庭菜单、做法、换菜和采购汇总，替换分散的固定人数乘法与份量占位。
4. 将聊天、今日三餐、购买页、专属计划和反馈统一接入结果与异常状态，补齐必要追问和重试。
5. 完成结果持久化、依据变化后的复核及已支付快照回归，再开展真实服务和微信真机验收。

## 验收标准

| 场景 | 必须满足的结果 |
| --- | --- |
| 建档与成员详情 | 没有孕期、产后、哺乳期等新字段；无相关信息也能完成建档和进入首页 |
| 儿童与成人同餐 | 不因未满 18 岁整餐拒绝；个人建议按成员返回，食材按实际需求合并 |
| 只有儿童参与本餐 | 不显示“原型暂不支持儿童”；能生成与已知情况相符的建议，或在对话中说明必要信息 |
| 婴幼儿成员 | 使用有效生日推导精细年龄；不默认成人固体菜谱，不强制新增喂养阶段建档项 |
| 对话明确孕期或哺乳信息 | 信息归属正确，参与当前建议；必要追问在对话完成，不跳转到不存在的阶段表单 |
| 未说明特殊情况 | 不猜测状态，不强制询问所有女性成员，也不声称已排除未知情况 |
| 旧档案在“其他”中写有孕期 | 识别为已有自述信息，不仅因没有演示标签而拒绝；不自动将孕期确认为基础病 |
| 生日未填或年龄为空 | 保持未知，不默认 30 岁、不当成 0 岁；按生成建议所需决定是否追问 |
| 生日与日期边界 | 生日前后年龄计算正确，未来生日与无效日期有明确输入提示 |
| 儿童身高体重 | 输入校验不套用成人健康阈值，不因低于成人常见范围误报健康异常 |
| 份量与营养 | 无 `XXg` 占位；区分熟重、生料和包装，保留未知值、真实零值、营养来源与配方版本 |
| 混合需求及换菜 | 不采用统一成人份量或固定身份系数；替代菜、做法、食材和报价一致 |
| 已知饮食冲突 | 仍阻止未经处理的个体化推荐进入结算；取消商品勾选不能绕过检查 |
| 服务失败 | 显示服务失败与重试，保留用户输入及已有内容，不伪装为资料缺失或成功生成 |
| 单餐成员修改 | 仅更新对应日期与餐次，家庭档案、其他餐次及不购买选择保留 |
| 今日采购 | 跨成员和跨餐合并后计算包装数，与同一份菜单和有效报价一致 |
| 21 天计划 | 各餐使用同一套适配逻辑；相关依据变化有可追溯复核，不靠反复打开页面重生成 |
| 已支付后的资料变化 | 当前吃法与冲突提醒可更新，已支付商品、金额、配方和配送快照不变 |
| 记录与反馈 | 使用实际确认的摄入；不把推荐份量写成已吃份量，未记录不代表未进食 |
