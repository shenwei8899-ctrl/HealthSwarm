## 3. 公共约定

### 3.1 地址、身份与响应

本文接口均写完整 `/api/...` 路径。健康业务基地址与商城基地址分别配置；不要再额外拼一个 `/api`。H5 同源可以使用空 `VITE_API_BASE_URL`，微信正式包使用已配置的 HTTPS 域名。本地回环 HTTP 仅在显式联调配置下允许。

除公开微信配置／登录外，业务请求带 `Authorization: Bearer <业务access_token>`。普通 JSON 请求使用 `Content-Type: application/json`；文件上传交给 multipart 实现。App 不上传任意 `uid`、`actor_uid`、模型密钥或管理员凭据来代替登录身份。

健康／家庭接口通常直接返回对象或数组，**没有统一的服务器 `{data: ...}` 外壳**。App `request.js` 返回的 `{data, traceId}` 是客户端包装。商城有自己的返回包与签名规则，继续走 `commerce-client.js`。

| 标识 | 含义／来源 | 禁止混用 |
| --- | --- | --- |
| `accountId` / `account.id` | 登录账号 ID；客户端可转字符串存储 | 不是成员 ID |
| `fid` / `householdId` | 业务家庭 UUID | 不是健康成员 ID |
| 家庭成员 `members[].id` | `/api/family` 系列和每日安排参与者使用 | 不直接填入健康识别／咨询接口 |
| `healthMemberId` / 健康成员 `id` | 从云端建档投影及 `/api/health/v1/members` 取得 | 两种成员 ID 必须经后端映射，不能猜成相同 |
| `client_request_id` / `request_id` | 客户端一次操作的 UUID；Run 提交时在 `meta.request_id` | 不是 `run_id`；一个排队请求可能暂时没有 Run |
| `task_id` | 识别异步任务 ID | 不是咨询 request_id |
| `draft_id` / `record_id` / `plan_id` | 候选／实际饮食／计划分别保存 | 候选或计划不能当作已吃记录 |

日期 `YYYY-MM-DD` 按业务北京时间自然日选择；测量／用餐时间使用带时区的 ISO8601，例如 `2026-10-22T12:00:00+08:00`。不要用 UTC 日期截断替代本地业务日期。数值中的 `null` 表示缺失，不能显示成 0；营养 Decimal 常以字符串返回，前端只负责显示，不补算缺失成分。

### 3.2 幂等、版本与错误

- 仅对接口明确要求的写入发送 `Idempotency-Key`，其值须等于正文的 `client_request_id`；家庭批量记餐等于 `group_id`。同一操作网络超时后保留原键、原正文重放，不换键重做。
- 需要 `If-Match` 时使用带双引号的版本，例如 `If-Match: "3"`，并与正文 `version`／`expected_version` 一致。每类版本各自使用：家庭、成员档案、关系、草稿、正式饮食、每日安排、采用记录不可互换。
- 无幂等契约的写入（例如创建家庭、人工草稿）超时后先列表回读，禁止盲目自动再次创建。
- 健康业务错误常见形态：`{detail, code, message, trace_id, retryable}`；认证／验证也可能为 FastAPI `detail` 字符串或数组。HTTP 状态和业务 `code` 分开处理，记录 `trace_id` 供后端排查。

| HTTP／客户端状态 | App 行为 |
| --- | --- |
| 401 | 当前会话失效，清理会话和旧私有内容，走登录；迟到的旧账号401不清除新账号 |
| 403 | 展示缺少当前授权／用途同意；重新读取能力和配置，不通过重试绕过 |
| 404 | 对象不可见或不存在；不泄露或继续展示旧成员数据 |
| 409 | 版本、来源、请求内容或处理快照变化；健康候选的 `If-Match` 缺失／不匹配也属此类；回读现状再确认，不强制覆盖 |
| 410 | 来源／引用已失效，移除旧结果并说明需重新读取 |
| 422 | 必填、枚举、请求键不一致或数据校验失败；展示可修正信息 |
| 429／503 | 按响应退避；写入仍保留原键，不能把 `retryable` 理解为可新建业务操作 |
| 网络中断／5xx | 写入结果未知，先回读，具备幂等契约时原样重放；取消轮询不等于取消后台任务 |
| `SESSION_CHANGED` | 丢弃该响应，清理当前旧页面，不写入新的账号／家庭状态 |

GET、POST `/api/family/{fid}/miniapp-profile`。POST 必须携带同值 `Idempotency-Key`；整体保存三步表单，不额外要求每位家庭成员分别点击确认。

```json
{
  "client_request_id": "11111111-1111-4111-8111-111111111111",
  "scope": "self",
  "family_version": 1,
  "usage_mode": "个人使用",
  "default_diners": ["self-ref"],
  "analysis_consent": null,
  "members": [{
    "client_ref": "self-ref",
    "member_id": "22222222-2222-4222-8222-222222222222",
    "version": 1,
    "name": "合成本人",
    "relation": "本人",
    "birth_date": "1990-01-01",
    "sex": "unspecified",
    "height_cm": null,
    "weight_kg": null,
    "dietary": {
      "healthStatus": "none", "conditions": [],
      "allergyStatus": "none", "allergies": [],
      "intoleranceStatus": "none", "intolerances": [],
      "avoidanceStatus": "none", "avoidances": [],
      "doctorStatus": "none", "clinicianGuidance": "",
      "goals": ["均衡饮食"], "cuisines": ["家常菜"], "tastePreferences": ["清淡"]
    }

```

示例全部是合成值，ID／版本必须替换为真实回读结果。新增成员 `member_id/version` 可为空；`client_ref` 只负责本次映射，`default_diners` 引用它。`scope` 为 `household`（默认）或 `self`；按当前账号可用范围提交，非家庭所有者的既有适配仅提交本人。`usage_mode` 为“个人使用”或“家庭使用”。

出生日期必填且不能在未来；五项状态必须明确选择 `none` 或 `set`，`set` 时补明细；不能把未填写自动改成“无”。目标、口味列表必填；菜系可留空数组并后补，不能自动改成“无特别要求”。“其他／自定义”必须换成实际内容。现有App仍要求菜系必填，需客户端同事对齐。AI处理配置可用并经用户同意时，`analysis_consent` 才传配置回读的 `{processor, policy_version}`；当前正式政策暂停，不能自行补值。

已完成建档的本人来源，在没有专业快照时可返回 `source_kind:user_reported`；缺少编码规则、建档不完整或确认过期时返回 `status:not_ready`、`reason`及空`payload/attestation`，不可显示为专业确认。已有专业快照撤回不能退回自述。专业导入页面使用 `profile-import-context.current_profile.next_version`，不以家庭档案版本自行加一。

保存后 GET 回读 `source:"api"`、`householdId`、`onboarded`、`familyVersion`、`members[].id/healthMemberId/version`。不要只凭本地“已完成”标记跳过表单；`onboarded` 以当前本人完整档案和版本确认结果为准。

## 5. 今日三餐：本轮重点接口

以下 `D=/api/family/{fid}/daily-arrangements`，`day=YYYY-MM-DD`，`meal=breakfast|lunch|dinner`。

| 方法与路径 | 正文／查询 | 返回与行为 |
| --- | --- | --- |
| GET `D/{day}` | 无正文 | 首开和重进先读；不创建 Run、不下单 |
| POST `D` | `{client_request_id,date}`＋同值幂等头 | 创建／登记后台任务；`generating` 不是完成 |
| POST `D/{day}/resume` | 无正文 | 登记继续原任务；无需每两秒 POST，状态轮询用 GET |
| POST `D/{day}/resume?retry_failed=true` | 无正文 | 用户明确重试失败任务；修正已随37838ef部署，仍须当前用途同意 |
| GET `D/{day}/meals/{meal}` | query `arrangement_id,version` | 严格绑定首页已保存版本；不匹配409 |
| POST `D/{day}/members` | `{client_request_id,version,meal,member_ids}`＋同值幂等头 | `member_ids` 为业务家庭成员 UUID，至少1人；只重算指定餐 |
| GET `D/{day}/meals/{meal}/purchase` | query `arrangement_id,version` | 本餐商品预览，只读 |
| POST `D/{day}/meals/{meal}/purchase` | `{arrangement_id,version}` | 用户明确购买后发布采购包，后端沿持久键幂等；不传自算价格／数量 |
| GET `D/{day}/purchase` | query `arrangement_id,version,meals` | 今日汇总预览；多餐查询使用重复参数 `meals=breakfast&meals=lunch` |
| POST `D/{day}/purchase` | `{arrangement_id,version,meals:[...]}` | 明确购买后发布汇总采购包 |

推荐调用顺序：保存建档并 GET 确认 → GET 当天安排 → `absent/stale` 时按已有 client 建立一次请求 → GET 轮询 → 验证完整 `ready` 后展示说明和三餐 → 详情使用原安排 ID＋版本。页面离开只停止订阅，Worker 继续处理；再次进入读当前持久结果。

| 读取结果 | 展示和操作 |
| --- | --- |
| `absent` | 当天没有安排，按前置条件登记生成 |
| `generating` | 展示处理中；轮询超时显示可重新读取，不当作失败后新建请求 |
| `failed` | 展示服务端固定错误提示，提供明确重试入口 |
| `stale` | 档案来源已变化，旧快照不可继续当当前结果；按当前来源重新登记 |
| `ready` | 仅在完整校验字段齐全时展示；存在 `update.status=generating/failed` 时保留原已发布快照并说明调整中／失败 |

`ready` 必须核对：`id,version,date,saved:true`、`validation.status:"passed"`、`procurement.checked:true`、`analysis.text/source/request_id/run_id`、唯一三餐 `meals[]`。每餐须有 `type,members,dishes,detail_ref,nutrition,nutritionSource,memberNotes,purchase`；菜品须有版本、食材和做法。采购既可为已匹配状态，也可含已发布 `package_sn/package_version`。完整字段验收函数已在 `validateDailyArrangement`，复用它，不接受空卡片充当成功。

本轮重试语义：当前所有参与者授权及同意有效、只是旧 Run 处理快照过期时，明确重试才创建新的 Run；未同意新配置返回403。暂时服务故障保留原有效 Run 和采购键。客户端不能清空 `run_id` 强制生成，也不能自动代表用户接受新政策。

改单餐成功后原安排 ID 保持、业务版本递增；其他两餐内容与采购来源不变。更新途中继续展示原快照，不把新 `update.version` 与旧内容拼接；409 时整体回读。已支付订单独立存在，改单不改订单或履约事实。

## 6. 营养咨询和三项健康 Agent

### 6.1 前置授权与配置

| 方法与路径 | 用途 |
| --- | --- |
| GET `/api/health/v1/members` | 当前健康成员与 `scopes`；只允许选择当前用途已授权成员 |
| GET `/api/health/v1/members/{mid}/readiness` | 成员来源、能力前置是否就绪 |
| GET `/api/health/v1/members/{mid}/capabilities` | 当前能力集合，不由 Agent 卡片存在与否决定可用 |
| GET `/api/health/v1/configuration` | 各用途 `available/processor` 与 `policy_version` |
| POST `/api/health/v1/members/{mid}/processing-consents` | `{purpose,accepted,processor,policy_version}`；撤回用 `accepted:false` |

`purpose` 为 `report,meal,consultation,meal_plan,diet_analysis,quality_review,purchase` 之一；三指标 Agent 解释沿咨询用途。共享档案、字段范围 grant、用途处理同意分别校验；同意不能替代 grant。前端不得调用管理接口替用户批量授予权限。

### 6.2 创建入口、提交和恢复

1. POST `/api/health/v1/members/{mid}/task-entries`，正文含 `task_type,client_request_id`，按下表传对应选择，幂等头同 `client_request_id`。`diet_analysis` 的目标使用顶层 `target_selection`，不能放进 `selection`。
2. 检查 `entry_status`：`ready` 才使用返回的 `thread_id,agent_slug,request_submit_url`；`needs_input` 展示问题补齐选择；`dependency_not_ready` 展示原因／缺失依赖，不创建运行。
3. POST `/api/agent/runs`，正文见下例。请求 UUID 与入口操作 UUID 分开生成；一次问答重试沿原 `meta.request_id` 和正文。
4. GET `/api/health/v1/tasks/{request_id}` 回读 `request_status/execution_status/run_id/result`。SSE 负责实时更新，最终业务结果以该受控查询为准。
5. 未分配 Run 时订阅 `/api/agent/requests/{request_id}/events`；已有 Run 后订阅 `/api/agent/runs/{run_id}/events?verbose=false&after_seq={cursor}`。断流保留游标和请求身份，不发起另一次问答。

```json
{
  "agent_slug": "health-consultation",
  "thread_id": "33333333-3333-4333-8333-333333333333",
  "query": "请介绍一般饮食记录应包含哪些信息",
  "meta": {"request_id": "44444444-4444-4444-8444-444444444444"}
}
```

`agent_slug/thread_id` 必须来自业务入口，示例仅展示结构。不能从智能体卡片直接开通用线程代替健康入口。

| task_type | 当前角色／用途 | selection |
| --- | --- | --- |
| `consultation` | `health-consultation`，一般科普咨询 | 不传选择 |
| `blood_glucose_review` | `health-blood-glucose`，血糖记录回顾 | 日期、实际记录 ID 与版本 |
| `blood_lipids_review` | `health-blood-lipids`，血脂记录回顾 | 同上 |
| `blood_pressure_review` | `health-blood-pressure`，血压记录回顾 | 同上 |
| `initial_meal_preview` | `health-meal-planner`，明确来源的初始配餐 | `InitialPlanSelection`；普通今日三餐优先走第5节，勿由App拼批准规则 |
| `diet_analysis` | `health-diet-analyst` | `selection` 不传或为null；顶层可选 `target_selection:{rule_code,rule_version,profile_version}`，不传仍可做无目标分析；现有单餐反馈走下述独立入口 |
| `quality_check` / `purchase_requirements` | 质量检查／采购需求 | 各自已保存方案和规则／采购选择，缺项不得自动猜测 |

指标 `selection` 例如 `{"start_date":"2026-10-01","end_date":"2026-10-22","records":[]}`。空 records 取该范围最近100条，范围最长366天；指定记录用 `{"record_id":"实际UUID","version":1}`。不通过照片、订单推断疾病。

不调用模型的指标事实回顾：POST `/api/health/v1/members/{mid}/indicator-reviews/{kind}`，`kind=blood_glucose|blood_lipids|blood_pressure`，正文直接为上述日期选择；返回事实统计／缺项追问，不等于医疗判断。

现有日聊入口：POST `/api/health/v1/members/{mid}/daily-consultations`（无正文）；日聊列表 GET `/api/health/v1/members/{mid}/daily-conversations`，历史 GET `/api/chat/thread/{thread_id}/history`。单餐反馈入口 POST `/api/health/v1/diet-logs/{record_id}/feedback-conversation`，正文 `client_request_id,source_version`。复用 `health-task-flow.js`，避免另建第二套对话身份。

执行 `completed` 不等于业务成功或专业批准。按 `result.result_type` 分别展示 `needs_input`、`general_education_answer`、`meal_plan_preview/diet_analysis/meal_feedback/quality_check/ingredient_requirements` 或 `error`。正式营养咨询当前只按 `scope:"general_education"` 展示；引用撤回或来源失效后不可继续显示旧引用正文。知识库绑定由后台管理，App 不传库 ID 绕过范围。

## 7. 食物照片与报告识别

两类复用同一任务／草稿链路，**上传成功、任务完成、候选存在、用户确认是四个不同状态**。

| 阶段 | 方法与路径 | 请求和回读 |
| --- | --- | --- |
| 上传 | POST `/api/health/v1/uploads` | multipart `file,member_id,purpose=meal|report`；静态JPEG/PNG/WebP图片≤10MiB，未加密报告PDF≤20MiB且1–20页，PDF只用于report；按 `configuration.limits` 回读及服务端校验；回读 `upload_id,purpose,status=ready` |
| 私有预览 | GET `/api/health/v1/uploads/{upload_id}/preview` | 带认证获取文件；报告可选 `page_index`，不能将原图变成公开静态URL |
| 食物任务 | POST `/api/health/v1/meal-photo-tasks` | `{member_id,upload_ids,client_request_id,meal_type,eaten_at}`，幂等头同请求UUID；同餐最多3视角 |
| 报告任务 | POST `/api/health/v1/report-tasks` | `{member_id,upload_ids,client_request_id}`，幂等头同请求UUID；任务按报告页数约束校验 |
| 任务进度 | GET `/api/health/v1/vision-tasks/{task_id}` | 读取 `execution_status,review_status,result_id,error_code`；执行常见状态为 `pending/running/success/failed/cancelled`，成功是 `success`，不是 AgentRun 的 `completed`；有 result_id 再读候选 |
| 取消／重试 | POST `/api/health/v1/vision-tasks/{task_id}/cancel`、`/retry` | 仅failed/cancelled任务可retry；正文 `client_request_id`＋同值幂等头；用户明确重新识别使用新的UUID，同一次retry网络重放保持该UUID和正文；新任务有新task_id，取消后回读终态 |
| 恢复列表 | GET `/api/health/v1/members/{mid}/vision/page` | `kind,jobs_limit,jobs_offset,drafts_limit,drafts_offset`；两套 next_offset 独立，空页也按游标继续 |
| 读取候选 | GET `/api/health/v1/meal-drafts/{id}` 或 `/report-extractions/{id}` | 核对 `member_id,kind,version,review_status,payload` |
| 编辑候选 | PATCH 同候选路径 | `{version,reason,meal}` 或 `{version,reason,report}`＋`If-Match`；不能同时传两类载荷 |
| 食物计算 | POST `/api/health/v1/meal-drafts/{id}/calculate` | `{version}`；保存返回的 `calculation_id,draft_version`，修改后必须重算 |
| 确认 | POST 同候选路径＋`/confirm` | `{version,client_request_id,accept_incomplete}`，食物另传 `calculation_id`；幂等头同请求UUID |

确认成功须读到 `review_status:"confirmed"`、`confirmation_id,target_ids`，再回读实际饮食或报告指标。报告字段使用 `ReportPayload.fields/pages/excluded_pages` 原结构，不只保留OCR纯文字；修改须保留原证据定位。报告部分页重识别：POST `/api/health/v1/report-page-tasks`，正文 `draft_id,version,client_request_id,page_indices`，同时提供幂等头和 `If-Match`。

照片中菜名、份量均是候选；由用户核对实际吃过的项目和份量。没有完整营养来源时展示缺失／估算及确认项，不能由 App 或模型补造营养值。现有 `health-vision-client.js`、`meal-photo-client.js`、`cloud-meals.js` 已覆盖主要操作和未知写入恢复。

## 8. 实际记餐、多人部分成功和更正

`MealPayload` 包含 `meal_type,eaten_at,items,photos`。每个 `MealItem` 至少有稳定 `item_id,name`；食物／菜谱关联使用 `food_id` 或 `recipe_version_id`，数量用 `grams` 或已发布 `portion_reference_id + portion_count`，并明确 `share_ratio,portion_source`。详细枚举与互斥约束见文末类型文件。前端不提交营养合计代替计算。

| 方法与路径 | 关键正文／响应 |
| --- | --- |
| POST `/api/health/v1/meal-recordings` | `{member_id,client_request_id,meal,accept_incomplete}`＋同值幂等头；人工直接记餐要求实际个人份量、`share_ratio=1`、非unknown来源，不传照片／位置或整桌比例 |
| POST `/api/health/v1/family-meal-recordings` | `{group_id,members:[上述单人输入]}`，`Idempotency-Key=group_id`；逐人结果在 `results[]` |
| GET `/api/health/v1/members/{mid}/diet-logs/page` | `limit,offset`；读取 `records,next_offset` |
| GET `/api/health/v1/members/{mid}/diet-logs/{record_id}/detail` | 当前正式饮食详情与 `source_version` |
| PATCH `/api/health/v1/diet-logs/{record_id}` | `{expected_version,client_request_id,reason,meal,accept_incomplete}`，幂等头＋`If-Match` |
| GET `/api/health/v1/diet-logs/{record_id}/revisions` | 更正历史，只读 |

家庭桌菜口径已经确认：不要求每个人各点一次确认；没吃的人不提交；允许部分成功。`results[].status=saved/failed` 分别展示。已成功的人不回滚、不重复保存；原失败项重试保留原键和内容；明确要更改失败输入时走既有“编辑未保存项”流程，不能修改已成功请求的内容。

不要把“允许部分成功”理解为所有成员都可无授权写入。每个成员在服务端独立校验权限。照片候选路径和无照片直接记餐路径均已有消费者，应分别沿已有 client，不将同一餐同时提交两条路径。

更正后保留原 `record_id`、`source_version` 递增，程序重新计算，旧营养分析／反馈依据失效。用新详情替换当前视图；不能只改卡片文字仍显示旧分析。用户要求 AI 重新分析时，再用当前版本进入反馈／分析入口，受当前处理政策控制。

## 9. 正式餐单采用与商城边界

普通今日安排展示和正式餐单采用是两个流程。已有 `health-plan-client.js` 应继续检查批准状态：

| 方法与路径 | 必要约定 |
| --- | --- |
| GET `/api/health/v1/members/{mid}/meal-plans` | `limit,offset`，读取 `plans,next_offset` |
| GET `/api/health/v1/meal-plans/{plan_id}` | 回读当前成员、版本和来源 |

| GET `/api/health/v1/members/{mid}/adopted-plan?plan_date=...` | 当前采用，替换前明确给用户看 |

真实采购联验仍需小刘提供测试账号关联、SKU／库存、配送及交易环境；“今日已支付／昨日提议／按档案建议”优先级需联合验证真实来源。App 不应把本次合成目录或测试商品加入正式环境。

## 11. 联合验收清单

全部使用合成账号／数据。每例保留客户端版本、后端版本、业务ID／版本、request_id／run_id、响应状态和trace_id；不得在日志附原图、token或真实健康正文。

1. 两个账号、两个家庭：共享档案可编辑，外家庭不可见；切号后的旧网络／SSE响应不覆盖新页面。
2. 三步建档：所有必填和“未知／无／有”校验；保存超时后原键恢复；多人家庭中本人是否已建档不继承其他成员状态。
3. 后台三餐：发起后退出页面，重新进入可读取同一安排；默认两人三餐，改午餐为一人后仅午餐内容和采购来源改变。
4. 重试：网络暂时失败复用有效 Run；处理快照变更而未同意返回403；明确重新同意后重试生成新 Run，并发点击只产生一次业务任务。
5. 撤权／撤回：恢复入口和最终发布前均阻止失效结果公开；当前页面清理不可用结果。
6. App 生命周期：冷启动、深链刷新、返回前台、切号不触发未处理导航取消，无重复生成请求。
7. 食物／报告：上传进度和取消、任务恢复、候选改版冲突、重新计算、确认回读、源文件失效；真实模型质量另行验收。
8. 多人记餐：一人成功一人失败，不重复保存成功人；无进食成员不创建记录；更正同ID、递增版本，旧分析不可沿用。
9. 采购：查看无发布／订单写入；当前版本明确购买；库存或价格变化需重新确认；支付失败／未知状态从商城查询。

## 13. 专业复核与用户主动交接

后台 Web 的专业复核工作台和主动交接入口已于2026-10-23随 main `7f5f56f` 部署。已完成数据库备份、健康 Schema28→29迁移及 API／Worker／Web 一致发布；正式 App 由客户端同事按[工作台与交接接口](../Yuxi-main/docs/advanced/health-actual-meals-and-reviews.md#专业复核工作台)接入，不重复实现后台。

发布验收分开记录：服务器独立拓扑使用同一发布镜像，7项真实 HTTP／Worker 测试通过，覆盖专业权限、来源变化、目标独立同意、幂等及来源撤回失效；浏览器验证提交→退回→重提→批准，以及交接预览→取消／确认→目标路由且不自动发起 Run。生产检查 Schema29、服务健康、页面文件一致性及新读取接口拒绝匿名访问，未在生产创建合成专业资格或专业批准，也未开放真实用户咨询。

| App需要接入的页面 | 行为与验收 |
| --- | --- |
| 我的复核申请 | 当前成员列表、来源版本及材料引用；退回后补说明，实际档案或餐单改变后创建新检查/申请；旧批准保留失效状态 |
| 专业复核收件 | 仅有资格及成员授权者可操作，按照服务端 `allowed_actions` 展示；不能允许申请人自审，管理员身份不替代资格 |
| 健康任务完成页 | 血糖/血脂/血压回顾转营养咨询、饮食分析转基础配餐；先预览最小事实及范围，再确认目标独立用途同意，进入返回的 `thread_id` |
| 未知响应与失效 | 原幂等键/正文重放；403、409、410、503显示具体原因并重新核对。预览取消不写会话，确认不自动提交 `/api/agent/runs`；切号及来源失效清除旧预览 |

后端联调负责人刘潇；App页面、生命周期和真机验证由客户端同事负责。专业资格与审核责任仍需业务负责人落实，正式政策继续暂缓。后台合成验收不替代正式App、真实模型或专业生产验收。
