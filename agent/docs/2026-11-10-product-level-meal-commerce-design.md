# 餐单按商品匹配、购买时选择规格设计

## 目标

日常参考餐单先根据当前登录用户、就餐成员和真实档案选择可核对菜谱，再把菜谱食材匹配到商城商品。餐单阶段保存 `食材原文 -> product_id`，向小程序返回该商品的全部有效规格；用户购买时才选择 `sku_id` 并实时核价、校验库存。该链路适用于所有已认证用户，用户 12 只作为验收账号。

## 非目标

- 不把商城商品复制成需要人工重建的静态 Agent 知识库。
- 不由 Agent 猜测价格、库存、营养数值、过敏原或专业结论。
- 不在生成餐单时创建购物车、订单或支付记录。
- 不重做三方页面视觉，只调整接口契约和现有组件的数据适配。

## 已选方案

采用商城版本化全量目录与 Agent 短周期探测缓存。商城目录仍是商品事实 Owner；Agent 每 30 秒探测目录版本，版本改变才重新分页读取。菜谱知识库拥有菜名、食材原文和做法；Agent 后端程序按标准化商品名和明确别名匹配 `product_id`，不让模型遍历或选择 SKU。

商城目录返回所有已发布、Agent 可见商品的有效规格，包括暂时缺货规格，并为每个规格标明 `sale_status`。餐单保存不因库存或价格变化失败；商品删除或下架后，历史餐单仍保留来源快照，当前展示标记不可用。购物车、核价和下单继续以用户明确选择的 SKU 为输入，并在交易边界重验当前价格、库存和状态。

直接读取全部目录可以动态但每次请求慢；永久复制到 Agent 可以快但会过期；版本化缓存同时保留动态性和响应速度，因此采用该方案。

## 三方职责

### 商城

`CatalogService` 输出商品级目录：`product_id`、商品名、描述、分类、商品图和 `skus`。每个 SKU 包含规格名、净含量、价格、库存状态、可售数量和图片。商城目录版本在商品或规格变化后更新，交易接口继续拥有最终价格和库存。

### Agent

Agent 从认证上下文取得当前用户、家庭、成员、日期和餐次，读取授权档案后检索真实菜谱。菜谱食材通过后端匹配服务生成候选商品；模型只选择已读菜谱和候选 `product_id`，不提交 SKU、包装数量或采购价格。服务端保存商品关联和未匹配缺口，菜品图片异步生成，不阻塞餐单完成。

“再换一批菜”沿用同一用户、家庭、成员、日期、餐次和档案，并排除近期已使用菜谱来源。一次商品分类调用仍最多四类，但一次餐单可以分批读取多于四类；最终商品选择只受菜谱候选和当前商品事实约束，不受某一次分类读取限制。

### 小程序

小程序沿用现有页面风格。聊天先显示搭配说明，再显示菜品卡片；菜品详情显示营养说明、原谱食材和商城商品。每个商品展示全部有效规格，用户选中一个可售 SKU 后才能进入现有购物车、核价和下单流程。缺货规格可见但不可选。

## 数据契约

新餐单快照使用：

```json
{
  "product_matches": [
    {
      "product_id": "50",
      "product_name": "富硒鸡蛋",
      "ingredient_refs": ["鸡蛋 2 个"],
      "skus": [
        {
          "sku_id": "56",
          "sku_name": "10 枚装",
          "price_cent": 1680,
          "sale_status": "available",
          "available_quantity": 12
        }
      ]
    }
  ],
  "purchase_items": []
}
```

`purchase_items` 只用于兼容历史快照或交易阶段已经明确选择的 SKU。新餐单不生成固定 SKU。历史餐单继续按原契约可读。

## 匹配与失败规则

匹配顺序是标准食材名称、标准化商品名、明确别名和已维护映射。模糊相似词不能自动替代。未匹配食材形成 `purchase_gaps`，但保留菜品和其余商品。单个规格缺货、价格变化、图片失败、某次分类未读都不能使餐单失败。

餐次缺失、候选结构错误和可恢复的目录版本变化作为一次工具纠错反馈，不直接发布通用失败。菜谱来源失效、未授权档案或身份不一致仍然失败关闭。

## 性能与隔离

商城目录缓存可跨用户共享；档案、对话、餐单、最近推荐、地址、购物车和订单按认证用户、家庭和成员隔离。模型输入只包含本次必要档案、菜谱候选和商品级候选，不包含全部 SKU。图片任务异步执行并复用来源哈希缓存。

## 验收

1. 任意已认证用户按自己的档案生成餐单，不能写死用户 12。
2. 商品名称匹配成功即保存 `product_id`，不要求 Agent 选择 SKU。
3. 小程序得到匹配商品全部有效规格；缺货规格可见且不可购买。
4. SKU 库存或价格变化不导致餐单生成或历史读取失败。
5. 用户选定 SKU 后，购物车、核价和下单实时校验当前事实。
6. 商城目录版本变化后 Agent 在探测周期内刷新，未变化时不重复拉取全量目录。
7. 未匹配单个食材、图片生成失败不导致整份餐单失败。
8. “再换一批菜”保持用户、成员、日期和餐次一致并排除近期菜谱。
9. 多用户并发时档案、餐单和交易数据互不串联。
