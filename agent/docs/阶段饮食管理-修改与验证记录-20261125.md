# 阶段饮食管理修改与验证记录

代码实现完成，尚未部署服务器、推送 GitHub 或增量合入现用小程序目录。数据库版本需要先迁移至 health 42，API 与 Worker 必须共同升级，才能启用新增入口。构建产物使用合成地址作验证，不能直接作为正式发布包。

## 用户可见行为

- “我的家”当前成员下增加“饮食目标与行动”。完整页面位于健康分包，日常饮食反馈保持原有入口和功能。
- 推荐方向和自填目标交给 AI 整理成草案，用户可编辑并确认。开启后统一维护目标，原档案展示同步摘要；旧客户端不能独立覆盖阶段目标。
- 连续七天的行动清单支持勾选划掉、重复计次、撤销及调整。勾选不改变档案或配餐目标版本。
- 默认三个自然月为阶段，月底按实际月末计算。阶段到期自动准备复盘，用户确认下一阶段后切换，不自动替用户换目标。
- 复盘读取有效饮食记录、手动行动、当前账号相关自述及已核对报告；无新报告仍可生成。页面不显示“依据”或相关记录入口。
- 目标修订和周行动保留版本关联。已结束复盘冻结正文，之后的新报告作为补充显示；来源撤回或更正后不继续暴露旧派生正文。
- 今日和七天参考选菜读取实际就餐者目标，可支持的明确行为方向参与软排序，原有硬限制继续执行。营养数值目标仍属于既有专业模块。已存七天菜单仅行为目标变化时可只读，其他依据仍严格核对，订单不自动改写。

## 核心实现

阶段、操作收据、周行动、私有生成结果分别持久化。服务端统一承担家庭/成员权限、请求幂等和事务；同一事务更新阶段与兼容目标摘要。后台生成复用既有持久任务、当前模型配置、用途边界、预算和任务租约。网络模型调用不持有业务事务。

自动扫描按 checked_at 轮转，避免最早100条饿死后续成员。同来源失败采用30分钟退避，24小时两次自动失败后等待用户明确重试；来源改变可重新准备。普通读取不直接触发模型。前端轮询独立校验生命周期、阶段和账号，离开页面不会重新复活轮询。

报告查询不使用旧列表的100指标上限；按实际检查日期和指标编码整理，相同原单位和已知采样条件才计算原始数值差，不宣称临床改善、恶化或饮食因果关系。
