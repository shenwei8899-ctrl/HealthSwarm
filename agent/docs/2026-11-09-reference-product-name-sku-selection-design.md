# 参考餐单商品名匹配与 SKU 选择设计

## 意图

参考餐单只用菜谱食材名称与商城 `product_name` 判断商城是否有该原料。命中商品后，由 Agent 在服务端给出的真实候选 SKU 中，结合实际就餐人数、菜谱可靠用量、包装规格、价格和库存选择包装组合；没有名称匹配或没有可售 SKU 时，餐单仍成功保存并展示为“自行购买”。

## 目标

- Agent 不再复制原谱食材文字、编写自由格式 `match_basis` 或提供目录外 SKU。
- 服务端拥有菜谱食材原文、商品名候选、SKU 候选和最终保存关联。
- 同名多个 SKU 时优先覆盖所需量且剩余最少，再选总价最低的组合。
- 没有名称匹配不再使餐单失败；对应项没有 SKU 和价格，不能进入商城购物车。
- 旧参考餐单继续可读。

## 非目标

- 商品描述、营养、配料、过敏原和图片不参与商品名匹配或 SKU 排序。
- 本变更不创建商城商品、不修改商城管理后台页面、不声称 SKU 具有医学或营养适用性。
- 家庭档案中的饮食限制继续影响菜谱选择，但不扩展为同名 SKU 的健康判定。

## 约束

- 菜谱原文和商城数据都由服务端同 Run 回执拥有，Agent 只引用服务端产生的候选键。
- 有可靠份数时才按就餐人数缩放用量；缺少份数时保留原谱量，不推断个人份量。
- 只做同维度安全换算（kg/g、L/ml）；无法可靠比较或原谱未明确份数时不猜包装，保存为自行购买。
- 商城接口故障不能伪装成“无匹配商品”。
- 本地 Git `main` 与线上运行源存在差异，实施前必须同步受影响的线上源并保留现有能力。

## 方案比较

### 纯后台选择

稳定但不能利用家庭参与人数和候选组合作细化判断。

### 纯 Agent 选择

灵活但会继续承担复制原文、编造 SKU 和格式错误风险。

### 混合方案（采用）

服务端按商品名生成候选并拥有原文关联；Agent 只在候选中选 SKU 和包装数；服务端重验并在无候选时生成自行购买项。该方案保留 Agent 对包装组合的判断，同时把商品身份和失败降级固定在程序边界。

## 主链路

1. `reference_recipe_matching` 将原谱食材和商城商品名归一到受控食材名称，不读取商品详情字段。
2. `read_reference_recipe` 返回每条食材的服务端候选组、原文、匹配商品名及候选 SKU。
3. Agent 根据当前就餐成员和候选 SKU 返回本轮 `candidate_key`、SKU 与整数包装数，不返回食材原文或匹配理由。
4. `reference_meal_selection_service` 验证 SKU 属于候选集合，由服务端附回完整原谱 `ingredient_refs`。
5. 未命中商品名、全部 SKU 无货或有效候选耗尽时生成不含 SKU 和价格的 `purchase_gaps`，由既有 API 投影为自行购买说明。
6. 小程序将商城商品和自行购买项分区展示；购物车请求只包含商城商品。

## 失败边界

- 无商品名匹配、无可售 SKU：正常保存，自行购买。
- Agent 返回候选外 SKU：拒绝该选择并按同一候选集纠正；纠正仍无效时转自行购买，不终止餐单、不自动选 SKU。
- 保存前库存变化：重读候选；没有可用候选时转自行购买。
- 商城不可访问、菜谱来源失效或当前限制无法核实：保持原有显式失败，不伪装成自行购买。

## 兼容和页面

- 持久快照继续使用现有 JSON，不增加数据库表。
- 保留 `purchase_items` 和 `purchase_gaps`；自行购买继续使用无 SKU、无价格的缺口结构，不破坏旧消费者。
- 只修改小程序参考餐单卡片和采购详情；Agent 管理后台、商城管理后台不改页面。

## 验收

- 重放 2026-11-09 的燕麦、虾仁、西兰花和鸡蛋案例不再产生 `reference_purchase_coverage_invalid`。
- 多 SKU 选择满足“覆盖用量、剩余最少、总价最低”。
- 无匹配食材显示“自行购买/暂无价格”并且不能加入购物车。
- 旧餐单读取、今日餐单复用、明后日餐单和换菜流程保持可用。
