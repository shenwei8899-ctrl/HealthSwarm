# 阶段饮食管理：代码审查与实施方案

本文件记录源码审查结果和拟实施方案。功能尚未实现；本次不修改业务代码、数据库、服务器和现用小程序包。依据为当前开发目录中的实际源码，未将历史备份或演示页面视为生产入口。

## 已确定的范围

- 唯一主入口是“我的家”当前成员下的“饮食目标与行动”。页面内显示阶段目标、本周行动及可展开的阶段复盘。
- 饮食反馈保留当餐、当日、近期趋势，不加入阶段复盘入口、页签或新报告面板。
- 目标支持推荐选项和自填；模型提出草案，用户确认后生效。原档案目标作为首次参考；开启阶段后档案摘要展示当前目标，通过同一入口编辑。
- 阶段约三个月，执行清单连续七天一组；餐单仍是既有七天计划。目标和行动属于个人，家庭餐单结合实际就餐者各自目标与既有硬约束。
- 一次性行动完成后划掉，重复行动达到本周次数后划掉；支持撤销、调整。先采用手动完成，不由模型推断完成。
- AI 先根据已有记录生成复盘，补充情况是可选项。没有新报告也能复盘；新报告核对后补充指标变化和目标调整建议，不自动替换当前目标。
- 复盘页面不显示“依据”或“查看相关记录”。服务端仍须保存并校验实际使用的来源及版本。

## 当前代码事实与缺口

### 成员入口与分包

[FamilyMemberDeck.vue](../../App/src/components/FamilyMemberDeck.vue) 拥有卡片拖动以及下方“健康与偏好”“饮食限制”区域。[CloudFamilyOverview.vue](../../App/src/components/CloudFamilyOverview.vue) 管理当前成员、账号与家庭上下文，以及档案弹层。

增加独立的小入口并跳转阶段页面，不把整套页面同步引入首页。现有下方区域有固定高度，新增入口时必须同时调整容器高度和切换布局，不能只插入一个按钮；保留拖动中禁用点击及滑动后的误触保护。

[pages.json](../../App/src/pages.json) 已使用健康等分包。阶段页面及完整编辑界面应放在健康分包，只让首页加载必要摘要，结合官方包体检查决定组件位置。

### 目标存在多种表示

[member-profile.js](../../App/src/services/member-profile.js) 的 `memberProfileChanges` 同时更新 `dietary_details.goals` 与普通 `goal` 文本。[miniapp_profile_service.py](../Yuxi-main/backend/package/yuxi/services/miniapp_profile_service.py) 的建档保存也写这两种表示；读取时 dietary 中的 goals 可覆盖由 goal 推导的值。

[family_schemas.py](../Yuxi-main/backend/package/yuxi/services/family_schemas.py) 已有 `HealthGoal`：内容、来源、开始日期、复盘日期和 active/completed/paused 状态。它尚不拥有独立阶段 ID、稳定目标 ID、行动清单和复盘历史。

[family-archive-fields.js](../../App/src/services/family-archive-fields.js)、[MemberFields.vue](../../App/src/components/MemberFields.vue) 与 [MemberAdditionalFields.vue](../../App/src/components/MemberAdditionalFields.vue) 分别暴露普通目标及结构化健康目标编辑。仅增加新页面会留下多套写入口。

拟用阶段实体拥有当前阶段的目标；既有字符串字段作为兼容摘要同步更新，行为型 health_goals 纳入同一编辑入口。旧数据只作为用户可选择的参考，不批量开启阶段，也不把旧 completed/paused 目标重新激活。现有旧客户端写目标时，服务端必须识别已开启阶段并拒绝独立覆盖，不能只在新界面隐藏按钮。

已有 [health_personal_target_service.py](../Yuxi-main/backend/package/yuxi/services/health_personal_target_service.py) 与 [health_agent_personal_target_service.py](../Yuxi-main/backend/package/yuxi/services/health_agent_personal_target_service.py) 管理批准来源下的营养数值目标；这类专业数值不是本功能的用户行为目标，不修改或覆盖其计算及来源。

### 日常反馈可以复用事实查询，不能直接改成阶段复盘

真实入口是 [CloudDietFeedback.vue](../../App/src/components/CloudDietFeedback.vue)，而非 mock 分支的 nutrition-feedback.js。它读取实际确认餐次和既有日/周期分析。

[health_diet_analysis_types.py](../Yuxi-main/backend/package/yuxi/services/health_diet_analysis_types.py) 只允许 1、7、30 天。[health_diet_analysis_service.py](../Yuxi-main/backend/package/yuxi/services/health_diet_analysis_service.py) 输出有效记录统计、覆盖情况及用户自述反馈；趋势分类明确为 rules_not_ready。把 period_days 改成 90，既不满足现有契约，也不能得到报告对比和阶段目标总结。

[health_diet_analysis_repository.py](../Yuxi-main/backend/package/yuxi/repositories/health_diet_analysis_repository.py) 已按 eaten_at 查询并排除失效来源；窗口上限 1000 条，之后逐条复验来源。阶段查询应抽取并复用有效性语义，用批量读取避免三个月记录逐条查询，超量时分页处理或明确报错，不能静默截断。

### 对话与记忆不是完整的执行历史

[health_memory_context_service.py](../Yuxi-main/backend/package/yuxi/services/health_memory_context_service.py) 与 [health_memory_repository.py](../Yuxi-main/backend/package/yuxi/repositories/health_memory_repository.py) 已有成员归属、账号归属、来源版本和撤回控制。当前有效记忆主要是偏好、限制与健康自述，不能代替整个阶段的执行历史。

复盘只读取本次操作者有权访问、与目标成员相关、处于阶段范围内的必要内容。以实际饮食记录和手动完成状态为事实，以对话中的自述为补充；区分已经做、计划做、AI 建议和替家人询问。不得把模型回复或已生成菜单当成已执行事实，也不得因为管理员身份读取其他账号的私人对话。无法明确归属的内容不进入个人完成判断。

### 报告确认已经存在，历次比较尚需新增

[health_vision_service.py](../Yuxi-main/backend/package/yuxi/services/health_vision_service.py) 的 `confirm` 在核对确认后逐字段写入 `HealthObservation`；未核对 OCR 草稿不应参与阶段分析。

[health_vision_types.py](../Yuxi-main/backend/package/yuxi/services/health_vision_types.py) 的 ReportField 保存 observation_code、原始值、可选数值、单位、参考范围、实际检查日期和空腹状态。可识别 code 目前有限，unknown 不应靠菜名式文本匹配强行合并。

[health_vision_repository.py](../Yuxi-main/backend/package/yuxi/repositories/health_vision_repository.py) 的通用报告记录列表默认只取 100 个指标行，并按入库时间排序。不能拿这个列表直接做历次体检比较，否则指标较多会截断，补传旧报告也会排错。

阶段报告查询需按 confirmation 分组，按实际检查日期和指标编码整理时间序列，并校验确认来源、可见性和当前版本。必要时读取阶段开始前最近一次可比结果作为基线。只有单位和采样条件等足够可比才计算差值；没有日期、数值或可靠映射时保留原始结果，不编造。不同机构或方法的差异需保留，不自动写成改善/恶化，更不作饮食因果结论。

### 现有七天参考选菜没有直接消费阶段目标

[reference_meal_plan_service.py](../Yuxi-main/backend/package/yuxi/services/reference_meal_plan_service.py) 的 `reference_context_in_session` 逐人检查档案和配餐用途授权，并记录 member version/profile hash。[exclusive_reference_plan.py](../Yuxi-main/backend/package/yuxi/services/exclusive_reference_plan.py) 复用这个上下文安排七天参考计划。

[reference_recipe_variety.py](../Yuxi-main/backend/package/yuxi/services/reference_recipe_variety.py) 的排序目前消费菜系、口味、历史曝光等，七天路径另考虑三档费用；单纯同步 goal 文本不保证目标改变选菜。

需要给共同上下文增加各实际就餐者已确认的阶段目标与版本，使今日餐单与七天餐单读取同一语义。可被已有食材/做法事实支持的行为目标才参与软排序；“规律吃早餐”等日程目标由行动清单支持。自由文本不能直接转成医学禁忌或未经批准的营养阈值，不能伪称任意自填目标都能由菜谱排序实现。过敏、忌口、不耐受与医生要求继续沿原校验执行。

## 拟实施结构

### 最小持久化边界

建议新增阶段、阶段修订、周行动及复盘记录四类持久实体，沿用现有 PostgreSQL 和迁移机制，不另建数据库或队列。

| 实体 | 拥有的事实 |
| --- | --- |
| 阶段 | 家庭/成员关联、当前目标、开始/复盘日期、状态及当前版本；一个成员最多一个未结束阶段 |
| 阶段修订 | 用户确认过的目标及修改时间，避免新目标倒算旧周执行情况 |
| 周行动 | 阶段内连续七天的日期范围、稳定行动 ID、目标次数、当前次数/完成状态及版本；日期范围唯一 |
| 复盘记录 | 阶段/截至日期、所用目标修订、来源版本摘要、生成任务引用、生成状态和结果；结束确认后冻结正文，后续报告形成补充 |

周行动可在单行 JSON 内保存少量结构化条目，不为每次勾选新增一套事件系统。写入采用 expected_version 和幂等请求 ID；重复“记一次”、撤销及网络超时重试都不能多记或漏记。草案保留在已有任务结果中，只有明确确认后成为正式目标。

目标确认时，通过同一 service、同一事务更新阶段和兼容档案摘要，复用现有字段授权及版本快照语义。现有 FamilyService.update_profile 自行 commit，不应先调用它提交摘要再另开事务创建阶段；实施时在必要范围抽取共享的事务内写逻辑。

勾选行动只更新行动版本，不更新档案版本或餐单目标依赖；生成复盘也不改变配餐来源。只有用户确认目标变化才更新目标版本，避免每次勾选都触发餐单失效或重排。

### 日期口径

统一 Asia/Shanghai。阶段从用户确认日开始，默认三个自然月后复盘，月底按目标月末处理。内部使用开始含、结束不含的区间，页面显示明确日期。行动周从阶段开始每七天接续，最后一周可不足七天，不产生阶段以后的执行任务。

行动周与餐单均为连续七天，但餐单可能由用户在另一日期重新生成；关联时按实际日期范围交集，不假定“第几周”编号始终相同。复盘截至今天，不能评价未来天数。阶段到期后生成总结；下一阶段从用户实际确认日开始，不回填不存在的行动。

### 页面及接口职责

- “我的家”只批量读取有权查看成员的当前目标/本周进度摘要，不逐成员调用模型，不在打开入口时自动创建阶段。
- 健康分包新页面承担读取阶段、选择或自填目标、确认草案、调整行动、完成/撤销、展开复盘及确认下一阶段。
- 路由层复用认证，业务 service 拥有跨档案和阶段的事务，repository 拥有来源查询与持久化。具体路由名在实现提案中固定。
- 读页面与普通勾选不调用模型。初始目标建议、下一周行动建议和阶段总结使用现有 TaskService/Worker；复用状态查询和断线恢复，不新增 SSE 协议。
- 服务端来源和权限按请求重新校验；生成任务在读取输入前及发布结果前再验。只读家属不能通过新接口获得写权限或代替本人接受处理用途同意。
- 前端复用 sessionRevision/storageContext/epoch：切账号、切家庭、切成员后迟到响应丢弃；403/410 等权限失效时清空旧内容。不同成员进度和缓存不得共用一个未分区 key。

### 自动生成与刷新

[task_registry.py](../Yuxi-main/backend/package/yuxi/services/task_registry.py) 和 [run_worker.py](../Yuxi-main/backend/package/yuxi/services/run_worker.py) 已有 durable task 注册、lease 与周期扫描。阶段生成复用此机制，不新增独立调度服务。

阶段/周到期的扫描只查当前需要处理的索引记录，幂等创建缺失任务；页面可补触发漏掉的准备任务，但不需要用户主动填问卷。记录更正、行动调整和报告确认先标记已生成总结需要更新，将同一来源版本的更新合并处理；已有结果可先显示截至日期与正在更新状态。到期及必要刷新时才生成，不为每次打开或每条对话立即调用模型。

提交事务后再投递；模型和 OCR 外呼不持有成员或家庭行锁。Worker 失联、重复投递、旧 attempt 晚写必须沿现有 lease 机制收敛，失败可重试且不影响手动清单。

报告确认本身不等待复盘任务。仅对已开启阶段标记待更新；未开启时只保留现有报告完成流程，回到“我的家”可选择制定目标。已经结束的总结不静默重写，新报告形成补充；撤权、来源撤回或删除时仍需禁止读取不可见来源的派生私密内容，冻结不构成授权豁免。

### AI 输出边界

先由程序统计记录覆盖、行动完成次数及可比指标差值，再让模型组织摘要、困难和下一步建议。输入有范围和长度预算，记录过多使用可重建的分段汇总，不直接拼接三个月所有聊天。

输出使用结构化字段，分清事实、用户自述及建议。缺记录不算没吃，缺营养不补零；无新报告不宣称指标改变；无任何记录时诚实描述信息不足，仍可提供下一步建议。用户自填的目标和报告正文都作为数据，不能变成模型执行指令。

目标/行动建议和复盘文案需要独立于既有 diet-analysis 的“模型只能选择来源”输出契约，不能修改旧分析师契约来绕过来源校验。沿用现有模型配置和用途同意边界，在新模块落实必要授权、来源校验及输出约束；不扩大已有同意的用途范围。

### 餐单兼容

新生成或明确调整的餐单读取当前目标。已确认历史菜单、已用餐餐次、采购快照和订单不自动覆盖。当前既有来源检查会因档案版本变化返回失效，必须同时处理历史读取与新生成校验的差别，不能只把阶段版本塞进 hash 导致旧页面重新出现读取失败。

历史显示保留当时目标快照和来源时间；安全相关字段变化继续受原服务限制。下一次生成用最新版本；目标冲突或无法从现有菜谱事实支持时明确说明，不用当前查看的成员覆盖其他就餐者。

## 实施与验证顺序

1. 先固定阶段/周/复盘契约和幂等、授权语义；建立 proposed decision 与幂等数据库迁移，验证旧数据保留及单成员未结束阶段唯一约束。
2. 完成阶段与档案摘要同事务写入、旧入口收敛、手动清单及“我的家”入口，验证取消、撤销、重复写、断网重试及刷新回读。
3. 加入记录/报告/必要对话的有权来源聚合、后台生成和失效更新，验证无报告、只有一份报告、补旧报告、报告超过100指标、来源更正/撤回及账号切换。
4. 把目标接入今日和七天共同上下文及可解释的排序，验证多成员目标、硬限制、历史菜单/订单保护，以及只勾选行动不改变餐单来源。
5. 用真实 HTTP、隔离 PostgreSQL、Worker 和浏览器闭环验证，再构建 H5/微信分包，执行现有 miniapp-size 检查及官方包体检查。合并现用包时按最新版本增量更新并校验未涉及文件，避免覆盖并行改动。

关键负向案例包括跨成员 ID、管理员无旁路、只读成员写入、撤回授权后任务晚到、重复计次、两端同时编辑、阶段末周、月底日期、没有记录却生成完成率、计划当实际、相同 code 不同单位强比、旧报告被当最新、晚生成任务覆盖已修改目标，以及历史订单被改写。
