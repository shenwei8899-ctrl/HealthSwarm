# 小程序与 HealthSwarm Agent 对接修订

日期：2026-10-13。读者：小程序、Agent 后端、家庭档案、专业资料与商城负责人。

本文件修订小程序同事的《小程序与HealthSwarm-Agent源码对齐修改说明-20261013.md》涉及 Agent 服务端的基线、接口状态和交付顺序。小程序当前工作区、微信开发者工具和商城环境未在本次核对中运行；小程序文件修改清单仍由客户端负责人依据自己的当前源码维护。服务端可执行契约以所引用的 DTO、路由和运行环境 OpenAPI 为准。

## 基线与已交付入口

团队 `main` 已包含提交 `a6f3554742952a2806caed75cf446416c1fc011b`。这只证明源码已合并，不证明联调环境已部署该提交。联调开始时双方记录部署提交、业务及健康 Schema 版本、API/Worker 镜像版本和公开 API 地址；不使用一个未标版本的接口地址作为验收依据。当前源码的 business Schema 为 12、health Schema 为 24。

固定健康 Agent 共有八个，均处于 `partial`：咨询、配餐、饮食分析、质量审核、采购、血糖记录回顾、血脂记录回顾和血压记录回顾。`health-profile` 是业务能力。统一 `task-entries` 支持十一类可创建线程的任务；新三类为 `blood_glucose_review`、`blood_lipids_review`、`blood_pressure_review`，创建线程后仍须显式提交同 Agent/线程的 `/api/agent/runs`。三类助手只做授权记录回顾、资料追问和审核知识解释。`glucose_plan`、`multi_day_plan`、`automatic_family_coordination` 仍返回 `dependency_not_ready`；血糖记录助手不等于控糖计划。

现有接口支持本人家庭档案显式关联、成员能力与就绪诊断、用途同意、普通及每日咨询、Request/Run/Task 查询、单日个人与家庭餐单预览及版本化业务动作、餐照和报告候选确认、单成员饮食记录、反馈和 1/7/30 天事实分析。客户端按各自 DTO 投影和回读，不能把线程创建、Run 完成、专业批准和交易完成压成一个状态。服务器权限、当前来源和用途同意仍在提交、工具读取与发布边界重验。

源码定位：[健康任务 DTO](../Yuxi-main/backend/package/yuxi/services/health_task_types.py)、[任务 service](../Yuxi-main/backend/package/yuxi/services/health_task_service.py)、[健康路由](../Yuxi-main/backend/server/routers/health_vision_router.py)、[角色目录](../Yuxi-main/backend/package/yuxi/services/health_agent_roles.py)、[任务恢复说明](../Yuxi-main/docs/advanced/health-task-recovery.md)。

## 双方可立即联调的最小链路

| 顺序 | 服务端事实 | 客户端动作 | 完成证据 |
|---|---|---|---|
| 1 | 账号 token 能通过现有认证依赖 | 选择实际账号和家庭；旧会话响应不能污染新会话 | 账号、家庭、token 来源与部署版本一致；跨账号读取被拒绝 |
| 2 | 家庭成员和健康成员是两个 UUID | 本人明确关联 `source_member_id` 与 `healthMemberId`，再回读关联 | 重启客户端后仍回读同一来源；昵称相同不能建立错误关联 |
| 3 | `capabilities`、`readiness` 和用途同意分别表达准入 | 按成员及用途显示当前可操作项，不把基础档案 `ready` 当成完整专业就绪 | 无权、缺用途、缺专业来源和运行依赖分别呈现 |
| 4 | `task-entries` 的 `ready` 仅创建固定线程 | 保存 `client_request_id`；按返回 `agent_slug`、`thread_id` 提交新的 Request ID | 同一创建键重放不重复建线程；Request 与业务创建键各自独立 |
| 5 | PostgreSQL 中的 Request、Run 与最终业务结果分别拥有状态 | 保存实际 `request_id`；派发后从同一健康 Task 的 `run_id`（或通用 Request 的 `dispatched_run_id`）取得 Run，断线后查询同一 `/tasks/{request_id}` | 完成只读取同 Run 结果；取消、追问、失败与来源失效有不同页面状态 |
| 6 | 餐照、报告和餐单持久事实经业务确认 | 图片上传后读取候选、校正、计算、确认；餐单读取保存版本及专业状态 | 最终记录、餐单和引用在重新进入时可从服务器回读 |

新三项指标助手的 `task-entries` 请求正文使用对应 `task_type` 与合法 UUID `client_request_id`，不包含 `selection`。返回 `ready` 后使用返回的 `agent_slug` 和 `thread_id`，不从角色显示名构造 slug。服务端当前只把本人有权读取的实测指标和当前有效的审核科普来源交给对应 Agent；无数据时由助手追问，不推断诊断或目标值。

指标回顾最小请求示例；`Idempotency-Key` 与正文 UUID 必须完全相同。`entry_status=ready` 的响应中读取 `agent_slug`、`thread_id` 与 `request_submit_url`，不要预设服务器一定返回 `ready`：

```http
POST /api/health/v1/members/{health_member_id}/task-entries
Authorization: Bearer <业务账号 JWT>
Idempotency-Key: 0f33c524-2cd6-4e5a-89f5-815427604cff
Content-Type: application/json

{"task_type":"blood_glucose_review","client_request_id":"0f33c524-2cd6-4e5a-89f5-815427604cff"}
```

血脂与血压分别将 `task_type` 改为 `blood_lipids_review`、`blood_pressure_review`，每次新操作使用新 UUID。准备好提问后，客户端将该线程和角色连同文字 `query` 提交 `POST /api/agent/runs`，保存返回的真实 `request_id`；任务入口的 `client_request_id` 不能当作这个 Request ID。恢复时先读 `GET /api/health/v1/tasks/{request_id}`：`request_status` 是排队事实，`execution_status` 是 Run 事实，`result.result_type` 才是当前可展示的业务类别。`needs_input` 属于已完成运行的追问，`interrupted` 属于运行中断。需要流式进度时，仅订阅响应给出的 `request_events_url` 或 `run_events_url`，结束后仍回读同一 Task。血糖、血脂、血压及普通咨询的流只公开固定进度，不传候选回答正文。

该路由的健康业务错误带 `detail`、`code`、`message`、`trace_id`、`retryable`；`retryable` 只按当前路由实现对 429/503 为真。请求键不一致返回 `request_key_mismatch`；读取权限或来源失效应按实际 HTTP 状态停止展示旧内容。其余登录、家庭及通用 Agent 路由不保证同一错误 JSON 形状，客户端保留分别解析。完整状态和断线规则见[任务恢复说明](../Yuxi-main/docs/advanced/health-task-recovery.md)，字段定义见[Task DTO](../Yuxi-main/backend/package/yuxi/services/health_task_types.py)。
