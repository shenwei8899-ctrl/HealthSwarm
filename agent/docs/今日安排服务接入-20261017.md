# 今日安排服务的真实依赖与本地接入

适用于部署本次每日安排接口的维护者。页面可用的判据是：真实账号完成建档、得到已保存三餐，重新进入不生成新任务，详情 ID/version 与卡片一致。readiness 通过本身不能代替业务验收。

## 后端部署条件

使用 agent/Yuxi-main 既有部署及迁移流程，将健康 Schema 升级至 27；API 与 Worker 需要使用同版代码。保留正式数据，不能用测试库覆盖。

- `HEALTH_DAILY_RULE_CODE`：已发布批准规则；其中 miniapp_profile_codes 提供年龄区间到人群、性别、活动、疾病、过敏、不耐受、忌口、医嘱和偏好的编码。不存在的专业编码不能临时编造。
- `HEALTH_COMMERCE_API_URL`：真实商城签名接口的地址，可以包含网关前缀，例如 HTTPS 域名后的 `/commerce-api`。默认要求 HTTPS；仅内部受信网络确实使用 HTTP 时显式设置 `HEALTH_COMMERCE_ALLOW_INTERNAL_HTTP=1`。前缀不参加商城内部 API 路径的 HMAC 签名。
- `HEALTH_COMMERCE_CLIENT_ID` / `HEALTH_COMMERCE_CLIENT_SECRET`：已有商城集成凭据，仅服务端保存。
- 使用现有管理接口发布专业规则、完整营养配方，再通过 `/api/health/v1/recipe-commerce-sources/{recipe_version_id}` 绑定准确配方 hash、真实来源、步骤和每种原料的商城标准食材编码。映射不可原地修改，变化使用新配方版本。
- 配置真实 meal_plan 处理方及政策、模型供应方、批准知识库和 planner Agent；确认 Worker 能产生同一 Request/Run 的最终预览与 explanation。

商城返回的推荐包必须包含 package_sn/package_version、available/passed 交易校验及实际 items 的 sku_id、整数 quantity。系统在三餐包发布后重新读取目录，合计实际商品包核对共享库存；缺字段或超库存不会展示卡片。不预占库存，购买时继续重新报价。

## 本地微信开发者工具

项目 `.env.local` 已选择 api 模式和本机回环代理；`npm run dev:health-proxy` 将请求转发到用户提供的 `http://8.136.134.29`，商城请求转发到其 `/commerce-api`。代理只监听 127.0.0.1，不制造菜单、字段或模型结果。

HTTP IP 当前可访问 health/ready 与商品目录，但 HTTPS 握手及微信登录配置尚未就绪。开发者工具本机联调可使用回环代理并关闭本地合法域名校验；真机无法通过 127.0.0.1 连接开发电脑，正式发布仍需配置 HTTPS 合法域名及正确微信 AppID。新接口在服务器部署前，本地会显示服务错误，不能当作可用的 AI 分析。
