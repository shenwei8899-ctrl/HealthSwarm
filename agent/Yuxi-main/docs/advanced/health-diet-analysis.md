# 饮食分析与餐后反馈

面向在健康后台复核饮食和发起分析的用户。开始前，成员需要饮食记录访问权限与 AI 处理授权，管理员需要批准独立的饮食分析用途及处理政策。照片或人工草稿经确认后形成可分析的饮食记录。

## 开始饮食分析

在“健康识图”选择成员，再打开“饮食分析”。按日期统计时选择北京时间1日、7日或30日及结束日期；选择一餐时从已确认记录中选具体菜品与进食时间。页面先用业务接口核对当前来源，再请求单独的饮食分析用途同意。

勾选本次处理同意后点击“同意并开始分析”。服务创建绑定该成员的线程，页面提交所选范围的问题后进入饮食分析师对话。后续可以在同一成员会话中补充问题或改变分析范围；普通分析的时间窗口属于问题内容。对话结果显示服务器实际选用的记录或窗口，应核对它是否符合问题。

统计只使用当前有效的确认记录。未记录天数和缺失营养项保留未知，当前个人目标与历史窗口分别展示；专业资料未就绪时，结果仅说明记录事实。此入口不自动生成实际饮食、采用餐单或临床达标判断。

窗口内的记录或反馈集合变化后，旧周期结果会失效，需要重新进入分析，不能将旧统计当作当前结果。

完成后，对话中的结果卡片显示实际分析范围。单餐列出确认食物、份量和营养值；按日期分析列出窗口内有记录的天数、餐次与未记录日期。营养项缺失时显示“未知”，已知部分不能代替完整摄入量；没有记录的日期也不代表没有进食。

既有显式绑定个人目标的会话保留完整结果呈现，当前目标与历史记录分别保留，暂不切换为事实卡片。

## 记录这餐的反馈

在“已确认记录”找到要反馈的一餐，点击“这餐反馈对话”，填写吃完程度、口味和补充自述，再单独同意饮食分析处理。点击“同意并记录反馈”后进入绑定该餐次及确认版本的会话；模型通过受控工具记录当前用户原文的反馈。

在对话中核对保存结果，并在原餐次的“餐后反馈”查看、修改或撤回。吃完程度属于自述，反馈不改写原营养快照。手动“餐后反馈”可直接填写表单，与对话入口同时保留。

反馈回执卡片显示保存版本、吃完程度、体验和原文补充。需要补充信息时，卡片显示追问；回答后仍由同一会话执行受控保存。

## 处理未就绪与未知请求结果

未启用分析模型、缺少成员授权或确认版本时，页面说明原因并禁用开始操作。来源、版本、政策或授权变化后，刷新记录并重新选择和同意。切换成员会清空本地选择、同意和旧响应。

网络请求结果未知时，页面保留原幂等键，使用“重试原请求”恢复同一操作；线程已创建时可“进入会话恢复状态”。进入对话后的排队、Run 事件与最终查询沿用[Agent 运行机制](../mechanisms/agent-runtime.md)。服务端从 PostgreSQL 回读当前授权下的权威结果。

管理员在“服务与食品数据”分别配置各模型用途，保存时保留未改用途的模型值。任何非空模型，包括仅采购模型，都需要明确的处理政策与云处理确认。采购用途和饮食分析用途分别审批；配置保存与具体成员同意分别执行。工程验收及边界见[后台入口决定](../develop-guides/decisions/implemented/2026-10-10-health-analysis-web-entry.md)。
