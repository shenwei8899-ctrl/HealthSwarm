# 咨询 Worker 重启暴露旧镜像 schema 不兼容

日期：2026-11-24
Owner：backend/package/yuxi/storage/postgres/manager.py
关联决策：[对话正文选取与引用追问](../decisions/implemented/2026-11-24-chat-selected-reply.md)

## 影响

发布重启后，咨询 Worker 无法通过启动校验，API 进程可存活但就绪检查返回 503。按原镜像回退也未恢复该角色。数据库未降级、未恢复旧数据，部署没有执行 schema 迁移；实际受影响的用户请求数未知。

## 事实时间线

2026-11-23 的按天计划发布更新 API 和主 Worker，并将健康 schema 升到 41，咨询 Worker 仍使用要求版本 40 的镜像。2026-11-24 13:02（上海时间）执行引用功能切换，随后候选和原镜像回退均未通过健康检查。内部状态探针确认 API 与主 Worker 要求 41，咨询角色要求 40 且持续重启；API 的 PostgreSQL、Redis 和启动组件均正常，Worker 租约检查失败。核对源码、技能、依赖及运行配置后，咨询角色换用支持 41 的主 Worker 基镜像，三个角色恢复健康，API 就绪检查恢复。

## 因果链

旧咨询进程没有重启时，已有健康租约掩盖了镜像与数据库版本不匹配。发布重启触发 manager 的严格 schema 校验，咨询进程拒绝版本 41，无法续租咨询队列健康键。启用咨询隔离的 API 同时要求该租约，因此存活探针正常但接流量就绪失败。原镜像本身要求旧 schema，按原镜像回退不能修复数据库已经前进后的启动兼容问题。

## 安全网为何漏过

隔离单测和 HTTP 测试在镜像自身支持的 schema 上创建测试库，证明了功能行为，却没有比较每个生产角色及回退镜像与现有数据库的版本。发布前的现用进程健康、源码摘要和环境比较也不能证明冷启动兼容性。数据库运行时校验正确拒绝了旧版本，缺少的是停服前的跨角色镜像版本预检。

## 修正与验证

恢复采用包含当前 schema、模型及仓储的完整 Worker 基镜像，保留咨询角色命令、健康检查、环境、用户、入口和挂载。没有单改版本常量，也没有降级数据库。两个 Worker 的完整代码摘要没有咨询独有路径；技能、提示词和依赖核对没有额外差异。候选镜像的相关单测每角色 223 项通过，API 真实 HTTP/PostgreSQL 用例通过。版本探针直接读取 manager 常量并与线上18/41/2比较；旧健康版本40镜像构成实际拒绝负控，兼容候选及回退镜像通过预检。

## 防复发措施

本次发布工作流在停止 API 前，对每个候选与回退镜像执行版本探针；任何一个域与当前数据库不一致即拒绝切换。版本常量与严格比较由 [manager](../../../backend/package/yuxi/storage/postgres/manager.py) 拥有，咨询消费者租约要求由 [Worker 健康服务](../../../backend/package/yuxi/services/worker_health_service.py) 拥有。发布材料保留旧镜像拒绝负控、新旧镜像版本预检以及最终角色健康证明。

## 未解决风险

其他历史发布流程尚未统一复用此次版本预检。完整 API/ARQ/SSE E2E 和微信真机操作未运行。本文记录已观察到的冷启动兼容事故，不用现用进程健康替代未来镜像的启动证据。
