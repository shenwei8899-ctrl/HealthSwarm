# 日常参考配餐召回完整资料并约束工具调用

状态：proposed
类型：bug-fix
Owner：backend/package/yuxi/services/reference_meal_plan_service.py

## 问题

日常参考配餐的标题检索只要有命中就跳过其余召回，目录和疾病食养资料会挤占完整烹饪文档。修复检索并正式发布后，普通合成账号的真实输入已能读取档案和菜谱、完成一次保存工具，但模型随后继续检索和调用保存，最终达到图循环上限。Preview 已写入不等于日计划已发布；该次 Run 失败、没有最终输出消息，今日餐单仍为 version 0、空餐次。

追加保存收尾并发布 `42f9ae5` 后，新的真实请求在保存前失败：30 次并行检索调用的参数为空、缺少必需的 `query`；随后四次有效检索均返回候选，但此前重试已耗尽流程步数。这次没有读取或保存回执，不能据此判定保存后收尾再次失效。

显式串行参数的 `f77c981` 正式发布后，普通账号的新请求仍因循环上限失败：15 次检索和 6 次读取均缺少必填参数，四次检索及一次原文读取成功，没有保存。运行清单确认了配餐 Agent、有序的四个 reference 工具和 OpenAI 兼容模型；当前供应商配置没有覆盖工具或流式控制字段。审计中仍有三个空参数调用的批次，但没有实际出站载荷或原始响应分片，不能据此确认参数未透传、供应商忽略参数或本地解析丢失。

`2ffb23e` 的真实请求能够完成回复并读出所选档案限制，但仍没有保存餐单：六次有效检索、一次原文读取完成，另六次检索因空参数缺少 `query` 失败。只读核对同一固定库，确认其中另有 54 份已索引的 NHLBI 家常烹饪参考文档；现有两个文件名前缀将这些文档全部排除。它们有受控中英标题及原始英文食材、步骤，不能把当前中文检索没有命中等同于知识库不存在完整做法，也不能据此声称空参数问题已全部解决。

## 提案

### 实现方案

已发布的检索服务保留成员授权、固定知识库和当前 Run 回执，先查完整烹饪与 USDA 家庭菜谱标题，再用同类文档正文补充。每文件仅返回首个实际命中分片，最多四项；没有普通菜谱命中时使用既有家庭知识库关键词检索 Owner。模型按明确偏好选择实际原文，保存仍逐字核验菜名、食材和步骤。

本次追加的收尾修改只作用于 reference 模式。配餐中间件在带当前服务器 request_id 的最新 HumanMessage 之后查找唯一成功保存回执，并通过原 `planner_final_result` 重验当前 Run、完成工具审计、成员权限、选择和菜谱来源。确认后仍调用一次真实模型，但关闭工具入口，只完成最终回复。随后保留真实模型消息 ID、用量和审计身份，沿用原权威快照装配和发布事务，不合成 AIMessage，不把旧 tool-call 消息改成最终答案。

失败保存不形成候选；相同 Preview 可归一，多个不同 Preview 明确拒绝。旧请求、旧轮次或其他模式不触发收尾；缺少完成审计、来源失效或最终模型仍返回工具调用时失败关闭。没有成功保存回执时维持原配餐或具体补充问题路径。服务不新增数据库、依赖或配置，不修改营养计算、专业状态、权限、循环上限与发布 Owner。代码完成不代表真实双轮验收通过，状态继续保留 proposed。

当前局部兼容方案仅在生产 `ChatCompletionsAdapter` 的 reference 准备分支为模型创建浅副本，启用默认关闭且不外发的 `complete_tool_responses`，并在保留原模型设置的基础上显式传入 `parallel_tool_calls=False`。适配器有工具时接收一次完整 HTTP 响应，将其中真实消息、工具参数、用量与完成元数据转换为标准模型分片，再沿原 v3 生命周期进入 ToolNode 和审计服务。原模型实例及其他模式保持原行为，保存后的无工具最终模型调用继续使用原流式请求；普通 `ChatOpenAI` 实例也不获得这个内部适配行为。业务数据仍只来自原工具和服务，完整参数也必须通过原来源、成员权限及保存校验。该方案不把尚未定位的流式因果当成事实，真实供应商两轮验证仍是完成条件。

适配器转换不设置末片标志，保留原 SDK 的工具参数完成解析。推理模型的 v1 内容视图需要附带消息中原有的非法工具记录，避免它们在转换中遗漏；原非法 ID、名称和参数保持原样，不补成合法参数。模型审计继续由原协议消费者和 repository 持久化，不新增 whole-message 审计入口或合成最终答案。

### 实际家常菜谱目录

检索方案纳入已确认存在的 `家常菜谱_` 来源，并将这类完整日常烹饪参考优先于一般烹饪匹配。`get_reference_plan_context` 在既有成员及 Run 授权通过后，从固定库读取最多 60 个已索引、非目录的真实家常标题，帮助模型从实际库存选择三餐。目录只提供查找线索；模型仍须逐项检索、打开实际原文，取得本 Run 回执后才能保存。

受控导入的中文名与分类用于检索，食材、单位和步骤保留原始英文。模型可以用原文菜名或食材继续检索，保存引文仍来自实际打开的正文，不能把自由翻译伪装为逐字原文，也不能把 NHLBI 来源名称或 `indexed` 状态当作专业批准。三餐继续按档案和实际来源合理搭配，不能用每餐一道孤立配菜、省略主食或蔬菜来替代正常三餐。

英文来源同时需要核对当前明确的牛肉、羊肉及牛羊肉限制与 `beef`、`veal`、`lamb`、`mutton`、`goat meat` 等原词。原完整正文限制检查保留，新增对应只做食品词汇匹配，不能将牛奶等不同食材误当作牛肉；采购边界使用相同限制事实。词汇检查不构成完整过敏原标注或专业适用性证明，成分不明仍需核实。方案不新增外部材料、改写原菜谱、推算营养或改变专业状态。

### 未核实的硬限制

档案中的过敏、忌口、不耐受和医嘱保留用户原始文字。参考配餐要求逐项完整识别这些限制；现有有限词汇不能解释的条目、组合或自由句明确进入未核实状态。原文直接出现限制词时仍拒绝冲突；未出现同语言文字不构成符合限制的证据。系统不要求用户删除限制来继续，也不临时扩写临床食物分类或把来源未审核提示代替硬校验。

当前上下文向模型说明未核实状态，保存、采购及旧 Preview 的结果读取、历史和发布通过相同业务 Owner 复验。无法核实的结果不能形成 `reference_ready` 或沿旧回执继续使用。要扩大可支持限制，必须接入可核对的受控食品词汇或批准分类及原料绑定；商城别名表或专业分类类型存在，本身不证明已有完整数据。

## 替代方案

保留标题短路或单纯增加召回数仍会读取无做法资料。放宽引文和偏好会产生无法核对的结果。提高循环上限只延后同一失败；仅修改提示词不能阻止已保存后的再次工具调用。`return_direct`、直接结束图或合成最终 AIMessage 无法单独满足当前 Run 的真实 Model 审计关联，因此复用已有无工具最终模型调用模式，不另建发布通道。

标准 SDK 流式分片在独立内存 HTTP、真实 SDK 和 create_agent 路径中能保留完整参数；模拟缺失分片字段时的实际错误形态也与线上不同。因此不增加猜测式分片修补或为 `{}` 自动补词。完整工具响应会减少准备阶段的逐 token 事件，但当前配餐界面本就等待核验后的结构化餐单，保留已有处理状态即可。

直接设置 `disable_streaming="tool_calling"` 会让框架发布整条 AIMessage，而原模型审计消费者只接收协议事件，独立 SDK 实验已观察到准备阶段审计遗漏。因此保持模型流式事件入口，只在现有适配器内部获取完整工具响应，再翻译真实响应数据，避免扩展 canonical 审计输入协议。
