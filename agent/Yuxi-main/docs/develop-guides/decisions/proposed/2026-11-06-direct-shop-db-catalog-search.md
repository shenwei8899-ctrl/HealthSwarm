# 咨询商品直读商城数据库

状态：proposed
类型：feature
Owner：backend/package/yuxi/repositories/shop_catalog_repository.py

## 问题

咨询商品工具先读取当前有货分类，再按选定分类从商城接口完整分页读取商品目录并在 Agent 内筛选；目录增大时请求数和模型输入量仍随分类内目录增长。商城数据库与 Agent 数据库是不同部署，生产访问路径尚未交付，真实耗时也尚未测量。

## 提案

### 实现方案

咨询商品仍先验证本轮分类回执及最多四个已读分类，然后使用专用只读 DSN 连接商城 PostgreSQL，在 `shop_catalog_repository.py` 中参数化筛选所选分类的当前可售 SKU，单次最多返回 3 个 SKU 身份。`conversation_purchase_service.py` 通过商城现有详情接口读取本页 SKU 详情，以当前详情构造目录索引、可展示商品和签名回执；选品、历史读取和发布按当前 SKU 详情与本人档案复核。数据库中只查候选身份和已知限制的食材代码，不读取用户、订单和支付数据。未配置 DSN 时维持原路径，已配置但不可用时明确失败。

商城负责人提供私有网络、最小 SELECT 权限、索引和 Schema 变更通知；Agent 负责人负责只读查询、模型可见结果、回执复核和联调。核价、下单及支付仍由商城交易服务拥有事实。

## 替代方案

商城条件搜索接口可让商城完整封装可售规则，但需要商城接口开发。继续完整分页不需要新连接，首次查询成本随目录增长。多份 SKU 知识库需要同步和删除恢复，交易时仍需商城回源。

## 风险

Shop 生产 PostgreSQL 未对 Agent 提供访问路径和只读角色。数据库列与商城 PHP 的可售规则可能演进，双方需用真实数据对照和 Schema 变更通知保持一致。模糊匹配在大目录上依赖合适索引；没有生产测量前不宣称提速。受限档案只以能唯一解析的当前食材代码判断交易资格，未知或歧义仍拒绝。商城详情接口仍是商品说明、价格与配料的正式解释边界。
