# 今日安排的后台完成与真实来源接入

状态：proposed
类型：feature
Owner：backend/package/yuxi/services/daily_arrangement_service.py

## 问题

每日安排依赖页面调用继续接口完成菜单保存和采购发布；配餐与商城的身份、SKU选择和版本读取存在不一致。知识库片段、审核发布的营养数据和用户自述具有不同来源语义，不能互相替代。

## 提案

每日安排复用持久 Task 和既有 AgentRun。创建安排与 Task 在同一 PostgreSQL 事务提交，提交后发布；页面只读进度，明确重试通过 POST 提交。后台使用稳定键恢复已完成的 Agent、菜单及采购发布，失联按有限次数恢复。单餐修订保留上一份完整快照，成功后原子替换。

统一家庭入口沿用同一业务账号关联商城会员，保留既有购物车、地址、采购和订单功能。云端建档与三餐流程接入统一入口；餐次详情与采购读取已保存安排绑定的包编号及版本，禁止按当前餐次查询替代该版本。服务器发布包中的业务改动与本地未发布能力逐项合并，健康记录、上传与撤权边界继续保留。模型采用已选定的 DeepSeek-V4-Flash；处理政策未确认时保持未配置状态，不自动代表成员授予处理同意。

商城身份统一使用经服务器验证的 uid 引用；采购按同一算法分配三餐共享库存，并将实际选定SKU提交商城复核。采购详情绑定安排保存的包编号及版本。商城只允许已核验映射参与推荐，购买继续重新报价。

知识库仅提供带文件、片段、版本的真实候选及解释依据；候选导入沿用营养数据发布边界，缺少营养来源、实测规格、分类或审核资料的内容保持待处理。成员文字保留原文和归属，结构化限制经当前批准编码和程序校验后参与配餐，不将未知字段默认为明确无。

## 替代方案

页面轮询推进业务使完成依赖页面存活；自由生成营养数值或将待审核映射直接发布不能满足来源要求。独立复制模型、知识库或交易系统增加第二套业务事实。

## 后果

后台执行与来源回读增加持久任务和商城校验调用，页面离开后仍可完成同一业务请求。采购来源使用逐餐内容摘要绑定，单餐调整不使未变餐次的采购凭据失效。处理政策、批准营养资料或商品映射未就绪时保持明确不可用状态，系统不以测试数据替代正式来源。

## 风险

真实模型调用、微信登录和支付仍需各自环境验收；合成协议与数据库测试不证明这些外部服务可用。处理政策待确认时不启用真实健康资料的云端分析。来源签名密钥未配置或旧采购包没有保存来源凭据时，须区分新流程与既有交易契约，保留订单快照。

## 验收标准

验证稳定身份、实际SKU和整包共享库存、版本绑定、原安排保留、后台退出恢复及重复投递；使用隔离 PostgreSQL 和合成账号覆盖真实HTTP/Worker链路。专业资料与处理配置的启用以真实来源和责任人确认为条件，测试通过不代表生产三餐已可用。
