# 参考配餐工具缺参在下一模型节点纠错

状态：proposed
类型：bug-fix
Owner：backend/package/yuxi/agents/buildin/health_meal_planner/graph.py

## 问题

参考配餐的实际模型运行出现一批带名称但参数全为空对象的检索或读取调用。工具的必填字段验证拒绝这些调用，模型随后再次返回同类批次，最终耗尽图执行步数。完整响应传输、单调用命名探针和标准多调用回放没有重现参数清空，因此原始空参数的外部原因仍未证实。

## 提案

### 实现方案

参考配餐 middleware 在每次准备调用中明确要求一次只调用一个工具并填写全部必填参数。它仅检查当前 Human 消息的 `health_request_id` 匹配当前请求之后的最后一批模型调用；只有服务器允许且本次开放的检索、读取或保存工具全部返回空参数，并且各自真实工具反馈均为错误时，才在下一普通模型节点指定首个失败工具的名称。模型自行填写查询、来源标识和餐单，不从程序补造数据。

单个必填工具仍以空对象失败时，middleware 返回明确错误并停止继续模型调用。合法的无参数上下文工具、未知工具、旧请求、部分成功和未完成反馈保持原路径。既有来源、硬限制、授权、保存与最终发布服务继续拥有其校验；图执行上限保持不变。

纠错使用正常模型节点，第一次模型及 ToolNode 验证错误保留在图历史和现有审计中，每次外呼继续经过原有授权、执行预算与用量链。middleware 每次仅调用一次 handler，TokenUsage 的 Command 在节点间自然累计。

## 替代方案

提高递归上限无法修复重复缺参。适配器中隐藏重发会绕过正常节点观察边界。在同一 middleware 调用内连续两次 handler 并直接返回第二结果的回放实际产生三次 SDK 请求，但最终用量仅累计两次，因此不采用该方案。直接填写查询或来源标识会取代模型选择和原来源证据，也不采用。

## 验收标准

| 验收主张 | 失败面 | 语义 Owner | 直接证据 / 命令 | 负向案例 | 当前结果 |
|---|---|---|---|---|---|
| 空参数批次在下一普通节点指定一个允许工具 | 同节点隐藏重发或未限制工具名称 | 配餐 graph middleware | 真实 SDK/v3 回放及 wire、checkpoint | 旧请求、未知名称、合法上下文空参数不触发 | Not run |

| 原安全与发布边界保持 | 纠错跳过权限或服务校验 | HealthAuthorizationMiddleware、配餐 service | 授权拒绝及保存/最终结果既有回归 | 权限拒绝时无新模型请求 | Not run |

本地从当前源码 AST 加载配餐 middleware，使用真实 SDK、LangGraph v3、ToolNode、checkpoint 和未修改的 TokenUsage 默认计数器完成四个合成 HTTP 回放：正常纠错累计三次调用、15 tokens，并保留首批两个验证错误；授权 fixture 撤回后不再外呼；单个空参数调用失败即停止；命名纠错仍为空参数时停止。业务保存、最终结果与授权读取使用合成 fixture，此结果不代表真实服务、供应商或权限数据库验收。

目标测试位于 `backend/test/unit/middlewares/test_reference_meal_finalization.py`。Windows 常规 pytest 在现有 POSIX 文件系统导入处因缺少 `os.O_DIRECTORY` 而阻塞，收集零项，不能报告目标 pytest 通过。ruff 检查与格式、差异空白检查、工程 contracts 及其 63 项测试通过。完整 Linux 单元测试、真实 PostgreSQL、部署及真实两轮配餐 E2E 均为 Not run。

## 风险

命名调用只能约束工具选择，不能保证外部模型完成正确的菜谱选择。单元回放证明协议和用量边界；完整 Linux 检查、真实数据库、部署和真实两轮配餐仍需分别验收，不能由合成响应替代。
