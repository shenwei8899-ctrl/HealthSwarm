# 专属计划自动准备与分批配送

状态：proposed
类型：feature
Owner：backend/package/yuxi/services/exclusive_plan_service.py

菜单准备的前置条件由[专属菜单与采购资料分离](../implemented/2026-11-16-exclusive-menu-procurement.md)取代：菜单沿用今日餐单原谱，采购及交易资料不阻断生成与读取。本提案的配送、订单及支付部分仍为独立待验收能力，不作为菜单可用条件。

## 问题

建档后的家庭需要自动收到三档专属计划。当前生成依赖进入计划页，配送按每天一批排程，无法在结算时选择每周配送频次。

## 提案

建档确认和配餐用途授权仍从服务端档案读取。Worker 在商城计划规则生效后统一准备缺少推荐组的家庭。新建档和存量家庭共用入口，使用现有账号、家庭和计划请求的并发锁。原计划依据变化时由用户在专属计划页确认重排。

经济型、标准型和品质型各保存 21 天早餐、午餐和晚餐。专属计划复用今日餐单的餐次搭配校验，同时保留正式配方、营养校验、档位目录、用量转换和商城来源凭据。

用户选每周配送两次或三次。以首批送达日为起点，每周两次按三天和四天分组，每周三次按两天、两天和三天分组。区域或时段停运时，商城过滤受影响的首批日期。结算按批次合并需求和匹配包装，订单保存每批菜单日范围和食用日期区间。历史每日配送批次以其原有日期回读。

## 替代方案

页面打开时发起任务会漏掉未访问计划页的已建档家庭。按天累加商品包装会重复计算跨天共用食材。按周频次自动顺延停运批次需要重新定义食用日期和覆盖范围。

## 验收标准

| 验收主张 | 失败面 | 语义 Owner | 直接证据 / 命令 | 负向案例 | 当前结果 |
|---|---|---|---|---|---|
| 已授权家庭首次自动生成，已建档家庭补跑 | 重复生成或错误使用授权 | exclusive_plan_service 与 Worker | 后端 backfill 单测与独立 PostgreSQL 联调 | 无生效规则、撤权、并发调用 | Not run |
| 两种配送频次覆盖每个菜单日 | 批次缺天或重叠 | PlanScheduleService 与 CheckoutService | php tests/unit/PlanDeliveryFrequencyTest.php | 停运日期和无效频次 | Passed |
| 订单按购买时的批次范围报价、履约和退款 | 包装重复、金额或批次被改写 | CheckoutService 与 PlanChangeService | 商城 PostgreSQL 和支付联调 | 报价后库存变化、修改频次、暂停后恢复 | Not run |

## 风险

正式启用需要生效的商城规则与可履约商品。正式菜谱和商品必须覆盖三个档位以及两种实际配送频次。PostgreSQL、Worker 和真实支付链路需单独验收。
