# 独立可交付的记餐、指标回顾与导入工作流

状态：implemented

类型：feature

Owner：backend/package/yuxi/services/health_meal_recording_service.py

## 问题

范围为 TODO 10.3 客户端、10.2、10.1 明确克数、06.1.4 结构化回顾、11.4 导入准备及 QA.1 的工程子阶段，生产和专业闭环未完成。

用户目标是完成不依赖真实模型、微信、域名和专业资料交付的工程能力。已完成的饮食更正事务和计算器复用，不再实现第二套营养计算。

## 决策

- 正式 App 在 API 模式读取授权成员及服务端日记，提供同 ID 更正；版本冲突重新读取，未知响应保留原请求，账号切换清除私有视图。草稿和旧分析不作为新结果展示。
- 新增人工记餐事务复用 VisionDraft、NutritionCalculation、VisionConfirmation、DietLog。按账号、成员、请求键幂等；计算、确认和记录同事务。菜谱选择必须引用已发布版本，保存后聊聊只导航，不再次记餐。
- 家庭桌菜按用户明确填写的每人实际克数一次提交，每人成为独立事务，允许部分成功，未吃成员省略。批次 UUID 与成员组成稳定请求身份；失败仅重试原项，已成功项不可改参重放。暂不换算未审核的“半碗/少量”，不把计划当实际摄入。
- 指标回顾接受北京时间日期闭区间（最多 366 天）和可选记录 ID/版本，服务端固定成员、类型和范围。原值保留，统计按血糖条件分组、血压成对、血脂同条四项。空数据、截断、缺资料问题、审核解释分别返回。模型接入保持关闭。
- 管理端批量导入只持久化候选和逐行异常、重复/冲突、待补审核资料清单，不写入正式食品/菜谱表，不自动发布。已发布数据继续走既有审核发布入口。

## 替代方案

沿用前端串行创建草稿、计算和确认会留下中间失败状态；选择后端一个事务复用既有对象。家庭整单回滚与用户允许部分成功的决定不符，采用逐人事务。自动把未审候选发布到食品表会扩大其正式用途，候选单独持久化。

## 后果

健康 Schema 26 需要同步升级 API 与 Worker。正式 App 保存结果未知时在当前页原样重试；页面退出会清除私有输入。后台导入准备只支持 JSON，分权审批及批量发布继续由原 TODO 11.4 跟踪。完整后台启动、生产、微信、专业资料和真实模型仍有独立验收范围。

真实 HTTP/PostgreSQL 覆盖幂等并发、部分成功、权限、版本与来源失效，入口为 `backend/test/integration/services/test_health_independent_workflows_http.py` 与更正测试。App 单元测试验证未知响应、账号切换、固定记录版本及创建线程重试；H5 浏览器完成实际保存并由独立 PG 会话核验。后台组件在隔离页面调用真实 API 验证三类指标和候选导入，未代替完整后台启动验收。设计 Word/计划 Excel 同步实际证据，不把模型质量、专业签认、微信真机标为完成。
