# 当前餐单按单道菜替换

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/daily_dish_swap_service.py

## 问题

聊天重排整餐会连带改变用户未选择的菜。每个有合格候选的菜品展示“换一换”，最多展示三张候选卡；用户选择后仅替换原位置。卡片展示名称、原谱或既有封面、主要食材、已有标签与制作时间；缺失展示资料保留待补充状态，不编造。

候选不检查营养结构和热量相似性，缺少这些字段仍可推荐。先沿用现有成员授权与硬限制核对，再按可识别的烹饪菜品类型匹配，以商品覆盖、口味、明确制作时间和价格排序。无法核对的限制或类型不提供候选。正式审核配餐不降级为未审核参考菜。

## 决策

### 实现方案

候选按家庭、日期、版本、餐次和原菜绑定；确认时重新计算合格候选。事务复用家庭日期锁和版本号。新菜使用服务器保存的原文来源快照，原菜来源作为授权锚点；读取重验来源哈希、原成员授权和限制。其余菜保持各自来源与顺序，不调用整餐生成。幂等回执随当前每日计划持久保存，采购继续走现有按菜范围重新装配接口，订单快照不修改。

界面不询问换菜理由，不自动写偏好。无候选隐藏入口；请求失败显示刷新提示，不把失败当作无候选。历史聊天与过期计划不提供换菜写入。

## 替代方案

未采用整餐重新生成，也不伪造 AgentRun 的参考餐单回执。复用当前计划 JSON 来源避免额外的候选存储和数据库迁移；代价是保留少量每日幂等回执和授权锚点。当前限制词库不能验证所有自由文本医嘱，相关菜品保持无入口。

跨模块整合的实际检查和未执行范围见[源码整合决定](../proposed/2026-11-16-reviewed-source-integration.md)。此处的 HTTP 用例通过真实数据库回读证明事务行为，不替代独立 Worker、真实模型或真机验收。

## 后果

当前有限硬限制词库不能完整验证所有过敏和医嘱；无法核对时不提供入口。菜名不能识别类型时同样不猜测。原谱图片、时间和标签缺失时不补造。

正式审核菜谱不通过此入口替换成未审核参考菜。当前菜品类型由菜名及荤食材词汇识别，不构成完整菜品分类体系。价格使用可购商品的最低在售规格价格作为排序参考，不声称整道菜的精确成本。原文与索引分片不一致的候选被排除，不阻断其余有效候选。没有新增偏好记忆或数据库表。
