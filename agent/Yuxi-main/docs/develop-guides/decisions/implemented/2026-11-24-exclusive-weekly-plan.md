# 专属周计划与分趟采购建议

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/exclusive_plan_service.py

## 问题

专属参考计划按21天逐日生成，采购合并后失去食材使用日期。旧商城每周两次或三次配送按连续餐单天数分段，不能表达首趟包含整周耐存食材、后续只补充需要新鲜的食材。供应商尚未接入，配送费也未确定。

## 决策

新参考规则为 `exclusive-week-v1`，三档各生成连续7天。生成起点取北京时间当天，保存于既有推荐组的 `selection.plan_date`；刷新、重试、后台恢复和跨日读取沿用该起点。起点和周期进入语义摘要。用户明确重新生成时才重新选取当天，不新增日期选择器。

沿用推荐组、逐日检查点、Durable Task lease、权限与来源复核。新计划按1至7天验证，三档进度共21个生成日。旧参考组返回重新准备提示，旧后台参考任务收敛为stale；旧快照和历史正式商城订单不裁剪。原来允许1至21天的数据库约束保持不变。

采购先保存每项原谱食材的使用日、餐次、食谱来源和可解析克重，再生成整周汇总与配送建议。明确用量仍是原谱参考，不能宣称已核定家庭用量。建议按已确认保存窗口分配食材，并合并同一天的配送；保存周期可覆盖整周的食材放入第一趟。每项已分配需求只出现一次，未匹配食材需自行准备。用量不明仍采用原有可手调初始包装数；缺储存规则时沿用旧默认按使用日安排，不阻断采购，也不填写未经确认的保存天数。

同一食材在本周各趟分别按包装取整，已知商品小计从分趟商品相加，跨趟合计库存另行检查。配送费和最终应付金额保持null。配送建议本身不创建订单或预约。商品选择、包装数量调整、来源回验及真实报价沿用原CloudMealPurchase和商品包发布流程，不因缺储存规则新增拦截。

## 储存规则输入

[配送建议服务](../../../../backend/package/yuxi/services/exclusive_delivery_suggestions.py)消费商品目录中 `storage_rule` 的一致规则。同一食材相关商品缺少规则或规则不一致时，不猜测保鲜期，配送建议沿用原默认按使用日安排。规则须包含：

- `review_status: approved`
- 正整数 `max_days`
- `condition: ambient | refrigerated | frozen`
- 非空来源 `source` 和版本 `version`

`optional_exclusive_catalog`通过既有目录获取路径提取规则。规则变更须遵循商品目录版本更新契约。没有已确认供应商储存资料不阻断商品选择和包装数量调整；测试中的规则和配送趟次均是合成数据，不作为正式食材储存建议。未来供应商接入负责规则真实性、商品状态、送达时间和费用报价。

## 后果

按天浏览依赖来源校验回执表，健康域版本为41，由既有迁移入口幂等创建。参考菜单发布继续执行整周连续性与重复校验，浏览仅核对当日原谱与当前授权。

## 替代方案

只修改前端文案仍会生成21天并无法读取新目录。只采用旧商城weekly_2或weekly_3会把耐存食材重复分入各个餐单批次。商品采购继续复用原购物车流程，配送建议与未定配送费独立展示。因此本次保留旧订单排期，通过健康业务层生成独立建议，不改造旧履约记录，不新增储存规则缺失拦截。

## 验证

相关单元覆盖整周与分趟包装差异、缺规则、未知数量、跨趟库存、来源版本变化及恢复原商品包发布。真实TCP/PostgreSQL集成覆盖任务中断恢复、三档完整7天、跨日读取、旧记录不变、权限隔离及按天来源失效。浏览器在320/390/430宽度检查7天目录、周采购、分趟清单和待定费用。

本地验证不代表真实供应商、真实模型质量或微信真机验收。此决定描述源码行为，线上API、Worker及小程序须同步更新后才能使用新协议。
