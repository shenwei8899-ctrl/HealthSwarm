# 健康主流程提交恢复、换菜记忆与数据库版本收敛

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/daily_dish_swap_service.py

## 问题

微信单项缓存容量小于允许提交的图片大小，缓存异常会使未发送的请求进入待确认状态。API 模式下拍照页提前读取空成员列表；商城页动态导入在小程序编译后不能生成请求标识。换菜仅使用档案限制，遗漏账号记忆中的明确忌口；两个历史数据库分支共同使用版本 38，单看版本号不能保证结构完整。

## 决策

### 实现方案

前端提交 Owner 在发送前按 256 KiB 缓存图片，并在收据中保存账号作用域内的分片键。缓存或收据写入失败时恢复提交前状态；未发送的请求允许重新提交。结果不明时恢复原请求标识和完整图片；分片缺失时只核对原请求，避免以不完整图片重发。拍照页容忍空成员列表，API 模式跳过演示初始化。商城页静态导入轻量请求标识模块。

换菜 service 与配餐共用当前账号、当前家庭和本餐参与者的有效记忆查询。明确 restriction 同时进入食材过滤及候选来源指纹；提交时重算，回读时核对当前版本及限制。repository 强制刷新会话内已加载事实，避免使用过期 ORM 对象。

数据库迁移 Owner 把健康版本提升为 40，并幂等执行共享餐单、账号记忆、菜谱展示和用餐归档结构补齐。历史 38 的两类结构和版本 39 均执行完整收敛链；版本仅在全部成功后记录。

## 替代方案

缩小图片提交上限会拒绝现有允许的输入；只捕获异常仍不能恢复完整图片。单纯提高历史分支的版本号不能修复已经标记 38 的数据库。把忌口交给前端或生成提示词无法约束后端换菜入口。当前方案在各行为的现有 Owner 内修复这些边界。

## 后果

图片恢复增加多个小缓存项，并在结果确认后清理。记忆限制发生变化会使旧候选及不再适用的已保存替换菜失效，调用方需刷新。数据库升级采用增量补齐，不删除业务记录。代码合并和本地构建不会自动完成生产发布。

## 验证

前端完整测试 1767 项通过，覆盖超 1 MB 图片、缓存失败、收据失败、结果不明后的原请求恢复、API 空档案拍照页和首次修改就餐人数。H5、微信小程序及 API 模式小程序构建成功。

后端定向测试 178 项与 6 个 subtests 通过。独立 PostgreSQL 中 6 项测试覆盖无版本历史结构、37、两种历史 38、39 的重复升级与业务数据保留，以及账号、家庭、参与者和撤销记忆的隔离。验证连接使用隔离容器和合成数据。

未验证生产数据库升级、真实设备交互、真实模型调用及生产 HTTP 全链路。修复源码和本地包具备回归证据，线上生效仍取决于对应部署与发布验收。
