# 参考餐单剔除未对应菜谱的模型选品

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/reference_meal_selection_service.py

## 问题

模型在换菜后可能把已读目录里与所选菜谱无关的商品一并提交。即使其余商品覆盖了所选菜品，原装配器也因多余规格触发 `reference_ingredient_mismatch`，一次模型纠错再次提交相同商品时整条请求失败。线上失败 Run 的两次保存均含五个规格，其中两个未对应原谱食材，其余三个覆盖全部所选菜品。

## 决策

### 实现方案

仅在 `read_selection` 装配路径中，服务端按本 Run 已打开的原谱与已读商品重新计算食材匹配。未被选为匹配结果的规格，只有商品食材身份可识别且与全部可识别原谱食材均不同，才作为无关模型附带项剔除；同类重复规格、零库存或商品身份无法识别时仍明确拒绝。保留匹配规格的原包装数量，并按原谱逐项生成 `needs_confirmation`、`no_match`、烹饪用水等真实缺口。已知有匹配规格但模型漏选时仍拒绝；全部选品无效时返回 `reference_product_required`。最终 `save_reference_plan` 继续核对来源、当前商品事实、库存、成员限制和每道菜的商品覆盖。完整草稿直接保存路径及其有限纠错机制不变。

## 替代方案

只依赖一次模型纠错已在真实请求中失败。把不匹配商品强行归为菜谱食材会生成错误采购关系。扩大模型重试次数增加时延和费用，也不保证模型修正。当前方案仅删除与当前原谱无关的模型附带项，不新增商品或食材关系。

## 后果

用户换菜时，模型多选的无关商品不会单独导致整份参考餐单失败，也不会变成采购建议；来源不明、加工形态未证实和缺少商品的食材继续以真实缺口或明确失败呈现。参考餐单不支持额外购物清单，未来若增加该需求，需要独立用途和确认流程。失败 Run 不自动重跑。

## 验证

定向 `test_reference_meal_selection.py`、`test_reference_meal_completion.py`、`test_reference_meal_finalization.py` 共 130 项通过，覆盖多余规格剔除、同一食材多有效规格与零库存同类规格仍拒绝、无法识别的商品不能擅自剔除、已知必需商品漏选仍拒绝、全部选品无效仍拒绝、ToolNode 装配真实缺口与保存收敛。线上失败 Run 的原有两次选择以只读方式回放新装配逻辑，均只保留三个匹配规格，全部所选菜品各有匹配项；未写入生产餐单。真实模型端到端请求和最终持久化结果须在部署后另行核对。
