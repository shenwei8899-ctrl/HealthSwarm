# 已确认饮食记录分页

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_vision_service.py

## 问题

饮食记录只提供最近100条数组；后台无法继续查看历史记录。既有饮食分析消费者仍使用此数组，不能直接改变其返回结构。

## 决策

### 实现方案

认证GET `/api/health/v1/members/{member_id}/diet-logs/page`接收limit（默认20，1至50）和offset（默认0，0至2147483647），返回records和next_offset。路由与DietLogPage拥有协议，HealthVisionRepository按成员、确认入库时间降序及ID升序读取limit+1条，HealthVisionService每次检查当前diet_edit授权并复用源草稿/图片有效性检查。记录是成员事实，不按写入账号二次隔离；管理员同样需要授权。接口不写业务数据。原最近100条数组接口保留。

next_offset指向下一批已确认入库记录；失效来源被过滤，因此空页仍可能有next_offset，消费者使用服务端位置继续，不能按可见条数推算。成功响应和资源不可见错误均禁止缓存，非法参数返回422。详细协议见[分页参考](../../../advanced/health-diet-log-pagination.md)。

后台已确认记录入口使用独立HealthDietRecords组件，保留单餐反馈/咨询入口。组件切换成员、撤回授权、卸载或重新请求时丢弃迟到响应，翻页前清空旧页数据，提供加载、空页、错误和重试。组件刷新由用户显式触发，父页OCR轮询不会重置当前分页或正在填写的反馈。饮食分析仍沿用现有最近100条来源。

## 替代方案

改原数组为对象会破坏当前分析消费者；响应头分页需要额外跨域暴露约定，字段也无法直接在OpenAPI响应模型中发现。数据库快照游标和总数查询超出当前浏览历史的需求。

## 后果

offset分页不是跨请求一致快照；期间新增记录可能使页边界变化，刷新回到第一页。不提供总页数，空中间页仍可继续。源有效性仍由已有业务边界拥有，分页不改变营养计算或专业适用性判断。普通读取不创建Run，不调用模型。OCR任务/草稿列表分页和正式小程序真端接入仍未完成。

## 验证

2026-10-11，真实TCP/PostgreSQL integration 3项通过且零跳过。121条预先确定顺序的合成记录覆盖旧100条上限、同时间ID排序、默认参数、末页和越界参数；覆盖其他成员、管理员撤权、来源图片由有效转删除及空中间页继续。27次GET前后全schema行及xmin一致，3个独立schema清理后回读确认。

后端定向unit 5项通过；恢复缺失授权、lookahead、来源过滤、offset和ID排序的5项负控均在目标oracle失败。后端完整unit 4407项通过、59项跳过；前端最终定向7项和完整unit 852项通过，lint/build通过。命令由[测试规范](../../testing-guidelines.md#饮食记录分页验证)维护。

隔离的实际后台使用41条持久化合成记录验证20/20/1三页、上一页、刷新、空成员、撤权后清空与恢复后重试、反馈弹窗，以及浅色、深色和671 CSS像素单列布局。浏览器夹具未提交反馈或创建Run，饮食事实回读未改变；账号、成员和记录清理后数量均为0。合成查询快照不代表营养计算、真实模型或专业医学质量验收。
