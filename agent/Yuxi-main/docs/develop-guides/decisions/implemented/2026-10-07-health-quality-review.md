# 版本化依赖下的独立质量检查与专业审核

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_quality_service.py

## 问题

六Agent工程目标要求独立质量检查与专业审核。现有三餐草稿只有营养计算和未就绪说明，无法绑定正式档案及批准规则，也缺少提交、退回、批准和失效状态。读者为健康业务及外部档案、规则联调维护者；本阶段以现有保存餐单为真实消费者，家庭及21天对象随其业务阶段接入，六Agent目标保持完整。

## 决策

AI边界接收健康档案服务的不可变已确认版本和专业内容方的不可变批准规则投影，保留来源、确认或审核凭据、有效期与内容摘要；不实现外部建档流程、不从用户记忆推断正式字段。新版本按同一来源递增，撤回后不能复活。未交付、未知字段、过期或哈希不符明确返回未就绪或未知。管理投影写入必须通过服务器管理员及相应成员权限，模型不具备写入工具。完整档案负责人及真实生产内容继续外部TODO。

确定性检查从当前餐单版本重新加载发布菜谱和食品，复算五项营养。批准规则提供适用人群及年龄范围、已支持疾病组合、完整配料分类、医嘱限制及每日范围；代码不硬编码临床阈值，一般范围与同时生效的医嘱共同求交集，不默认医嘱覆盖一般限制。过敏、不耐受、忌口、医嘱分别区分未知、明确无及有明确条目。缺字段、空配料或配料归类不能标通过；已知冲突与未知分别记录。检查绑定餐单指纹、每位参与者档案版本、规则版本和执行来源，工程检查通过与专业批准保持不同字段。

专业审核在PG业务事务中完成，保存提交人、独立资格登记的审核人、时间、理由和证据。状态为待提交、待审核、退回补资料、审核通过和失效；同键异参数拒绝，版本前置条件防止覆盖。审核人员须有当前有效专业资格及明确成员审核授权，不能自审；管理员身份不自动获得专业批准权。批准须当前工程检查通过且依赖版本仍有效。规则、档案、对象变化、撤回或过期使旧结论失效，使用入口重新校验，不继承上一版本批准。长期待审核不占worker。

升版使使用旧来源的流程失效，撤回最高档案或规则版本不回退到历史版本；撤回历史档案/规则版本不影响依照当前新版重新检查后的批准。资格撤回按批准所用资格版本失效，不波及其他版本的批准。

独立health-quality Agent由用户显式选择餐单版本和规则后创建不可变会话，只开放读取选定检查上下文与运行服务器检查两个工具，按quality_review用途单独审批与同意。模型最终只选择本Run检查收据或提出补充问题，不传营养、身份或批准标记。每次外发、历史、checkpoint及发布事务重新验证当前依赖和执行所有权，原始模型正文不直接发布。Checkpoint内历史收据核对同账号、同质量角色及同会话的原始Run，最终选择仍限当前Run。审核在成员锁后刷新当前状态；撤回审核或档案读取授权永久使对应已批准记录失效，恢复授权须重新检查和申请。

质量模式的有限LangGraph节点预算为40，允许授权、计量、上下文读取、检查及最终投影在正常工具链内完成。普通分析、咨询和配餐仍使用20；预算不扩大资源白名单或批准权限。失败Run可以保存属于自身的空正文错误诊断消息及指针；该消息带is_error，不能成为安全检查或专业批准结果。

## 替代方案

仅要求模型判断安全缺乏确定性Owner，也无法证明外部版本和专业决定。复用通用科普知识不能表达个体限制、疾病组合和已批准范围。AI侧重建完整档案或支付服务会越过既定责任；版本投影和现有PG用例保留外部事实Owner并允许隔离合成工程验证。

## 后果

本阶段验证现有保存三餐对象，完整家庭参与者、控糖计划及采购商品安全随其消费者扩展。专业凭据登记和外部投影由受信管理操作提供，真实资格核验、规则生产和完整档案交付仍由外部负责。隔离合成资料不能进入生产或被记为专业质量验收。每阶段同步本地Word与Excel，当前角色与六Agent目标只有全部范围验证后才能标完成。
