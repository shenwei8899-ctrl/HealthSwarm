# 参考餐单译文修正与批量菜谱读取

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/agents/toolkits/meal_planner.py

## 问题

参考餐单生成需要多轮菜谱检索与原文读取。译文校验失败后，模型重新提交整份餐单可能改变首次选择的菜谱和餐次，导致用户明确选择与保存稿不一致；页面在等待时也无法区分查找、核对和保存阶段。

## 决策

### 实现方案

`search_reference_recipes` 一次接受至多四个关键词，只读取一次固定库候选行，逐词排序后按来源去重并最多返回九份；`read_reference_recipe` 一次接受至多三个来源，逐份执行原有的本 Run 来源与权限校验。批量读取的持久工具回执在 `reference_meal_plan_service.tool_payloads` 展开，恢复和保存时仍逐份重验原文。

`save_reference_meal_plan` 首次完整选择因中文译文失败后，从当前请求已校验的工具调用恢复首次选择，仅接受包含菜谱来源和 `display_zh` 的修正。`reference_meal_selection_service` 同时支持已读原谱选择和完整原文稿，合并译文且保留原餐次、菜谱和采购选择；原有一次修正预算与最终保存校验继续生效。`health_answer_stream` 根据真实工具生命周期投影固定进度阶段，前端仅显示固定中文标签。修正失败只公开固定错误文案。

## 替代方案

继续让模型重新生成整份保存稿，实现较少，但会再次允许餐次、菜谱或采购选择漂移。把菜谱索引直接拼入 prompt 可减少调用，但会增加模型上下文与来源核对成本。当前选择保留原有查询和保存边界，仅合并网络往返与模型调用轮次。

## 后果

批量搜索一次最多返回九个去重候选。译文修正需要首次保存调用和错误回执仍在当前 Run 的消息状态中；无法核对时明确失败，不改写餐单。实际耗时仍受模型生成速度、菜谱命中情况和外部服务影响。

## 验证

工具输入与译文合并使用 unit 覆盖单项、批量、重复来源、越权修正和保留完整餐次；真实 PostgreSQL integration 覆盖批量查询与读取回执展开；前后端进度投影使用固定标签测试。部署后以同类型三餐请求记录模型轮次、菜谱查询次数、首字与完成时间，并核对保存结果的三个餐次和来源。
