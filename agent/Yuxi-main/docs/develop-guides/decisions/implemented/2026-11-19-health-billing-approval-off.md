# 健康 AI 默认关闭计费审批

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_ai_budget_service.py

## 问题

计费审批和账本状态会拦住健康任务。用户要求取消所有健康功能的计费审批，截图中的今日餐单也曾遇到该报错。

## 决策

API 和 Worker 默认使用 `HEALTH_AI_BUDGET_MODE=off`。健康任务就绪检查和实际外呼在此模式下跳过价格、期初和月账本检查。模型与 OCR 凭据、处理方审批、成员授权、用途同意、任务限流、单次输出上限和 OCR 任务检查点继续由原服务维护。历史账本保留，供应商实际额度和用量仍由供应商计算。

## 替代方案

逐项增加例外会让新功能重新遇到审批。旧参考模式覆盖部分文本用途，同时写入月账本冻结标记。统一关闭应用内审批即可覆盖这些路径，旧模式保留显式兼容入口。

## 验证

| 验收主张 | 失败面 | 语义 Owner | 直接证据 / 命令 | 负向案例 | 当前结果 |
| --- | --- | --- | --- | --- | --- |
| 所有健康用途无审批也可外呼 | 缺价、价格过期或冻结账本导致就绪或实际调用被阻止 | 健康预算服务 | 129 项定向单测、32 项独立 PostgreSQL 测试及线上配置检查 | 无效模型或缺少 PaddleOCR 凭据仍拒绝 | Passed |
| 今日餐单可以生成 | 已通过就绪但 Worker 仍报计费审批 | 今日餐单 API、Worker | 合成家庭完成早餐，接口和 PostgreSQL 均读回餐单版本 1 | 未知成员请求返回 404 | Passed |

线上 API 和 Worker 均为 `off` 且通过健康检查。合成早餐和普通咨询均由 Worker 完成并保存，未产生计费预留。血糖、血脂和血压入口均显示可用。合成报告由 PaddleOCR 和 DeepSeek 提取两个指标，合成餐照由 DeepSeek 生成待确认候选，两条链路均保留用量并在缺少用途同意时返回 403。已清理合成账号和数据。四项小程序失败重试测试通过，另有一项微信编译交互测试因本地缺少 `picocolors` 无法运行。微信真机未测试。

## 后果

应用内的历史费用金额只覆盖已登记调用。实际费用和可用额度以模型供应商和 PaddleOCR 为准。若同一计费月明确切回旧严格模式，须先核对该月供应商账单与已有余额。
