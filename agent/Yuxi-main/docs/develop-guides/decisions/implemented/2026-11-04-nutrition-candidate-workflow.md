# 营养资料候选的来源路由与审核准备

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/health_knowledge_import_service.py

## 问题

知识库正文与正式营养目录属于不同持久化边界。候选整理始终检索家庭科普库，未使用已配置的菜谱库；候选报告缺少复用和恢复入口，用户需要重新录入资料。准备状态只有目录总数和布尔结果，不能区分历史规则、指定规则及未发布候选。资料数量不能证明专业批准或多日计划可用。

## 决策

### 实现方案

知识提取按食品或菜谱选择既有受控来源范围，并以相同范围重验资料，来源绑定、文件或分片变化时拒绝保存。食品保持现有家庭库；菜谱使用配餐角色已绑定的菜谱库。输入不允许任意扩展知识库权限。

候选及逐项证据使用任务已有 lease 事务一起提交。最终来源重验失败时，候选写入一起回滚；管理员手工导入沿用相同校验与幂等逻辑。

后台候选界面支持按批次 ID 重新读取原报告、查看并带入候选 JSON 进行修正和重新校验；这些操作不调用正式发布接口，也不将文件名或模型生成许可变成专业签发。冻结请求的类型和主题保持一致，账号变化后的迟到响应不得回填。

准备状态保留既有计数字段，增加当前规则的明确原因与候选统计，并分别报告科普库、菜谱库绑定。规则来源完整性、撤回和有效期仍由既有规则服务核对。正式规则、食品或菜谱不会通过本次资料整理自动发布。专业签发材料缺失时保留待审，21 天计划继续使用既有业务门禁。

## 替代方案

继续增加知识库文件无法修复错误来源路由和候选复用缺口。自动填入正式发布表单并替用户确认专业批准会越过现有专业内容边界。直接把所有草稿计为正式记录会使就绪统计失真。

## 后果

专业审核人的身份、资格和外部批准文件继续由正式发布链路核验。候选恢复与修正保留资料准备能力，正式个体化计划仍依赖获批规则、食品和菜谱。候选统计按管理员隔离，跨批次重复记录会重复计数，界面明确说明其含义。
