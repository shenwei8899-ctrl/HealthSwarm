# 专属计划从完整原谱生成可保存内容

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/exclusive_reference_plan.py

## 问题

知识库分片可在句中断开。检索索引以换行拼接分片后会把一条步骤拆成两条，首日菜单保存与完整原文比较失败，重试沿用同一候选而重复失败。

## 决策

### 实现方案

检索索引继续负责选菜。新生成日菜单在保存前通过已有 recipe_document 读取摘要校验后的完整原文，确认来源版本未变，再从完整原文提取名称、食材、步骤，执行现有严格来源、限制、组合校验并按原谱重算采购。已保存菜单继续严格验证，不自动改写其内容。

权限、任务所有权、事务提交和发布状态保持既有服务负责。完整原文不可读取或来源变化时明确失败。

## 替代方案

修改分片拼接符无法判断断句边界；关闭步骤校验会放行篡改；修改知识库内容会改变原始来源。采用已校验的完整原文作为新菜单内容来源。

|---|---|---|---|---|---|
| 句中断开的分片不会改变最终步骤 | 分片解析与原文解析不一致 | exclusive_reference_plan.py | 单元测试、真实PG及HTTP任务测试 | 旧实现保存分片步骤失败 | Passed |

## 后果

选中原谱的对象读取与解析发生在保存事务中；复用验证缓存避免同日重复读取。采购结果必须以完整原谱重算，不能残留分片断句造成的错误用量。

生产重试另确认约2700份原谱与601商品的费用排序每天重复计算，导致单日约180秒并可能超过任务时限。费用计算结果只在同一次任务、固定商品快照内按文件及分片摘要复用；候选来源变化重新计算，新任务重新建立缓存。每日权限、来源、已保存菜单校验和采购重算仍按既有路径执行。

定向单元30项、真实TCP/独立PostgreSQL三档63天与断点恢复测试通过。Ruff限定检查和工程契约检查通过。扩大参考餐单测试69项通过、2项旧mock失败，在现用基线同样复现；本修复不改相关接口。工程契约测试在Windows遇到符号链接权限限制，随后在Linux候选镜像63项全部通过。

加入任务内费用复用后，精确最终镜像定向单元31项和三档63天真实HTTP/独立PostgreSQL集成测试通过；Ruff与工程契约检查再次通过。生产原失败组通过既有Worker检查点恢复后达到ready，三档各21天；服务层回读和真实认证HTTP摘要及三档详情均通过，佛跳墙为完整原文的7条步骤。已核验服务端，未执行小程序真机界面验收。
