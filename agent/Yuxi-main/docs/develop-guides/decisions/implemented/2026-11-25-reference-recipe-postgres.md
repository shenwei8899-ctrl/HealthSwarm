# 日常参考餐单接入 PostgreSQL 菜谱目录

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/reference_meal_plan_service.py

## 问题

知识库新增文件与 PostgreSQL 参考目录是两个独立数据源。家庭参考餐单需要从实际存在的菜谱生成，并在选菜前看到商城覆盖情况，同时保存本次人数对应的烹饪建议。

## 决策

### 实现方案

- `HEALTH_REFERENCE_RECIPE_SOURCE=postgres` 只给新建日常参考餐单绑定 PostgreSQL；默认 `knowledge`。新入口读取 `recipe_catalog.recipes` 与 `recipe_catalog.reference_recipe_ingredient`，核对排序后的食材行与原菜谱一致，沿用检索回执、同 Run 读取选项、保存及发布校验。已有知识库绑定保留原数据路径，数据库未就绪时报错。
- 搜索选菜时使用当前有库存的规格计算覆盖率。必须从商城买齐时，检索排除缺货或匹配不明的必需食材，保存按实际匹配及库存再核对一次；允许自备时保留原采购缺口。采购规格、包装数量和订单继续使用现有商城入口。
- Agent 可提交原谱食材位置及本餐建议用量，按需要附用餐成员的分菜比例。服务端校验引用、成员和数据范围，单独保存建议，使用现有餐单份量说明展示，不改原料原文、不写营养值。
- 新餐单持久化 `recipe_id`、原文事实及经哈希核对的参考图地址。原图按内容哈希保存到既有公共菜谱图片存储，不包含成员资料。已发布餐单用该快照回显；当前成员授权与采购校验继续生效。
- 本餐已授权档案中的高血压、糖尿病、高血脂标签分别使用既有血压、血糖、血脂固定库配置，每专题最多两条资料。专题用于一般搭配参考，硬限制仍由现有服务端规则核对；范围不支持时不声称已核验。

### WebP 原图与小批试导入

菜谱目录接受 JPEG 和 WebP。图片展示从已核对的目录元数据读取 MIME，核对图片头、字节哈希和来源版本后按内容哈希冻结图像；由原知识库复用的 AI 图保留「AI 生成示意图」标签。

[图片约束迁移](../../../../backend/scripts/recipe_catalog_allow_webp.sql)属于独立菜谱目录，按实际导入环境执行。[导入脚本](../../../../backend/scripts/import_reference_recipe_catalog.py)先对照结构与图片，再读取目标库预检；显式传入 `--apply` 才在同一事务写入主表与食材表。同 ID 的一致记录跳过，冲突中止，同名不同配方保留。清单和菜谱图片留在本地任务材料。


## 替代方案

继续从知识库生成菜谱无需新增数据接入，但很难把一份已核对的食材表和原图作为稳定引用。把目录导入正式配餐表会提前要求出成率、食品营养和专业审批，超出日常参考范围。

## 后果

生产启用前要单独核对更新的知识库文档、去重、图片和目录覆盖；启用后不会把知识库增量自动同步进数据库。现有专属方案、换菜候选和正式营养计算的数据源不因这项配置切换。

## 验证

参考餐单的定向单元测试与隔离 PostgreSQL／真实 HTTP 用例分别覆盖原合同和新链路。集成使用合成商城、知识库检索和对象存储边界；真实模型、客户端与生产切换独立验收。

在与线上约束一致的隔离 PostgreSQL 中，用 1,005 道已有菜谱的文本和占位 JPEG 作对照，首次新增 15 道和 98 条食材，复跑新增 0 道，已有行未改。15 张 WebP 从本地 MinIO 经 HTTP 回读的 SHA-256 与原图一致；对照实际参考餐单 HTTP 用例覆盖 JPEG、WebP、损坏图拒绝和历史回读。尚未使用真实模型或真机验收。

本地联调使用试导目录中的两道菜、三位合成家庭成员及模拟模型选择和商城库存。通过实际 ToolNode、PostgreSQL、MinIO 和 HTTP 回读三人晚餐与今日安排，核对缺货菜未入选、原图哈希一致和建议用量分开存储。聊天摘要从已校验的餐单用量生成，现有小程序聊天能显示建议用量；菜谱详情继续显示原文用量。真实供应商调用与真机验收均未执行。

隔离环境已调用真实 `deepseek-flash`，使用当前参考配餐提示和生产中间件；商城库存与家庭仍为合成数据。一次通过场景中调用模型 6 次，输入 36,891 token（缓存命中 13,824），输出 631，从发起模型到回读 7.82 秒。模型两次检索均传入必须买齐，缺货菜未进入菜单；保存的两道菜持久回读，图片 SHA-256 和小程序客户端的用量文本校验通过。一次场景不代表线上时延、库存或真机验收。

数据库参考餐单每次运行只经一个带库存核对的批量查菜调用；缺少组合时展示已核对缺口。该路径不单独读商城分类，模型仅接收菜单、完整原谱、匹配缺口和需要选择的商品。完整回执继续供服务端重验、审计及历史回放。知识库路径沿用原来工具顺序和次数。用真实 `deepseek-flash` 同题复跑，查菜 2 次变 1 次、模型 6 次变 5 次，总 token 从 37,522 变 18,660（减少 50.3%），原图、用量、最终产物和客户端回读通过。上述是一组隔离对比，未部署。

随后通过商城签名 GET 读取真实目录和库存，配餐继续在隔离 PostgreSQL 和 MinIO 中运行。使用同一三人餐请求，15 道试点内无全购组合，9.89 秒返回缺口；扩大到本地 1,020 条目录记录后，同题在 15.24 秒完成保存与回读，核对 14 个商品的 15 个有库存规格。允许自备场景在 16.86 秒保存并回读 WebP，11 项未确认原料标为自备。将实际目录快照中的一个虾仁规格在本地置零后重跑，原菜被排除并返回替代组合。目录冷读一次版本、五页商品，用时约 6.2–6.7 秒，缓存命中约 13 毫秒。覆盖扫描中，827 道原谱可参与核对，13 道的必需食材全部匹配到有货商品。生产商城只读，未部署，未执行微信真机验收。

2026-11-26，生产菜谱表图片约束已扩展为同时接受 JPEG 和 WebP。原文哈希与 MinIO 原图逐项核对后，首次试导新增 15 道、98 条食材，生产合计 1,020 道、7,007 条食材。数据库回读核对了 15 道原谱步骤、食材原文与顺序以及 WebP 二进制 SHA-256；原有 1,005 道的记录、食材与图片指纹前后一致。重复执行新增 0 道、0 条食材，15 道原样复用。此操作未部署或重启 API／Worker，线上菜谱来源未切换。

随后只读回采生产新增的 15 道及 98 条明细到隔离环境，逐张比对图片 SHA-256 后用 DeepSeek Flash 验收三人晚餐。真实商城严格全购返回缺口，允许自备则安排肉片花菜、麻薏杏鲍菇地瓜汤并列出 11 项自备。在本地构造可买齐的目录并仅将黄油库存置零，原餐单中的波兰花菜配面包屑被替换为麻薏杏鲍菇地瓜汤。三份成功餐单均可经当天详情和历史列表／详情读取，WebP 原图可打开且与生产快照一致，当前餐单含三人份建议用量。历史详情即使商城不可用也能打开，但只保留原菜谱用量，建议用量字段未进入归档。未验收微信真机，生产未部署或切源。
