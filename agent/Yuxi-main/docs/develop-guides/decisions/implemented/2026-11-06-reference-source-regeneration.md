# 参考餐单来源失效后的有限重生成

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/reference_meal_plan_service.py

## 问题

成员资料或菜谱版本变化后，旧参考餐单与追问结果无法读取，原任务还可能占用当日餐次。相同档案反复保存也会额外递增家庭版本，使有效餐单失效。普通授权拒绝与可恢复的旧来源变化不能仅按相同错误码区分。

## 决策

`ReferencePlanSourceChanged` 只在重新核对当前成员访问、字段及配餐用途同意后，由旧资料或菜谱版本变化产生，并携带已核验的选择。每日餐单只把该类型与已有明确来源错误投影为待重生成，普通权限拒绝继续返回原状态码。

过期追问读取不修改数据库，投影不再占用餐次，后续预占仍由既有事务和当前版本控制。缺失餐次沿用原就餐成员。保存相同档案及相同设置时保留家庭版本，真正的成员关系和设置变更继续推进版本。

## 替代方案

统一吞掉 403 或 410 会掩盖撤权。客户端反复重试旧任务不能更新被冻结的来源。采用服务端有类型的失效边界和原事务内的重新预占。

## 后果

用户可以重新安排来源已失效的餐次，已有有效餐次继续保留。用途同意或成员授权撤回仍拒绝读取，旧菜谱正文不会随重生成提示返回。本变更没有数据库迁移。

## 验证

独立 Linux 容器和 PostgreSQL 的 12 项真实 HTTP 用例通过，覆盖家庭与菜谱变化、历史与当前来源、过期追问、相同档案保存、未分类错误，以及来源变化同时发生的真实授权撤回和菜谱删除。测试复用现有 `replace_source` 更新精确对象字节与 PostgreSQL，商城和对象网络采用合成边界，不代表自主模型或 Worker 全链路。
