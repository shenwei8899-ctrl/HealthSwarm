# 参考菜谱检索复用目录索引并隔离同步计算

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/reference_recipe_index.py

## 问题

菜谱检索在 Worker 事件循环中同步解析完整菜谱集，并按每条食材重复构建商品别名和商品分组。真实目录扩大后，同步计算使 Worker 心跳与任务续租无法及时执行，配餐以 `worker_lease_expired` 结束。商品工具同时返回商品层和规格层的重复详情，增加下一轮模型输入。模型抄错分类编码时，业务错误直接结束整次配餐。

## 决策

检索调用在当前授权知识库读取菜谱分片后，把纯计算交给容量为二的后台线程。数据库会话不传入线程。线程内每批检索共用一个 `ReferenceProductIndex`，预编译商城别名，建立商品身份分组并复用同一食材字符串的解析结果。索引只在单次调用中存在，后续调用仍读取当前目录，不跨账号缓存选择或授权。排名只计算所需的紧凑匹配摘要，打开原谱时继续返回完整商品及规格。

`MealPlanResultMiddleware` 只在模型输入副本中删除商品工具回执的重复 `catalog`、规格列表与图片地址。商品身份、配料、过敏原、营养原文和缺项提示完整保留；checkpoint、工具审计与服务端来源校验仍使用未压缩回执。分类编号无效转为工具错误提示，要求重新读取本轮分类并原样复制编码，后续查询仍执行原服务授权与来源验证。其他错误不转为可重试提示。

## 替代方案

延长租约会推迟发现阻塞，仍无法保证其他用户和心跳正常运行。永久缓存整个商城匹配结果会失去动态更新语义。截断营养说明或减少候选菜谱可能改变健康依据和排序；本方案保持原始来源与匹配结果，通过请求内复用减少计算。

## 后果

固定 `ThreadPoolExecutor(max_workers=2)` 允许两项同步检索并发执行，额外调用等待线程槽。已进入后台线程的计算不能强制终止；请求取消后仍占用原线程槽直到计算结束，避免原生 `task.cancel()` 提前释放限流令牌后堆积后台线程。模型供应商响应、图片生成和完整餐单保存各有独立耗时，检索基准不能替代端到端生成验收。
