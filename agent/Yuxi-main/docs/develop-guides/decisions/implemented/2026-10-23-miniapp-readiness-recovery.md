# 小程序开发测试的配置诊断与资料恢复

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/miniapp_profile_service.py

## 问题

模型未配置时建档可以保存，但不会创建健康资料关联。首页随后把缺少成员来源的业务 503 当作临时故障重复请求，并引导用户进入不能补齐用途同意的资料页面。

## 决策

### 实现方案

服务端 miniapp_profile_service 拥有资料关联和用途同意的持久化契约。仓库同级 App 中的 cloud-profile、daily-arrangement-client 和 CloudNutritionChat 分别负责配置读取、重试条件及页面恢复，不新增服务端授权写入路径。

将配置可用性随云端档案读取；首页区分服务配置未就绪和资料需要重新确认。资料恢复进入已有建档页，由用户核对档案和当前用途后保存，继续使用既有事务和同意接口，不自动授权。已认领家人的资料由该成员登录确认，家庭管理员可调整默认就餐成员。明确不可重试的业务错误不自动重试；旧服务统一返回可重试的依赖错误按已知业务码识别，网络错误和未分类服务故障继续保留恢复行为。新建和恢复生成共用配置守卫，已保存安排继续通过后端读取和校验。

开发测试使用用户提供的 DeepSeek 兼容凭据和明确标识的开发测试配置，模型能力仍由实际提供方核验。专业来源校验和成员权限保留；合成规则和菜谱只在隔离测试范围使用。

## 替代方案

自动给已保存档案补用途同意会替用户授权；取消后端来源校验会生成没有依据的安排，因此均不采用。前端需要新增配置状态及恢复入口，但不更改数据库结构或正式营养计算契约。

## 验证

App 的 462 项测试全部通过，H5 和微信小程序构建通过。后端单元回归为 4913 passed、59 skipped；每日安排的 3 项真实 HTTP/Worker/PostgreSQL 集成回归通过。独立 Reviewer 对完整差异及手机号功能保留进行了只读复查，未发现阻断项。

实际浏览器从缺少健康关联的已保存档案进入恢复建档，核对后得到两条成员关联和两份 meal_plan 用途同意。使用官方 DeepSeek Flash、真实 Worker、PostgreSQL 和 Milvus，合成科普片段经过检索及来源版本核对，三餐返回 ready、saved=true、validation=passed；页面刷新后仍能读取同一份安排。测试规则、菜谱、商品和科普片段位于独立测试槽位，不作为真实专业资料。

## 后果

真实每日三餐仍依赖规则、营养资料、菜谱和商品映射。独立合成三餐验证不证明服务器实际专业目录或支付闭环可用。报告识别缺少 OCR 凭据，图片识餐缺少支持图片的模型，均未计为通过。微信构建通过不代表微信平台上传或真机合法域名验收完成。
