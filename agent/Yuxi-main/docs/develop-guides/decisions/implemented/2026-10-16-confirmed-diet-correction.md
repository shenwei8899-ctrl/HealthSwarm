# 已确认饮食同 ID 更正

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_diet_correction_service.py

## 问题

草稿修改不能更正已确认记录。产品已确认保留记录 ID、递增版本、重新计算，并禁止旧分析继续作为当前结果。

## 决策

### 实现方案

新增已确认记录 PATCH 与修订历史 GET。服务在成员锁、记录锁内检查 diet_edit、原图片有效性、expected_version 与请求幂等性。记录独立版本从原确认版本初始化，原草稿与确认保持不变；当前快照、不可变修订、新计算和反馈失效同事务提交。计算继续使用已发布食品/食谱及确定性算法，不调用模型。计算失败或未接受缺失值时全部回滚。

分析及反馈对话使用记录当前版本；历史与工具回执继续复用版本核对。所有账号在该餐次的有效反馈递增版本并失效，既有依赖过滤阻止旧建议继续展示或进入模型。旧快照仅通过带权限的审计历史读取。

本决定的范围为更正后端，Owner 为刘潇。正式 App 更正、冲突/重算状态及逐人记餐由[后续工作流决定](2026-10-16-independent-health-workflows.md)覆盖；原图重识别、模型政策和生产发布仍在本决定范围之外。

## 替代方案

拒绝创建新的餐次 ID，避免重复计餐。拒绝覆盖原确认和草稿，保留原始证据。采用同步计算，避免持久化新记录而旧营养仍可见的窗口。

## 后果

旧 API 消费者必须继续拿 source_version；不能以固定1覆盖当前版本。客户端本地缓存无法由服务端追溯删除，后续接入必须刷新并处理409。生产与正式客户端验收另记，不由后端测试替代。

计算同步完成或全部回滚，没有持久后台重算任务。记录独立版本从原确认版起递增；计算表保留原草稿版本作为来源血缘，当前业务版本在DietLogRevision中关联计算ID。旧版无版本的普通咨询回执只兼容未更正的原确认，不能借此绕过失效。运行时没有自动生成新AI建议；长期派生结果保留/清理仍待完成；正式 App 刷新与版本冲突处理见后续工作流决定。
