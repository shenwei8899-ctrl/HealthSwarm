# 普通营养咨询执行队列与正文准备

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/agent_run_service.py

## 问题

一次生产咨询等待约 46 秒才被 Worker 领取，其中 ARQ 日志直接记录 45.35 秒领取延迟。同窗有配餐 Run、耗时约三分钟的专属计划任务和重复后台唤醒。Worker 领取后约 81 秒开始正文调用，其中知识检索约 10 秒。检索返回到最终模型开始之间仍有一次模型选择、纯阶段标记工具及调度间隔。

## 决策

### 实现方案

生产可启用普通咨询专用 Redis 队列与独立 ARQ 进程。提交、FIFO 接力和恢复都使用持久化 Run 的角色选择队列。每个队列使用自己的 ARQ 唤醒 ID，关闭隔离时 PostgreSQL 中的 pending Run 可由通用 Worker 重新投递。AgentRun 执行、续租、取消与终态仍由原 PostgreSQL 机制决定。通用 Worker 负责默认队列、定时与运行恢复。API readiness 检查两个队列的消费租约，两个 Worker 的容器健康检查各自核对需要的租约。启用和停用步骤见[部署说明](../../../advanced/deployment.md#普通营养咨询专用-worker)。

普通咨询的授权科普工具允许声明单次检索已足够。只有显式短科普问句、当前轮第一条模型工具消息独立调用且命中正常资料时，工具回执与最终阶段在同一图更新中提交。引用由最终结果工具结构化提交，经同轮来源核对、流式发布校验和终态落库验证。个人或混合问题、交接、多个工具、空结果或未声明准备完成继续使用完整准备流程。[引用结构化契约](2026-11-14-consultation-citation-structured-output.md)继续适用。

## 替代方案

增加共享 Worker 并发仍会与长任务竞争。仅压缩提示词保留原流程的模型往返。对所有普通咨询自动结束准备会丢失个人档案等业务需求的后续工具步骤。

## 后果

专用消费者增加一个进程和对应的数据库连接预算。两类进程共享 PostgreSQL、Redis、知识库与供应商，检索和实际生成耗时仍随负载波动。短科普识别保守，未命中的问法可沿完整流程得到答复。

2026-11-19 用生产旧版与同机隔离候选执行同样三条合成普通咨询。三条问句都从各自新会话发起，使用现行 DeepSeek V4 Pro 模型和知识库。以服务器持久请求时间、首次公开正文和完成事件计算中位数，排队 0.063→0.079 秒，首段正文 13.132→12.695 秒，完成 13.502→13.031 秒。每条图内模型调用均由 3 次减为 2 次，候选结果接口分别返回 1、2、2 条引用，SSE 和同 Run 最终答复通过核对。两条请求的总时间在候选中变长。受控 Redis 竞争实验独立验证排队隔离，三条线上低负载样本用于观察供应商和业务链路，不作为高峰性能保证。

最终镜像复测同样三题，每题均为两次模型调用且结果接口均返回两条引用。排队、首段正文与完成时间中位数分别为 0.072、13.396、13.709 秒。两轮候选数据呈现了低负载下的模型和检索耗时波动。

全量 Linux 单元基线与候选的 154 项失败用例清单一致，候选另有 5953 项通过。既有隔离咨询 E2E 的技能版本断言仍使用 `2026.10.22.1`，先于问答步骤失败。上述真实模型的 HTTP、SSE、专用 Worker 和 PostgreSQL 回读独立完成。
