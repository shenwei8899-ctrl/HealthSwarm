# 我的餐单自动收录

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/daily_meal_plan_service.py

## 问题

每日餐单与我的餐单读取不同数据，生成成功后用户无法直接找到餐单，聊天也拦截重新生成请求。

## 决策

### 实现方案

共享每日餐单行保存同一家庭、日期的最新成功餐次和只读展示快照。生成完成事务同时更新来源、每日版本和快照，部分生成仅替换对应餐次。我的餐单按日期分页读取快照，展示菜品与做法，不要求专业批准或采用。服务端在家庭权限边界检查访问，展示只含成员身份和姓名，不复制个人健康档案、成员分析或采购凭据。

聊天明确重新生成时创建新请求，保留明确日期、餐次和原就餐成员，并使用每日版本防止旧任务覆盖新结果。旧线程缺少初始每日版本时，在请求提交事务记录版本，成功发布只读取匹配请求的登记值。失败、取消和生成中不改写快照。餐次就餐成员不同时，现有生成协议需要逐餐提交或明确统一的新就餐成员。

首页读取同一每日记录；来源失效时可回看最后成功的餐次，并停用该餐次采购入口。内部来源校验、专业校验及采购规则仍由各自服务拥有。历史页面没有采购写入或实际饮食记录写入。

归档列表和详情使用普通 MVCC 读取，不申请家庭排他锁；权限子查询与餐单快照在同一条 SQL 中校验有效成员和未归档家庭。列表额外执行无锁家庭存在性检查，保持不可访问家庭返回404。读取以 SQL 语句快照为边界，已提交的退出家庭与家庭归档会阻断后续读取。家庭写入及其他需要串行授权的操作继续沿用原锁规则。

## 替代方案

客户端生成后额外保存存在漏存窗口；从历史聊天拼接无法保证请求终态与当前餐次一致；直接回读来源会因商品或来源变化丢失历史展示。

## 后果

v039 添加 JSONB 快照并从已发布每日来源幂等回填。历史仅恢复仍有成功发布来源的当前餐次，不能恢复已被覆盖或从未发布的内容。列表采用日期游标。归档显示生成时保存的媒体与译文，不依赖商城或模型在线。

归档复用通用家庭上下文会申请排他锁；换菜候选计算在相同事务内持锁时，列表实测等待30～53秒，超过小程序15秒请求期限。延长客户端期限会保留锁排队；放松通用家庭上下文会扩大其他业务的授权事务影响。独立的带权限只读归档查询只改变这两个展示入口，无数据库结构变更。

2026-11-17 服务端与 H5 已部署，API 与 Worker 同镜像运行健康，health schema 已升级至39，43条共享日期记录具有成功餐单快照。微信开发者工具已上传版本 `2026.11.17-my-meals`；上传不代表审核通过或正式发布。生产切换前保留完整数据库备份与旧网页版本。
