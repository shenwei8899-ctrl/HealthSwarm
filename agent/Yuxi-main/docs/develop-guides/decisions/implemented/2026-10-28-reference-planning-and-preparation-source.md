# 日常参考餐单、建档准备与固定规格采购来源

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/reference_meal_plan_service.py

本记录面向维护参考配餐、建档准备和商城接口的开发者，说明已装配契约的来源边界与验证范围。源码、数据库模型和接口实现拥有运行事实；本记录不触发部署或迁移。

## 问题

日常吃饭安排需要使用当前家庭档案、菜谱原文和真实商品规格。专业营养配餐、日常参考选择、商品交易资格分别拥有不同含义；将参考状态改为专业校验通过会改变用户可见结论。建档后后台准备还需要保存请求身份和结果引用，页面关闭不能成为任务丢失的原因。

Agent 已使用的参考采购载荷允许空食材克数清单，并保持 `nutrition_validation.status=reference_only`。商城源码必须同时具备创建、来源复验、采购清单及菜单读取分支，单独保存 Agent 代码会使同一仓库的生产者和消费者契约不一致。

## 决策

### 实现方案

参考任务通过既有健康任务入口进入固定配餐角色。`reference_meal_plan_service` 固定所选家庭、成员、日期及餐次，检查饮食字段权限、`ai_use/profile_view/diet_edit` 授权和独立配餐用途同意；最终结果绑定同一 Run 的真实工具审计、菜谱来源摘要和保存的预览。读取、恢复及采购时重新核对当前成员与来源，失效来源返回明确拒绝。

用户明确选择参考采购后，Agent 签署保存的来源标识和商品摘要，并发送固定 SKU 与包装数量。商城 `AgentMealSourceService` 回源验证签名来源，核对 `selection_mode=reference`、账号、菜单版本及完整商品数量集合；`RecommendationPackageService` 仅在参考来源核验成功时接受空食材克数清单和 `reference_only`。采购清单按实际包装数量传递，菜单读取保留 `daily_reference` 范围。原专业 `passed` 分支继续维护自身营养和交易校验，参考分支不改写专业结论。

固定规格的正式每日采购使用独立的 `commerce_sku_selection` 与商城 `AgentSkuSelectionService`。Agent 的保存回执拥有食材需求和商品选择，商城核对 `purchase_authority` 中的账号、版本、需求、规格数量及 `passed` 状态，并复验当前商品身份和包装。参考采购与正式采购均拒绝使用旧清单重新匹配来替换已保存来源。

`onboarding_preparation_service` 在既有档案事务中登记准备请求和后台任务，事务提交后由原 Task Owner 发布。健康 schema 版本由 `storage/postgres/manager.py` 的常量固定为 32；`HealthOnboardingPreparation` 保存请求唯一性、来源、用途说明、日期、attempt 和已有结果引用，迁移由原 `storage-migrator` 执行。准备 worker 在任务租约内核对来源及用途，服务端只衔接本人或有效监护关系允许的成员，并拒绝覆盖已撤回的授权或同意。读取准备状态不新建模型执行；完成投影继续依赖当前咨询、每日安排和完整三餐的真实结果。

新请求键复用同日、同来源准备时，在同一事务写入 `alias` 收据并固定首次目标。响应丢失后重放该键，继续读取同一准备；来源变化只返回失效状态，不重新保存档案或创建任务。同键更改输入返回冲突，新键才可请求新的准备。保留显式 alias 行的代价是多一条请求收据，换取跨设备与跨来源变化时可回读的稳定幂等身份。

## 替代方案

- 把参考采购标为 `passed`：交易资格会被解释为专业营养校验结果，失去状态边界。
- 在商城按普通食材清单重新匹配规格：固定的 Agent 来源、包装数量及当前商品身份无法继续对应。
- 只保留服务端 PHP 文件：仓库无法复现 Agent 已使用的消费者契约，代码评审也无法看到完整权限链路。

## 后果

参考菜单可以展示和采购真实商品包装，同时保留参考性质与待核实事项。商品身份、档案、授权、菜谱或保存来源改变后，需要重新核对，旧采购来源不能继续使用。来源服务暂不可用时拒绝交易，价格和库存继续由商城事实决定。

健康 schema 32 和建档准备任务属于持久化变更。数据库重复迁移、并发请求、Task 租约恢复以及真实采购事务需要 PostgreSQL、Worker 和商城链路证据；源码摘要、纯函数单测与 PHP 语法检查只覆盖各自观察边界。源码归档不代表执行迁移、发布商城或完成真实订单。

`Inspected`：只读核对商城实际入口、发布目录和五份关联 PHP 的 SHA-256，候选文件与读取的已装配源码逐字节一致。Agent 当前参考任务、来源验证、固定 SKU 回执、准备 Task 注册及 schema 32 模型和迁移入口已经逐项核对。直接记录 `implemented` 是对已运行契约的源码归档，不增加新的运行模式或部署操作。

`Passed`：五份 PHP 的 `php -l` 检查通过。`shop/tests/unit/ReferencePurchaseContractTest.php` 载入候选真实类，通过 PHP 标准输入执行 29 个独立合成案例，覆盖空克数清单的合法参考、签名和保存回执替身、账号及版本错配、SKU 及数量变更、空明细、重复规格、伪造 `passed`、未知参考来源和正式旧分支。七个仅作用进程内源码副本的负控分别关闭状态、账号、版本、数量、模式或来源约束，均在预期案例失败。数据库和 HTTP 调用由立即失败的测试边界禁止，测试不加载应用 bootstrap；签名与回源结果使用合成验证器，生产签名 HTTP 不在该证据范围内。具备 PHP 的本地环境可运行 `php shop/tests/unit/ReferencePurchaseContractTest.php`。

`Passed`：包含准备幂等回归的相关后端 218 项 unit、工程契约校验及其 63 项 unittest、71 个变动 Python 文件的 Ruff 检查与格式检查通过。后端单测使用真实执行图或原生产函数与明确的合成依赖，不能代替数据库事务或完整参考配餐验收。

`Passed`：`test_onboarding_preparation_idempotency.py` 的三项回归原样执行生产入口 AST、实际 SQLAlchemy 模型与查询，并用内存会话验证首次复用、来源变化后同键重放和同键改输入冲突；独立复现同样回读首次准备标识且未登记新任务。原实现两项失败，修复后三项通过。内存会话不证明 PostgreSQL advisory lock、唯一约束或真实事务并发语义。
