# 家庭已保存餐单的 Agent 预览与页面确认

状态：implemented
类型：feature
Owner：web/src/components/health/HealthFamilyMealPlanner.vue

## 问题

家庭已保存餐单已有换菜、重生成和参与者／个人份量调整的 Agent 与业务接口，但餐单页面仍按单成员快照显示。家庭汇总没有公共 dishes，个人参与的餐次也不一定覆盖全天；单成员展示和同意流程不能表达此合同。

## 决策

### 实现方案

在现有餐单页面按 family_recipe_draft scope 与成员快照分支挂载独立家庭快照及家庭 Agent 面板。沿用已有应用、API 包装、Request/Run 轮询与业务确认接口，不新增 Schema、Agent 注册或模型配置。家庭快照显示多人合计及逐成员覆盖餐次、菜名和确定克数；公共菜位使用 family_dish_index。

全部原参与者固定选入；参与调整可以明确选择拟加入者。逐成员核对 ai_use、diet_edit、profile_view，读取当前专业投影并取得独立 meal_plan 用途同意。冻结入口成员、选定集合、餐单版本、专业来源、政策及操作；变化后清空预览并丢弃迟到响应。用户以自然语言给出明确成员和份量调整，不自动均分、补齐未知份量或声称保留未投影的原份量参考。服务端预览是最终确认前可审阅的完整分配。

权威输出必须来自本 Request 的本 Run，身份、scope、operation、preview_id 及完整结果逐层校验。output.member_ids 是全部绑定者，结果 sources.profiles 按实际结果参与者核对；不能把两者强制等同。首次确认重读同一 Run，再通过普通 family-safe-swap、family-safe-regenerate 或 family-participation 写入。参与调整确认包从服务回执完整 plan_spec 提取三餐原菜位 allocations，展示实际参与者与克数后明确确认。未知写入保留冻结 body 与幂等键直接恢复，不因已提交改版后的旧 Run 失效阻止恢复。业务 POST 返回包含 503 的 5xx 仍属未知写入；首次 Run 读取的 503 按依赖失败清理旧预览。

保存后回读当前餐单、修订与审核状态。预览不写正式餐单，不产生实际饮食；改版后旧审核和采用失效，新版本仍待独立专业审核。首次 Run 读取和业务写入是两个 HTTP 边界，不声明并发撤销 AI 授权与保存的原子互斥。

## 替代方案

修改单成员快照和状态机会混合个人全天与多人汇总、不同来源集合和授权语义。独立家庭组件保留已有单成员行为，复用同一父页面与业务接口。

## 后果

本轮只覆盖已保存家庭餐单的三种调整。家庭初次生成、小程序、完整健康档案、生产专业规则及医学适用范围另行验收。主服务已有获批模型配置不属于本轮变更；真实页面验收使用隔离合成协议回放与真实 API、Worker、PostgreSQL。
