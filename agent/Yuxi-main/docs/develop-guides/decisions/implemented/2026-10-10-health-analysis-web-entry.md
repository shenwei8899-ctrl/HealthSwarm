# 饮食分析与选餐反馈后台入口

状态：implemented
类型：feature
Owner：web/src/views/HealthVisionView.vue

## 问题

健康后台可以读取确认饮食和填写餐后反馈，但已装配的饮食分析、选餐反馈会话缺少页面入口。管理员配置表单遗漏采购模型，保存其他用途时会把已有采购模型提交为空；仅采购模型的配置输入也遗漏与其他用途相同的云处理确认检查。

## 决策

### 实现方案

后台增加饮食分析入口，并在当前确认饮食上提供选餐反馈对话。页面使用业务接口创建绑定成员或餐次的线程，经独立用途同意后复用既有初始化与 AgentChat 的 Request、Run、恢复和权威结果投影。普通分析的单餐或北京时间1日、7日和30日选择先经无模型业务读取核对，然后进入初次问题；同一成员会话允许后续问题改变范围。选餐反馈由既有服务不可变绑定餐次及确认版本。成员、来源或窗口切换使旧异步响应失效。手动反馈继续保留。

已确认饮食列表投影增加实际确认事务的草稿版本，直接供分析选择与反馈绑定使用。此字段由现有 VisionConfirmation 拥有，客户端不猜默认版本。

聊天消息组件仅在饮食分析师、相同 Run 的 completed 状态及持久化文本消息吻合时，将现有分析或反馈最终 JSON 呈现为事实卡片。最终输出与来源有效性仍由服务端消息投影校验，客户端不新增输出权威。卡片显示实际窗口、记录覆盖、确认营养值、已知部分与未知项，以及反馈保存回执；不引入另一套运行或结果状态。无法核对来源的消息沿用原渲染。公共布局仅对健康后台及聊天路由放开窄屏最小宽度，让正文收缩、表格在自身容器滚动。

配置表单完整加载和提交已有七种模型用途；输入 DTO 对采购用途执行已有政策与显式确认约束。配置保存和启用审批仍由现有服务拥有，本决定不审批主服务采购模型。

已有显式绑定当前个人目标的分析结果保留完整 Markdown 呈现，避免事实卡片隐藏服务端附加的目标、来源与未应用于历史窗口的说明；个人目标展示另由既有能力拥有。

## 替代方案

直接开放普通 Agent 聊天无法建立业务成员、用途和餐次绑定。另建聊天运行器会复制已有排队与恢复语义。只增加表单字段无法覆盖仅采购配置的审批遗漏。

后端非 slow 单元集4331项通过、59项跳过；隔离 HTTP/Worker 八项通过，模型使用受控合成回放。可复现的真实接口案例位于 `backend/test/integration/services/test_health_diet_analysis_http.py`、`test_health_diet_period_http.py`、`test_health_dialog_feedback_http.py` 和 `test_health_purchase_http.py`；Worker 案例位于 `backend/test/e2e/test_health_diet_analysis_e2e.py` 与 `test_health_dialog_feedback_e2e.py`。前端回归位于 `web/test/healthDietAnalysis*.test.js` 与 `healthVisionAdmin.test.js`，通过组件编译与明确服务器事实样例校验。

真实页面核对单餐、七日统计、选餐反馈、配置保存、空记录、撤回来源错误及历史恢复；CSS约1440、1024、768、375宽度核对正文换行与表格滚动。深色主题未单独人工验收。提交门禁沿用前端 `lint:check`、`test:unit`、`build` 及工程契约检查。
