# 参考菜品展示原食谱整道菜营养

状态：implemented
类型：simplification
Owner：backend/package/yuxi/services/reference_serving_nutrition.py

## 问题

参考菜品同时展示原食谱用量、本餐建议用量、个人原料分配以及三种营养口径，用户难以分辨。原有整道菜营养按本餐建议原料量计算，与原食谱清单的数量可能不同。

## 决策

展示与营养口径取代[逐人份量与营养回读](../implemented/2026-11-27-reference-member-servings.md)的对应部分，成员身份和原料分配守恒约束保留。

### 实现方案

菜品详情通过成员卡展示姓名、建议熟食克数及估算提示；食材展示工具沿用原食谱及中文助译，保留商品关联。参考菜品移除每百克摘要和个人营养切换，整道菜组件只读取带原食谱用量依据的总营养，未知项和真实零值由展示工具分别处理。

营养计算由参考营养 service 拥有：通过当前目录编号和文档指纹关联已发布配方，按配方原料克数与当前有效的已发布食品数据计算，不使用模型建议用量或建议熟重缩放。新总量带有 `quantity_basis: source_recipe`。历史快照不重写，缺少该依据的旧总量不显示成原食谱总量；缺失项保留未知，真实零值正常显示。个人原料分配继续供已有份量校验使用。

## 替代方案

保留三种口径会继续暴露重复信息。仅隐藏按钮并沿用旧总量，会把计划用量误标为原食谱用量。按文本猜测原食谱克数或自动审批候选食品，会失去可靠的计算依据。

## 后果

沿用既有快照 JSON，无数据库迁移。新结果不再计算无展示消费者的每百克及个人营养，旧结果保持原值且可读。正式餐单的营养卡不变。资料不足的原食谱继续显示暂未核算，数据导入和审批不属于本次范围。

旧能力不存在：参考营养选项构造函数、每百克和个人营养计算、切换状态及按钮没有运行时消费者；成员卡不输出原料描述，食材展示工具不追加计划量。正式餐单的每百克卡继续由原消费者使用。原始份量分配仍参与成员及总量校验；既有快照字段保留，无新依赖、配置或 schema 变更。

重新引入条件：只有新增明确的用户需求，并同时定义用量依据、旧快照兼容方式及独立数值用例时，才增加其他展示口径。

前端渲染用例编译真实 SFC。PG/HTTP 用例在隔离测试库中实际发布合成食品与配方、保存归档后重新读取；外部模型和真实生产资料不参与。生产营养资料导入、真机验收与发布 Not run。文档构建 Not run：本地未安装文档依赖，站内链接由工程检查验证。
