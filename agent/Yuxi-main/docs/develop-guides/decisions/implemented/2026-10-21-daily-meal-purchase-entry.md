# 今日三餐生成与本餐合并采购

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/daily_arrangement_service.py

本决定已实现于候选源码，尚未部署生产。

## 问题

首页首次生成依赖商城会员会话，未关联会员时无法安排饮食；云端餐次详情与采购分成两个页面，档案版本变化后缺少原安排的重新生成入口。

## 决策

### 实现方案

每日安排由既有后台 Task 和 AgentRun 完成。生成阶段使用服务端签名目录核对食材，保存菜谱、份量、营养、食材需求与实际 SKU 的匹配快照；该阶段不要求用户关联商城会员。采购包在本餐合并页中用户明确结算、商城身份就绪后，按原安排、餐次、版本和稳定幂等键发布。商城重新核验库存和价格，订单保留既有来源校验与支付快照。

档案来源版本变化时，GET 返回需重新分析状态并停止展示旧建议；POST 在重新核验家庭、成员授权及当前档案后重启同一安排的新版本。撤权与不可读来源继续拒绝，不自动授予权限。尚无可靠正式来源的已购计划或家庭明日提议不能伪装成新生成结果。

小程序沿用原本餐布局与结算抽屉，成员、营养、菜品做法、可勾选食材及金额在同页展示。查看与刷新不创建购物车或订单，明确结算后才同步本餐购物车并核价。

首页及家庭餐单卡将各自保存的日期、安排 ID 和版本传给汇总采购页。后端合并所选餐次的原料需求，再匹配整包装；汇总采购签名包含全部所选餐次摘要。旧版已发布包缺少原料字段时回读保存的发布载荷。单餐调整保留其他餐的发布载荷与重试状态，并废弃原汇总引用。

商城明确返回 blocked 时持久推进采购尝试；下一次明确购买重新匹配当前可售 SKU。每次匹配先提交到数据库，再调用商城，网络超时继续重放该尝试的原请求键和载荷。新来源记录默认就餐者集合；旧来源没有这个基线时不能用逐餐参加者并集推断，避免升级抹去用户单餐调整。

## 替代方案

保留首次商城关联会使饮食安排受购买身份阻挡；在前端生成菜单或价格会形成另一套业务事实；按当前餐次查询采购包会丢失安排版本关联。

## 后果

真实模型、批准规则、营养配方、商品映射及处理政策由运行环境和资料 Owner 提供；合成测试不能代替正式数据或微信验收。代码交付与线上部署分别核验，保留原有用户资料、商城关联及已支付快照。

已购 21 天计划与家庭明日提议的正式来源优先级仍未实现：现有单成员私人提议和正式采用记录不能代替已支付家庭计划。正式规则与菜谱资料尚待明确；生产镜像缺少当前每日任务及资料准备模块，也未设置每日规则代码。本次不部署、不替换正式资料、不写生产业务数据。
