# 所选菜品采购与独立结算加载

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/meal_dish_service.py

## 问题

打开采购会重复查询采购内容、装配整日展示并在报价前写入购物车；地址和商品相互等待。采购需要保留当前家庭授权、菜品版本及交易时效校验。

## 决策

### 实现方案

采购 service 从当前家庭日期索引定位所选餐次和菜品，使用已发布快照与采购映射；参考来源重验完成状态、当前成员授权和数据库中的来源摘要，避免展示译文、媒体与原文件下载。当前请求复用解析后的来源。商城保留服务端来源校验与实时交易校验。

前端已保存餐次采用一次采购发布，不额外发出重复预检；商品、地址、配送分段加载并按账号和选菜作用域丢弃迟到响应。直接推荐包报价接受服务器包内的 SKU 子集和合法数量；打开、取消和改数量均不写购物车。报价与下单继续校验来源、价格、库存和配送，旧报价立即失效。

## 替代方案

保留串行流程只增加超时时间会延长等待。缓存整个展示接口会扩大失效和授权边界。沿用购物车报价会引入无关持久写入与更多往返。

## 后果

新商品包使用版本 2 的采购摘要；旧商品包保留原有回源分支。来源失效时服务端拒绝购买。正式餐单仍复用质量 Owner 的整份审核校验，每个来源在同一采购请求中复用一次结果；参考来源只读取所选菜谱元数据。既有购物车与对话推荐包调用保持兼容。新增来源、目录与发布耗时日志，地址、配送与报价耗时由前端状态记录，供运行环境复测。

当前本地验证：前端相关 132 项、后端采购 21 项和真实 HTTP/PG 2 项通过；H5 与微信小程序编译通过。发布前独立审查补齐后台暂停释放忙状态、商品版本失效保留地址、统一刷新入口及提交期间恢复后补读；最终独立审查无阻断问题。浏览器使用明确标注的合成商品、地址与报价，不作为线上耗时或真实支付证据。正式餐单继续由现有质量 Owner 核对审核状态；参考餐单的授权绑定仍覆盖原选择成员，避免削弱已发布来源约束。

验证范围：真实 PostgreSQL 子集报价和订单覆盖未选项缺货、数量调整、无购物车写入、价格/库存/来源/地址变化拒绝。工程契约检查通过，其 63 项自测在 Linux 容器中通过。采购相关 Python 代码通过 ruff check。全量后端 unit 在收集阶段因隔离环境缺少 sandbox_provisioner 路径及解析依赖 InputFormat.XLS 不匹配中止；文档构建因本地 VitePress 未安装而未完成。线上完整服务链路耗时与真机网络耗时尚未测量。
