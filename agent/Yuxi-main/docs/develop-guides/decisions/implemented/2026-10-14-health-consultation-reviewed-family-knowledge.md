# 成员营养咨询使用固定家庭知识库做一般科普问答

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_family_kb_service.py

## 问题

“成员专属营养咨询”需要让已获该成员 AI 咨询授权的账号读取固定的“家庭营养与食养知识库”，回答一般营养科普问题。普通知识库 ACL 不能表达成员 AI 咨询授权，既有 `NutritionEvidence` 的 `[证据:UUID]` 表示另一套审核证据。把通用知识库片段直接当作审核证据，会使资料来源和正式个体化建议的边界混淆。

这项能力限于一般科普、资料追问和另行授权的记录回顾，不以逐篇许可、专业审核或适用范围登记为前置条件。部署方仍需确认整库有使用权限并维护内容；知识库索引和来源可追溯性均不证明医学适用性。

## 决策

### 实现方案

`health-consultation` 通过服务端环境变量 `HEALTH_FAMILY_NUTRITION_KB_ID` 绑定一个知识库 ID。专用 `query_family_nutrition_knowledge` 工具只接受最长 120 字的主题词，不让模型指定库、成员或文件；配置缺失、库不存在或不是 Milvus 知识库时返回资料不可用。通用 `context.knowledges` 仍为空，图不开放通用 `query_kb`、文件打开或下载工具。此工具按成员授权读取固定库，不要求该账号同时拥有知识库管理页的普通 ACL；部署方负责把环境变量指向预期的家庭库。

咨询创建按成员 `ai_use` 授权与固定成员绑定校验；请求提交、当前 Run、检索及历史读取均核对当前 `consultation` 用途同意，运行时还核对处理配置。血糖、血脂、血压指标 Agent 的历史入口同样检查当前咨询用途同意；主咨询列表及每日历史日期元数据也检查，撤回后不返回线程信息。`report_view`、`diet_edit`、`profile_view` 与档案编辑权限分别控制对应个人数据工具，图只装配当前可用工具，工具执行仍由业务 service 复核。旧线程的 Run manifest 和已完成工具审计决定继续读取或重放时需要哪些个人数据权限；旧格式或无法可靠确认来源时保留更严格的报告和饮食权限要求。用途同意或授权撤回后，旧线程不能借 checkpoint、历史、结果或审计时间线重新读取。三个指标 Agent 仍保持本人限定及原工具集合。

知识库运行时最多召回四个片段。检索强制使用 Milvus 内置 BM25 关键词模式，关闭重排与图检索，不把查询词另发给知识库的外部嵌入或重排模型。家庭库请求显式只读加载既有集合：集合缺失、嵌入模型描述不符或没有 BM25 结构时拒绝检索，不在读取中创建、删除或重建集合。工具从 PostgreSQL 重读 `KnowledgeFile` 和 `KnowledgeChunk`，只接受固定库中状态为 `indexed`、文件及片段 ID 和正文与检索命中一致的来源，每段向模型最多给 1200 字。向量库命中但 PostgreSQL 来源全部失效时返回来源失效；真正零命中才返回资料不足。ToolMessage 与 checkpoint 保存同 Run 的来源 ID、文件名、文件摘要或更新时间、片段摘要及短正文；资料正文作为不可信输入，不能改变工具或授权。模型调用前检查 checkpoint 中的资料工具消息是否对应同线程成功的持久工具审计及当前文件版本。

答复采用独立的 `[资料:source_id]`，并显示来源文件名；版本在工具回执内部校验，不作为已审核来源向用户展示。命中资料的答复必须引用本 Run 成功工具审计中真实返回的来源。模型结束后及最终消息发布前，从同 Run ToolMessage 审计重新核对来源；当前结果、历史、原有审核引用读取、审计时间线和日终摘要消费也重验文件与片段当前版本。审计时间线在分页前复查本线程所有家庭库工具审计：成功回执必须通过当前来源校验，过期返回 410；运行中或失败的回执仍允许查看同 Run 的状态、标识和时间等诊断元数据，但隐藏该 Run 的 Model/Tool 正文、工具输入输出、推理、原错误及 ToolCall 参数和结果。这样既可排查失败，也避免旧来源落在分页外或异常输出中泄漏。来源删除、重新解析、原位改写、回执缺失或跨 Run 冒用时，相关答复失效。既有 `[证据:UUID]` 仍只用于 `NutritionEvidence`，不与家庭库 `[资料:source_id]` 互换，也不增加独立公开资料来源接口或正式建议结果。

咨询 prompt、内置 Skill、角色发现与任务投影把家庭库定位为一般科普资料。咨询可解释一般营养概念并回顾已授权的事实；它不凭这批资料生成正式个体化营养建议、个人餐单或份量目标，不作疾病诊断、治疗和用药调整。已有审核科普检索保留原有独立用途。

## 替代方案

将固定库加入 `context.knowledges` 并开放通用 `query_kb`，会沿用普通 KB ACL、允许模型选库，且不会经过成员咨询的 Run、来源版本与历史读取校验。逐篇导入 `NutritionEvidence` 可复用专业审核引用，但会引入本期一般问答不需要的逐篇许可、审核和适用范围登记。固定专用工具复用既有 ToolMessage 审计，避免新增审核记录表或公开引用协议。

## 后果

仅有成员 `ai_use` 和咨询用途同意的账号可以使用固定库的一般科普功能；个人报告、饮食和本人指标仍受各自权限限制。资料更新后，旧答复及依赖它的日终摘要可能返回来源失效，需要重新咨询。库 ID 配错为另一 Milvus 库时，服务只证明该 ID 存在及类型正确，部署核对仍须确认它指向预期的家庭库。生产集合若为旧结构，需由管理流程核对并迁移后才能用于一般科普。底层 `MilvusKB` 首次初始化在 Milvus 数据库完全不存在时仍可能创建空数据库；本次收紧的是家庭库查询对集合的只读边界，这个既有数据库初始化行为留待基础设施后续改造。

家庭库含慢病和特殊人群资料，检索相关性及来源校验不能证明某位成员适用。模型输入约定使用不含个人病历的短主题词，服务端校验长度和固定库身份，并强制查询走 Milvus 内置关键词检索，不调用独立的外部嵌入或重排模型；内容准确性、个体适用性及任意提示词注入下的输出不能由这些工程检查担保。正式个体化建议仍需另行确定资料、适用规则、成员安全档案和独立业务发布契约，不由一般科普答复升级得到。

## 验证

容器内完整非 slow unit 共收集 4802 项，结果为 4743 通过、59 跳过、10 条警告；其中覆盖固定工具装配、成员与个人数据权限、当前来源校验、失败审计脱敏、完整 embedding 模型 ID 校验、Milvus 孤儿命中失效和一般科普结果。隔离 PostgreSQL 来源校验与咨询用途同意撤销的集成测试、仅有成员 AI 咨询授权账号的真实 HTTP 用例均通过；创建幂等重放另以真实 HTTP/PostgreSQL 验证并发重放、已删除 Conversation 和失效 Project。最终发布的真实 PostgreSQL 并发用例通过 `pg_blocking_pids` 证明文件改写与片段删除均被来源共享锁阻塞到发布事务结束，变更完成后的答复读取返回 410。隔离真实 HTTP、ARQ Worker、PostgreSQL 与 checkpoint 的主咨询回放共 73 项通过，家庭营养师审核证据闭环 E2E 1 项通过；这些回放校验新工具的运行清单和既有证据边界，但没有实际调用固定家庭库检索。Ruff 检查与格式检查、工程契约检查和文档构建也通过，独立审查未发现剩余功能或安全阻塞。固定家庭知识库的真实 Worker→Milvus→PostgreSQL→答复引用链路及生产知识库联调仍未运行，现阶段不据此声明完整家庭库运行链路或正式个体化建议通过验收。
