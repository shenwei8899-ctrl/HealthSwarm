# 家庭餐单参与者和份量调整

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_family_participation_service.py

## 问题

家庭共同餐单在调整参加餐次或个人份量时，需要保留共同菜品和旧历史，并重新检查新增成员及新的个人覆盖范围。后端维护者需要明确的新版本用例，同时保护已经移出成员的历史数据。该用例属于[六 Agent 工程目标](../proposed/2026-10-07-health-agent-engineering-completion.md)中的家庭参与者调整。

## 决策

用户按原三餐及菜位提交完整参与分配，协议只接受参与成员和明确个人份量，不接受新菜谱、日期、营养、医学目标或审核状态。服务器保留原菜谱及日期，入口成员仍须参加至少一餐；不能把共同计划转成不同对象或在调整中删菜。预览重新计算逐人实际覆盖营养，使用全部新参与者当前档案和批准规则检查，移除成员不再进入新版本个人结果。

用例先只读原计划和拟调整分配，再排序锁定原参与者与新参与者的并集，核对编辑及档案读取权限，刷新计划并检查版本，然后锁批准规则来源。全部新参与者档案版本必须准确选择。预览不写业务事实，确认摘要绑定原版本、调整分配、全部新来源与逐人质量结果；任何冲突或缺依赖都不能确认保存。

确认在当前来源下重新试算，复用安全修订事务保存新版本、新质量检查，并使旧专业决定及共同采用整体失效。失败全部回滚，旧快照不改写，新检查不继承专业批准。请求幂等遵从既有计划修订 Owner；历史重放额外检查该修订参与者权限。统一质量/专业审核读取也锁定当前与历史来源成员并集；既有家庭安全重放在当前成员锁之前选定历史修订集合，禁止通过已移出成员的历史数据绕过授权或逆序追加成员锁。

该阶段不包含家庭模型工具、多成员处理同意、初始生成、日终联动、控糖/采购及页面；这些仍按六 Agent 目标交付。红阳完整档案、专业生产资料与真实模型验收保持外部未完成状态。复用现有表，无 Schema 变更。

## 替代方案

另存全新家庭计划会失去同一计划的修订追溯。直接提交完整家庭 Spec 会允许改变日期和菜谱，混入参与调整以外的行为。专用分配协议保留原共同菜位、服务器来源和安全修订事务。

## 后果

新增成员可能使原菜品与目标不适用；预览显式返回逐人冲突或未知，用户可调整份量或使用既有安全改菜流程。调整参与者不自动采用新版本。所有写入仍由明确用户确认触发，模型无专业批准或自动采用能力。移出成员的历史质量、专业审核及家庭安全修订重放仍需其当前授权；当前版本不再包含该成员不能解除历史可见性约束。
