# 个体配餐必须计算个人目标，活动水平由公式明确依赖

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/health_personal_targets.py

## 问题

用户要求家庭成员餐单必须按个人资料计算份量，不增加活动水平必填项。现有建档保存身高体重，但目标计算无条件要求活动编码；缺个人公式时质量检查还能以通用范围通过。

## 决策

个人目标计算是餐单质量通过的必要条件。没有匹配公式或资料缺失时返回 unknown/not_ready，不以通用范围替代。公式必须显式提交 activity_factors；null 表示直接使用已发布公式的结果，不使用活动水平，非空映射表示公式依赖活动水平。省略字段、空映射和无效因子仍拒绝。保留旧公式和已存在活动编码的读取，不增加建档字段，不自动填写因子、身体资料或医学系数。

## 替代方案

增加建档活动字段不符合当前产品选择；把缺失活动默认当轻体力或乘 1 会隐含改变已发布公式；仅改变文案不能堵住通用检查放行。

## 后果

已发布的个人目标公式和菜谱决定客户端可展示的成员份量。

## 验证

验收：无活动但显式直接公式可算；需要活动的公式缺资料仍不可用；缺公式不能通过；体重身高变化按合成公式改变目标；健康限制缺失继续阻断。现有个人目标、家庭和初始生成回归在隔离环境运行。生产 SQL 仅做只读核验，不写配置或导入合成规则。

2026-11-11 线上只读事实：API/Worker HEALTH_DAILY_RULE_CODE 均为空；health_rule_snapshot、health_food_record、health_recipe_version、health_published_recipe_classification、health_recipe_commerce_source 均为 0。食谱知识库有 4206 个文件，营养知识库有 332 个文件；这些参考文档尚不等于结构化正式配方和个人公式。上线还需建立真实公式及配方数据，本变更不编造专业口径。

本地实现验证：通过现网同一依赖镜像建立无网络、无生产数据挂载的独立容器，个人目标、质量、初始生成、家庭配餐、换菜及体重来源共 367 项回归通过；ruff check 通过。原文件既有的无关格式块保留。恢复旧可选公式检查时，两项缺公式回归按预期失败；恢复旧活动依赖和模型时，无活动直接公式回归按预期失败。验证记录在 agent/.tmp/portion-runtime-audit-20261111/。只读线上证据记录为 runtime-evidence.json。

单餐详情按保存餐单 `memberNotes` 的菜谱版本匹配各成员克数。每道菜默认展示最多四位，超过时在卡片内展开。餐次统一说明使用成品可食重量，做法和食材用量仍从菜品详情读取。参考餐单缺个人分配时展示“个人份量待确定”。若将食谱原文克数直接填入卡片，会把食材用量或原始食谱份量误作个人分配。

小程序 1710 项测试及正式 API 构建通过。测试覆盖不同成员的克数、精确匹配菜谱和缺失时的显示。2026-11-12 线上复查确认生产未选定规则，正式食品、菜谱和规则仍为空。生产资料通过管理端现有食品、菜谱及批准规则发布入口登记。知识库资料可以作为整理候选的来源。
