# 专属菜单与采购资料分离

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/exclusive_plan_service.py

## 问题

专属计划把采购映射、库存、完整包装价格和三档价格递增作为菜单生成、发布及读取条件；资料不足时无法交付可用菜单。现有预览没有每日完整食材、采购缺口和明确审核状态。

## 决策

### 实现方案

新版沿用今日参考餐单的知识库原谱、成员授权与用途同意、原文和明确限制校验、搭配及去重规则。既有 Durable Task 顺序生成三档各 21 天，逐日保存，完成时在 owning transaction 再验菜单。所有保存、恢复、发布、读取复核均独立于商品目录。新版使用独立 policy 版本，旧组保留记录并提示重新准备，不混用两种来源。

采购读取为可选步骤，目录不可用保存明确状态。食材原文始终保留，只有原谱明确克重且商品身份、净重、映射、库存和价格足以计算时计入包装小计；其余保留原因及自行准备/待确认。小计不等于个体化完整预算，不用于比较三档总费用。三档是食材费用目标；仅有可靠食材费用证据时参与候选排序，不强制实际总价递增。详情及列表展示能力、审核、计价状态，按日期展示食材与缺口。

不接入供应商、订单、配送、支付或退款；不新增营养计算、专业审核能力或编造价格。

本决定取代[独立发布预览](../proposed/2026-11-14-exclusive-plan-preview.md)中的严格价格递增及首日商品预览，并取代[自动准备与分批配送](../proposed/2026-11-14-exclusive-plan-automation-and-delivery.md)中的正式配方、商城规则作为菜单准备前置条件。历史交易和未来履约能力沿各自边界管理。

## 替代方案

- 只去除生成 guard：保存、完成发布和读取仍会失败，拒绝。
- 沿用审核配方目录但放宽采购：不能满足与今日餐单相同来源，拒绝。
- 商品完整后才上线：不符合用户已确认范围，拒绝。

## 后果

原谱份量不是家庭个体化用量；明确说明核算依据。可用原谱不足以满足跨日去重时保留真实菜单缺口，不以采购失败描述。真实 Linux TCP HTTP/PostgreSQL 测试通过任务 lease 执行和断点恢复验证；外部对象存储字节与商城网络使用合成边界，独立 ARQ 进程和生产服务尚未部署验证。
