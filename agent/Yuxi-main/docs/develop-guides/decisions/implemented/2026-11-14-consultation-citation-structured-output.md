# 咨询最终答复的结构化引用提交

状态：implemented
类型：bug-fix

Owner：backend/package/yuxi/agents/middlewares/health_final_answer.py

## 问题

用户提问“聚餐可以吃啥”已被分类为普通咨询，Run 也已创建，但最终答复失败。线上咨询模型在取得本轮知识来源后先输出普通中文正文；最终答复阶段要求带 `answer` 和 `citations` 的 JSON，因而返回 `citation_invalid`。随后启用供应商 JSON 对象模式，第二次真实运行的模型审计记录最终输出 407 个空白字符、`finish_reason=stop`，仍无法解析。该供应商在此配置下不能靠提示词或 JSON 对象模式稳定提交引用。

## 决策

本轮存在家庭资料或审核证据引用候选时，最终阶段只绑定 `submit_consultation_answer` 结构化结果工具，并强制模型调用它；这不是业务工具，服务端截取参数，不执行工具函数。参数必须通过 `ConsultationAnswer` 校验，且每个引用 ID 必须来自本轮成功回执。服务端把通过校验的参数转为普通最终消息和可信答复流，再由现有发布边界复验来源。纯文本、伪造 ID、多余工具调用或无效结构仍拒绝公开。不需要引用候选的普通咨询保留现有纯文本流。

本次同时将已部署的结构化咨询引用实现与当前生产源文件对齐至 Git，避免后续镜像构建回退到旧的正文标记协议。生产发布只在现行镜像上叠加最终答复中间件，API 和 Worker 使用同一候选镜像。

## 替代方案

直接接受普通正文会绕过本轮来源引用校验；提示词 JSON 和供应商 JSON 对象模式均已在真实运行中失败。最终改用同一咨询模型在资料准备阶段已成功使用的工具调用协议。

## 后果

有引用候选的咨询需要供应商支持强制工具调用；无引用候选时仍使用纯文本流。结构化参数只在校验通过后公开，模型若继续返回不合法结构，本轮仍报错，不公开未经核实的来源主张。

## 验证

隔离 Linux 镜像中的中间件、引用、答复流、任务投影及 Run 服务定向单元测试覆盖真实图内的最终工具调用、结果截取和纯文本拒绝；本地 OpenAI 兼容分片流测试覆盖参数聚合、可信事件和 checkpoint；跨服务回归已通过。生产就绪和真实问答结果另按发布回执记录。
