# 参考餐单只从本轮检索回执打开原谱

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/agents/buildin/health_meal_planner/graph.py

## 问题

生产 Run 的菜谱检索已有目标菜和可组合菜单，但模型没有按受限工具选择读完菜单就尝试保存；在保存失败后的补读中，又提交了不在本轮检索回执里的文件编号。来源服务正确拒绝读取，未处理的 `reference_receipt_invalid` 随 ToolNode 异常让整个 Run 失败。只看容器就绪不能发现此路径。

## 决策

首次保存前，若当前 Run 的检索回执包含可核对菜单，服务端从首个菜单选出每批最多三份尚未读取的 `file_id`、`chunk_id`，要求真实模型只调用 `read_reference_recipe` 并提交这些编号。服务端校验模型调用的工具名和编号；若供应商无视约束，在重新检查授权后只重试一次，仍无效则返回补充问题。有效调用经真实 ToolNode、模型调用审计和来源服务校验。保存失败后的修正仍由原有策略管理；若模型请求未检索的编号，读取工具保留服务端拒绝，向图返回有类型的错误回执，本轮以明确的补充问题结束，不把该编号当作可信来源，也不保存未核对餐单。其他权限和来源异常仍向上拒绝。

## 替代方案

仅加强提示词不能保证供应商遵守 `tool_choice`。直接允许读取当前档案或模型填写的文件编号会绕过本轮检索归属。曾尝试由服务端合成工具调用，线上发现工具生命周期要求调用必须关联真实模型审计，合成调用在工具开始时失败，已回滚该镜像。保留真实模型调用并检查其输出，既缩小选择范围，也满足审计契约。

## 后果

首个检索菜单决定优先打开哪些原谱；后续菜单仍保留在回执中供模型选择。供应商不遵守限定时最多额外调用一次模型。若服务端无法验证候选编号或来源已失效，仍可返回补充问题而非伪造菜谱。真实业务保存仍需通过参考餐单服务校验。

## 验证

单元图测试核对真实模型发出的受限批量读取进入 ToolNode，错误工具调用最多重试一次；未检索编号经真实 ToolNode 成为错误回执，并使最终结果为 `needs_input`。发布后需核对实际 Run 的模型与工具审计关联、持久回执和结果，不能用 mock 服务或 readiness 代替同题验收。
