## 问题

Git 主线与运行发布存在源码漂移。成员档案、自动咨询、调用预算、知识来源读取和统一计划的补丁分别保存在运行镜像、H5、微信及商城发布目录。仅拉取 Git 不能重现这些现有能力。

## 决策

### 实现方案

以 `origin/main` 的 `3a048ff` 为基线，按源码摘要恢复已部署补丁。最终取证来源是 API 镜像 `91bf5630270fc06e60b92cc556c668472af21596cf239dd8d42fb70465a1cd6e` 与 `unified-plan-sync-20261026` 的 H5、微信和商城源码；此前的 `e3542dc`、`onboarding-steps23-20261026` 和 `product-summary-20261026-105536` 用于三方比较，避免覆盖两端已有恢复行为。

成员档案服务拥有本人关联和自动咨询事务；预算与任务服务拥有费用预留、参考预算和稳定失败状态；计划 service、repository 和 Worker 拥有推荐组、依据版本、检查点及商城导出。App 保留会话切换、原幂等提交结清、明确不可重试的业务错误和草稿恢复。知识来源页面沿用主线权限模型，补齐引用行读取和完整正文入口。

商城继续拥有价格、库存、计划规则和履约。默认 Migrator 注册手机号及计划合同两项新增 SQL，并验证重复升级不改已有事实。复合商品匹配按同批累计库存选择候选，遇到无解时回退；有界搜索耗尽有独立状态，不冒充真实缺货。能力声明将 `multi_day_plan` 的用途、权限和家庭选择与实际入口统一。

只回存源码、对应测试及必要说明。环境、凭据、真实用户资料、依赖目录和构建物不进入 Git。构建、合成数据库验证和独立代码复审在本地完成。运行发布版本及原开发分支保持可追溯。

## 替代方案

只拉取 Git 会遗漏已发布补丁。以某一端源码整包替换会丢失另一端的幂等或自动咨询保护；因此按真实共同基线合并。直接覆盖运行服务会与同期发布竞争，服务器写入必须另行通过部署前置检查。
