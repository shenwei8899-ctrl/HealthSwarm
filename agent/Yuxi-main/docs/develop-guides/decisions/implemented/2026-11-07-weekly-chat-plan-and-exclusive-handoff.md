# 对话多日餐单与专属计划入口

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/weekly_meal_plan_service.py

## 问题

咨询对话绑定的单日配餐请求不能产生连续七日结果。“安排一周三餐”曾被当作单日请求并返回补充问题。专属计划页面打开时自动生成 21 天三档计划，不能让用户先看七日安排后自行决定是否启动更长任务。

## 决策

### 实现方案

聊天入口识别连续 2 至 7 天完整三餐请求；“一周”按七天、未指定起始日按今天处理。教育、取消、单日及无法确定起始日的文本继续走现有咨询或单日流程。多日生成只接受限定的家庭默认成员请求格式；包含新增忌口、指定个人或其他附加条件的表达会提示先核对档案并改写请求，不把这些条件静默丢弃。客户端提交原文、日期、天数、咨询线程及稳定请求键，服务端重新验证原文、账号、咨询成员、家庭关系和档案关联。

服务端在 PostgreSQL 保存多日请求归属，按日期复用现有每日安排任务，并固定每天的安排标识和版本。每日安排持有 Agent、规则、食材、授权、Worker 与最终餐单；同一日期仍受每日唯一约束。读接口逐日重验来源，只有全部日期就绪且各有三餐才返回菜名摘要。初始化中断超过 90 秒且有缺失日期时显示失败和重试入口；用户明确重试时仅恢复失败或缺失的日期。聊天恢复按当前咨询线程读取最近的多日请求；点日期回读绑定版本的正式餐单展示详情。切换账号、家庭、对话或页面时丢弃迟到的重试结果。

七日摘要后提供可选的 21 天专属计划入口。专属计划页打开只读取已有推荐组；缺失或过期时，用户点击“生成 21 天专属计划”才登记生成请求。原有档案、处理同意和规则检查仍由服务端执行。

## 替代方案

- 在一次 Agent 回复中拼接 21 餐：没有逐日业务来源、恢复和版本校验。
- 把七日请求直接当作 21 天专属计划：天数与用户请求不符，也会提前启动三档长任务。
- 客户端连续提交七个独立单日请求：离开页面后缺少统一的请求事实和恢复入口。

## 后果

多日餐单与 21 天三档专属计划分别拥有自己的结果和恢复状态。多日生成可能耗时，聊天提供进度并允许离开后回读；卡片只在所有日期完成后展示完整摘要。每日正式餐单的后续修改会使多日读接口重新核对来源。该流程不会自动创建订单。

## 验证

- 客户端全量测试 1526 项通过，覆盖一周/三日识别、附加条件拒绝、教育与取消文本、专属计划只读打开及相关聊天恢复。
- 小程序构建通过。
- 隔离 PostgreSQL 中的真实 HTTP 测试 2 项通过，覆盖建表幂等、多日请求去重、部分结果不发布完整摘要、另一账号拒绝回读、附加条件拒绝、版本失效与中断后重试。测试以合成每日结果验证多日编排；完整七日 Worker 与模型生成尚需部署后端到端验证。
