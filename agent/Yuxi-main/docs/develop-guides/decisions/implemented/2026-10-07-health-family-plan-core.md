# 家庭逐餐参与者与逐人质量检查

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_family_meal_plan.py

## 问题

单成员餐单无法表达家人只参加某一餐、同菜不同份量或不同成员的限制。家庭计划需要保存逐餐参与者和逐菜个人份量，逐人读取当前档案、复算营养及检查来源。目标读者为配餐和健康后端维护者。

## 决策

家庭餐单在既有预览、草稿及不可变修订中使用明确family类型。三餐分别包含参与成员；每道发布菜谱为明确吃该菜的成员保存克数或发布参考份量，不默认均分。参与者与实际菜品分配一致。计算器输出家庭汇总、逐成员各餐份量及营养、个人覆盖餐次和共同菜品索引；未知个人份量保持对应个人与家庭汇总未知。

计划repository核对当前版本及历史各版本全部参与者的编辑授权，质量repository核对全部档案读取和编辑或专业审核授权。写入按成员ID排序持锁，再锁规则及排序审核资格；刷新对象后参与者改变则拒绝。质量检查保存所有档案版本及来源摘要，逐人检查其实际选择配方的配料。任一参与者档案改版、撤回，以及申请人失去编辑或档案读取授权、审核人失去审核或档案读取授权，均在对应写事务永久使相关专业状态失效；恢复授权不复活旧决定。

完整参加三餐的成员消费既有全天目标。部分参加的成员消费外部批准的五项营养餐次分配比例，按实际覆盖餐次逐营养求和后约束覆盖量；缺分配规则明确未知。全天通用、医嘱和个人范围先求交并检查矛盾，再缩放到覆盖范围；零餐份比例不能消除无交集的医嘱。结果包含个人covered_meals及全天覆盖标签，家庭总量不作个人全天比较。任一成员未知或冲突即阻止整体专业批准，模型没有专业批准工具。

外部规则导入省略新的空可选字段，保持旧持久化协议摘要及检查兼容。JSON类型增加复用既有持久化表，不升级健康Schema或迁移身份/数据库架构。

## 替代方案

将总份量默认平均会改变个人事实，分别保存独立计划会丢失共同餐次和版本。只核对入口成员授权会暴露其他参与者信息。现有计划Owner保存家庭表达、全部授权与逐人检查，后续消费者继续使用这一事实。

## 后果

确定性HTTP家庭预览、显式保存、历史读取、逐人检查及当前专业状态可使用。后续用例分别由[家庭安全改版](2026-10-07-health-family-safe-regeneration.md)、[共同采用及成员今日读取](2026-10-07-health-family-plan-adoption.md)、[参与者和份量调整](2026-10-07-health-family-participation-revision.md)拥有。旧单成员换菜、候选/重生成、次日提议和质量Agent路径对家庭对象返回明确未就绪；共同采用使用既有采用入口的家庭协议。多成员模型处理同意、Agent工具、批准初始生成、日终联动及页面仍属于[六Agent工程目标](../proposed/2026-10-07-health-agent-engineering-completion.md)的后续范围。04.3/08.1完整任务保持部分完成。

完整档案及专业生产规则继续由外部交付。隔离合成批准资料只验证工程运算、权限和状态，不代表生产医学或真实模型质量通过。

## 验证

家庭unit独立手算A三餐300、B仅早餐60和家庭360，验证未知与发布参考份量、参与分配协议、个人限制、部分覆盖比例、零比例医嘱冲突及午晚不同营养比例。实际HTTP/PG证明预览保存幂等、不可变历史、全部成员授权及来源、逐人专业提交/批准、第二成员改版/撤回与申请人/审核人撤权永久失效。持有排序首成员行锁时，独立PG观察事务确认两条HTTP请求的阻塞链，释放后相反入口正常完成。

相关验证为128项不同unit（23家庭、99既有业务、6独立回放oracle）及83项不同真实HTTP/PG（11家庭、72既有个人目标/质量/配餐/换菜/重生成/采用）分组通过。历史读取按既有契约显示current=false及失效专业状态，旧幂等检查重放因来源变化返回410。此前已批准的单成员范围保持原检查协议，家庭未接入的旧入口负控返回409。既有实际worker/SSE回归、格式和文档检查在本地交付证据中分别记录，不以本决定替代运行结果。
