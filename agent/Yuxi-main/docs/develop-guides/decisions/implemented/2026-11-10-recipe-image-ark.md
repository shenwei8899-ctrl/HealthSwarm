# 菜品示意图接入方舟图片服务

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/reference_recipe_presentation.py

## 问题

图片供应商模型不可用时，图片任务吞掉生成失败并返回成功，餐单没有可读的成品图片。图片服务配置依赖无关的聊天供应商启用状态，不能独立配置。

## 决策

### 实现方案

已保存预览的图片任务由现有 handler 调用图片服务，结果存入 MinIO，原餐单展示读取接口回读图片地址。

图片生成采用私有环境配置的方舟接口及 Seedream 模型，显式请求 2K Base64 图片。完整生成地址和 API 根地址均可配置，使用已有 `RECIPE_IMAGE_BASE_URL`、`RECIPE_IMAGE_API_KEY`、`RECIPE_IMAGE_MODEL`，不读取聊天供应商凭据。请求只包含原谱菜名、食材、做法，保持服务水印；Base64 经格式和尺寸限制、WebP 压缩后存入 MinIO。接口协议以[方舟官方文档](https://docs.volcengine.com/docs/ark/image-generation-api?lang=en)和真实服务返回为依据，Flash 模型不接受的组图参数不发送。

沿用既有来源哈希和缓存路径，已生成图片不重复付费。图片任务继续后台运行，不阻塞餐单生成；任一图片生成失败则任务抛出异常，交由现有任务执行器记录失败。重新执行复用已存在图片，仅生成缺失项。日志记录异常类型及 HTTP 状态，不记录密钥、用户健康信息或供应商原始响应。

## 替代方案

只更改模型名称不能解决协议字段差异和失败被标记成功的问题。图片 URL 下载引入额外网络请求和外部链接信任边界，使用 Base64 返回即可满足需求。修改缓存前缀会让历史图片重新生成，保留原路径。

## 后果

聊天供应商配置不再为图片服务兜底，部署必须提供独立图片服务环境变量。外部额度、网络和模型权限仍可导致失败，但失败不再被报告为完成。历史任务状态保持原记录，补图通过实际生成和图片回读验证。页面、餐单事实及订单不变。
