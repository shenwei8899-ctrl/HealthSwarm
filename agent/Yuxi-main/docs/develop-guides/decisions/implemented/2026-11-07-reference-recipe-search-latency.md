# 参考餐单菜谱检索与商品回执减负

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/reference_recipe_index.py

## 问题

2026-11-07 一次已完成参考餐单 Run 耗时约 86 秒，其中两次批量菜谱检索分别耗时 6.3 秒和 11.6 秒。每次批量检索虽然只读取一次数据库，但为每个关键词重新拼接全部菜谱正文、识别食材，并对重叠候选重复解析原谱和匹配商品。同一次商品查询还为 49 个 SKU 重复发送完全相同的三条资料缺项说明及不参与食材判断的图片地址。模型调用仍占有耗时，不能把总耗时全部归因于检索。

## 决策

### 实现方案

`reference_recipe_index.py` 在一次检索调用内只拼接一次菜谱分片、计算一次正文食材提示；每个关键词仍独立评分和排序。某份菜谱首次进入候选时才解析原谱、计算同次商品匹配及来源哈希，后续关键词复用该次局部结果。复用范围仅为一次函数调用，不跨用户、Run 或知识库版本；真实原谱读取及保存时的来源复核不变。

`reference_meal_plan_service.py` 只收紧模型可见的商品查询回执：当多个 SKU 的 `data_issues` 完全相同且非空时，顶层 `shared_data_issues` 表示这些缺项适用于本次全部 SKU，逐项不再重复发送；不同缺项仍逐项保留。查询回执省略 `image_url`。商品事实哈希仍从商城原始数据生成，保存时重新读取并逐项核验；最终保存结果与展示继续使用完整商品资料。配餐提示和内置 Skill 明确共有缺项的适用范围。

## 替代方案

- 缩短菜谱摘录或商品描述可以进一步减少模型输入，但可能丢失食材、过敏原和来源核对依据。
- 跨 Run 缓存可以避免更多扫描，但需处理知识库更新失效与用户商品目录隔离。
- 保持原样没有兼容风险，但批量关键词持续重复解析同一批菜谱。

## 后果

搜索结果字段、顺序和来源身份保持原有语义。商品查询回执新增可选的 `shared_data_issues`，仅当全部商品缺项一致时出现；旧回执仍可重放。模型不再看到商品图片地址，但最终餐单的商品图片仍从当前商城资料取得。此优化未改变模型服务商、Run 状态或授权边界，用户端总耗时仍受模型和其它步骤影响。

## 验证

- 隔离 Linux 容器中，批量检索与参考餐单相关定向单测 70 项通过；最终化、保存完成和咨询链路另有 95 项通过。工程契约检查及其 63 项自测、Ruff 检查通过。
- 对当前菜谱库 7265 个分片、3687 份文件和本次 49 个已读商品做只读对照，两批实际检索参数的候选完整结果与原版相等；计算耗时分别由 6.076 秒降至 1.939 秒、由 11.291 秒降至 7.168 秒。数据库读取约 0.144 秒，不是主要耗时。
- 本次商品回执按新规则模拟投影，字符数由 56487 降至 40859；保留各 SKU 的事实哈希，异缺项不共用。此数字是回执体积对照，不等于真实模型或用户端时延。
- 全量单测在隔离镜像中受缺失沙盒测试文件和其它既有失败阻断；一个参考餐单选择测试的失败已在未挂载补丁的同一镜像复现。真实模型端到端耗时及部署后表现未验证；本决定对应代码尚未部署。
