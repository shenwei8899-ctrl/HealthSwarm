# 普通用餐建议与可保存参考餐单的边界

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/health_consultation_service.py

## 问题

本文面向维护营养咨询提示、商品查询协议及参考配餐的开发者。普通“直接配餐、安排晚餐”进入咨询角色，但固定提示与内置 Skill 对候选建议、正式餐单和商品推荐的区分不一致；商品中间件还会为没有购买意图的吃饭问题强制查询商城。参考任务只接受本 Run 检索并打开的受控食谱，聊天内补交食谱不能形成保存回执，追问用户提供来源无法解决缺源。

## 决策

### 实现方案

`health_consultation_service.py` 的固定提示与 `family-nutritionist` 内置 Skill 区分普通候选建议和显式保存任务。咨询按当前授权读取已确认的过敏、忌口及医嘱，以真实资料给出不保存的候选；不要求用户提供可保存食谱，不新增 planner 或 save 工具，不生成个人营养目标或专业适用结论。

`HealthCatalogMiddleware` 仅为明确商品、选购或商品营养意图强制查询；按标点和转折分句排除否定购买，保留后续明确商品查询。显式下单和加购措辞只触发商品查询与选择，不增加订单能力。已经查询的本轮仍须提交结构化选择后才能完成答复。普通吃饭问题可以直接结束准备并答复，真实商品推荐继续通过查询和选择回执生成卡片，未知 SKU、营养值及交易资格保持未知。

参考提示保留受控知识库、原文引句、用途同意和同 Run 保存回执要求。受控来源不足时明确说明“当前资料不足以保存”，只询问用户能回答的偏好或限制；停止重复索要当前工具不能摄入的食谱材料和来源。现有 questions 协议及持久化不变。

工具实际提供当前计划时的解释与只修改所选餐次约束，见[参考餐单保留未选餐次](./2026-10-28-reference-selected-meal-preservation.md)；该规则不要求所有上下文版本提供同一字段，也不替换参考保存 Owner。

## 替代方案

- 所有普通用餐问题查询商城：扩大商品调用范围，使不涉及购买的建议依赖商城可用性与额外模型调用。
- 让咨询调用 planner/save：跨越当前用途与显式保存边界，不能仅用提示语增加能力。
- 允许聊天食谱绕过受控来源保存：失去当前知识库版本和原文回执校验。

## 后果

普通用餐问题可以在当前咨询完成，不因缺少可保存食谱或商品资料进入额外查询。真实商品请求仍拥有本轮查询与结构化选择回执，参考保存仍绑定受控来源、明确日期成员和当前运行。固定提示只约束模型输入，不保证实时模型一定遵循，原失败运行的后端类别仍需只读轨迹核对。

reference 的整篇打开正文过敏扫描会因其他菜谱出现限制食材而误拒。该问题仍存在；修复须先定义可证明完整的所选菜谱原文范围，不能仅扫描模型挑选的食材词。本文决定保留现有硬校验，不对其误拒行为声称修复。
