# 参考餐单完整执行与重复请求上下文

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/health_consultation_service.py

## 问题

真实三餐请求经过上下文、逐菜检索和读取后，在第十三次工具附近触发 80 超级步限制。保存预览不等于 Run 成功；最终回执未完成时，日计划仍为空。重复请求还向模型发送旧轮工具流水及完整商品营销详情，输入持续膨胀。客户端将“只换明天晚餐”误识别为普通咨询，因而只产生文字回复。

## 决策

### 实现方案

参考模式的服务端运行准备提供 224 超级步，覆盖现有 DTO 上限三餐十五道菜的逐菜检索、读取、保存、一次引句纠错和最终核验。其他健康模式的预算保持现有值。原权限、租约和来源核验在每个节点继续执行；不将失败预览自动激活为日计划。

`MealPlanResultMiddleware` 仅在模型输入中删除当前带请求标记的 Human 之前的工具调用及回执；用户文本、补充追问和当前轮证据保留，checkpoint 与审计保持原文。`reference_meal_plan_service` 的上下文商品目录省略营销详情和重复缺项文本，保留包装、配料、过敏原、完整性状态与完整事实哈希；保存服务继续按完整商品数据回读并拒绝冲突或变更。

小程序的意图识别与现有续改入口接收明确换餐命令；如何操作等咨询问句不触发改餐。修改按服务端日计划版本和用户指定日期执行；不存在原计划时明确要求先生成，不退回通用回答假装完成。

## 替代方案

单独提高步数不能消除上下文膨胀；自动采用失败 Run 的预览会改变发布边界；删除持久化历史会破坏审计。新增批量工具可以减少往返，但同时改变工具协议与来源回执，独立评估后再推进。

## 后果

224 是有限图步数，不是模型调用数；仍可能因供应商延迟、资料缺项或校验失败而停止。多菜逐项检索读取仍有多次外呼，不能由输入字符减少推断真机延迟已经改善。正式专业规则、菜谱和 SKU 资料尚未交付，日常参考餐单不等于专业审核通过。

2026-11-02：当前源码参考配餐与日计划采购真实 HTTP/PostgreSQL 回归 57 项通过；小程序全量 1090 项通过。生产构图的 15 菜测试使用合成工具服务与内存 checkpoint，不代替真实 Worker 和真机验收。

发布交接：按用户要求，本轮仅提交代码，由同事拉取构建发布。后端三文件候选镜像已准备，尚未切换 API/Worker；客户端入口修复必须随新小程序包生效。复测应先生成指定日期三餐并回读有效日计划，再只换晚餐，核对早餐和午餐对象及来源保持不变。
