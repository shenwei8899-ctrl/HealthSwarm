# 单成员安全配餐预览与页面确认

状态：implemented
类型：feature
Owner：web/src/components/health/HealthSafeMealPlanner.vue

## 问题

单成员已保存餐单的安全配餐Agent提供只读预览，现有餐单页面只有基础草稿生成与手动换菜。用户需要在明确的专业来源下选择AI换菜或整份重生成，查看具体菜品、份量及营养变化，再确认保存新版本。

## 决策

### 实现方案

餐单页面在当前单成员保存版本下挂载独立安全配餐面板，复用健康API、Agent Request/Run轮询与餐单快照组件。用户输入批准规则代码，读取当前专业档案和批准规则后明确同意meal_plan用途；发起时冻结成员、餐单及所有来源版本和操作。线程响应、Request、Run与输出逐层核对身份及操作；页面切换成员、版本、授权或处理政策时丢弃迟到响应并清空私有预览。

候选快照与数值来自服务端投影。用户选定候选或整餐预览并明确确认，首次写入前重新读取原Run，核对当前AI回执权限、来源及完整投影，再调用现有safe-swap/safe-regenerate接口。普通业务确认接口独立按饮食与专业字段授权；前端回执读取与业务事务是两个边界。页面冻结原始确认包和幂等键以恢复未知响应，已有确认包重试直接调用原业务确认接口，由服务按原幂等键恢复已提交收据或完成尚未提交的操作；保存后失效的原Run不会阻止恢复。保存成功回读餐单与当前审核状态；来源冲突、撤权或旧预览失效清除预览并给出补充或重新生成入口。页面不能以模型回执直接保存基础草稿，也不能继承旧专业批准。

## 替代方案

在基础草稿生成状态机中增加模式会把新建草稿与已保存版本的确认语义混在一起。独立面板保留两种业务入口，共享计算快照与API基础设施。

## 后果

基础草稿生成、手动换菜与安全Agent改餐保留独立入口，复用原有快照、Request/Run和业务确认Owner。首次确认重验当前AI回执，最终写入及收据恢复继续由安全业务服务校验饮食与专业字段授权、来源版本和幂等性。回执读取与普通业务确认分别提交，两次HTTP不构成撤销AI授权与餐单保存之间的原子互斥。

挂起轮询可以停止当前请求，取消开始时失效旧读取代次。Agent Request的404保留原请求与恢复入口；健康对象、专业来源或业务确认的403/404清空私有内容。预览、当前专业审核和实际饮食是三个不同状态，保存新餐单版本后必须重新专业审核与采用确认。

完整专业档案、生产专业规则、真实外部模型、小程序和长历史性能仍需独立验收。宿主Web全局最小宽度为450px；375px视口仍受该既有约束，不能据此声明手机端已完成。正常桌面及768px布局复用现有主题与响应式快照。
