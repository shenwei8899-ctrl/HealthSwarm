# 统一健康对话意图分流

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_intent_router_service.py

## 问题

聊天输入同时承载营养咨询、单日餐单和长期专属计划。当前前端规则会把多日输入直接启动长任务，单日日期只支持今天和明天；后台普通咨询仍可看到商城工具，导致“后天吃啥”等输入进入错误角色并出现商品卡片。

## 决策

统一由服务器提供意图分类结果。明确的单日餐单、明确的多日/长期计划和普通咨询由确定性规则处理；歧义文本进入无业务工具的意图分析阶段。协议入口为 `nutrition_consultation`、`single_day_meal`、`exclusive_plan`、`needs_clarification`；分析模型只能选择咨询、单日和追问，专属计划由明确规则产生。分类只决定入口，后续健康资料读取、商城和生成任务仍分别执行现有授权。

单日结果携带服务器业务日期、餐次和动作（生成、查看、调整）；前端用结果建立现有参考餐单任务，并沿用成员、授权、处理同意、模型审批、预算、FIFO 和已保存餐单复用。明确多日请求只返回专属计划入口提示，用户点击后才进入现有专属计划页面。普通咨询默认不暴露商城工具；只有明确商品、价格、库存或购买意图时才开放已有商品工具。所有分类输入采用稳定请求键幂等，超时或无法判定返回追问，不回退到专属计划。

### 实现方案

后台在 `health_intent_router_service` 保持纯分类规则与协议校验，HTTP 路由只装配输入输出。现有健康任务入口继续负责授权和任务创建；分类结果不创建 Request/Run。前端在发送前调用分类接口，单日分支把精确日期传给 `referenceSelection`，多日分支展示入口卡片，咨询分支继续现有咨询流程。Agent 的 `HealthCatalogMiddleware` 在没有明确商品意图时从模型工具列表移除目录查询和选品工具，最终阶段仍对明确商品请求执行已有强制查询与选品校验。

分类服务先校验咨询线程、成员授权和处理审批，使用对话行锁提交幂等占位，然后执行规则或一次最长 12 秒的模型调用。模型复用当前已审批的咨询模型和费用预留，外呼前再次核对处理授权，结束后结算真实用量；模型仅接收当前问题、日期餐次上下文和最近两条各最多 800 字的正常对话。发布结果前再次核对处理授权。回执保存在对话元数据；多日入口和追问同时保存用户及助手消息，历史接口只公开与已提交回执完全一致的助手提示，前端恢复入口按钮。重复请求不会再次外呼；占位尚无结果时返回待确认追问，用户可编辑问题发起新请求。已受理的生成任务继续由现有 Request/Run 与 FIFO 管理。

## 替代方案

继续由前端正则独立分流会在不同客户端产生不同结果；所有输入直接进入配餐师会污染普通咨询并触发商城查询；让分类 Agent 直接创建任务会绕过用户点击和现有授权边界。这些方案均不采用。

## 后果

每次文本发送增加一次分类 HTTP 请求；确定性规则无需模型外呼，歧义分析增加模型延迟和费用。服务器业务日期作为日期事实源，客户端只携带待核对的已有餐单上下文。未匹配输入进入分析或追问，用户点击专属计划入口后由原页面完成档案、授权和规则检查。已有下午加餐选品行为沿用商城意图规则；普通营养科普和单日配餐请求不使用该选品入口。

幂等占位在进程中断后保留，重放不会自动重新外呼；它不代表仍有任务运行。用户使用新问题请求键重试。对话元数据保存小型分类回执，随对话存续，后续规模扩大时可迁移到独立回执表。新客户端依赖分类接口，需要先上线后台再发布小程序。
