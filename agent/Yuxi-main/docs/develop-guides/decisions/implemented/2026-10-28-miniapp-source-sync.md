# 小程序源码与业务接口同步

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/daily_meal_plan_service.py

## 问题

可运行的小程序包与主线源码缺少同一份聊天恢复、每日计划、参考餐单和地址交互实现。只保存编译包无法重建业务行为，覆盖旧源码快照会丢失主线登录修复。

## 决策

### 实现方案

每日计划服务以账号、家庭和业务日期保存各餐次的正式安排或参考预览引用，内容和授权仍由原业务服务拥有。完成发布与每日版本校验位于同一持久事务，重复生成、调整餐次和采购继续核对当前来源。健康 Schema 33 保存每日引用与待处理请求，建档准备沿用同一任务注册、幂等回执与恢复链路。

参考餐单保留知识来源、营养未核算和未专业审核标记。旧聊天卡片及已签发采购证明也要核对当前餐次，省略每日版本不能继续购买已替换的内容。商城分别识别参考餐单与聊天目录选品的来源类型和菜单引用，并核对账号、商品及包装数量；收货地址偏好通过商城自己的迁移与事务维护。

客户端在 App 源码中恢复聊天任务、业务日期和页面返回状态；导航缓存绑定账号、家庭、邀请与待提交状态，前台恢复强制回读，权限继续由后端执行。主线欢迎页的原生导航回执、微信事件阻止冒泡、工程入口与登录测试保持有效，新增导航和每日计划测试进入默认测试入口。API 地址和知识库 ID 从环境注入。

## 替代方案

编译包归档只能提供运行快照；仅合客户端会留下缺失接口；整目录覆盖临时快照会带入主线回退和无关配置。按源码路径组合客户端、服务、迁移与契约测试，维护成本由各业务 Owner 承担。

## 后果

服务部署需要先执行健康域与商城地址迁移，再启动对应 API 和 Worker。餐单变更、档案失效、商品变化或授权撤回会拒绝继续使用旧来源。并发库存检查读到同版本已完成事实时返回原快照，保留赢家的 attempt 和回执。

普通聊天商品工具的查询与选择受本轮请求和已确认档案约束；档案版本或内容变化使已有工具上下文失效。正式营养建议仍依赖发布规则和校验，参考采购的交易资格不表示个人营养审核通过。

## 验证

Passed：客户端默认 Node 回归 649 项；后端全量 unit 5070 项及后续变更范围 unit 28 项。新负向用例覆盖指定工具未执行、查询后未选择、拒绝商品推荐、旧档案上下文及未查询的 SKU。

Passed：参考餐单、每日安排、建档准备和恢复使用真实 TCP 与独立 PostgreSQL Schema；旧卡片、旧采购证明、跨账号、并发替换和延迟库存失败均有拒绝或快照保持断言。外部模型和商城端口使用合成输入，测试不表示真实 Worker 或模型质量验收。

Passed：商城 PHP 语法、参考商品契约与地址服务规则；地址迁移在独立 PostgreSQL Schema 重复执行三次并核对原数据与标签保持。旧 PHP 来源实现和旧库存分支的负控均在预期断言失败。

Passed：H5、微信构建、上传体积检查、文档构建、工程信任检查及其单元测试。主线欢迎页、微信工程配置、代理脚本和登录测试逐文件保持。

Not run：微信上传、真机、真实商城 HTTP/支付/退款、生产模型/OCR/ASR 与 Run/Worker 完整 E2E。源码同步通过独立评审后以分支交付，部署与主线合并单独执行。
