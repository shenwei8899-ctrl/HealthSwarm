# 参考餐单的逐人份量与营养回读

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/reference_serving.py

## 问题

数据库参考餐单原先只保存家庭用量及可选分菜比例，菜品详情不能解释每位成员如何分餐。食材营养资料、已发布配方与碗勺换算表尚未完整填充，不能把原谱说明或商城包装营养当成个人摄入。

## 决策

### 实现方案

新保存的数据库参考餐单每道菜必须包含 `serving_suggestion.members`，记录实际就餐成员、预计熟食克数、可执行分餐说明及按原料位置分配的用量。个人原料合计必须等于家庭建议总量，单位一致；替代菜只覆盖实际食用者。所有份量标为建议估算，计划不自动变为饮食记录。旧快照读取不新增必填校验。

菜品详情的展示与营养计算口径由[原食谱整道菜营养](./2026-11-27-reference-original-recipe-total.md)拥有；成员卡继续显示建议熟食克数，原菜谱食材原文保留。

营养只由程序读取已发布的 `health_recipe_version` 和 `health_food_record` 计算。参考目录版本绑定使用配方版本既有 `record_code=reference:<目录菜谱id>`、`dataset_version=<当前目录file_hash>`，由有发布权限的数据维护流程显式建立，不能按菜名模糊匹配。该配方 ingredients 顺序必须对应目录原料顺序，每项 `ingredients[].food.id` 指向实际发布的食品版本。计算要求原谱原料项及其克数完整；任何缺项时保持未核算，不使用候选待审食品，不生成零值兜底。食材营养缺项逐项保留未知。

保存营养计算结果和已发布版本引用，历史归档保留成员规划及计算依据。新增资料使用现有版本表和 JSON 快照，无 schema 迁移，不改动现有目录或生产数据。

## 替代方案

仅展示分菜百分比不能指导实际分餐；按整菜营养乘同一百分比会在成员肉菜比例不同时算错。依赖模型直接填写营养数值缺少可核对来源。重建一套营养或份量库会重复已有版本结构。

## 后果

未发布营养资料的菜显示暂未核算，资料完成发布和目录版本绑定后才提供数值。

## 验证

单元测试覆盖成员越界、分配守恒、重复位置、非有限数值、模型注入营养和原料营养缺失；隔离 PostgreSQL/HTTP 测试验证保存及读取成员规划。具体执行结果在本次任务验证记录中保存，不以代码存在替代运行通过。

共享说明只由原谱原料和已验证的分配构造；模型自由说明仅保留在有授权的私有快照，归档与共享响应删除该自由字段。新营养计算同时复核配方和全部食品来源是否仍有效，历史计算快照保持原值。

隔离 PostgreSQL／HTTP 用例验证 JPEG 与 WebP 保存回读、缺少成员规划拒绝、实际历史归档，以及配方和食品来源变更拒绝。原食谱总营养的数值和旧快照兼容证据由[后续决策的验证](./2026-11-27-reference-original-recipe-total.md#验证)拥有。生产模型和微信真机验收 Not run。
