# 家庭默认就餐名单与已有餐单联动

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/meal_roster_service.py

## 问题

默认就餐名单保存在家庭 settings，既有餐单保存生成时的成员。此前保存名单不会更新已有餐单，且今日餐单入口无法直接选择人员。

## 决策

今日餐单卡片与弹层共用成员入口，支持当天全部已存在未用餐餐次或某一餐。名单设置保存与持久 Task 登记共用事务，提交后投递；pending publisher 负责提交后投递失败的恢复。普通成员只调整当前家庭当天名单，家庭默认设置仍由原权限控制。

每日来源索引保留 `_roster` 元数据，逐餐记录 default/explicit、目标名单及明确的 consumed_at。已确认用餐和历史日期不被重新发布。个人记一道菜不等于确认整餐吃完；新增明确整餐确认入口。旧餐次只在原成员等于原默认名单时迁移为默认，其他旧例外保留。

服务端每日版本拒绝旧结果覆盖。后台沿用现有参考配餐入口、来源校验和最终索引发布，不把前端名单或模型成功文本当成已更新。参考餐单仍保持未核算营养及未专业审核语义。失败保留最后成功的展示快照，阻止未完成成员更新的采购；新名单可重试。

多日对话计划在同步后的日期读取当前共享每日索引。专属推荐按新名单重新生成未执行日期，保留过去日期及明确已用餐/单餐例外内容，保留内容不计入新采购；已导出商城订单快照不写入。

## 替代方案

复用现有 JSON 来源索引与 TaskRecord，未新增数据库域或 schema 版本。用餐确认保留原菜谱，不能仅凭钟点推定已吃过。界面移除本餐详情的成员修改入口，避免用户重复逐餐操作。

## 旧餐单的资料版本变化

线上曾出现已有共享餐单回读时抛出 `memory_changed`，三餐归档仍在，但页面整体读取失败。读取每日餐单时，将 `memory_changed` 与 `profile_source_changed` 视为旧资料待重验：参考来源及用户选菜组合保留归档菜谱、原成员和版本，返回 `needs_regeneration`，该响应不提供未核对餐次的采购选项。已确认用餐仍按原记录读取。家庭访问、权限、缺失来源及回执错误继续拒绝，不把所有 409/410 统一降级。

相比直接跳过记忆校验，这一处理保留重排要求；相比清空餐单，它保留最后成功保存的内容。没有修改记忆发布校验、独立采购接口、数据库结构或现有成员名单。新增 HTTP/PG 用例以合成来源错误验证归档、重排、权限与回执边界；真实记忆失效另以当前生产餐单在旧版和候选版的隔离进程回读对比确认，会话回滚、不输出餐单正文。

## 验证

定向前端单测、H5/小程序构建；独立 PostgreSQL/TCP 验证名单保存、任务原子登记、幂等、跨家庭拒绝、确认用餐、旧结果拒绝及持久 worker 的忙任务恢复。模型和供应商使用合成替身，真实模型全链路和微信真机仍需验收。

## 后果

名单变化登记后台任务；更新中保留展示并拒绝未核对采购，历史餐次与已有订单保持原事实。
