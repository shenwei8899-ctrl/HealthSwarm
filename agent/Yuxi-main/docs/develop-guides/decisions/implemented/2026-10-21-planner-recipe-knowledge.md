# 基础配餐师菜谱参考检索

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_family_kb_service.py

## 问题

菜谱文档库与可计算的已发布菜谱目录分别存储。配餐师需要检索烹饪资料，同时保持结构化菜谱版本、营养计算和批准规则的权威性。

## 决策

配餐师复用受控知识检索工具，通过独立的 `HEALTH_RECIPE_KB_ID` 绑定单个库，结果标记为 `recipe_reference`。四种配餐模式在原固定业务工具外增加参考检索；成员身份、处理政策、同意及有效 Run 由服务端校验。采用现有只读 BM25、当前 PG 分片重验、工具审计和历史失效机制。

工具片段仅供烹饪和食材搭配参考。计划 DTO 仍要求已发布菜谱版本，所有数值由程序计算；最终输出只接受本 Run 预览回执或补充问题。参考文件不转换为批准目录，不修改专业规则。后台编辑页读取实际绑定并说明用途。

## 替代方案

直接把文档命中当作可计算菜谱会缺失原料映射、净成品重量和版本审批。通用知识库选择器会形成另一份可编辑绑定。固定只读参考检索复用既有边界，并保留结构化数据发布流程。

## 验证

2026-10-21：非 slow unit 分组 4845 + 10 项、最终相关 126 项通过；隔离 PostgreSQL/HTTP 来源失效和发布共享锁 7 项通过。四模式 API/Worker/SSE/PG 回归 14 项通过。新增真实 Worker 菜谱参考案例用合成 Milvus BM25 分片，完整执行参考检索、模型继续、程序预览及最终持久化，资料改版后任务回读 410。为容纳额外检索轮次，普通配餐与其他配餐模式统一为 40 步上限；原 20 步会使该正例失败。生产实际库只读检索 4 条均与当前 PG 分片一致，无外部模型调用。

工程契约、63 项检查器、Ruff 和 docs build 通过。正式政策暂缓，真实供应商与生产成员完整配餐链路为 Not run；本地实现和验证不等于生产启用。

## 后果

管理员需提供已索引的实际库 ID 并使 API/Worker 配置一致。业务负责人仍需发布可计算菜谱、份量及适用规则；资料库数量不等于可配餐数量。真实模型验收须另有批准用途与调用预算。
