# 换菜候选复用本次商品索引

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/services/daily_dish_swap_service.py

## 问题

换菜候选在家庭事务内逐份菜谱重建商品索引，拉长家庭锁持有时间；同一家庭的专属计划读取等待该锁，超过小程序请求时限后显示待重试。冷菜谱解析还占用 API 事件循环，延迟其他请求。

## 决策

### 实现方案

候选读取先用短事务验证家庭访问并读取公共菜谱行，提交后在线程中只解析原文、分片哈希和菜谱结构，跳过排序不使用的全文召回信息。随后新事务重读当前餐单并重验权限和版本，再计算候选；入选原谱仍在该事务中逐一锁读并核验完整原文。换菜写入继续在原写事务中准备和重验候选。每次候选排序只创建一次当前安全商品列表的索引，所有候选食材复用同一索引。索引生命周期限定在该次排序，成员限制、目录变化和后续请求仍使用各自的实际输入。

最终读取和写入的家庭授权锁、餐单版本、当前成员限制、完整原文及分片哈希、食材做法校验和替换持久化顺序由原服务继续执行。修复保持接口与候选排序语义，直接记录完整局部修复，无需先裁决新的事务或缓存协议。

## 替代方案

跨请求缓存商品或已验证候选需要额外失效协议。将全部候选计算移出最终授权事务需要重新设计撤权和版本竞态；只提前解析公共菜谱保留最终事务边界。延长客户端超时保留重复计算。当前方案直接复用既有索引参数及后台线程设施。

## 后果

候选排序减少重复索引构建，解析不独占事件循环。数据库与对象存储读取及家庭锁等待仍受运行环境影响，耗时需通过真实服务探针衡量。

## 验证

定向单元覆盖多份候选只构建一次索引、排序与逐份独立索引对照一致、匹配与缺口结果、解析使用其他线程及已释放的预检事务、解析后撤权拒绝、精简解析与完整解析的原文及排序一致、本餐成员限制及完整原文变化拒绝。真实 HTTP/PostgreSQL 集成覆盖单菜替换、幂等、版本及越权拒绝。定向单元130项及真实HTTP/PostgreSQL集成2项通过，后者以另一连接的家庭行锁 NOWAIT 验证解析阶段已提交预检事务。原实现重复索引的220份候选与复用索引的结果逐项一致。独立进程冷启动并发探针在公共解析期间读专属计划4.924秒且ready；候选计算3.154秒，不作为全部接口时延保证。实际部署镜像和后续线上结果保存在独立发布证据中。
