# 批准规则驱动的整份三餐安全重生成

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_safe_plan_regeneration_service.py

## 问题

单菜换菜要求替换后全天合格，不能修复必须同时替换多道菜的冲突。配餐工程需要提供整份保存三餐的候选及用户确认保存流程，保留来源、历史和专业审核边界。

## 决策

使用当前确认档案与批准换菜目录，针对全部三餐中的每道菜枚举同类型、适用餐次及批准营养差异以内的实际发布版本。保留服务器复算份量，逐配方过滤明确禁忌、未知分类和旧来源；用户不提交营养或安全结论。组合搜索按批准差异排序，同时替换多道菜并执行完整全天质量检查。

搜索拥有有限运行预算；达到预算明确返回搜索未完成，只有穷尽允许组合才返回没有合格方案。完整档案、批准营养范围或目录未就绪明确返回缺依赖，代码不补医学阈值。

预览只返回服务器方案、来源和摘要，不修改原餐单。用户确认摘要时在原权限、计划、档案及规则锁下重新生成；摘要不符拒绝写入。保存使用与单菜换菜相同的修订、检查及专业状态 Owner，在同事务失效旧审核/采用并生成新检查；最终复核不通过使整个事务回滚。幂等重放保留原应用版本，不能恢复失效的专业批准。

## 替代方案

连续调用单菜接口会在必须共同换菜时停住，且产生多个中间版本。无限穷举不能保证有限接口延迟；固定截取三候选后声称无解会丢弃真正的合格组合。有限搜索和明确未完成原因保留真实结果边界。

66项相关unit通过，包括9重生成、11单菜、24质量、16配餐和6采用。68项不同HTTP/PG用例分组通过：10整份、1整份末次到期回滚、19既有单菜及38质量/采用/配餐回归。三餐原50/100/150克、合成110kcal/100g配方全部替换后手算为55+110+165=330 kcal；批准范围和三餐过敏限制各有必须共同修复的实际负控。保存后原300 kcal修订、原采用快照及饮食记录独立保留。

预算反例使用差异[0,1,2]与[0,100,200]的两个槽位，差异2与100均可行；不能保留完整前沿时返回搜索未完成，充足预算选择差异2。真实整份写入在专业审核失效行锁处暂停，用pg_blocking_pids绑定等待关系，规则自然到期后最后quality_not_passed，计划、修订、检查、审核和采用全部回滚。

8项既有E2E通过，其中2项实际API/worker/SSE、6项直接PG发布/checkpoint边界。隔离worker确认无非终态Run及排队请求后重载当前源码；证据证明运行回归，不证明新增Agent重生成工具或真实模型质量。Ruff、工程契约/62项检查器unit、docs build及独立复核通过；无Schema变更。测试分别由test_health_safe_plan_regeneration.py、test_health_safe_plan_regeneration_http.py及test_health_safe_meal_swap_guards_http.py拥有。
