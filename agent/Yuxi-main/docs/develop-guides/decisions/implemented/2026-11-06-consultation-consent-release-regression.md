# 普通咨询同意检查的发布回归修复

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/repositories/health_vision_repository.py

## 问题

已有本人档案的用户发送问题时被咨询就绪检查阻断。真实 HTTP 读取显示普通咨询为 `unavailable / consent_required`，目录和每日历史为 403。当前 API 与 Worker 的 SKU 发布镜像同时携带独立咨询处理同意检查，与建档后直接咨询的契约存在偏差。

## 决策

### 实现方案

本决定部分取代[固定家庭知识库咨询](./2026-10-14-health-consultation-reviewed-family-knowledge.md)与[餐单完成及恢复](./2026-11-06-reference-meal-completion.md)中的独立咨询同意约定。成员访问、逐来源校验和其他用途处理同意继续由各业务 Owner 核对。

以当前 SKU 运行镜像的不可变 ID 为基线，在用途校验、会话访问、目录和每日历史四个 Owner 恢复普通咨询契约。成员 `ai_use`、线程归属和逐来源访问由现有服务端授权负责。发布前核对运行文件哈希，候选使用独立 PostgreSQL 验证，并使用当前配置下的候选应用进行只读真实 TCP HTTP 验证。切换等待空闲任务并使用发布锁，失败恢复原镜像及原 Compose 配置。Compose 镜像引用解析为不可变 ID 后再校验，API 与 Worker 的容器健康和网关就绪共同决定切换成功。

小程序普通咨询遇到异常同意状态时显示服务状态异常和重新连接操作。需要明确同意的结构化用途沿用当前处理方、政策版本与勾选确认入口。恢复操作只重读入口，用户确认发送后才提交原草稿。

## 替代方案

整份本地后端覆盖运行文件会混入其他未发布修改。恢复早晨的整个镜像会丢失后续 SKU 发布。增加普通咨询独立开关会改变既定产品契约。采用当前镜像上的四处定向补丁。

定向小程序同步回读确认三文件哈希匹配，其他 629 份文件一致，主包为 1,865,175 字节并通过现有体积检查。工程校验器的 63 项测试在 Linux 通过。基于最新主分支的独立提交工作区通过全仓工程契约检查。当前改动文件的差异空白检查通过。

提交工作区的 150 项相关后端测试包含真实 PostgreSQL 回归，270 项相关前端回归、锁定 Ruff 版本的检查及格式检查、微信构建和文档构建通过。全量后端 unit 已执行，隔离环境中的资源文件缺失、可执行位丢失及只读目录写入导致失败，完整源码复跑尚未获得成功完成结果。最后一次远程连接与健康重验超时，发布时的 HTTP 与 Worker 回读记录保留对应验证时点的结论。

## 后果

普通咨询继续沿用成员权限，配餐等独立用途继续读取有效处理同意。小程序包采用三文件定向修改，保留当前包中的其他业务逻辑、作用域标识和配置，源码仍可正常构建。生产真实咨询已经由 Worker 完成，最终消息与同一 request/run 关联且交付状态为 complete。小程序上传、发布和手机体验为 Not run，仍需使用对应版本在设备上验收。
