# 批准规则驱动的单菜候选与安全换菜

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_safe_meal_swap_service.py

## 问题

当前手动换菜会重算营养并使旧审核失效，尚未筛选三道合格候选。配餐后端及接口维护者需要按已确认档案和批准条款判断同类型、营养相近和整天安全，用户明确换菜只修改选定一道菜。

## 决策

批准质量规则提供可选换菜条款：绑定菜谱配方摘要的菜品分类、允许餐次，以及五项营养的绝对差异上限。未提供条款时保留通用草稿接口，受控换菜返回缺依赖；代码不自定专业阈值。当前范围是单成员保存三餐的一道菜，计划份量沿用服务器复算克数，用户不提交营养或安全结论。

候选由批准分类内的实际发布版本生成。只保留同类型、适用所选餐次、营养差异不超过批准上限且替换后整天质量通过的菜谱；按标准化差异与版本ID确定顺序，最多三道，不足不凑数。返回规则/档案/计划版本、差异、服务器营养与来源。读取不保存餐单或写记忆。

安全换菜明确携带计划/规则/档案版本与候选菜谱ID。请求在同一事务重新筛选合格候选，提交新修订及质量检查收据，原审核和采用在同事务失效。幂等键和版本冲突不能重复改菜或覆盖历史。新工程检查不继承旧专业批准，原DietLog及已支付商城快照独立保留。

来源解析逐配方拒绝损坏的持久JSON，未选坏配方及共享食品的错误副本不会污染有效候选。候选批量加载来源，复用同一批准规则的已解析模型与食品分类索引，只保留前三份全天快照。原菜和其他菜的参考份量按真实版本计算，未替换菜的输入保留原样；换算克数不能转为支持的六位小数输入时明确不可用。

## 替代方案

硬编码相近热量或从菜名猜菜品类型会产生无批准依据的适用性判断。存储一份候选镜像增加失效维护，现有有界批准目录和当前版本可在使用事务直接复算。客户端提交任意替换而只检查营养总量会绕过同类型与三候选约束。

## 后果

这是[六Agent工程目标](../proposed/2026-10-07-health-agent-engineering-completion.md)中的单菜安全换菜阶段。[单成员整份重生成](2026-10-07-health-safe-plan-regeneration.md)单独交付；家庭逐餐参与者、个人目标生成、Agent固定工具与日终联动、未付采购及做法联动仍按原目标继续交付。红阳完整档案、专业生产分类/阈值、真实模型与商城保持外部TODO。通用手动草稿换菜接口不声明安全合格，后续页面需要明确区分。
