# 咨询商品查询与模型上下文去重

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/agents/middlewares/health_catalog_context.py

## 问题

营养咨询同轮重复空关键词第一页查询，每次回传完整目录、商品说明和签名，增加后续模型输入与等待。一次成功查询后继续并行重复查询，是已观察到的慢请求模式。目标是减少重复商城读取和模型输入，同时保留工具协议响应及原始来源、档案、选品和发布校验。

## 决策

### 实现方案

`backend/package/yuxi/agents/buildin/health_consultation/graph.py` 在授权中间件之后、目录选品中间件之前装配 `HealthCatalogContextMiddleware`，保留主线的选品与最终正文阶段。查询身份沿用服务的空白忽略、大小写和分页规则；同轮已有真实成功回执时，后续顺序或并行重复调用只返回原调用位置，不重新读取商品或声明新事实。首批查询尚无成功结果时仍走原服务；本中间件不缓存失败回执，若调用继续则仍交原工具，新用户消息重新查询。完整咨询仍沿用既有授权检查，商品错误回执可触发 `source_invalidated`，不承诺全图自动重试。去重依据消息和 checkpoint，不引入跨请求缓存。

模型输入只对新版 `catalog_context_version=1` 投影：同版本同内容目录保留首次原文，商品说明去掉 `note` 内重复副本，签名 token 留在原始消息。营养说明、未知项、适用限制、档案上下文和选品理由保留。旧版正文 `reference` 回执原样保留。原始 checkpoint 与审计消息不变，授权和最终发布继续使用原始来源。

## 替代方案

直接修改商品接口返回值会扩大业务回执和签名契约的变更范围。独立中间件仅在模型入口投影，并利用已存在的成功回执去重。提交前已同步主线 `0d987d3` 的选品及流式回答实现，用最小装配变更接入。批量 SKU 详情接口、模型轮次和客户端等待策略不属于本修复范围。

## 后果

首次同批并行的相同查询没有已成功来源时不会合并；这避免把未完成或失败调用当作成功查询。原始记录继续保存完整回执，节省的是后续模型输入与成功查询后的重复访问，不减少原始证据留存。生产发布仍需核对线上版本并执行实际链路验收，本次提交不等于部署。
