# 参考餐单按商品名生成候选并选择 SKU

状态：implemented
类型：simplification
Owner：backend/package/yuxi/services/reference_meal_selection_service.py

## 问题

参考餐单若让 Agent 复制原谱食材、自由编写匹配依据并选择 SKU，格式偏差会在菜谱和商品均已读取后阻断保存。商城没有对应商品也不能等同于餐单生成失败。

## 决策

### 实现方案

`reference_recipe_matching.py` 只根据原谱食材名称和商城 `product_name` 生成候选组，候选包含真实 SKU 的包装、价格和库存。商品详情、营养、配料、过敏原和图片不参与商品身份匹配或 SKU 排序。

`reference_meal_selection_service.py` 拥有原谱 `ingredient_refs` 和采购缺口。Agent 的 `read_selection` 只提交已读菜谱、本轮菜谱回执签发的 `candidate_key`、候选 `sku_id` 和整数包装数，并按当前就餐成员、原谱明确写出的用量与份数、包装覆盖、剩余量和总价选择候选。候选外 SKU 被拒绝；第一次错误允许纠正，纠正后仍无法可靠选择时降级为自行购买，不自动选第一项或一包。

没有同名在售商品或食材名称无法可靠归一时，服务端保存不含 SKU 和价格的 `purchase_gaps`。每日餐单继续投影这些缺口，小程序显示“自行购买 · 暂无价格”；购物车请求只包含 `purchase_items`。

## 替代方案

- 纯后台选择最低价忽略家庭人数、菜谱用量和包装浪费，因此不作为纠正耗尽后的兜底。
- 继续让 Agent 自由映射会保留目录外 SKU、食材原文复制和匹配依据格式错误，已删除该输入能力。
- 为缺失食材创建商城商品会伪造价格、库存和供应关系，不采用。

## 后果

- 商品名称规范化成为商品身份候选的语义 Owner；服务端保存前仍重验商品在售状态、库存、当前商品事实和已确认的饮食限制。
- 未匹配商品不再阻断菜谱和餐单，但用户必须自行购买并核对品种、形态与用量。
- 旧快照中的 `selection_pending` 采购兼容路径继续可读，新餐单不由 Agent 生成该状态。
- 商城接口不可用、菜谱来源变化或饮食限制无法核实仍显式失败，不能降级成“自行购买”。

- 参考链路当前已通过全部相关单元测试；小程序全量 1529 项通过且微信构建成功。
- HTTP 集成文件在本机没有集成数据库环境，61 项被 pytest 跳过，未计为通过。
- 小程序包体检查当前主包为 1,892,466 bytes，超过仓库预算 5,030 bytes；基线在本变更前已超预算，没有修改无关资源规避预算。
- 旧能力不存在：`ReferenceReadSelection` 不接受 Agent 提交的 `ingredient_refs`、`match_basis` 或 `purchase_gaps`。
