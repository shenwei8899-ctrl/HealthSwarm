# 专业复核工作台与用户主动角色交接

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_quality_service.py

## 问题

专业审核已有提交、退回、批准及失效事务，但用户无法在后台完成资料核对与补充闭环。固定健康角色已有独立用途和任务结果，用户仍缺少携带明确来源转入另一角色的受控入口。本轮先交付工作台，再交付主动交接；仅修改agent目录，使用隔离合成数据，不启用正式政策或调用真实供应商，不修改独立App客户端。

## 决策

### 实现方案

专业工作台沿用HealthQualityRepository和health_quality_service的当前资格、逐成员授权、检查版本及不可变动作。按成员提供“我的申请”和“待我复核”分页列表；详情展示原餐单、检查结论和来源版本，标明失效。申请人可提交理由与补充材料引用；有当前资格和全员授权的独立审核人可退回或批准。需要修改业务资料时回到已有档案、餐单入口，修改后重新检查产生新申请；不修改历史审核证据。

主动交接只支持指标回顾转营养咨询、饮食分析转基础配餐。用户预览服务端生成的最小交接摘要后明确确认；来源须为本人同成员已完成且仍有效的任务，目标用途独立检查配置、授权和同意。交接幂等绑定来源、目标、当前版本和操作者，创建独立会话，不自动提交模型请求。执行、历史和结果使用入口重新校验来源，撤权或改版后拒绝旧交接。普通独立会话继续使用原协议。

界面复用健康工作区、Ant组件和主题变量，提供加载、无资料、无资格、失效、冲突与未知提交结果的恢复路径。App接口交接文档记录新增协议，客户端同事另行接入。

## 替代方案

让管理员直接批准会绕过现有专业资格和自审隔离。复制专业审核状态机制造第二个事实Owner。自动角色协调或传递整段聊天超出本轮用户主动交接范围。只在客户端拼接摘要无法保护来源版本与服务端重放。

## 后果

健康Schema29只添加可空交接绑定，旧会话保持原行为；发布先迁移，再一致更新API、Worker与Web。来源变更会使交接会话后续运行及历史不可继续读取，用户需要重新预览确认。专业资格、真实审核责任和正式资料仍待业务方落实；正式政策保持关闭。正式App接入、生产发布及真实专业/模型验收不在本次合成工程结论内，协议见[工作台与交接参考](../../../advanced/health-actual-meals-and-reviews.md)。
