# 建档后先保存完整三餐，再展示今日安排

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/daily_arrangement_service.py

## 问题

卡片先于真实菜单完成时，用户进入详情会遇到空结果或笼统的饮食问题提示；只等待模型文字结束不足以证明三餐可用。库存、保存超时和多端重入也会导致重复生成。

## 决策

### 实现方案

每日安排由 PostgreSQL 的 actor/family/date 唯一记录持有。GET 只读；POST 创建或继续既有 Request/Run。Agent 解释必须绑定同一最终预览，营养数值仍由批准规则、正式配方及确定性计算产生。三餐完整、检查通过、保存成功，且逐餐商品包合计库存复核通过后，才提交 ready 快照。前端先展示解释，再展示卡片；卡片、详情和菜谱使用同一 ID/version。

建档服务在一个事务内保存明确归属的原有字段、版本和默认就餐成员。用户点击已展示当前处理方的“保存并分析”后，建立精确 ID 的自述来源关联与 meal_plan 用途同意；不创建专业确认快照，不替其他已认领家人授予 AI 权限。自述到配餐编码仅使用批准规则的 miniapp_profile_codes。

每个 Agent 提交、菜单保存及逐餐商品包使用稳定幂等键。Agent 结果在跨系统发布前持久化，网络或保存重试恢复原结果。模型不完整或库存变化允许有界自动重试；耗尽后记录 failed，由用户明确重试启动下一组分析。调整成员只重排目标餐次，固定另外两餐；服务不写订单或履约表。

## 替代方案

- 仅等模型文字结束：无法保证可读取详情，拒绝。
- 前端缓存拼接三餐或静默示例回退：缓存不能拥有服务端事实，拒绝。
- 把商城问题当作饮食冲突：会阻断查看已保存食谱，拒绝；采购时单独重新核对。

## 后果

新增表随健康 Schema 27 幂等创建。正式环境需要真实规则编码、菜谱步骤及食材映射、Agent Worker、处理方配置与商城签名接口。外部商城商品包和本地菜单不能共用数据库事务；稳定键和最终库存复核控制恢复，不声称锁定或预占库存。购买仍以商城最终报价为准。

服务缺项返回具体不可用状态，前端不显示空卡片。已有档案变化导致原来源失效时，须重新核对来源；已支付交易快照不改写。本记录落地于本地源码，不表示已部署服务器或完成真实模型验收。

## 验证

前端：daily-arrangement.test.mjs 覆盖三餐门槛、读写恢复、并发重入、账号切换与详情版本；npm test 和 H5/微信构建验证集成。

后端：test_daily_arrangement.py 验证逐人食材和逐餐整包库存、固定非目标餐次；test_daily_arrangement_http.py 在独立 PostgreSQL Schema 通过真实 HTTP 验证原子建档、重放、权限及服务缺项。相关初始配餐、专业校验、planner 回归另行运行。真实 Worker/模型/线上库存联动仍需部署后的完整链路验收。
