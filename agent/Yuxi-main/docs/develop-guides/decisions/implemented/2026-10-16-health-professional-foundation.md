# 专业营养资料与知识库来源关联

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/health_source_service.py

## 问题

档案投影、食品菜谱发布、批准规则、个人目标及配餐检查已经存在，但专业资料库与这些业务版本缺少可校验的来源关联。管理页面缺少批准规则的完整维护入口，用户难以知道个人目标及初始配餐还缺少哪些依赖。资料已进入知识库不代表已经完成结构化、专业确认及业务发布。

## 决策

### 实现方案

原始公共专业资料保存在现有知识库，通过服务端 URL 导入或内存整理后直接上传；不在客户端或开发机器保存中转文档。知识库继续拥有文件、权限、内容摘要及删除状态。食品、菜谱、份量和批准规则使用现有来源字段保存受控 `knowledge://` 引用（知识库、文件及原始内容摘要），外部普通引用保持兼容。发布时检查操作者的来源管理权与当前文件；业务使用时检查来源仍存在且摘要一致。数据库仍由已有食品、菜谱、规则和档案模型拥有，不另建重复专业文档库。

健康管理页增加知识库来源选择与批准规则管理，提供当前版本读取、明确确认后导入和撤回。专业档案页增加按用途的依赖检查，分别报告档案确认、批准规则、个人目标和配餐目录状态；就绪仅表示可尝试预览，不替代具体菜单计算、专业审核和用户采用。规则与菜谱继续使用已有计算和审批服务。

个体目标与配餐预览分别判断：既有生成服务允许使用批准的通用每日范围时，缺少个体公式不额外封锁该预览能力。来源失效沿用既有审核和采用失效事务，保留历史快照；新份量发布同时核对目标及其原料来源。

每日安排的采购包绑定安排身份、原始质量依据、成员来源及单餐摘要。商城在采购确认、报价和建单时将签名凭据回传，服务在同一事务重验当前账号、授权与专业来源；本餐内容或来源变化时拒绝消费。单餐调整保留其他未变化餐次的有效采购包，不因无关餐次的安排版本或尝试号推进而使其失效。当前协议与迟到失败保护的整合取舍见[分支整合记录](2026-10-28-branch-consolidation.md)。既有采用导出保留原任务及签名正文。

不从知识库正文自动推断疾病、公式、禁忌、审核资格或成品重量。正式公共数据只按可追溯原始来源整理；工程合成测试与专业数据验收分别报告。成员原始健康资料不进入公共知识库。首期保持现有五项营养指标，适用人群由批准规则明确限定。

## 替代方案

仅补充原始文档不能闭合业务数据消费；把资料直接放进提示词不能满足确定性计算与失效检查；建立第二套文档及规则存储会重复现有 Owner。引用使用已有不可变业务版本字段，避免为单一关联引入新的同步索引或后台任务。

## 后果

公共资料的专业适用性、许可和字段映射必须逐项核对。没有明确依据的参数保持缺失，不能为跑通流程构造生产审核记录。直接整理上传的来源清单和 USDA 363 条有效食品字段核对表已回读为已索引；这不代表正式食品、菜谱或专业规则已发布。

缺失收据、来源变化和晚到失败会拒绝当前消费并保留历史快照。原有未携带来源凭据的商城包继续遵守既有兼容契约；新签名包在采购确认、报价及建单时回源，普通餐单历史展示与直接加购仍遵守各自既有行为。

来源关联复用现有业务字段，不增加数据库迁移。部署保留当前每日安排、微信身份与商城连接代码，使用本地封装的不可变 API、Worker 和 Web 镜像；服务器只加载及替换目标服务，保存配置、数据库备份和精确回滚方式。
