# 家庭营养师商城订单供应链系统改造开发设计 V5

## 1 文档定位

本文档是刘北萍负责范围内的商城、订单、供应链系统改造开发总设计，用于产品复审、技术设计、接口联调、数据库设计、开发拆分、测试验收和上线准备。

本版以《家庭营养师-离线体验版(3).html》表现出的最新业务流程为依据，整合并替代 V4。除单餐食材包外，本版新增 21 天 AI 专属计划、一次支付分批履约、菜品级换一换、可选专业人工审核引用、逐批售后和供应商合作申请。后续开发以本版评审结果为准。

### 1.1 负责人范围

- 商城商品、分类、规格、SKU 和库存。
- 菜单食材需求到商城商品的转换。
- 向营养师 Agent 提供可售商品目录、SKU、食材组成、价格、库存和配送能力接口。
- 保存 Agent 动态组合的推荐食材包、版本、商品明细和换一换记录。
- 保存 AI 专属计划、计划版本、家庭成员适用范围、菜单日历和专业审核引用。
- 采购清单、购物车、结算、订单和支付。
- 专属计划一次支付、配送批次、逐批库存分配、逐批签收、暂停顺延、恢复重评、不退款确认和例外售后。
- 供应商合作申请、供应商商品、供应商订单、备货、配送和售后。
- 商城与供应链管理后台。
- 商城、订单及供应链相关服务端 API，供小程序团队调用。
- 与 AI Engine、微信支付、供应商和物流服务的接口联调。

### 1.2 不在本系统内部实现的范围

- 家庭健康档案和成员授权体系本身。
- 营养目标、营养成分及个人份量计算。
- 智能配餐和跨食材替换决策。
- 饮食图片识别和摄入量估算。
- AI Agent 的提示词、知识检索和内部编排。
- Uni-app 小程序页面、组件、路由、状态管理和前端交互代码。
- 小程序端微信支付调起、订阅消息授权弹窗和页面错误展示。

商城系统可以接收上游给出的过敏原和禁忌标签用于交易拦截，但不保存完整病史、用药、健康指标或专业评估详情。

### 1.3 后台与小程序的职责边界

刘北萍负责的是后台系统和服务端，包括管理后台页面、数据库、业务服务、自动任务及供小程序调用的 API。小程序团队负责修改 `uniapp` 目录中的页面、组件、路由和交互代码，并调用本系统提供的 API。

双方联调时，商城后端负责接口正确性、业务状态和错误码；小程序团队负责把接口结果展示给用户并收集用户确认。本项目改造不直接修改 Uni-app 源码。

## 2 改造目标和最终边界

现有项目是 FastAdmin、ThinkPHP 和 Uni-app 配套的通用商城插件，已经具备商品、SKU、购物车、地址、订单、支付、发货、物流、售后、优惠券和基础统计能力。本次只改造后台及服务端，不修改 Uni-app 前端代码。

本次改造在现有商城底座上增加两条可以并存的交易路径：

1. 单餐路径：菜单或菜品生成食材需求，匹配固定食材包或动态 SKU 组合，用户按需删减家中已有食材后直接结算或加入购物车。
2. 专属计划路径：Agent 生成多套 21 天计划，用户选择计划并完成 Agent 营养、过敏原和适用性校验，一次支付全部 21 天费用后形成 21 个每日配送批次。专业人工审核不是一期默认步骤。

单餐路径闭环：

```text
用户完成健康建档
                |
                v
营养师Agent读取已授权档案并调用商城商品目录接口
                |
                v
Agent先生成菜单/菜品，再从固定食材包和当前可售SKU中形成采购方案
                |
                v
Agent完成首次营养、过敏原和适用性校验
                |
                v
商城后端校验SKU状态、库存、价格和配送并保存推荐包版本
                |
                v
小程序向用户展示推荐食材包
                |
                v
用户确认或对某一道菜点击换一换并选择候选菜品
                |
                v
Agent对替换后的整份菜单重新做营养、过敏原和适用性校验
                |
                v
商城保存新版本并重新校验价格、库存和配送
                |
                v
用户删除家中已有食材，确认采购项并直接结算或加入购物车
                |
                v
支付后自动推单并同步备货、配送、签收及售后
```

AI 专属计划闭环：

```text
Agent生成多个21天计划候选和计划版本
                |
                v
用户查看21天三餐、食材包预估、适用成员和过敏原
                |
                v
Agent完成全计划营养、过敏原和适用性校验
                |
                v
用户选择地址和第1批预计送达日；每天一批，默认提前一天送达下一食用日食材
                |
                v
商城生成21个配送批次并按实际SKU、库存、费用重新报价
                |
                v
用户一次支付计划订单
                |
                v
系统按每批截单时间分配库存、生成供应商订单并配送
                |
                v
用户逐批确认收货；可暂停、恢复或修改未发货批次地址，不能主动取消已付款计划
                |
                v
暂停会顺延计划，恢复前由 Agent 重新评估；付款后不支持用户主动退款，平台未履约或质量问题按例外售后处理
```

系统边界可以概括为：

- AI Engine 决定“哪些商品组合适合本次用户食用”，并负责换一换后的整包营养复核。
- AI Engine 还负责菜单、菜品候选、专属计划内容，以及暂停恢复前的重新评估。
- 商城系统向 Agent 提供真实可售商品数据，并决定“商品是否可售、价格多少、库存是否足够、能否配送”。
- 商城系统负责计划报价、一次支付、配送批次、不退款确认和平台责任类例外售后计算。
- 供应商系统负责按配送批次接单、备货、发货和配送。
- 小程序负责“向用户展示、收集确认并发起支付”。

Agent 不直接修改商城商品、价格和库存。商城系统也不根据健康档案自行判断营养是否合格。单餐食材包和专属计划必须满足 Agent 校验及商城交易校验，才允许购买。只有未来明确配置高风险人群人工复核规则时，才额外要求专业人员审核。

固定食材包和动态组合同时存在，但不存在后台强制的二选一优先级。Agent 先根据用户和菜单产生食材需求，再从真实可售商品中组合 SKU，这是一期主路径。运营维护的固定食材包只是目录中的快捷商品；仅当它完整覆盖本次需求且经过 Agent 校验时才可被选用，不能为了优先卖固定包而牺牲个性化和营养适用性。两种来源进入结算后都拆成真实 SKU 明细，不以虚构组合库存扣减。

### 2.1 已确认的专属计划规则（2026-09-30）

1. 计划固定 21 天，每天一个配送批次，共 21 批，不合并配送。
2. 每个批次对应一个食用日，默认在食用日前一天送达，以保证食材新鲜；例如第 1 天送达第 2 天食用的食材。首批送达日与首个食用日的对应关系由排程明确展示。
3. 用户在计划开始时一次支付全部 21 天费用，不是每天付款。
4. 用户支付后，21 天菜单和未来菜品不允许修改；单餐付款前仍可使用“换一换”。
5. 计划暂停后结束日期顺延。恢复前必须由 Agent 根据最新档案版本重新评估原计划是否仍适合；评估不通过时不能恢复，也不能静默修改已支付菜单，计划保持暂停并转人工处理。
6. 每个未来批次在计划送达日前 3 天锁定库存并推送供应商；支付时只做 21 天需求预测，不一次锁死全部库存。具体执行时刻通过系统配置确定。
7. 专属计划一旦支付成功，用户不能主动取消计划或申请剩余批次退款。小程序必须在付款前展示“不支持退款”的明确警告并取得用户主动确认，后端保存政策版本、确认时间和确认凭证。
8. 专业人工审核用于未来高风险或需要人工营养师/医生复核的场景，一期默认不启用、不阻断购买；后台保留可选扩展能力并默认隐藏菜单。
9. “费用分摊”不是让用户分次支付，也不是提供常规退款入口；它是一次付款后的内部记账，用于逐批确认收入、财务对账，以及平台未履约、食品质量问题或法律强制情形下的例外售后计算。
10. “不支持退款”仅限制用户因个人原因反悔取消专属计划，不免除平台对未配送、错漏发、食品质量问题及法律强制权利承担补发、赔付或例外退款责任。

专属计划采用“计划交易主单 + 配送批次”的扩展模型：用户支付对应一笔计划交易，21 次备货、供应商推单、配送和签收分别记录在配送批次中，不能复制成 21 次用户支付。

### 3.2 现有底座必须优化的问题

- 当前订单状态较粗，不能完整表达待推单、供应商接单、备货、配送异常和退款中等状态。
- 当前库存主要直接增减，缺少库存占用、释放和流水记录。
- 当前订单与菜单版本、采购清单和供应商订单没有关联。
- 当前支付记录主要放在订单字段中，不足以追踪多次支付尝试、回调和退款。
- 当前没有统一的接口幂等记录，无法系统性防止重复下单、重复推单和重复退款。
- 当前没有供应商商品、供应商订单和履约事件模型。
- 当前没有标准食材到商城 SKU 的映射能力。
- 当前没有供 Agent 查询的标准化商品目录接口和商品数据版本。
- 当前没有 Agent 动态推荐食材包、包版本、营养校验引用和换一换记录。
- 当前没有 21 天专属计划、计划版本、计划日历和专业审核引用。
- 当前订单只能表达一次性履约，不能表达一次支付后多批配送、逐批签收、不退款确认和平台责任类例外售后。
- 当前库存逻辑不适合提前锁定 21 天生鲜库存，需要增加按批次分配和缺货补偿。
- 当前没有供应商合作申请的接收、审核和转供应商档案流程。
- 当前后台菜单仍是通用商城插件结构，需要按实际岗位重新组织。

## 4 目标系统架构

一期不建议拆成多个独立微服务，先在现有项目中按领域分层，确保可以在约定周期内交付。

```text
管理后台                 微信小程序                 外部系统
   |                         |                         |
   +------------ HTTP API / 回调接口 ----------------+
                             |
                             v
                    身份认证与接口控制层
                             |
                             v
 商品服务 | 菜单采购 | 专属计划 | 结算服务 | 订单支付 | 批次履约 | 售后退款
                             |
                             v
 商品库存 | 菜单/推荐版本 | 采购清单 | 计划订单 | 配送批次 | 供应商订单 | 审计与幂等
                             |
                             v
  MySQL | 微信支付 | AI Engine | 供应商接口 | 物流接口 | 消息服务
```

### 4.1 分层规则

- 控制器负责参数接收、登录校验、权限校验和统一响应。
- 服务层负责金额计算、库存处理、状态流转、匹配规则和事务。
- 模型层负责数据访问和简单关联，不在模型事件中隐藏复杂外部调用。
- 微信支付、供应商和 AI 接口通过独立适配器调用，避免业务代码绑定某一家供应商。
- 外部调用结果通过接口日志、业务事件和异常任务留痕。

## 5 后台信息架构

最终采用 5 个一级菜单、18 个二级菜单。功能不删除，只把同一业务链路的入口合并；独立数据表、服务、状态机和权限点保持不变。

```text
工作台

商品与配餐
├─ 商品管理
├─ 食材资料
├─ 食材包与推荐
├─ AI专属计划
└─ 采购清单

订单与履约
├─ 订单管理
├─ 配送批次
├─ 备货配送
└─ 售后与异常

供应链
├─ 供应商档案
├─ 供应商商品
├─ 供应商协同
└─ 配送规则

运营与系统
├─ 经营数据
├─ 营销管理
├─ 会员管理
├─ 系统配置
└─ 权限与日志
```

页面中的新增、编辑、删除、上架、下架、审核、发货、退款、重试等操作作为按钮权限或隐藏权限节点，不占用左侧菜单层级。

### 5.1 页面合并规则

| 二级菜单 | 页面内页签/入口 | 合并前功能 |

“固定食材包”“Agent 推荐包”和“AI 专属计划”虽然在菜单上合并归类，业务概念仍必须区分：固定食材包是长期商品，Agent 推荐包是一次任务的临时 SKU 组合，AI 专属计划是一次支付、每日配送的 21 天服务。

## 6 管理后台功能设计

### 6.1 工作台

#### 业务概览

功能：

- 今日订单量、支付金额、退款金额和客单价。
- 待付款、待推单、待备货、配送中订单数量。
- 待处理售后和异常订单数量。
- 低库存、缺货及商品同步异常提醒。
- 支付、供应商和物流接口异常提醒。
- 常用业务页面快捷入口。

使用方式：运营人员登录后先查看异常和待办，再进入对应页面处理。

### 6.2 商品与配餐：商品相关页面

#### 商品管理：分类页签

- 管理蔬菜、肉类、水产、蛋奶、主食、调味品和食材包等分类。
- 设置分类排序、图片、启停状态和小程序是否展示。
- 复用原商品分类模块。

#### 商品管理：商品页签

- 管理商品名称、图片、分类、品牌、产地和详情。
- 管理净含量、单位、保质期、储存条件和配送范围。
- 管理配料组成、标准食材编码、过敏原、营养标签或营养数据引用及数据来源版本。
- 管理普通商品与组合食材包标识。
- 管理商品上架、下架和售罄状态。
- 查看关联食材、供应商及可售 SKU。
- 复用并扩展原商品管理。

#### 商品管理：SKU与库存页签

- 管理商品规格、SKU编码、条码、售价和市场价。
- 查看现有库存、占用库存和可售库存。
- 手工调整库存并填写原因。
- 设置库存预警值。
- 查看库存流水和供应商库存同步结果。
- 复用原 SKU 模块并增加库存领域能力。

#### 食材包与推荐：固定食材包页签

- 创建运营人员预先配置的固定单餐包、净菜包或组合食材包。
- 设置包含的商品 SKU、食材及数量。
- 设置组合包价格、库存和配送区域。
- 校验组成商品是否全部可售。
- 组成商品缺货时标记不可售或进入替代处理。
- 维护适用菜品、餐次、人数范围、过敏原、展示图片和推荐标签。
- 支持“清蒸鲈鱼鲜蔬包”等可反复销售的固定包，并与 Agent 推荐结果关联。

固定食材包与 Agent 动态推荐包必须区分：固定食材包是长期上架商品；Agent 动态推荐包是针对某个用户、某次任务临时组合的一组真实 SKU，不必创建成新的 `shop_goods` 商品。

动态推荐包在结算和订单中按包内真实 SKU 形成商品明细，推荐包编号只负责关联、展示和追溯，不作为一个虚构库存商品扣减。

### 6.3 商品与配餐：配餐相关页面

该模块不是公司向供应商进货，而是管理 Agent 如何使用商城商品组合动态食材包，以及动态包如何经过换一换、复核、确认并进入交易。

#### 食材资料：食材库页签

- 维护标准食材编码、名称、别名和分类。
- 维护标准单位、生熟口径和可食部口径。
- 维护交易校验需要的过敏原标签。
- 管理启用、停用和版本时间。
- 不保存商品价格和库存，不承担营养计算。

#### 食材资料：SKU映射页签

- 一个标准食材可关联多个商品 SKU。
- 配置 SKU 实际包含的食材净量和单位换算。
- 配置首选商品、候选商品和替代优先级。
- 配置最小购买包装和最大可接受余量。
- 查看映射是否可售、库存是否正常及配送是否覆盖。

示例：

```text
标准食材：西兰花
需求：300克
候选SKU A：净菜西兰花300克/盒
候选SKU B：有机西兰花400克/盒
候选SKU C：普通西兰花500克/袋
```

#### 食材包与推荐：菜品映射页签

- 维护菜品/菜谱引用与标准食材需求的关系。
- 维护菜品可以推荐的固定食材包及优先级。
- 记录固定包无法覆盖时允许 Agent 使用的动态 SKU 组合规则。
- 展示菜品变化后受影响的食材、食材包、采购项和烹饪步骤。
- 映射只负责交易落地，不代替 Agent 判断菜品是否适合家庭成员。

#### 采购清单：清单页签

- 查看来源菜单、菜单版本和用户确认状态。
- 查看每种食材原始需求量。
- 查看用户确认的家中已有量。
- 自动计算净采购量。
- 查看匹配到的 SKU、包装数量、覆盖率和余量。
- 查看无法匹配或库存不足的项目。
- 重新运行商品匹配。
- 查看是否已生成购物车或订单。
- 支持用户取消勾选家中已有的采购项，但保留原始菜单需求和取消原因。
- 支持采购清单直接进入结算，也支持加入购物车后与普通商品一起结算。

正常采购清单由系统自动处理，后台主要处理异常和用户申诉。

#### 食材包与推荐：Agent推荐页签

- 查看 Agent 任务、用户引用、菜单版本和当前推荐包版本。
- 查看包内真实商品、SKU、数量、价格、库存和配送状态。
- 查看 Agent 首次校验结果、规则版本、校验时间和结论摘要。
- 查看商城交易校验结果，包括下架、库存、价格和配送问题。
- 查看推荐包是否已展示、已换一换、已确认、已结算或已失效。
- 支持按版本对比包内商品变化，但后台不能绕过 Agent 校验直接将未通过版本设为可购买。

Agent 推荐记录可以引用运营维护的固定食材包，也可以保存 Agent 针对某次任务提交的动态 SKU 组合。无论来源如何，最终都必须展开为真实 SKU 进行交易校验和下单。

#### AI专属计划

- 查看 Agent 提交的 21 天计划、计划版本、适用家庭和成员引用。
- 查看每天早餐、午餐、晚餐的菜品/菜谱引用及对应食材包。
- 查看计划预估价、一次支付最终报价，以及系统内部的商品、配送费、服务费和优惠批次分摊。
- 查看 Agent 校验、过敏原核对和商城交易校验状态；专业人工审核仅在未来启用时展示。
- 查看用户选择的首批送达日、每天一批的食用日/送达日关系和已经生成的 21 个配送批次。
- 查看计划当前处于待确认、待支付、生效、暂停、部分履约、取消中或已完成。
- 支付前计划内容修改必须生成新版本；支付后菜单和未来菜品不允许修改，商品、价格和批次快照不得被覆盖。

#### AI专属计划：可选人工审核页签

- 本页面属于未来可选能力，一期默认隐藏，不作为 Agent 计划的默认购买门禁。
- 仅在平台明确引入人工营养师、医生或高风险人群复核流程后启用。
- 接收 AI/专业审核系统返回的审核单编号、审核状态、结论摘要和时间。
- 状态至少包括不需要审核、待审核、退回补资料、审核通过和审核拒绝。
- 商城后台只保存审核引用和购买门禁结果，不保存完整病历、报告原文或专业人员详细判断。
- 需要审核但未通过的食材包或计划不得进入结算，后台也不能人工绕过。

#### 食材包与推荐：换菜记录页签

- 查看用户发起换一换的原菜品、原菜谱版本、原因和候选菜品。
- 区分“同主食材换做法”和“同营养结构换食材”。
- 查看用户最终选择的新菜品、食材复用率、烹饪时间和面向用户的营养差异摘要。
- 查看菜品变化对菜单、步骤、食材包、采购清单、SKU 和价格的影响。
- 查看 Agent 对修改后整份菜单的二次营养校验结果。
- 查看替换前后菜单版本、推荐包版本和价格变化，并支持查看撤销记录。
- 查看换一换失败原因，例如营养校验不通过、库存不足、已下架或无法配送。
- 支持异常情况下重新通知 Agent 或重新执行商城交易校验，不能在后台跳过专业校验。

同主食材只改变做法时，采购清单可以保持不变；跨食材替换必须生成新的菜单版本、推荐包版本和采购清单版本。已经支付的订单永远保留购买时快照，不随之后的菜单变化。

#### 采购清单：缺货处理页签

- 查看缺货商品、对应食材和受影响订单。
- 从同食材候选 SKU 中选择替代品。
- 重新校验价格、库存、配送范围和过敏原标签。
- 将替代方案发送给小程序等待用户确认。
- 同食材换规格、品牌或包装，只要商品食材组成不变，也必须按双方冻结的规则决定是否需要 Agent 快速复核。
- 更换不同食物、配方或组合时，必须创建 Agent 重新校验请求，不在商城后台直接替换。

### 6.4 订单与履约

#### 订单管理：普通订单页签

- 查询订单列表和订单详情。
- 查看用户、地址快照、商品快照、金额和优惠。
- 查看来源菜单、采购清单和商品匹配记录。
- 查看支付、库存、供应商、配送和售后状态。
- 查询支付结果、取消允许取消的订单、添加内部备注。
- 查看完整状态时间线。

#### 订单管理：专属计划页签

- 查看计划订单号、计划版本、适用家庭引用、支付金额和计划有效期。
- 查看一次支付对应的商品价、计划服务费、配送费、优惠及各批次金额分摊。
- 查看 21 个配送批次的待排程、待分配库存、待备货、配送中、已签收和异常数量。
- 暂停或恢复后续可变更批次；已发货和已签收批次不受影响。
- 查看用户付款前确认的“不支持退款”政策版本、确认时间和确认凭证；付款后不提供取消剩余计划按钮。
- 计划状态改变必须保留原因、操作来源和前后状态，不允许直接覆盖。

#### 配送批次

- 每个批次保存计划订单、批次序号、计划日期、三餐菜单快照、SKU 明细和金额分摊。
- 每个批次独立保存地址、配送时段、库存分配、供应商订单、物流和签收状态。
- 支持只修改未到截单时间且未发货批次的地址，并重新校验配送能力和运费影响。
- 支持逐批确认收货、逐批售后和逐批异常处理。
- 批次内容因缺货需要跨食材修改时，必须进入 Agent 复核和用户确认流程。

#### 备货配送：待备货页签

- 查看已支付但未完成供应商接单或备货的订单。
- 自动或手工推送供应商。
- 查询接单结果和备货进度。
- 处理整单拒绝、部分缺货和接口超时。
- 提供有限次数的人工重试。
- 同时展示普通订单和到达备货窗口的专属计划批次；未来批次只做需求预测，不提前生成正式供应商订单。

#### 备货配送：配送页签

- 查看配送批次、物流公司、运单号和预计送达时间。
- 同步供应商或物流轨迹。
- 查看配送中、已签收、拒收和配送异常订单。
- 支持后台补录物流信息。
- 复用原发货和电子面单能力。
- 专属计划按批次展示，支持按计划订单聚合查看 21 次履约进度。

#### 售后与异常：售后页签

- 普通订单继续处理未发货取消、缺货退款、漏件、错件、破损和质量问题。
- 支持仅退款和退货退款。
- 查看用户凭证、供应商处理意见和责任归属。
- 审核退款金额并发起微信退款。
- 查询退款状态并完成售后工单。
- 专属计划付款后不接受个人原因取消或退款；平台未履约、漏件、错件、破损、质量问题及法律强制情形进入“例外售后”。
- 例外退款金额按支付时冻结的批次分摊、优惠、服务费和配送费规则计算，不由前端自行提交。

#### 售后与异常：异常页签

- 支付状态不确定。
- 支付成功但库存或订单状态异常。
- 供应商推单失败或状态不一致。
- 部分商品缺货且无法自动替代。
- 配送长时间无更新。
- 退款调用或退款回调失败。
- 消息通知失败。

异常订单页面提供重新查询、重新推单、转售后、取消退款和关闭异常等受控操作。

### 6.5 供应链

#### 供应商档案：合作申请页签

- 接收小程序供应商合作表单，包括公司名称、供应品类、联系人、手机号、供货地区和补充说明。
- 查看待跟进、审核中、通过、驳回和已转供应商状态。
- 审核通过后由有权限人员转换成供应商档案，原申请记录保留。
- 合作申请数据与消费者订单、家庭档案和健康数据完全隔离。

#### 供应商档案：正式供应商页签

- 维护供应商资料、联系人、服务状态和结算信息标识。
- 维护配送区域、服务时间和售后规则。
- 维护接口模式、超时、重试次数和限流配置。
- 认证密钥加密保存，后台只显示脱敏结果。

#### 供应商商品

- 维护平台 SKU 与供应商 SKU 的映射。
- 同步供应商商品状态、价格和库存。
- 查看同步失败、字段缺失或已停止供货的商品。
- 设置商品来源供应商和备选供应商，为以后扩展保留结构。

#### 供应商协同：供应商订单页签

- 查看平台订单号和供应商订单号。
- 查看推单、接单、备货、发货、取消和售后状态。
- 查看供应商返回的缺货项目和错误原因。
- 在权限允许时执行查询或重试。

#### 供应商协同：接口日志页签

- 按请求编号、订单号、接口类型和状态查询。
- 记录调用时间、耗时、结果码和错误摘要。
- 敏感字段和密钥必须脱敏。
- 大报文只保存安全摘要或受限存储地址。

### 6.6 配送规则与运营营销

#### 运营与系统 / 营销管理

- 复用原优惠券创建、领取和核销能力。
- 配置使用门槛、适用商品、有效期和数量。
- 优惠只影响成交价格，不能改变食材需求或专业建议。

#### 供应链 / 配送规则：运费模板页签

- 复用原按件、按重量和地区运费能力。
- 结算时以服务端计算结果为准。

#### 供应链 / 配送规则：区域与时段页签

- 管理可配送和不可配送地区。
- 管理预约日期、时间段、容量和截单时间。
- 管理节假日停运和临时暂停。
- 与供应商配送能力及结算校验联动。

### 6.7 运营与系统 / 经营数据

#### 销售数据

- 订单量、支付金额、退款金额和客单价。
- 商品、SKU、食材包销量排行。

#### 商品转化

- 食材需求到商品匹配率。
- 商品推荐到购物车转化率。
- 购物车到下单及支付转化率。

#### 专属计划数据

- 计划候选曝光、详情查看、审核通过、确认、支付和完成率。
- 计划暂停率、恢复率、按期完成率和平均履约批次数。
- 计划批次准时送达率、缺货率、逐批售后率和退款金额。

#### 缺货统计

- 高频缺货商品和食材。
- 无法匹配食材。
- 缺货率、替代成功率和用户接受率。

#### 退款统计

- 退款订单、退款金额和退款率。
- 售后原因、供应商责任及商品分布。

#### 履约质量

- 供应商接单率和推单失败率。
- 平均备货时长、配送时长和按时送达率。
- 配送异常和状态同步延迟。

### 6.8 运营与系统 / 会员管理

- 复用会员列表和收货地址。
- 展示会员商城订单、支付、退款和售后记录。
- 商城角色不得查看完整健康档案和专业评估。
- 后台敏感查询和地址修改需要记录操作日志。

### 6.9 运营与系统 / 权限与日志

建议角色：

- 商城运营。
- 商品管理员。
- 订单客服。
- 供应链人员。
- 财务或退款审核人员。
- 系统管理员。

权限需要细分到页面按钮。退款、库存调整、接口密钥、订单关闭和人工改状态必须独立授权。

### 6.10 运营与系统 / 系统配置

#### 支付配置

- 微信支付商户配置、证书、回调地址和退款参数。
- 密钥加密保存且不允许普通管理员查看明文。

#### 消息配置

- 支付成功、备货、发货、配送异常、售后和退款消息模板。
- 仅在用户已经授权订阅时发送。

#### 商城配置

- 订单支付超时、售后期限、库存策略和客服信息。
- 自动任务频率、供应商重试次数和异常阈值。

#### 权限与日志：操作日志页签

## 8 自动处理和人工确认边界

### 8.1 系统自动处理

- 向 Agent 返回当前可售商品、SKU、食材组成、标签、价格、库存状态和配送能力。
- 接收 Agent 已完成首次营养校验的动态食材包。
- 对动态包执行商品状态、价格、库存和配送校验并保存版本。
- 接收 Agent 对换一换结果的二次校验结论，并生成新的推荐包版本。
- 接收菜品级换一换结果，同步生成菜单、推荐包和采购清单新版本。
- 接收 21 天专属计划及版本，校验 Agent 与商城交易门禁并生成计划报价和配送批次；人工审核门禁一期关闭。
- 用户确认食材包后创建或更新采购清单。
- 合并相同食材并完成单位标准化，需要时扣减用户确认的已有食材。
- 根据用户确认的已有食材计算净需求。
- 校验 Agent 选择的商品 SKU 和包装数，必要时返回可售候选给 Agent。
- 结算时刷新价格、库存、优惠和运费。
- 采购清单可直接结算，也可以加入购物车后结算。
- 创建普通订单并占用库存；创建计划订单时生成批次需求和近期批次库存任务。
- 普通订单在下单时占用库存；专属计划只对临近履约批次分配或占用库存，不在支付时锁定 21 天全部生鲜库存。
- 处理支付回调和支付结果查询。
- 普通订单支付成功后向供应商推单；专属计划在每批到达备货窗口后生成并推送供应商订单。
- 同步供应商备货、发货和配送状态。
- 自动计算暂停顺延后的待排程批次；专属计划不生成用户主动取消退款预览。
- 订单取消或超时时释放库存。
- 记录接口日志、业务事件和异常任务。

### 8.2 必须由用户确认

- Agent 生成的初始食材包。
- 家中已有食材数量。
- 换一换的新菜品以及 Agent 二次校验后的菜单、食材包和采购清单新版本。
- 缺货替代方案。
- 收货地址、配送时间及结算金额。
- 专属计划、首批送达日、每日配送安排和一次支付总价。
- 付款前明确确认“专属计划支付后不支持个人原因退款”的政策版本。
- 暂停、恢复和修改批次地址。
- 每个配送批次的确认收货。
- 提交订单和调起微信支付。
- 跨食材替换结果。
- 售后和退款申请。

### 8.3 需要后台人工处理

- 接口多次重试仍失败。
- 支付结果长时间不确定。
- 供应商拒单或部分缺货。
- 无可用同食材替代 SKU。
- Agent 校验通过但商城商品已经下架、缺货或无法配送。
- 换一换任务长时间未返回或多次校验失败。
- 平台与供应商状态不一致。
- 配送异常和用户售后申诉。
- 专业审核状态长时间未返回或审核引用不一致。
- 专属计划批次无法分配库存、无法按期履约或退款分摊异常。
- 供应商合作申请审核和转供应商档案。

## 9 接口通用规范

### 9.1 协议和数据格式

- 正式环境统一使用 HTTPS。
- 请求和响应使用 UTF-8 JSON，文件上传除外。
- 时间对外统一使用 ISO 8601，例如 `2026-09-28T10:30:00+08:00`。
- 数据库存储时间可继续遵循现有时间戳规范，但接口层统一转换。
- 金额接口字段统一使用整数分，例如 `amount_cent: 2590`。
- 重量和数量使用十进制数值加单位，不使用含单位的字符串。

### 9.2 统一响应

```json
{
  "code": 0,
  "message": "success",
  "request_id": "req_20260928_xxx",
  "data": {}
}
```

说明：如果需要兼容现有项目 `code=1` 表示成功的约定，可在旧接口保持兼容；新增 V1 接口应统一一种成功码，并在联调文档中冻结，避免不同接口语义不一致。

### 9.3 认证方式

- 小程序接口使用现有用户登录 Token，由服务端从 Token 获取用户身份。
- AI Engine 使用应用级 `client_id`、时间戳、随机数和签名。
- 供应商回调按供应商协议验签，并增加来源限制和重放防护。
- 微信支付回调严格按微信支付平台证书验签。

### 9.4 幂等规范

以下接口必须携带 `Idempotency-Key`：

- AI 创建采购清单。
- 小程序创建订单。
- 支付请求。
- 供应商推单。
- 退款请求。

相同业务、相同幂等键重复调用时返回第一次成功结果，不重复创建业务数据。

### 9.5 分页规范

请求：

```json
{"page": 1, "page_size": 20}
```

响应：

```json
{"items": [], "total": 0, "page": 1, "page_size": 20}
```

## 10 与 AI Engine 和营养师 Agent 的接口联调

### 10.1 调整后的职责

营养师 Agent：

- 读取用户已授权的健康档案和营养目标。
- 调用商城商品目录接口查询当前可选商品及 SKU。
- 根据用户档案从真实商品中组合动态推荐食材包。
- 对初始推荐包做营养、过敏原、禁忌和适用性校验。
- 用户换一换后，对替换后的整包重新校验。
- 返回校验结论、规则版本、任务编号和可向用户解释的摘要。

商城系统：

- 向 Agent 提供标准化商品目录，不向 Agent 反向索取完整健康档案。
- 保证返回的价格、库存、上下架和配送数据来自商城当前状态。
- 保存 Agent 推荐包、版本、商品明细、校验引用和换一换记录。
- 对每个包版本执行交易校验。
- 只有专业校验和交易校验都通过，才允许用户确认并进入结算。
- 后续负责订单、支付、履约、退款和售后。

### 10.2 Agent查询商品目录

Agent 不应登录管理后台或直接读取数据库，而应通过专用服务间接口查询商品。

`GET /api/v1/integration/ai/catalog/products`

建议查询参数：

- `cursor`、`limit`：游标分页。
- `updated_after`：增量同步时间。
- `ingredient_codes`：按标准食材过滤。
- `category_codes`：按分类过滤。
- `delivery_area_code`：只返回指定区域可配送商品。
- `available_only=true`：只返回当前可售商品。

返回字段至少包括：

- `product_id`、`sku_id`、商品名和规格名。
- 食材编码、食材组成、净含量及单位。
- 过敏原和交易标签。
- 商品营养标签、营养数据引用、数据来源、数据版本及字段完整度。
- 当前价格、库存状态、可售状态和配送范围。
- 商品图片和小程序展示摘要。
- `catalog_version`、`product_updated_at` 和数据有效时间。

商品详情：

`GET /api/v1/integration/ai/catalog/skus/{sku_id}`

同食材候选：

`GET /api/v1/integration/ai/catalog/skus/{sku_id}/alternatives`

商城可以提供目录增量接口或定时快照，避免 Agent 每次任务全量拉取所有商品。下单前仍必须由商城实时校验。

如果商品缺少 Agent 完成专业校验所需的配料、过敏原或营养数据，目录必须明确返回 `data_completeness`，不能把缺失值当作零。是否允许该商品进入推荐由双方冻结的准入规则决定。

### 10.3 Agent创建动态推荐食材包

`POST /api/v1/integration/ai/recommendation-packages`

请求示例：

```json
{
  "agent_task_id": "agent_task_10001",
  "family_ref": "family_1001",
  "user_ref": "user_2001",
  "menu_version_ref": "menu_v_3001",
  "catalog_version": "catalog_20260929_1200",
  "meal_date": "2026-09-30",
  "items": [
    {
      "sku_id": 501,
      "quantity": 1,
      "ingredient_code": "ING_BROCCOLI",
      "planned_food_quantity": 300,
      "planned_food_unit": "g"
    },
    {
      "sku_id": 602,
      "quantity": 1,
      "ingredient_code": "ING_EGG",
      "planned_food_quantity": 6,
      "planned_food_unit": "piece"
    }
  ],
  "nutrition_validation": {
    "validation_id": "nv_90001",
    "status": "passed",
    "rules_version": "nutrition_rules_202609",
    "validated_at": "2026-09-29T12:05:00+08:00",
    "summary": "本次组合校验通过"
  },
  "callback_url": "https://ai.example.com/callbacks/commerce"
}
```

商城处理：

1. 验证 Agent 身份、签名、幂等键和任务编号。
2. 检查营养校验状态必须为 `passed`。
3. 实时检查每个 SKU 是否存在、可售、库存足够并支持配送。
4. 重新计算商城价格，不采用 Agent 传入的价格。
5. 创建动态推荐包和版本 1，并保存商品快照。
6. 返回可展示状态、当前总价、失效时间和交易校验问题。

商城只保存校验引用和必要摘要，不保存 Agent 使用的完整健康档案或详细推理过程。

### 10.4 查询推荐包

Agent查询：

`GET /api/v1/integration/ai/recommendation-packages/{package_sn}`

商城返回当前版本、包内 SKU、实时可售状态、价格、库存问题和用户确认状态。

### 10.5 换一换完整流程

推荐交互时序：

```text
用户在小程序点击某一道菜的“换一换”
  -> 小程序团队调用Agent换一换接口
  -> Agent基于原菜单版本返回候选菜品
  -> 候选标明同主食材换做法或同营养结构换食材
  -> 用户选择新菜品
  -> Agent对替换后的整份菜单重新做营养、过敏原和适用性校验
  -> 校验通过后Agent提交菜单新版本、菜品变化及完整食材需求
  -> 商城重新匹配固定食材包或真实SKU并刷新采购清单
  -> 商城校验价格、库存、上架和配送并保存关联版本
  -> 小程序获取最新版本，展示菜品、做法、采购项和价格变化
```

营养校验未通过时，Agent 不能调用“可购买版本”接口，应返回用户重新选择或提供新的候选商品。

### 10.6 Agent创建换一换后的新版本

`POST /api/v1/integration/ai/recommendation-packages/{package_sn}/dish-swap-versions`

请求示例：

```json
{
  "agent_task_id": "agent_swap_task_10002",
  "base_version": 1,
  "base_menu_version_ref": "menu_v_3001",
  "result_menu_version_ref": "menu_v_3002",
  "swap_request_id": "swap_70001",
  "change_reason": "user_dislike",
  "swap_type": "same_nutrition_structure",
  "old_recipe_ref": "recipe_steamed_fish_v1",
  "new_recipe_ref": "recipe_shrimp_tofu_v1",
  "ingredient_changes": [
    {"action": "remove", "ingredient_code": "ING_SEABASS"},
    {"action": "add", "ingredient_code": "ING_SHRIMP"}
  ],
  "full_menu_ingredient_requirements": [],
  "nutrition_validation": {
    "validation_id": "nv_90002",
    "status": "passed",
    "rules_version": "nutrition_rules_202609",
    "validated_at": "2026-09-29T12:15:00+08:00",
    "summary": "替换后整份菜单校验通过"
  }
}
```

处理规则：

- `base_version` 必须等于用户当前查看版本，否则返回版本冲突。
- 每次换一换创建不可变的新版本，不能覆盖旧版本。
- Agent 必须提交替换后的完整菜单食材需求，而不只提交一个新菜品。
- 同主食材换做法且食材需求未变化时，可以沿用采购清单，但仍创建菜单版本和换一换记录。
- 跨食材替换时，商城重新匹配食材包/SKU，生成采购清单新版本并重新计算价格。
- 商城校验全部采购 SKU，不只校验新增 SKU。
- 新版本创建成功后，旧版本不能继续结算。

### 10.7 Agent创建AI专属计划

`POST /api/v1/integration/ai/service-plans`

请求至少包含：

- `agent_task_id`、`family_ref`、`member_refs` 和使用的档案版本引用。
- 计划名称、计划版本、计划天数、固定每日配送频率和候选排序。
- 每天早餐/午餐/晚餐的日期序号、菜品/菜谱引用和完整食材需求。
- Agent 校验编号、规则版本、结论摘要。
- 可选的专业人工审核标记及外部审核单引用；一期默认不需要。

商城处理规则：

- 保存计划内容快照，不保存完整健康档案。
- 将计划食材需求匹配为固定食材包或真实 SKU，并生成每批交易草案。
- 在用户选择地址和首批送达日后，根据“21 天、每天一批、默认提前一天送达下一食用日食材”生成正式批次日历。
- 结算前按全部批次重新报价；不能采用 Agent 提交的价格、库存或配送费。
- Agent 校验和商城交易校验通过即可进入一期结算；仅当将来某计划明确标记需要人工专业审核时，审核未通过才只能查看。

### 10.8 专业审核结果回传

`POST /api/v1/integration/ai/professional-reviews/{review_ref}/result`

本接口为未来可选能力，一期默认不调用。启用后只接收审核状态、适用对象引用、结果摘要、审核时间和购买门禁结果。若审核退回补资料或拒绝，相关未支付计划/推荐包失去可购买资格；已经支付的订单保留原交易快照并转人工评估。

### 10.8.1 暂停计划恢复前重新评估

用户申请恢复后，商城创建恢复申请并向 Agent 发送 `service_plan.resume_evaluation_requested` 事件，包含计划编号、支付时计划版本、最新档案版本引用和申请编号。Agent 完成评估后调用：

`POST /api/v1/integration/ai/plan-orders/{order_sn}/resume-validations`

请求包含 `agent_task_id`、`change_request_sn`、`plan_sn`、`plan_version`、`profile_version_refs`、`validation_id`、`rules_version`、`status`、`summary`、`validated_at` 和 `valid_until`。只有结果为 `passed` 且仍在有效期内，商城才按顺延后的日历重新校验运力并恢复；失败时保持暂停并转人工，不能修改已支付菜单。

### 10.9 商城反馈交易校验失败

如果 Agent 校验通过，但商城发现商品刚刚下架、库存不足或无法配送，返回：

- 失败 SKU。
- 原因代码。
- 当前可用同食材候选。
- 当前目录版本。
- 是否必须重新进行 Agent 校验。

Agent 根据结果重新组合和校验，不能要求商城绕过交易限制。

事件类型增加：

- `recommendation_package.created`
- `recommendation_package.trade_validation_failed`
- `recommendation_package.version_created`
- `recommendation_package.user_confirmed`
- `recommendation_package.expired`
- `purchase_list.created`
- `order.created`
- `order.paid`
- `order.fulfillment_updated`
- `order.completed`
- `order.cancelled`
- `order.refunded`
- `service_plan.created`
- `service_plan.review_updated`
- `service_plan.paid`
- `service_plan.paused`
- `service_plan.resume_evaluation_requested`
- `service_plan.resumed`
- `service_plan.exception_aftersale_opened`
- `delivery_batch.fulfillment_updated`

回调失败进入 Outbox 重试，不影响订单主流程。Agent 也可通过查询接口补偿。

### 10.11 AI与Agent联调验收

- Agent只能获得已授权集成字段，不能直接访问管理后台或数据库。
- 商品目录支持分页、增量版本和实时详情查询。
- Agent提交的价格不会被商城采信。
- 初始推荐包只有营养校验通过且交易校验通过才可展示为可购买。
- 换一换后必须校验整包，而不是只检查被替换商品。
- 每次换一换生成新版本，旧版本不能继续下单。
- 重复请求不会重复创建推荐包或版本。
- 目录变化、库存不足和版本冲突有明确错误。
- Agent不可用时，已经确认并形成订单的交易流程仍可继续；未完成的换一换暂停。

## 11 提供给小程序团队的服务端接口设计

## 12 供应商接口联调

供应商协议尚未冻结前，商城内部先定义统一适配器，具体供应商接口映射到统一模型。

### 12.1 需要供应商提供的能力

- 商品全量或增量同步。
- SKU价格和库存查询。
- 配送区域与时段查询。
- 创建供应商订单。
- 查询订单和备货状态。
- 发货或配送轨迹查询。
- 取消订单。
- 售后和退款处理，视供应商能力决定。

### 12.2 平台调用供应商

建议统一内部方法：

```text
syncProducts
queryAvailability
createSupplierOrder
querySupplierOrder
cancelSupplierOrder
queryLogistics
submitSupplierAftersale
```

### 12.3 供应商推单字段

- 平台订单号和幂等请求号。
- 订单类型；专属计划还需传计划订单号、配送批次号和批次送达日。
- 供应商 SKU、数量及平台商品行号。
- 收货人、手机号和地址。
- 配送日期及时间段。
- 用户备注中允许传递的履约信息。
- 实付或结算字段按双方协议传递。

不得传递病史、健康指标、用药或完整营养建议。

### 12.4 状态同步方式

优先顺序：

1. 供应商主动回调并验签。
2. 平台定时查询补偿。
3. 后台人工查询或补录。

供应商回调必须使用供应商订单号和平台订单号双重定位；计划订单还要校验配送批次号，并检查状态是否允许迁移。

### 12.5 重试策略

- 网络超时和明确可重试错误使用指数退避。
- 参数错误、商品不存在等业务错误不自动无限重试。
- 达到最大次数后创建异常订单任务。
- 重试必须复用原幂等请求号。

### 12.6 供应商联调验收

- 重复推单不会生成多个供应商订单。
- 部分缺货能精确定位订单商品。
- 回调乱序不会导致状态倒退。
- 供应商超时后可查询补偿。
- 取消和售后状态能够回写平台。
- 敏感健康数据不出现在供应商请求和日志中。

## 13 微信支付和退款联调

### 13.1 支付流程

```text
小程序请求预支付
  -> 后端检查订单和金额
  -> 后端调用微信支付下单
  -> 小程序调起微信支付
  -> 微信回调后端
  -> 后端验签和解密
  -> 幂等更新支付记录及订单
  -> 普通订单确认库存并创建供应商推单任务
  -> 专属计划激活计划订单，仅调度进入备货窗口的配送批次
```

专属计划只有一笔用户支付。实付金额仍需按规则记账到各配送批次，用于逐批确认收入、财务对账，以及平台未履约或质量问题时的例外售后计算；这不代表用户可主动取消退款。

### 13.2 支付状态不确定

- 小程序支付结果不能作为最终依据。
- 回调未到时，后端主动查询微信订单。
- 查询仍不确定时保留订单并创建补偿任务。
- 不允许用户重复创建同一业务订单规避查询。

### 13.3 退款流程

- 售后审核通过后创建退款记录。
- 后端使用唯一退款单号调用微信退款。
- 微信退款回调验签并幂等更新退款记录。
- 退款完成后更新售后和订单状态。
- 是否恢复库存根据商品是否退回及验收结果决定。
- 专属计划只在平台未履约、漏错发、质量问题或法律强制情形下创建例外退款，并记录责任原因和审批证据。
- 同一批次已退款或正在售后的金额不能重复计入其他退款。

## 14 数据库设计总则

### 14.1 命名约定

- 保持现有 `__PREFIX__shop_` 表前缀规范。
- 下文省略 `__PREFIX__`，实际安装和迁移脚本使用项目动态前缀。
- 主键继续使用自增整数可兼容现有代码；对外使用独立业务编号。
- 新表统一包含 `createtime`、`updatetime`，需要软删除时增加 `deletetime`。

### 14.2 金额和数量

- 新增支付、退款和快照表建议使用整数分 `bigint` 保存金额。
- 为兼容现有订单 decimal 元字段，在服务层进行唯一转换，禁止各处自行换算。
- 食材数量使用 `decimal(14,4)` 加独立单位字段。

### 14.3 状态和历史

- 主表保存当前状态。
- 状态变更写入事件或日志表。
- 菜单、采购清单、商品快照和供应商订单不得覆盖关键历史版本。

## 18 状态机设计

### 18.1 Agent动态推荐包

```text
generating -> ready -> swap_pending -> ready -> confirmed -> ordered
     |          |           |           |
     v          v           v           v
  invalid     expired     invalid     expired
```

`ready` 表示当前版本同时通过 Agent 营养校验和商城交易校验。换一换开始后进入 `swap_pending`，旧版本可以查看但不能新建订单；新版本再次达到 `ready` 后才能让用户确认。

### 18.2 推荐包版本

```text
draft -> nutrition_passed -> trade_passed -> ready -> confirmed
   |             |               |
   v             v               v
rejected      invalid         superseded
```

每次换一换产生新版本。新版本生效后，旧版本进入 `superseded`，不得继续结算。

### 18.3 采购清单

```text
draft -> matching -> matched -> user_confirmed -> ordered -> completed
                 |          |
                 v          v
             unmatched    invalid
```

菜单版本变化、过期或 AI 撤销时，未下单采购清单进入 `invalid`。已创建订单的历史清单保留。

### 18.4 订单业务状态

```text
pending_payment -> paid -> supplier_pending -> preparing -> delivering -> completed
       |             |             |               |
       v             v             v               v
 cancelled       refunding      exception       aftersale
                     |
                     v
                  refunded
```

原 `orderstate`、`paystate`、`shippingstate` 继续兼容旧页面，新的细状态由订单服务统一映射，禁止页面直接随意赋值。

### 18.5 支付状态

```text
created -> paying -> success
   |          |
   v          v
 closed     failed
```

### 18.6 供应商订单状态

```text
pending -> pushing -> accepted -> preparing -> shipped -> completed
              |          |           |
              v          v           v
            failed    rejected     shortage
```

状态回调乱序时只能前进或进入允许的异常分支，不能直接倒退。

### 18.7 售后和退款状态

```text
applied -> reviewing -> approved -> refunding -> refunded -> completed
              |
              v
           rejected
```

### 18.8 AI专属计划

```text
draft -> validating -> review_pending -> ready -> user_confirmed -> ordered
  |          |              |            |
  v          v              v            v
invalid   rejected       returned      expired
```

`ready` 表示 Agent 校验、商城计划级交易校验，以及未来启用时的可选专业审核均已通过。

### 18.9 专属计划订单

```text
pending_payment -> active -> partial -> completed
                      |         |
                      v         v
                    paused   exception_handling
```

计划订单状态是 21 个批次的聚合结果。暂停顺延计划并阻止未来批次进入备货，恢复前必须取得 Agent 重评通过引用。支付后不存在用户主动取消状态，`exception_handling` 仅用于平台责任或法律强制售后。

### 18.10 配送批次

```text
scheduled -> allocating -> reserved -> preparing -> shipped -> delivering -> received
                 |             |          |            |
                 v             v          v            v
              shortage      exception  exception    aftersale
```

### 18.11 计划变更申请

```text
requested -> previewed -> user_confirmed -> processing -> completed
     |             |              |
     v             v              v
 rejected       expired         failed
```

## 19 核心事务设计

### 19.1 保存推荐包新版本

一个数据库事务内完成：

1. 校验 Agent 身份、幂等键、包编号和基础版本。
2. 校验 Agent 营养校验状态及校验引用。
3. 锁定推荐包当前版本，防止两个换一换结果同时覆盖。
4. 实时校验整包所有 SKU 的上下架、库存、价格和配送。
5. 创建不可变的新版本和商品快照。
6. 更新推荐包当前版本指针并将旧版本标记为已替代。
7. 写入换一换记录及推荐包版本事件。

### 19.2 用户确认推荐包

一个数据库事务内完成：

1. 校验用户归属和客户端提交的版本号。
2. 校验该版本的营养校验和交易校验均为通过。
3. 再次刷新商品状态、库存、价格和配送能力。
4. 标记当前版本为用户已确认。
5. 从确认版本创建采购清单或结算来源。
6. 使其他未确认版本失效或保持只读。

### 19.3 创建订单

一个数据库事务内完成：

1. 校验结算令牌和幂等键。
2. 锁定涉及 SKU 并检查可售库存。
3. 重新计算商品金额、优惠和运费。
4. 创建订单、订单商品和扩展快照。
5. 创建库存占用和库存流水。
6. 标记采购清单已下单。
7. 写入订单创建事件。

外部支付调用不放在数据库事务中。

### 19.4 支付成功

一个数据库事务内完成：

1. 锁定支付记录和订单。
2. 检查回调幂等。
3. 更新支付记录和订单支付状态。
4. 将库存占用转为确认扣减。
5. 写入供应商推单 Outbox 事件。
6. 写入 AI 状态回调和订阅消息事件。

### 19.5 取消订单

- 检查当前状态是否允许取消。
- 未支付订单取消并释放库存。
- 已支付未推单订单进入退款流程。
- 已被供应商接单时先执行供应商取消，再按结果退款或转人工。

### 19.6 创建并支付专属计划订单

1. 校验计划当前版本、Agent 校验、商城交易校验和用户归属；一期不默认要求专业人工审核。
2. 根据地址、首批送达日和配送能力，按每天一批生成 21 个不可变批次草案，并分别记录食用日与送达日，默认提前一天送达。
3. 将每批食材需求匹配为 SKU，重新计算商品金额、服务费、配送费和优惠。
4. 小程序展示后端当前不退款政策并取得主动确认，后端保存政策版本和确认凭证；随后生成绑定该凭证的结算令牌，创建一笔包含全部 21 天费用的计划主订单和全部批次快照。
5. 只为首个进入备货窗口的批次占用库存，其余批次记录需求预测。
6. 支付成功后激活计划并冻结菜单内容；任何未来菜品不得修改。
7. 在每个批次计划送达日前 3 天调度库存占用和供应商订单，具体执行时刻由配置确定。

### 19.7 计划批次进入备货窗口

1. 在计划送达日前 3 天锁定批次，并检查计划未暂停、未终止且未重复执行。
2. 实时校验批次 SKU、库存、供应商和地址配送能力。
3. 占用本批库存并生成一张或多张供应商订单。
4. 缺货时按替代规则进入 Agent/用户确认或异常处理，不修改已支付快照。
5. 写入批次履约事件和用户通知事件。

### 19.8 暂停、恢复和修改批次地址

- 暂停只影响未发货的未来批次，计划结束日期按暂停天数顺延；已经发货的批次不回退。
- 恢复前调用 Agent 按最新档案版本重新评估原计划是否仍适用。通过后重新计算剩余排程和运力；不通过时保持暂停并转人工处理，不能改写已支付菜单，也不能通过用户主动退款绕过不退款规则。
- 修改地址只作用于指定未来批次，并重新校验配送能力；不可静默修改其他批次。
- 所有变更使用计划订单版本号和幂等键，保存前后快照。

### 19.9 专属计划不退款确认与例外售后

1. 计划结算页先获取当前“不支持退款”政策版本和展示文案。
2. 小程序必须在调起支付前弹出明确警告，由用户主动勾选或确认；不得默认勾选。
3. 创建计划订单时同时提交政策版本和确认值，后端校验版本仍有效并保存确认凭证；未确认不得创建订单或预支付。
4. 支付成功后关闭用户主动取消计划和剩余批次退款入口，客服后台也不能用普通按钮绕过。
5. 平台未履约、漏件、错件、食品质量问题或法律强制情形进入例外售后，由有权限人员审核后补发、赔付或退款。
6. 例外退款按批次金额、优惠、服务费和配送费的内部记账分摊计算，写退款记录和退款分摊，避免累计退款超出实付。

费用分摊不改变“一次支付”和“不支持个人原因退款”。每批商品金额按本批 SKU 成交快照记录；每日配送费记到对应批次；订单级优惠按各批优惠前金额比例分配，分币尾差记入最后一个批次；一期如不单收计划服务费则该项为 0。

## 22 安全、隐私和审计

- 小程序所有私有资源按登录用户和订单归属校验，不能只凭 ID 查询。
- AI Engine 只能访问其授权的集成接口，不能调用后台管理接口。
- 供应商只接收履约所需的商品、地址和联系方式。
- 支付和供应商密钥加密保存并限制访问。
- 回调接口验签、校验时间戳和随机数，防止重放。
- 日志对手机号、地址、OpenID、Token和签名字段脱敏。
- 后台库存调整、退款、手工改状态和接口重试全部审计。
- 商品快照和订单金额不能被后台编辑覆盖历史。

## 23 降级和异常处理

| 故障 | 降级方案 |
|---|---|
| AI Engine不可用 | 已有采购清单、商品和订单继续可用；跨食材替换暂停 |
| 可选专业审核系统不可用 | 一期无影响；未来明确启用人工审核的计划保持不可购买 |
| 商品匹配失败 | 展示自主采购清单并进入后台待处理 |
| 供应商库存接口不可用 | 停止创建无法确认库存的新订单或使用明确有效期缓存 |
| 供应商推单失败 | 自动重试，超过阈值进入异常订单 |
| 微信支付回调丢失 | 主动查询支付结果 |
| 物流接口不可用 | 保留最近状态并提示更新延迟 |
| 消息发送失败 | 不回滚订单，进入消息重试队列 |

- Agent重复创建推荐包和重复创建换一换版本。
- Agent重复创建专属计划版本；未来启用时验证专业审核重复回调。
- 营养校验未通过时拒绝创建可购买版本。
- Agent目录版本过旧、SKU下架、库存不足和配送不可达。
- 小程序使用旧推荐包版本确认时返回版本冲突。
- 重复创建采购清单。
- 重复创建订单。
- 价格变化、库存不足和配送不可达。
- 支付成功、失败、取消、回调重复和回调乱序。
- 供应商超时、拒单、部分缺货和重复回调。
- 售后、退款及退款回调重复。
- 批次确认收货、计划暂停恢复、改地址和已付款取消请求拦截。

### 24.3 并发测试

- 多用户同时购买最后库存。
- 同一用户连续点击提交订单。
- 支付回调和主动查询同时更新订单。
- 供应商回调与定时同步同时执行。

### 24.4 端到端测试

至少覆盖：

1. 用户建档后 Agent 查询商品并生成动态食材包。
2. 初始包通过营养校验和商城交易校验后展示。
3. 用户不换商品，确认推荐包并支付完成。
4. 用户换一换、选择新商品、Agent整包复核并生成新版本。
5. Agent校验通过但新商品库存不足，返回重新选择。
6. 用户使用旧版本提交确认时被正确阻断。
7. 推荐包确认后生成采购清单并扣减已有食材。
8. 支付成功后供应商正常接单配送。
9. 供应商缺货后重新走替代复核或退款。
10. 用户申请漏件或质量售后。
11. 重复回调不产生重复包版本、订单、推单或退款。
12. Agent生成21天计划，Agent 与商城校验通过后一次支付全部费用并生成每日一批的21个配送批次。
13. 付款前小程序展示不退款警告，后端验证并保存用户确认凭证；未确认不能下单。
14. 用户暂停计划后，已发货批次不变，未来批次停止进入备货。
15. 用户恢复计划前由 Agent 重新评估，通过后再校验排程和运力。
16. 用户只修改一个未发货批次地址，其他批次地址保持不变。
17. 已支付专属计划的用户主动取消和退款请求被拒绝，后台普通角色也不能绕过。
18. 平台未履约、漏错发或食品质量问题可进入受控例外售后，且不重复赔付。

## 25 数据迁移和兼容策略

- 不删除现有商城核心表和历史订单。
- 新功能优先使用扩展表，减少直接修改原插件核心逻辑。
- 旧接口在迁移期继续可用，但内部逐步调用新服务层。
- 旧菜单先隐藏或迁移权限，不直接删除权限记录。
- 新订单使用新状态和扩展表；历史订单通过兼容映射展示。
- 数据迁移脚本必须支持重复执行检查和回滚方案。

## 26 分阶段开发计划

- 隐藏一期无关旧功能。
- 建立服务层、统一响应、错误码和审计基础。

### 阶段二 Agent商品目录、菜单与动态食材包

- 开发食材基础库、别名和 SKU 映射。
- 开发 Agent 商品目录、分页、过滤和增量版本接口。
- 开发固定食材包、菜品映射、动态推荐包、版本、商品明细和菜品级换一换记录。
- 开发双重校验门禁及供小程序读取和确认推荐包的接口。
- 与 AI Engine 完成初始组合、换一换和二次校验接口联调。

### 阶段三 采购清单和普通单餐交易

- 开发采购清单、已有食材扣减、净需求和商品匹配。

- 强化创建订单、取消、支付和退款幂等。
- 向小程序团队提供推荐包、购物车、结算、订单和支付接口并完成联调，不承担前端页面改造。

### 阶段四 AI专属计划和批次交易

- 开发专属计划、计划版本、21 天每日配送日历和餐次；专业人工审核引用作为可选扩展，不进入一期默认流程。

- 支付后冻结计划菜单；开发库存预测和送达日前 3 天占用、推单策略。
- 完成小程序计划详情、配送安排、计划管理相关接口联调。

### 阶段五 供应链履约

- 开发供应商、供应商商品和供应商订单。

- 完成供应商回调及定时补偿。

### 阶段六 售后、看板和上线准备

- 完成供应商售后和微信退款闭环。
- 建设销售、转化、缺货、退款和履约看板。

## 28 开发前必须冻结的事项

- AI 和商城共同使用的食材编码及单位字典。
- Agent 可读取的商品字段、目录过滤规则、分页方式和目录版本有效期。
- 商品进入 Agent 目录必须具备的配料、过敏原、营养标签或专业数据引用完整度标准。
- 商品食材组成和营养数据由谁提供、谁审核、多久更新以及数据缺失时的处理规则。
- 初始推荐包由哪个 Agent 节点提交，营养校验结果的签名和可信方式。
- 已确认：一期以 Agent 根据需求动态组合真实 SKU 为主；固定食材包仅作为完整匹配并通过 Agent 校验时可选的快捷商品，不设置强制销售优先级。
- “换一换”是否固定为菜品级；同主食材换做法和跨食材换菜分别需要哪一级复核。
- 已确认：21 天固定每日一批，共 21 批，默认提前一天送达下一食用日食材，不合并配送。
- 已确认：计划开始时一次支付全部 21 天费用；批次金额分摊只用于逐批收入确认、财务对账和例外售后。
- 已确认：支付后计划菜单和未来菜品不允许修改。
- 已确认：专业人工审核不是一期默认流程，后台能力保留但菜单隐藏；未来启用时再冻结责任方和签名规则。
- 已确认：暂停顺延结束日，恢复前由 Agent 按最新档案重新评估；最长暂停时长仍需产品确定。
- 已确认：每批在计划送达日前 3 天锁库存并推供应商；具体每日执行时刻、缺货替代截止时间仍需运营确定。
- 已确认：专属计划支付后不支持用户因个人原因取消或退款；付款前小程序明确警告，后端保存政策版本与确认凭证。
- 仍需法务/运营确认：不退款提示的正式文案、用户确认方式，以及平台未履约、食品质量问题和法律强制情形的例外售后规则。
- 仍需财务确认：如一期存在单独计划服务费，其收入确认和例外售后计算规则；如果不收取则固定为 0。
- 小程序换一换是直连 Agent 网关还是经过统一 API 网关；建议由 Agent 流程负责编排。
- 候选商品由 Agent 自主筛选还是商城先按同食材返回候选。
- 哪些变化可以使用快速复核，哪些变化必须执行完整整包营养复核。
- 推荐包有效期、换一换最大次数和版本冲突处理。
- 用户确认推荐包后由商城自动生成采购清单。
- 家中已有食材由哪个系统保存，以商城采购清单为建议落点。
- 商品匹配余量和优先级规则。
- 现有 `stocks` 的准确库存语义。
- 微信支付渠道、订单超时和退款规则。
- 一期供应商接口、配送区域、配送时段和售后政策。
- 是否允许一个平台订单拆成多个供应商订单；一期建议不拆或仅单一供应商。
- AI、小程序、商城之间的成功码和错误码规范。
- 数据保存期限、日志脱敏和备份恢复要求。

## 29 一期验收标准

- 后台固定以 5 个一级菜单展示，原商城功能通过页签整合且没有重复入口。
- Agent 可以通过授权接口分页或增量读取当前可售商品目录。
- 商品目录明确提供食材组成、过敏原、营养数据来源版本和完整度，缺失值不会被当作零。
- Agent 可幂等创建动态推荐食材包，商城不会采信 Agent 提交的价格和库存。
- 初始推荐包必须同时通过 Agent 营养校验和商城交易校验。
- 用户换一换后，Agent 对替换后的整包重新校验并生成不可变新版本。
- 换一换以菜品为入口，并同步菜单、烹饪步骤、食材包和采购清单；同做法变化与跨食材变化按规则复核。
- 旧版本不能被确认或下单，版本冲突能被正确阻断。
- 用户确认的推荐包可自动生成采购清单。
- 食材需求能够映射商品并正确计算包装数量。
- 用户修改已有食材后能够重新计算和匹配。
- 价格、库存、优惠、运费和订单金额均由服务端计算。
- 并发购买不会超卖。
- 重复提交不会创建重复有效订单。
- 重复支付回调不会重复记账或重复推单。
- 支付成功后正常订单可自动推送供应商并同步状态。
- AI专属计划通过 Agent 与商城校验后可一次支付全部费用并生成每日一批的 21 个配送批次；专业人工审核不作为一期默认门禁。
- 计划支付不会提前锁死全部未来生鲜库存，各批在送达日前 3 天独立分配库存和推单。
- 计划支持暂停顺延、恢复前 Agent 重评、单批改地址和逐批签收；支付后菜单不可修改且不提供用户主动取消退款。
- 付款前警告及确认凭证可追溯；平台责任和法律强制情形的例外退款有明确分摊且不会重复。
- 缺货或用户不喜欢时能提供候选，涉及商品变化的方案按冻结规则返回 Agent 复核。
- 供应商接口异常会自动重试并进入异常订单。
- 后台提供的接口能够支持小程序团队完成采购、购物车、结算、支付、订单、物流和售后闭环。
- 微信退款可查询、可追踪且重复回调安全。
- 关键状态和操作可从日志、事件和后台时间线追溯。
- 供应商和商城日志中不包含不必要的健康敏感信息。

## 31 最终系统形态

改造完成后，本项目是一套家庭营养师平台的食材交易与供应链履约系统。

它负责向营养师 Agent 提供真实商品目录，将 Agent 的菜单和菜品落到固定食材包或动态 SKU 组合，在菜品换一换后同步菜单、采购清单和交易版本；同时承接 21 天 AI 专属计划的一次支付、每日配送、暂停顺延、恢复重评、逐批签收、不退款确认和供应商履约。正常业务由系统自动流转，后台人员主要维护商品、食材包、映射和供应能力并处理平台责任类例外售后。

系统回答的是：

```text
需要购买哪些商品
每个商品购买多少件
价格、库存和配送是否有效
订单是否支付
供应商是否接单和发货
商品配送到哪一步
缺货、退款和售后如何处理
```

系统不直接决定用户应该吃什么，也不直接修改菜单、营养目标和个人份量。
