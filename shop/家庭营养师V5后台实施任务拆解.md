# 家庭营养师 V5 后台实施任务拆解

## 1. 文档目的

本文把《家庭营养师商城订单供应链系统改造开发设计 V5》拆成可排期、可分工、可验收的后端实施任务。

本次改造范围属于刘北萍负责的管理后台与服务端，包括商城、订单、供应链、数据库，以及与营养师 Agent、小程序、专业审核、供应商、物流和微信支付的接口联调。

明确不包含：

- 不修改 Uni-app 小程序页面、组件、路由和交互代码。
- 不在商城后台内实现健康建档、营养计算、菜谱生成和 Agent 推理。
- 不保存完整健康档案、病史或 Agent 推理过程。
- 不允许 Agent 直接登录后台或读取商城数据库。

### 1.1 已确认业务规则

- 专属计划固定 21 天、每天一批，默认提前一天送达下一食用日食材。
- 用户在开始时一次支付全部 21 天费用。
- 支付后菜单和未来菜品不可修改。
- 暂停会顺延，恢复前必须由 Agent 重新评估原计划。
- 每批在计划送达日前 3 天锁库存并推送供应商。
- 专属计划支付后不支持用户因个人原因取消或退款；付款前小程序警告，后端保存确认凭证。
- 平台未履约、错漏发、食品质量问题和法律强制情形作为例外售后处理。
- 一期以 Agent 动态组合真实 SKU 为主，固定食材包只是完全匹配时可选的快捷商品，不设硬优先级。
- 专业人工审核是未来高风险场景的可选能力，一期默认关闭和隐藏。

## 2. 改造后的系统边界

### 2.1 商城后端负责

- 管理真实可售商品、SKU、价格、库存、配送范围和供应商能力。
- 把 Agent 的标准食材需求匹配成固定食材包或动态 SKU 组合。
- 保存推荐包、菜单引用、换菜版本、采购清单和交易校验结果。
- 提供小程序需要的商城、结算、订单、支付、计划批次、履约和售后接口。
- 完成普通订单和 21 天专属计划的一次支付、每日配送、暂停顺延、恢复重评、不退款确认和例外售后。
- 对接供应商、物流、微信支付和退款。
- 执行幂等、状态机、库存占用、自动重试、异常告警和审计。

### 2.2 Agent 负责

- 读取用户已授权的健康档案。
- 生成菜单、菜品、食材需求和 21 天计划。
- 生成“同主食材换做法”或“同营养结构换食材”的候选菜品。
- 对初始方案和换菜后的整份方案执行营养、过敏原、禁忌与适用性校验。
- 向商城提交不可变版本、校验编号、规则版本和可展示摘要。

### 2.3 小程序团队负责

- 调用后端和 Agent 接口并完成页面展示。
- 收集用户确认、已有食材、地址、配送时间、换菜选择和售后申请。
- 调起微信支付，但不能自行认定支付成功。
- 展示后端返回的版本冲突、价格变化、库存不足、配送不可达和审核门禁。

## 3. 现有项目落点

当前底座是 FastAdmin/ThinkPHP Shop 插件，采用控制器、模型、视图、后台 JavaScript 分层。新增功能保持现有结构，复杂业务从控制器移入独立服务层。

| 类型 | 现有目录 | 改造策略 |
|---|---|---|
| 后台控制器 | `application/admin/controller/shop` | 复用商品、订单、售后控制器；新业务新增控制器 |
| 后台模型 | `application/admin/model/shop` | 简单查询模型留在此目录，不承载跨表事务 |
| 后台校验器 | `application/admin/validate/shop` | 每个可编辑业务对象配置场景校验 |
| 后台视图 | `application/admin/view/shop` | 按 FastAdmin 列表、详情、编辑页方式实现 |
| 后台脚本 | `public/assets/js/backend/shop` | 表格字段、筛选、按钮、弹窗和权限点 |
| 小程序 API | `controller/api` | 旧接口兼容；新增 V1 控制器调用统一服务层 |
| 领域模型 | `model` | 新业务表模型及关联关系 |
| 服务层 | 建议新增 `service` | 结算、库存、计划、退款等跨表事务 |
| 外部适配器 | 建议新增 `library/integration` | AI、供应商、物流、微信支付适配器 |
| 队列入口 | `controller/queue` | Outbox、供应商推单、消息与补偿任务 |
| 定时任务 | `controller/Autotask.php` | 仅作调度入口，业务下沉到 Job/Service |
| 菜单权限 | `data/menu.php` | 评审通过后再改；旧菜单先隐藏不删除 |
| 数据库安装 | `install.sql` | 正式开发时追加全新安装结构，不在本轮修改 |

### 3.1 必须先重构的底座风险

- 现有订单创建直接递减 `stocks`，缺少原子条件更新、占用记录和防超卖机制。
- 现有金额主要使用元和 `decimal`，新接口要求统一用“分”传输，服务层必须明确转换边界。
- 现有订单由 `paystate/orderstate/shippingstate` 多字段组合表达，新业务不得直接无限扩展这些字段，应通过扩展表维护新状态。
- 现有 API 成功码与 V1 规范可能不一致，旧接口维持兼容，新接口必须统一。
- 现有 `Autotask` 是单入口顺序扫描，需要增加任务锁、游标、重入和失败记录。
- 现有控制器包含价格、库存和订单事务，改造后同一规则只能存在于服务层，后台与 API 共用。

## 5. 页面级任务拆解

### 5.1 工作台

| 页面/区域 | 展示内容 | 操作 | 数据来源 | 优先级 |
|---|---|---|---|---|
| 今日经营 | 支付金额、订单数、退款额、计划新增 | 跳转明细 | 订单与退款聚合 | P2 |
| 今日履约 | 待备货、待推单、配送中、超时批次 | 跳转待办 | 批次、供应商订单 | P1 |
| Agent 待办 | 推荐失败、映射失败、版本冲突 | 查看问题、重试交易校验 | 推荐包、采购匹配 | P1 |
| 供应链告警 | 缺货、拒单、回调失败、物流超时 | 指派、重试、关闭 | 异常订单、接口日志 | P1 |
| 可选审核门禁 | 未来启用时展示待审核、退回、超时 | 一期默认隐藏 | 审核引用表 | P3 |

验收：所有数字可点击回到已带筛选条件的明细页；统计延迟和更新时间清晰可见。

### 5.2 商品与配餐：商品管理、食材资料和固定包

#### 商品管理：分类页签

- 复用现有分类管理。
- 增加“Agent 可见”开关、业务分类编码、排序和停用原因。
- 分类停用不删除历史订单快照。

#### 商品管理：商品页签

- 复用 `Goods` 控制器和现有商品编辑能力。
- 新增销售类型：普通商品、固定食材包、服务型商品。
- 新增 Agent 可推荐开关、供应状态、数据完整度、配送限制摘要。
- 增加“食材与营养资料”页签：配料、标准食材、过敏原、营养数据来源、版本、审核状态。
- 商品下架时触发目录版本、未来批次扫描和 Outbox 事件。

#### 商品管理：SKU 与库存页签

- 复用现有多规格 SKU 页面。
- 增加标准包装净含量、单位、可售库存、安全库存、库存更新时间和供应商映射状态。
- 库存调整必须填写原因并写库存流水。
- 页面禁止直接覆盖已占用库存；展示“实物库存、占用库存、可售库存”。

#### 食材包与推荐：固定食材包页签

- 创建或编辑具名食材包及包内 SKU、件数、排序、图片和展示摘要。
- 配置适用菜品、人数、餐次和有效期。
- 发布前校验所有成员 SKU 可售、数据完整且存在价格。
- 已被订单引用的版本不可覆盖，只能新建版本或下架。
- 固定包不凌驾于动态组合之上；只有完整覆盖本次需求并经 Agent 校验时才可使用。

### 5.3 商品与配餐：推荐、计划和采购

#### 食材资料：食材库页签

- 维护统一食材编码、名称、别名、类别、默认单位和启停状态。
- 解决 Agent 使用“西兰花”和商城 SKU 使用“有机西兰花 300g”无法直接关联的问题。
- 食材编码一旦被业务引用不可修改，只能停用或新增编码。

#### 食材资料：SKU 映射页签

- 建立标准食材与真实 SKU 的对应关系。
- 配置主食材/辅料、净含量、换算率、损耗率、优先级、有效期和审核状态。
- 支持一个食材对应多个 SKU，也支持一个组合 SKU 包含多种食材。
- 映射发布后 Agent 才能稳定从“需要 300g 西兰花”落到“购买 1 份 300g SKU”。

#### 食材包与推荐：菜品映射页签

- 保存 Agent 菜品引用与固定食材包的映射。
- 配置适用人数、餐次、默认包、备选包和有效期。
- 菜品只换做法且食材不变时可沿用原采购组合。

#### 食材包与推荐：Agent 推荐页签

- 列表查询包编号、用户引用、Agent 任务、菜单版本、当前包版本和双校验状态。
- 详情展示每版 SKU 快照、价格、库存、配送、营养校验引用和交易问题。
- 支持人工重新执行交易校验、失效推荐包、查看版本差异。
- 不允许后台人员篡改 Agent 已确认的营养结论或直接编辑已发布版本。

#### AI 专属计划

- 查看计划、成员引用、计划版本、每日一批的 21 天日历、三餐摘要和交易草案。
- 预览地址与首批日期对应的配送批次。
- 支持查看版本差异；已支付计划内容按快照只读。
- 查看付款前不退款政策确认凭证；付款后不显示取消或普通退款操作。

#### AI 专属计划：可选人工审核页签

- 未来明确引入人工营养师/医生高风险复核时再启用，一期菜单默认隐藏。
- 展示审核单引用、外部状态、购买门禁、摘要、时间和回调历史。
- 允许重新拉取状态和标记回调异常。
- 禁止后台手工把未通过状态改成通过；确需纠错必须由审核系统重发签名结果。

#### 食材包与推荐：换菜记录页签

- 展示用户操作、原菜品、新菜品、换菜类型、菜单前后版本、推荐包前后版本和校验状态。
- 换菜粒度是“菜品”，不是直接替换 SKU。
- 跨食材变化必须有整包复核记录；旧版本永久保留但不可继续结算。

#### 采购清单：清单页签

- 展示原始食材需求、家中已有量、净需求、匹配 SKU、购买件数和余量。
- 支持查看匹配原因和手工选择候选 SKU；手工选择后仍需交易校验，必要时返回 Agent 复核。
- 用户确认推荐包后系统自动生成；正常流程不要求后台人工创建。

#### 采购清单：缺货处理页签

- 展示原 SKU、缺货原因、受影响订单/未来批次、同食材候选和是否需营养复核。
- 同食材同规格替代可按冻结规则自动处理；跨食材替代必须返回 Agent。
- 已支付订单替代涉及价差或用户权益时必须用户确认或转退款。

### 5.4 订单与履约

#### 订单管理：普通订单页签

- 整合现有订单列表、详情、支付、商品快照、收货地址、物流和操作记录。
- 增加来源：普通商城、推荐包、采购清单。
- 后台操作包括备注、重试推单、查看支付、发货、关闭异常；不可随意改金额和支付状态。

#### 订单管理：专属计划页签

- 展示一次支付总额、计划版本、批次数、已履约金额、例外售后金额、不退款确认和总状态。
- 展开 21 个配送批次及其库存、供应商、配送和售后状态。
- 暂停和恢复必须走服务层和状态机；暂停顺延，恢复前要求 Agent 重评。付款后不允许用户主动取消。

#### 配送批次

- 每个批次独立维护送达日期、截单时间、地址快照、金额分摊、商品、库存和履约状态。
- 支持进入备货、推单重试、标记异常、查看轨迹、单批售后。
- 已过截单或已发货批次禁止改地址和取消。

#### 备货配送：待备货页签

- 聚合普通待发货订单和进入备货窗口的计划批次。
- 支持按供应商、送达日期、仓库和缺货状态筛选。
- 正常订单由任务自动推单，后台处理无法自动分配或需要确认的记录。

#### 备货配送：配送页签

- 维护运单号、承运商、物流节点、预计/实际送达时间和异常原因。
- 物流状态通过回调或定时查询自动更新，人工补录需要权限和审计。

#### 售后与异常：售后页签

- 支持普通订单商品售后，以及专属计划因平台未履约、错漏发、质量问题或法律强制情形产生的例外售后。
- 展示证据、责任方、审核记录、微信退款单和例外退款分摊。
- 退款申请、退款执行和退款完成分别授权，避免一人完成全流程。

#### 售后与异常：异常页签

- 统一接收库存不足、供应商拒单、推单失败、支付不确定、配送超时、退款失败等异常。
- 包含严重程度、责任模块、指派人、处理时限、重试次数和解决结论。
- 关闭异常不等于修改业务成功状态，必须由对应业务操作恢复。

### 5.5 供应链

#### 供应商档案：合作申请页签

- 接收小程序或公开入口提交的主体、联系人、经营范围、区域和资质附件。
- 支持待审核、补资料、通过、拒绝和转正式供应商。
- 转档时保留申请编号和审计关系。

#### 供应商档案：正式供应商页签

- 维护供应商编码、主体、联系人、结算资料引用、接口方式、服务区域和启停状态。
- 密钥仅显示掩码，修改需要高权限并记录审计。

#### 供应商商品

- 映射商城 SKU 与供应商 SKU，配置采购价、最小起订量、供应区域、优先级和同步状态。
- 支持库存和价格同步，但供应商价格不能直接覆盖商城销售价。

#### 供应商协同：订单页签

- 展示平台订单/批次与供应商子单的关系。
- 支持推单、接单、拒单、备货、发货、完成、取消和售后状态。
- 重复推单使用同一外部幂等号，不得产生重复供应商订单。

#### 供应商协同：接口日志页签

- 按合作方、业务号、接口、结果、耗时和重试次数查询。
- 请求/响应敏感信息脱敏；可执行受控重试。
- 日志失败不得阻断主事务，主事务通过 Outbox 保证后续可补偿。

### 5.6 供应链配送规则与运营营销

- 运营与系统 / 营销管理：复用优惠券模块，新增适用来源、计划适用规则和退款分摊规则。
- 供应链 / 配送规则 / 运费模板：复用旧模块，支持生鲜、供应商、区域、时段和批次维度。
- 供应链 / 配送规则 / 区域与时段：维护区域编码、邮编/行政区、可送日期、时段容量、截单时间和停运日。
- 计划恢复、改地址和结算必须实时调用配送能力校验。

### 5.7 运营与系统：经营数据

- 销售数据：支付金额、实收、退款、客单价、普通单与计划单。
- 商品转化：曝光、推荐、确认、结算、支付漏斗；曝光数据需小程序或 Agent 上报。
- 专属计划：创建、Agent 校验、支付、暂停、恢复、完成和例外售后率。
- 缺货统计：SKU、供应商、区域、受影响用户和替代成功率。
- 退款统计：原因、金额、责任方、批次和到账时长。
- 履约质量：接单率、准时发货、准时送达、拒单、漏件和破损。

一期看板允许 T+1 聚合，运营页面必须明确数据口径和更新时间。

### 5.8 运营与系统：会员、配置、权限与日志

- 会员管理复用现有用户基础资料，仅展示商城所需信息和业务引用，不展示完整健康档案。
- 权限管理基于 FastAdmin 权限节点，按页面查看、编辑、审核、执行退款、重试接口、导出分别授权。
- 支付配置、消息配置、商城配置按环境隔离，密钥不得明文回显。
- 操作日志覆盖库存调整、退款、人工发货、状态补偿、密钥修改和导出。

### 6.1 服务层强制规则

- 控制器只做认证、参数接收、调用服务和响应转换。
- 所有价格、库存、优惠、运费和可退金额由服务端重新计算。
- 跨表写入必须由服务层开启事务。
- 外部 HTTP 调用不得放在持有数据库行锁的事务内。
- 事务提交后通过 Outbox 异步通知 Agent、供应商或消息系统。
- 服务方法必须接收操作者和请求编号，便于审计与追踪。

## 7. API 控制器拆解

### 7.1 面向 Agent

- `IntegrationAiCatalog`：商品目录、SKU 详情、候选 SKU、增量版本。
- `IntegrationAiRecommendationPackage`：创建推荐包、查询包、创建换菜版本。
- `IntegrationAiServicePlan`：创建计划和计划新版本。
- `IntegrationAiProfessionalReview`：未来可选，接收专业人工审核结果；一期不启用。
- `IntegrationAiEvent`：供 Agent 查询事件或补偿业务状态。

### 7.2 面向小程序

- `RecommendationPackage`：读取、交易复检、确认和生成采购清单。
- `ServicePlan`：计划列表、详情、日历、排程预览和计划结算。
- `PurchaseList`：已有食材、重新匹配、确认、加购和直结。
- `Cart`：保留旧能力并增加来源引用。
- `Checkout`：统一结算预览、刷新和短期令牌。
- `Order`：普通订单创建、查询、取消、签收和再购。
- `PlanOrder`：计划订单、批次、暂停顺延、Agent 重评后恢复和改地址。
- `Payment`：微信预支付和支付状态查询。
- `Fulfillment`：物流轨迹和批次状态。
- `Aftersale`：售后申请、证据、查询和撤销。
- `SupplierApplication`：供应商合作申请和进度查询。

### 7.3 面向外部回调

- `WechatPayNotify`：支付通知。
- `WechatRefundNotify`：退款通知。
- `SupplierCallback`：接单、拒单、发货、缺货和售后回调。
- `LogisticsCallback`：物流节点回调。

回调控制器只负责验签、解密、落接收日志和投递业务处理，不直接包含复杂状态流转。

```text
规则冻结
  -> 数据库基础、统一服务层、幂等与 Outbox
  -> 商品/食材/SKU 映射
  -> Agent 商品目录
  -> 推荐包与换菜版本

  -> 供应商与物流
  -> 售后退款、看板和上线
```

支付接入不能早于服务端金额与库存规则稳定；供应商自动推单不能早于支付幂等和供应商子单唯一键完成；计划退款不能早于批次金额分摊规则冻结。

## 12. 每项开发任务的完成定义

一项任务只有同时满足以下条件才能标记完成：

- 数据表、索引和迁移脚本已评审，可重复执行。
- 控制器不包含重复业务计算，后台与 API 共用服务层。
- 参数、权限、归属、状态和版本校验完整。
- 写接口具备必要的幂等键和唯一约束。
- 关键事务具备并发测试，库存和金额没有竞态。
- 外部调用具备超时、重试、熔断或人工补偿入口。
- 操作、接口、状态变化和失败原因可追踪。
- OpenAPI、错误码和示例与实现一致。
- 单元、接口和端到端用例通过，并保留测试证据。
- 不影响旧历史订单查询和原商城未迁移功能。

## 13. 已确认规则和剩余阻断项

已经确认：每日一批、默认提前一天送达、一次付清、付款后菜单不变、暂停顺延并由 Agent 重评、送达日前 3 天锁库存推单、付款后不支持个人原因退款、动态 SKU 为主、专业人工审核一期关闭。

编码前只剩以下细节必须冻结：

1. 每日批次的固定送达时段和“送达日前 3 天”的具体执行时刻。
2. 最长允许暂停多久；Agent 重评不通过后人工如何处置长期暂停计划。
3. 不退款警告的正式文案、是否需要复选框加二次弹窗、政策版本生效方式。
4. 平台未履约、错漏发、食品质量问题和法律强制情形分别采用补发、赔付还是例外退款。
5. 一期是否收取独立计划服务费；如收取，如何逐批确认收入和计算例外售后。
6. 一期是否允许一个平台订单拆给多个供应商。
7. 缺货发生在已支付计划时，在菜单不可修改和不退款前提下的补发/等价履约方案。
