# 家庭营养师 V5 数据库迁移设计

## 1. 设计目标

本文将 V5 的数据模型拆成可编写迁移脚本的数据字典。正式编码时仍需根据开发、测试和生产数据库版本生成实际 SQL，并在副本上验证。

目标：

- 保留现有商城、历史订单和旧接口兼容性。
- 新功能优先使用扩展表，减少修改旧插件核心表。
- 支持推荐包、换菜、采购清单、21 天计划、多批配送、供应商、支付退款和审计。
- 用唯一约束、版本号和库存流水支撑幂等与并发安全。
- 不落完整健康档案和 Agent 推理过程，只保存外部引用、状态和必要摘要。

已确认的计划规则：21 天每日一批、默认提前一天送达、一次支付全部费用、支付后菜单不可修改、暂停顺延且恢复前 Agent 重评、送达日前 3 天锁库存推单、付款后不支持个人原因退款。数据库必须保存付款前警告的政策版本和用户确认凭证。

## 2. 数据库约定

### 2.1 表名与主键

- 本文使用逻辑表名 `shop_*`，安装脚本使用项目现有 `__PREFIX__shop_*` 方式。
- 新表主键统一 `id bigint unsigned auto_increment`。
- 业务编号如 `package_sn`、`plan_sn`、`order_sn` 使用 `varchar(64)`，建立唯一索引。
- 外部引用使用 `varchar(100)`，不假设外部系统为整数 ID。
- 不依赖数据库物理外键，使用应用层校验和普通索引，符合现有插件部署方式。

### 2.2 时间与软删除

- 与现有 ThinkPHP 模型兼容，使用 `createtime/updatetime/deletetime bigint unsigned`，保存 Unix 秒。
- 事件发生时间、外部回调时间也使用 Unix 秒，接口层转换 ISO 8601。
- 交易、支付、退款、库存、事件和审计表不得软删除。
- 商品资料、食材、供应商等主数据可以软删除，但已被引用的数据实际只允许停用。

### 2.3 金额、数量与 JSON

- 新交易扩展表金额统一 `bigint`，单位分，字段后缀 `_cent`。
- 旧表金额 `decimal(10,2)` 暂不修改，通过服务层转换，避免破坏旧代码。
- 食材数量使用 `decimal(14,3)`，换算率和损耗率使用 `decimal(14,6)`。
- 单位使用 `varchar(20)` 标准代码。
- 为兼容数据库版本，可变结构快照使用 `longtext` 保存 JSON；写入前在应用层校验结构。
- 高频过滤字段不能只藏在 JSON 中，必须拆成独立列。

### 2.4 通用列

除纯明细和日志表外，新表默认包含：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `id` | bigint unsigned | 自增 | 主键 |
| `status` | varchar(30) | 业务定义 | 状态 |
| `version` | int unsigned | 1 | 乐观锁版本 |
| `createtime` | bigint unsigned | 当前时间 | 创建时间 |
| `updatetime` | bigint unsigned | 当前时间 | 更新时间 |
| `deletetime` | bigint unsigned null | null | 仅主数据使用 |

### 2.5 字符集和引擎

- `InnoDB`。
- `utf8mb4`，排序规则与现有库保持一致。
- 唯一索引中可空列需谨慎，幂等键应使用非空空串或单独摘要列，避免多个 NULL 绕过唯一约束。

## 3. 现有表变更

### 3.1 `shop_goods`

建议新增：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `sale_type` | varchar(20) | `normal` | `normal/bundle/service` |
| `business_category_code` | varchar(50) | 空串 | 对外稳定分类编码 |
| `agent_visible` | tinyint unsigned | 0 | 是否进入 Agent 目录 |
| `catalog_status` | varchar(20) | `draft` | `draft/published/suspended` |
| `data_completeness` | varchar(20) | `insufficient` | `complete/partial/insufficient` |
| `catalog_version` | bigint unsigned | 0 | 最近一次目录变更序号 |
| `row_version` | int unsigned | 1 | 并发更新版本 |

索引：`idx_goods_agent_catalog(agent_visible,catalog_status,updatetime)`、`idx_goods_business_category(business_category_code)`。

不修改旧 `status/price/stocks` 含义；新服务通过 SKU 和库存服务获取最终可售状态。

### 3.2 `shop_goods_sku`

建议新增：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `sku_code` | varchar(64) | 空串 | 稳定 SKU 编码 |
| `net_content_value` | decimal(14,3) | 0 | 单件净含量 |
| `net_content_unit` | varchar(20) | 空串 | 净含量单位 |
| `safety_stock` | int unsigned | 0 | 安全库存 |
| `reserved_stock` | int unsigned | 0 | 有效占用库存缓存 |
| `stock_updated_at` | bigint unsigned | 0 | 库存更新时间 |
| `row_version` | int unsigned | 1 | 乐观锁 |

唯一索引 `uk_sku_code(sku_code)`；若历史数据没有编码，迁移时先回填 `SKU-{id}` 再设非空唯一。

可售库存口径：`max(stocks - reserved_stock - safety_stock, 0)`。是否把旧 `stocks` 定义为实物库存必须在开发前冻结。

### 3.3 `shop_carts`

新增：`source_type varchar(30)`、`source_ref varchar(64)`、`source_version int unsigned`、`purchase_item_id bigint unsigned`、`row_version int unsigned`。

索引：`idx_cart_source(user_id,source_type,source_ref)`。旧购物车行保持来源为空。

### 3.4 `shop_order`

不建议把全部新状态直接塞入旧表。最小新增：

- `order_type varchar(20) default 'normal'`：`normal/plan`。
- `row_version int unsigned default 1`。
- `request_id varchar(64) default ''`：创建链路追踪。

唯一索引保持现有 `order_sn`；新增 `idx_order_type_status(order_type,orderstate,paystate,shippingstate)`。其余新字段放 `shop_order_ext`。

### 3.5 `shop_order_goods`

旧字段继续保存兼容快照。新增 `row_version` 可选；推荐包、采购清单、批次和完整 JSON 快照放 `shop_order_goods_ext`。

### 3.6 `shop_order_aftersales`

若旧表允许扩展，新增 `batch_id bigint unsigned`、`source_type varchar(20)`、`request_id varchar(64)`、`row_version int unsigned`。复杂退款和微信状态仍放新表。

新增索引 `idx_aftersale_batch(batch_id,status)` 和唯一索引 `uk_aftersale_request(request_id)`；历史数据回填空值时注意唯一规则。

## 13. 状态字段约束

数据库字段使用 `varchar` 便于扩展，但服务代码必须通过统一枚举和状态机限制迁移。任何后台页面不得直接提交任意状态字符串。

核心状态：

- 推荐包：`draft/validated/available/confirmed/ordered/expired/blocked`。
- 采购清单：`draft/matching/ready/confirmed/ordered/expired`。
- 支付：`created/paying/paid/closed/failed/refunding/refunded`。
- 计划：`draft/reviewing/available/ordered/expired/blocked`。
- 计划订单：`pending_payment/active/paused/exception_handling/completed`；不提供用户主动取消状态。
- 批次：`scheduled/paused/preparing/supplier_pending/shipped/delivered/cancelled/exception`。
- 供应商订单：`created/pushing/accepted/rejected/preparing/shipped/completed/cancelled/exception`。
- 退款：`created/submitted/processing/success/failed/closed`。

## 14. 迁移批次与顺序

### M001：备份和基线

- 记录数据库版本、表结构、行数、最大 ID、索引和字符集。
- 备份现有库，验证恢复脚本。
- 为旧订单流程建立对账基线。

### M002：主数据

- 扩展 `shop_goods/shop_goods_sku`。
- 创建食材、别名、映射、组成、营养、食材包和菜品映射表。
- 回填 SKU 编码和商品默认值。

### M003：集成基础设施

- 创建幂等、Outbox、接口日志和异常单表。
- 上线后先观察空载任务和清理策略。

### M004：推荐与采购

- 创建推荐包、版本、明细、换菜、采购清单、采购项和匹配表。
- 扩展购物车来源字段。

### M005：订单、库存、支付

- 创建订单扩展、订单商品扩展、订单重要政策确认、库存占用、库存流水、支付和退款表。
- 扩展旧订单与售后最小字段。

### M006：计划

- 创建计划、计划版本、日期、餐次、成员、审核引用、计划订单、批次、批次商品、变更和退款分摊表。

### M007：供应链

- 创建供应商、供应商 SKU、供应商订单、明细、履约事件、区域、时段和合作申请表。

### M008：索引和历史回填

- 分批建立大表索引。
- 回填订单扩展行、SKU 编码和默认版本。
- 对比总行数、金额合计和抽样订单。

## 15. 回填规则

- 历史商品 `sale_type=normal`、`agent_visible=0`，未经资料补全不能自动进入 Agent 目录。
- 历史 SKU `sku_code=SKU-{id}`，净含量未知为 0 和空单位，数据完整度不足。
- 历史购物车来源为空，仍按普通商城处理。
- 历史订单创建 `shop_order_ext` 时，来源 `legacy`，业务状态由旧三状态字段映射。
- 历史订单金额以旧表为准，只在扩展快照中记录，不重新计算。
- 不为历史订单补造库存流水、支付回调和供应商事件。

## 16. 可重复执行和回滚

- 每个迁移有唯一版本号和执行记录。
- 新增列前检查是否存在，回填使用可断点的 ID 区间。
- 新索引上线前检查重复数据，不能直接因唯一索引失败中断整次发布。
- 代码发布采用“先兼容读写新旧结构，再迁移，再切流”的顺序。
- 回滚优先回滚应用版本并停止新入口，不立即删除新表和新列。
- 已产生的新业务数据不得用 DROP 回滚；需保留并提供只读或补偿处理。

## 17. 数据保留、隐私和审计

- 健康相关只保存外部引用、校验状态、规则版本和摘要。
- 收货地址和手机是履约快照，按法务确认期限保留并限制角色访问。
- 接口日志默认脱敏，签名、Token、支付证书、OpenID 不入明文日志。
- 幂等响应正文按接口保留期清理，支付退款记录按财务要求长期保留。
- Outbox 成功事件可归档，失败和死信必须保留处理证据。
- 库存、支付、退款、状态事件和后台操作日志只追加，不物理删除。

## 18. 数据库验收检查

- 所有业务编号和外部幂等号存在唯一约束。
- 所有定时扫描条件存在组合索引。
- 推荐包、计划和订单快照不可被主数据更新覆盖。
- 用户归属字段可支持每个私有资源的越权校验。
- 库存占用在并发下不会出现负可售库存。
- 同一支付/退款/供应商回调重复处理不产生重复状态和流水。
- 21 个批次金额分摊相加与订单实付一致，尾差有确定归属。
- 不退款政策版本、展示和用户确认凭证可从计划订单追溯。
- 平台责任类例外售后的责任原因、批次和退款金额可准确解释。
- 迁移前后旧订单数量、金额和查询结果一致。
- 备份可恢复，应用回滚后旧功能仍可运行。
