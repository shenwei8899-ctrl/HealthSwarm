# 家庭营养师 V5 联调测试与验收清单

## 1. 文档目的

本文用于验证 V5 后台改造是否真正支持最新小程序原型、营养师 Agent 和商城供应链闭环。测试对象是管理后台、数据库和服务端接口，不包含 Uni-app 页面代码开发；小程序团队需使用测试包配合接口验收。

已确认的计划口径：21 天每日一批、默认提前一天送达、一次支付全部费用、付款后菜单不可修改、暂停顺延且恢复前 Agent 重评、送达日前 3 天锁库存推单、付款后不支持个人原因退款。平台未履约、错漏发、质量问题和法律强制情形属于例外售后。

## 2. 验收参与方

| 参与方 | 验收责任 |
|---|---|
| 商城后端 | 接口、状态机、数据库、自动任务、支付、供应链和后台页面 |
| AI/Agent 团队 | 商品目录读取、菜单、换菜、整包复核和计划数据正确性 |
| 小程序团队 | 按契约调用接口、传递版本和幂等键、展示异常并调起支付 |
| 专业审核方 | 未来启用人工高风险复核时参与；一期不作为必需方 |
| 供应商 | 商品库存、推单、拒单、发货、售后及沙箱稳定性 |
| 物流方 | 运单查询、节点回调和异常状态 |
| 微信主体/财务 | 商户配置、支付退款证书、对账和真实小额验证 |
| 产品/运营 | 页面流程、业务规则、数据口径和用户可理解性 |

## 3. 测试环境和数据

至少准备四套逻辑环境：

- 开发环境：开发自测，可使用 Stub。
- 联调环境：各方共享固定契约和测试账号。
- 预发布环境：配置尽量与生产一致，使用微信沙箱或最小真实金额。
- 生产灰度：限制人员、区域、SKU、供应商和订单金额。

测试数据必须包含：

- 资料完整、资料部分缺失和禁止推荐的商品。
- 单规格、多规格、固定食材包和组合食材 SKU。
- 充足、低库存、零库存、安全库存和库存更新时间过期。
- 可配送、不可配送、容量已满和已过截单时间的地址/时段。
- 同食材候选、跨食材候选和完全无候选。
- 无需审核、待审核、通过、补资料、拒绝和过期计划。
- 普通订单、21 批计划订单、暂停计划和部分履约计划。
- 可退款、部分退款、退款中和退款失败。

测试账号不得使用真实健康档案；使用脱敏构造数据和虚拟用户引用。

## 4. 准入与退出标准

### 4.1 开始联调前

- OpenAPI、枚举、错误码、成功码、签名和幂等规则已冻结。
- 阻断业务规则已确认，尤其是批次频率、收费分摊、暂停和退款公式。
- 数据迁移已在备份副本执行成功。
- Agent、供应商、物流、微信的测试凭证可用；专业人工审核凭证仅在未来启用时要求。
- 日志能通过 `request_id` 串起请求、业务记录和外部调用。

### 4.2 上线前

- P0、P1 用例 100% 通过，无未关闭严重缺陷。
- 支付、退款、库存、金额分摊和权限用例全部通过。
- 关键接口重复、乱序、超时、并发和补偿用例通过。
- 历史商城订单回归通过。
- 备份恢复、应用回滚和任务停用经过演练。
- 产品、商城后端、AI、小程序、供应商和财务完成验收签字。

## 19. 数据迁移测试

### 19.1 迁移前检查

- 记录所有旧表行数、最大 ID、订单金额汇总和索引。
- 检查 SKU 编码重复、订单号重复、异常 NULL 和字符集。

### 19.2 迁移执行

- 每个迁移脚本执行两次，第二次安全跳过或得到相同结果。
- 大表回填可断点续跑，不长时间锁表。
- 唯一索引建立前先输出冲突清单。
- 新旧代码兼容窗口内，旧订单仍可创建和查询。

### 19.3 迁移后核对

- 历史商品默认不进入 Agent 目录。
- 历史订单数量和金额汇总不变。
- 抽查待支付、已支付、已发货、已完成、已取消、售后中订单。
- 新订单扩展表与旧主表一一对应。
- 回滚应用后旧功能仍可读历史数据。

## 22. 核心端到端验收脚本

### E2E-01：单餐直接购买

1. Agent 读取目录并创建推荐包。
2. 商城双校验通过，小程序读取当前版本。
3. 用户标记已有食材，商城重算采购清单。
4. 用户直接结算并创建订单。
5. 微信支付成功，供应商接单、发货、配送、签收。
6. 核对订单快照、库存流水、支付、供应商订单和时间线。

### E2E-02：菜品换一换后购买

1. 用户对一道菜发起换一换。
2. Agent 返回候选，用户选择新菜。
3. Agent 对替换后的整份菜单复核并提交新版本。
4. 商城重新匹配全部需求和交易校验。
5. 小程序刷新菜单、采购项和价格后用户确认支付。
6. 验证旧版本不能下单，前后版本均可审计。

### E2E-03：21 天计划正常履约

1. Agent 创建计划并通过 Agent 与商城校验；一期不要求专业人工审核。
2. 用户选择地址和首批日期，商城生成批次预览。
3. 用户一次支付，系统生成冻结规则对应的全部批次。
4. 首批进入备货窗口后占库存并推单。
5. 逐批发货、签收直至计划完成。
6. 核对支付金额、批次分摊和计划聚合状态。

### E2E-04：计划暂停、恢复和改单批地址

1. 计划部分履约后暂停。
2. 验证已截单批次不变，未来批次不再备货。
3. 恢复时重新校验运力并生成新排程版本。
4. 修改一个可变更批次地址。
5. 验证其他批次地址和历史排程不变。

### E2E-05：不退款确认与平台责任例外售后

1. 小程序在付款前读取后端当前政策并明确弹窗，用户主动确认。
2. 后端把政策版本、文案哈希和确认时间绑定结算令牌与计划订单。
3. 付款后用户因个人原因请求取消，系统拒绝且不创建退款。
4. 构造一个平台未配送批次，客服按权限建立例外售后。
5. 验证补发或例外退款、责任原因、金额分摊和审批证据完整。

### E2E-06：供应商缺货补偿

1. 支付后供应商返回部分缺货。
2. 商城获取同食材候选；跨食材时返回 Agent 复核。
3. 用户确认可接受方案或选择退款。
4. 验证价差、商品快照、供应商子单和退款均可解释。

## 24. 缺陷等级

- P0：支付/金额错误、超卖、越权、重复扣款退款、错误放开审核、订单或批次不可恢复。
- P1：核心流程受阻但有人工绕行，供应商/物流补偿失败，关键审计缺失。
- P2：非核心功能、看板延迟、低影响交互或展示问题。
- P3：文案、样式和不影响理解的小问题。

P0/P1 不允许带到生产。任何“手工改数据库即可解决”的方案均不视为正式修复。

## 25. 上线与回退验收

### 回退触发条件

- 出现金额不一致、重复扣款、负库存、越权泄露或无法补偿的状态错乱。
- 回退时停止新入口和相关自动任务，保留已创建业务数据，由补偿方案处理。
- 不删除新表、不覆盖快照、不用数据库脚本伪造完成状态。
